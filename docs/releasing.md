# Releasing, and the community directory

Maintainer notes: how a release is cut, what checks it against the Obsidian community directory's scanner, and what to expect from the public portal afterwards.

## Cutting a release

Everything lives in one workflow, `.github/workflows/pipeline.yml`. A push run tells you what a release would be; a manual dispatch is the release. The jobs are chained with `needs`, so what gets published is what passed `pnpm verify` a few minutes earlier in the same run, plus release-it's version bump on top of it — no run hands its release to another, and no green tick from somewhere else is taken on trust. (With the release App configured, the release commit does start one more push run afterwards, which verifies and ends at "nothing to release". That run releases nothing; see the App section.)

1. **verify** and **scan** run in parallel on every push to `main`, every pull request, and a manual dispatch that is not a republish. `verify` is the full `pnpm verify` (it builds, and the build is kept as the run's `dist` artifact); `scan` is Obsidian's own action, described below.
2. **plan** runs on `main` only, after both. It decides whether the commits since the last tag contain anything worth releasing, asks release-it for the version number, and writes the review surface into the run summary: the version (or "nothing to release"), the commits since the last tag, and a compare link. On a push run that is where the run ends, green either way.
3. **release** only ever runs on a dispatch — that is the whole approval, and nothing pauses. Before anything is bumped, pushed or minted, it audits the runtime dependency tree (`pnpm audit --prod --audit-level=high`), so nothing ships a bundled dependency carrying a known high or critical advisory; a dev-only advisory is not this job's business and does not stop it. Then it runs release-it on the planned version: bump `manifest.json`/`versions.json`/`package.json`, write the `CHANGELOG.md` section, commit, tag and push — with `GITHUB_TOKEN`, whose pushes deliberately start no new workflow run, or with the release App's token if one is configured (see the ruleset section, and expect the extra push run it causes). It then rebuilds (the manifest's version changed), attests build provenance for `main.js`, `styles.css` and `manifest.json` (the digests are this build's; the source revision recorded beside them is the run's triggering commit, one parent below the release commit, because the attesting action reads it from the event and takes no override), creates the GitHub release with that changelog section as its notes, and uploads the three assets.

So a push never releases and never leaves a run waiting for anybody: it ends completed, with the plan in its summary. Cutting the release is a deliberate second act, `pnpm dev:helpers:release`, which works the same plan out locally from `origin/main` — last tag, commits since it, compare link, and the version release-it would choose — prints it, asks, and dispatches only on `y`. It never bumps, tags or pushes anything locally; it then watches the run. `--yes` skips the question, which is how an agent asked to "cut a release" at the end of a coding cycle does it unattended. The script refuses to show anything unless this checkout is `main`, level with `origin/main`, clean and not shallow, and unless `gh` is pointing at the same repository as `origin` — otherwise what it prints is not what the runner would release. One thing it cannot check is whether the release-it installed here is the one the lockfile pins; run `pnpm install` if this machine has been away for a while.

What you approve is then carried into the run, and enforced there. The dispatch passes the commit and the version as `expected_sha` and `expected_version`, and the release job refuses to release anything else: a dispatch names a branch, so GitHub resolves `main` to a commit when it creates the run, and the run reads the tags when it gets to them — a push or a new tag landing in those seconds would otherwise move what gets released without moving anything the run could notice. The script identifies the run it started from the URL `gh` hands back after the dispatch. That is documented as returned "if available", so there is still a fallback — newest run by the same account on the same ref — and with two dispatches in flight at once that fallback can land on the other one. It only ever costs the wrong run being watched, never the wrong release, because what was approved is enforced inside the run.

Who may release is now bounded by who may dispatch this workflow: anyone with write access to the repository, and any app installation or fine-grained token granted `Actions: write` on it. On a one-maintainer repository that is the maintainer and whatever tokens they have issued. The reviewer rule that used to bound it is gone along with the pause it caused.

The same dispatch is two clicks away in the Actions UI (**Pipeline → Run workflow → main**, leaving all three inputs empty), with the previous push run's summary as the thing to read first — but that path is the weaker one, and deliberately so: with `expected_sha` and `expected_version` empty there is nothing for the run to hold itself to, so a push or a tag landing between reading the summary and pressing the button is released unreviewed, and the run's own plan summary is the only place it shows. Fill those two in from the summary you just read if you want the same guarantee by hand. Either way the dispatched run plans the tip of `main` itself; it never inherits the push run's numbers.

**What counts as releasable:** a `feat`, a `fix`, or any commit marked breaking with `!` or a `BREAKING CHANGE:` footer. Nothing else does — a batch of only `refactor`, `perf`, `docs`, `test`, `build`, `ci` or `style` commits gets you a green "nothing to release", which is the intended answer and not a bug. Those commits are not lost: the changelog preset renders most of them, and they appear in the section written by the next release that does happen. (release-it itself cannot answer this question — the conventional-commits preset recommends at least a patch for any commit at all — so the pipeline reads the commit subjects for it and only asks release-it for the number.)

**If `main` moved while the run was working**, the release job stops before it touches anything and says so: it verified one commit and will not release a different one. A dispatch still takes minutes to reach that job, which is long enough for someone to push. It never rebases and never releases the new tip — dispatch again on the new `main`. The same guard is what makes a double dispatch harmless: two runs verify in parallel, but only one `release` job executes at a time, and once the first has pushed its bump the second stops here rather than releasing the same commits twice.

**Republishing a tag** is the recovery path for a publish that died after the tag already existed. Run `pnpm dev:helpers:release --tag 1.2.3` (or fill the `tag` input in the Actions UI). That run skips `verify`, `scan`, `plan` and the dependency audit entirely — the tag was verified when it was cut, and a recovery must not be blocked by an unrelated failure on today's `main`, nor by an advisory filed since that re-uploading the same build could not fix — checks out the tag, rebuilds, attests, reuses the GitHub release if it exists, and re-uploads the assets with `--clobber`.

Because it re-uploads rather than re-verifies, the job is strict about which commit a tag may point at. Reachability from `main` and the manifest version are both weaker than they look: the bump writes `manifest.json` once per release, so every commit landed since carries that release's number and is trivially reachable — a tag force-moved onto today's tip would satisfy both and quietly republish today's code as an old version. So the job also requires the tag's commit to be a commit release-it itself made for that exact version, by matching its subject against `.release-it.json`'s `commitMessage` as read from the tag. That is defence in depth and not the defence: it assumes nobody can push a forged `chore(release): <version> :rocket:` commit to `main`, which is what the tag ruleset's **Restrict updates** — and any branch protection — are for. The GitHub release itself records no commit to cross-check against; its `target_commitish` is the branch name it was created from (`main` for every release here), not the tag's commit.

The republish dispatch runs against `refs/tags/<tag>` rather than `main`, so the build-provenance attestation records the tag's own commit as the source instead of whatever is on `main` this afternoon. One consequence: GitHub reads the workflow file from the ref it is dispatched against, so a tag cut before this pipeline existed — everything up to and including `0.2.0` — has no `pipeline.yml` on it. `pnpm dev:helpers:release --tag` checks the tag for a `pipeline.yml` before it dispatches, says so when there is none, and falls back to dispatching against `main`; those republishes work, and their attestation names the tip of `main` as the source, which is the old behaviour and is worth knowing when reading one back.

The other half of that trade is worth knowing before it surprises you: a republish of a tag that *does* carry a `pipeline.yml` runs **that tag's** copy of this pipeline, frozen at release time — its guards, its action pins, its inputs, not today's. A fix landed on `main` after a release does not protect a republish of it, and a narrow allowed-actions list that no longer names the action SHAs that tag pins would block it before it starts — which today's wildcard list does not do, but a later tightening would. So a republish of an old tag is a recovery with the security properties of its own era; if that matters for a particular one, cut a fresh release instead of republishing. On the ordinary release path the recorded source is the commit that triggered the run, one parent below the release commit release-it makes, because the attesting action reads it from the event and takes no override — so the attested `manifest.json` carries a version its recorded source commit does not yet have. An existing release goes back to draft while its three files are swapped and is published again afterwards, so nobody can read it with one new file beside two old ones; that does not disturb which release GitHub calls the latest, because that is decided by the date of the commit behind the tag, not by when the release was published. The one thing not to do is dispatch a republish of a version at the moment that version is being cut — that is the only way two runs can end up working on the same release at once.

The increment comes from the commits, so a commit that breaks compatibility must carry the `!` in its header, whatever its type (`feat(mcp)!: require the subtask text`) — with the space after the colon, which is what both the pipeline's reading of a subject and release-it's own parser require; a `BREAKING CHANGE:` footer is optional, for when the subject alone does not say what a user has to change. `.release-it.json` keeps `preMajor: true` until someone decides on `1.0.0`, which holds breaking changes to a minor bump; the pipeline has no way to force a version by hand, so `1.0.0` is reached by dropping that flag in a commit of its own and letting the next breaking change produce it.

Never rewrite older `versions.json` rows: Obsidian reads that file to send a user on an old app to the last plugin version that ran there, and every release up to `0.0.20` genuinely ran on `1.7.2`. The bump script adds the row for the current `minAppVersion` on every release.

### The one setting that lives in GitHub, not in this repository

The pipeline leans on it and cannot create it. A fresh fork or a restored repository has to have it set again by hand. (Nothing here uses a GitHub Environment any more. The workflow no longer names one, so a `release` environment left over from the approval gate this pipeline used to have is inert — no job is bound to it and no protection rule on it can stop or delay anything.)

**A tag ruleset, so only the pipeline can create a version tag.** The pipeline is the only thing that should ever create a `*.*.*` tag; a ruleset is what turns that from a convention into a rule. Go to **Settings → Rules → Rulesets → New ruleset → New tag ruleset**, name it (`Release tags`), set **Enforcement status** to **Active**, under **Target tags** add a target with **Include by pattern** `*.*.*`, and tick all three of **Restrict creations**, **Restrict updates** and **Restrict deletions**. All three matter, not just the first: the republish path trusts an existing tag instead of re-verifying it, and a tag that can be moved is not a version. The republish guard now refuses a tag whose commit is not the release commit for that version (above), so moving a tag onto an ordinary commit no longer gets through — but a forged `chore(release): <version> :rocket:` commit on `main` would, and moving a tag is also how the changelog boundary of a release *in flight* gets changed. **Restrict updates** is what makes both impossible rather than merely awkward.

**Do not create that ruleset until the release App below exists.** Rulesets apply to `GITHUB_TOKEN` too, and the pipeline pushes its tag with `GITHUB_TOKEN` by default, so **Restrict creations** would block every release. The obvious escape does not work: the built-in `github-actions[bot]` identity is not offered as a bypass actor in the ruleset UI and cannot be relied on through the API either. What can be bypassed is a GitHub App you own — which is why the release job can push as one.

**The release App, the thing that makes the ruleset survivable.** Create a GitHub App on the `stavarengo` account (**Settings → Developer settings → GitHub Apps → New GitHub App**), give it the repository permission **Contents: read and write** and nothing else, install it on this repository alone, and generate a private key. Then store its two halves as repository secrets: `RELEASE_APP_CLIENT_ID` (the **Client ID**, the `Iv23…` string on the App's settings page — not the numeric App ID beside it, which the token action now treats as deprecated) and `RELEASE_APP_PRIVATE_KEY` (the whole `.pem` file, `BEGIN`/`END` lines included). Keep the numeric App ID to hand anyway: that is the one the ruleset bypass wants below.

```bash
gh secret set RELEASE_APP_CLIENT_ID --repo stavarengo/folia-kanban --body '<Client ID>'
gh secret set RELEASE_APP_PRIVATE_KEY --repo stavarengo/folia-kanban < release-app.private-key.pem
```

The release job reads nothing but the presence of those two: with both set it mints an installation token with `actions/create-github-app-token` and release-it pushes the bump, the changelog commit and the tag as the App; with either missing it pushes with `GITHUB_TOKEN` exactly as before. Nothing else in the job sees the private key.

One consequence to expect, because it looks like a bug the first time: `GITHUB_TOKEN` pushes deliberately start no workflow run, an App's pushes do. So with the App configured, every release is followed by one extra push run of the pipeline over the `chore(release)` commit, which verifies, scans, plans and ends at "nothing to release" — `chore` is not releasable. The tag push starts nothing in either case; this workflow has no tag trigger.

With the App installed and the secrets set, create the ruleset with that App on its bypass list. In the UI it is offered by name under **Bypass list → Add bypass**. Over the API it is the `Integration` actor with the App's own numeric App ID — the one on the App's settings page, beside the Client ID; there is no `gh` lookup for it, because the endpoints that return it authenticate as the App itself, not as you. It replaces the `000000` below:

```bash
gh api --method POST repos/stavarengo/folia-kanban/rulesets --input - <<'JSON'
{
  "name": "Release tags",
  "target": "tag",
  "enforcement": "active",
  "bypass_actors": [{ "actor_type": "Integration", "actor_id": 000000, "bypass_mode": "always" }],
  "conditions": { "ref_name": { "include": ["refs/tags/*.*.*"], "exclude": [] } },
  "rules": [{ "type": "creation" }, { "type": "update" }, { "type": "deletion" }]
}
JSON
```

Then prove it before trusting it: the next release run has to get its tag pushed. If the `release` job fails on `git push` with a message about a ref protected by rules, the bypass did not take — widen or drop the ruleset. Nothing in this repository needs to change either way. The same warning applies to any rule added later on the `main` branch: the release job pushes the `chore(release)` commit straight to `main`, so a branch ruleset that restricts updates or demands a pull request has to carry the same bypass or it stops releases outright.

Read the bypass for what it is, too: it authorises the App, not this one workflow. It stops a person creating a version tag by hand, which is the point; it cannot stop some future workflow in this repository from minting the same token and doing it.

**And read what the ruleset cannot do at all: it binds hands, not dispatches.** Running a `workflow_dispatch` needs only `Actions: write` — not `Contents`, not admin. Anything holding that on this repository can start an ordinary release, and the release job then mints the bypass actor's token and pushes the commit and the tag straight past the ruleset. A token whose name suggests "re-run my jobs" is therefore a release credential here, and the ruleset cannot see the difference, because the push it sees is the App's. This is inherent to having a manual dispatch as the release trigger, and it is the reason for a recurring maintainer check rather than a setting: **audit who holds `Actions: write`** — fine-grained personal access tokens, installed Apps and their permissions, any CI integration — and keep that list down to the maintainer. Worth doing whenever a token or App is added, and once in a while regardless.

**Rotating the App's private key.** The key is the single point of failure this design creates: whoever holds it holds `Contents: write` plus the ruleset bypass. Rotate it if it may have been exposed, and when a machine that once held the `.pem` is decommissioned. On the App's settings page under **Private keys**, generate a new key, then `gh secret set RELEASE_APP_PRIVATE_KEY --repo stavarengo/folia-kanban < new-key.pem`, then delete the old key on that same page — new first, so no release is impossible in between — and remove the downloaded `.pem` files. Nothing in this repository changes, and the next release proves it took. Keep a copy of the new key in your password manager, since GitHub never shows a key again after the download.

**And one thing to check:** any required status check on `main` or on pull requests. The workflow's name changed from `CI` to `Pipeline`, its file from `ci.yml` to `pipeline.yml`, and the scan job's id from `obsidian-scan` to `scan`, so a rule written against the old identity may now be waiting for a check nothing reports. Both job display names are deliberately unchanged (`Verify`, `Obsidian community scan`), and so is the `verify` job's id, which should be enough for a rule keyed on those — but open the branch rule or ruleset and confirm the checks it lists are still being reported, rather than assuming it.

**And one thing to delete:** the `FOLIA_KANBAN_RELEASE_IT_GITHUB_TOKEN` repository secret. The pipeline pushes with `GITHUB_TOKEN`, or with the release App's token, so that personal access token is no longer read by anything and should be removed from the repository's secrets and revoked in the account's developer settings.

### Forks and pull requests

**A pull request from a fork** runs `verify` and `scan` and nothing else. `plan` is `main`-only and `release` only ever runs on a dispatch, so a pull request cannot reach either. Those two jobs get the workflow's top-level `contents: read` token, scoped to this repository and read-only, and no secrets: GitHub does not hand repository secrets to a workflow run triggered by a pull request from a fork, and the workflow never uses `pull_request_target`, the trigger that would run fork code with this repository's secrets and write token. A first-time contributor's run also waits for a maintainer to press **Approve and run** before it starts, which is where the code gets read before it executes.

So the worst a hostile pull request can do is make our own runners execute its code with a read-only token and no credentials. It cannot tag, release, push, read a secret, or reach the release App: none of that is present in the jobs it can start.

**Someone forking the repository** takes the workflow with them. It runs in their fork, on their Actions quota, with their token, and it is their repository it can release to: a dispatch in a fork cuts a tag and a GitHub release in that fork. The release App is not installed on it, so its release pushes with the fork's own `GITHUB_TOKEN`. Nothing a fork does reaches this repository — its tokens are scoped to itself — and nothing it publishes reaches the Obsidian directory, which follows this repository's releases by name.

### Threat model

The pipeline runs other people's code on machines holding this repository's release credentials, which is the `tj-actions/changed-files` shape of problem: a third-party action is compromised upstream, everyone floating on its tag picks the new code up silently, and it reads whatever the job it runs in can reach.

What each job could lose:

- **verify** and **scan**: the repository's own source, a read-only token, no secrets. The scan job is also where the one deliberately unpinned action runs (`obsidianmd/obsidian-workflows@v1`, floating so it tracks the directory's real scanner), so its blast radius is stated rather than eliminated: a read-only token, no secrets, and no output that anything downstream consumes — the release job rebuilds from the tag and never reads this job's artifacts. The scan job is also the one job without `cache: pnpm`, deliberately: the Actions cache is a write channel nothing opts into, scoped by branch, so what a push-to-`main` run saves there is what a later release run on `main` restores and installs from. That is the one way this job could have reached the job holding the release credentials, and it is closed by not having a cache rather than by reasoning about it.
- **the OSV scanner workflow** (`osv-scanner-pr.yml`): `security-events: write` and a read-only checkout, no secrets. Enough to file or dismiss a code-scanning alert — to hide a finding, not to release. Pinned to a commit SHA like everything else.
- **plan**: the same read-only token, plus the ability to influence which version the release job is told to cut, since it hands that number on.
- **release**: `contents: write`, the attestation identity, and — if it is configured — the release App's installation token while the push step runs. This is the job worth protecting.

The mitigation is that every third-party action in the release path is pinned to a full commit SHA (`uses: actions/checkout@3d3c42e5… # v7.0.1`), which a tag being moved cannot change. What the pins protect against is the upstream tag moving; they are a property of this file, so keeping them is a review job like any other change to `pipeline.yml`. A pin moves when somebody bumps it by hand, security fixes to the actions included, so check the pinned actions for newer releases when touching the workflow, and at least occasionally when not. Dependency install scripts are a second route in, and pnpm closes it: `pnpm-workspace.yaml` allow-lists build scripts per package (`esbuild` yes, `lefthook` no), so a newly compromised dependency's `postinstall` does not run on the runner. The root project's own `prepare` script is outside that allow-list and does run — and on a pull request it is the pull request's `prepare`, executing before `pnpm verify` rather than as part of it. That is not an escalation, since `pnpm verify` runs the same contributor's code moments later with the same read-only token and no secrets, but "it is our code" is only true on `main`.

A known advisory against a dependency we already have is the other half of the same problem, and it is handled in two places that block and one that reports. The pull-request OSV scan (`osv-scanner-pr.yml`) runs in diff mode against the base branch, so it fails only when the change in front of it is the thing that brings a vulnerable package in. The release job's `pnpm audit --prod --audit-level=high` fails when a dependency the bundle actually ships carries a high or critical advisory: a dev dependency never reaches a user of this plugin, and a runtime one below high does not stop a release — `--audit-level` sets the threshold for the exit code and for what the step prints, so anything under it leaves only a count in the log and is left to the reporting half below. Everything else is reported: an advisory filed against a dependency no commit touched arrives as a Dependabot alert on the repository, for the `npm` tree and for the pinned actions alike. That is a repository setting, **Settings → Code security → Dependabot alerts**, and it has to stay on for the reporting half to exist. Acting on an alert is manual: bump the dependency, and the release audit confirms the fix on the way out. (The `obsidian` typings are the one dependency not to bump on an alert's say-so: which version is installed decides which APIs typecheck, and that belongs beside `minAppVersion`. The two are not aligned today; [#49](https://github.com/stavarengo/folia-kanban/issues/49) has it.)

One more setting in the same place, and the one `SECURITY.md` at the repository root depends on: **Private vulnerability reporting**, enabled today. It is what puts the **Report a vulnerability** button on the Security tab, and `SECURITY.md` sends every reporter to that button — so on a fork or a restored repository, turn it back on (`gh api -X PUT repos/<owner>/<repo>/private-vulnerability-reporting`) or the file is pointing at a door that is not there. Without it a reporter's only route is a public issue, which for an exploitable finding is the disclosure itself.

That third case is why there is no scan failing `main` and no scan inside `pnpm verify`. A vulnerability scanner is a time-varying check — the same commit is green one morning and red the next because the world moved, not because the code did — and a check that turns red without anybody doing anything is a check people learn to stop reading, which is precisely the day a runtime dependency gets hit. `pnpm verify` stays a question about the commit, and `main` stays green for advisories the commit did not introduce. An advisory the pull-request scan raises and somebody judges unreachable is waived in an `osv-scanner.toml` at the repository root, with a reason and an expiry date on the entry so the judgement is re-made rather than inherited; there is no such file today, and muting a scan is never the alternative. The release audit has no waiver route by policy rather than by accident: `pnpm audit` does not read that file, and its own ignore list (`--ignore`, `pnpm.auditConfig.ignoreGhsas`) carries neither a reason nor an expiry, so using it would be the muting this repository refuses everywhere else. A high or critical advisory in something the plugin actually ships is a thing to fix before releasing.

**Two settings only you can change**, both at **Settings → Actions → General**:

1. **Fork pull request workflows from outside collaborators** → **Require approval for all external contributors** (or the strictest option offered). It puts every fork pull request behind your approval before any runner executes it, rather than only the first one from a given account.
2. **Actions permissions** → **Allow *stavarengo*, and select non-*stavarengo*, actions and reusable workflows**. What is set on the repository today is the two sub-options ticked — **Allow actions created by GitHub** and **Allow actions by Marketplace verified creators** — plus this list:

   ```text
   pnpm/action-setup@*
   obsidianmd/obsidian-workflows@*
   google/osv-scanner-action@*
   google/osv-scanner-action/*
   ```

   Read that for what it admits, because it is broader than the shape of it suggests: "verified creators" is most of the Marketplace, and the GitHub allowance covers every action in the `actions` and `github` organisations at any ref. A pull request cannot introduce some random author's action, and that is the whole of what this currently buys.

   Nothing in it names a ref, which is what makes bumping a pinned action an ordinary pull request rather than a pull request plus a settings edit. Three of the four patterns end in `@*` and admit their action at any ref; the fourth, `google/osv-scanner-action/*`, is the one that covers the OSV reusable workflow, and it demonstrably admits that workflow's pinned SHA, because that is what runs on every pull request today. The `actions/*` pins are admitted by **Allow actions created by GitHub**, which names no ref at all. So a bump's own run starts on the new SHA, and nothing has to be added here first.

   The box takes the same `owner/repo@ref` syntax as a workflow file, exact commit SHAs included, so the tighter setting is to untick both sub-options and name the pins themselves:

   ```text
   actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1
   actions/setup-node@820762786026740c76f36085b0efc47a31fe5020
   actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a
   actions/attest-build-provenance@4d101475d8b20a2381f78447822ac1eab6504dd8
   actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1
   pnpm/action-setup@ea17c68df8912ef543352723c149a84f56e3d413
   google/osv-scanner-action/.github/workflows/osv-scanner-reusable-pr.yml@6e4298ebc4db23e847df9b2e2de2939d6f066c67
   obsidianmd/obsidian-workflows@v1
   ```

   That is exactly what these workflows run today and nothing else could start, whoever opens the pull request. A reusable workflow is named in full, path included, so no wildcard is needed for the OSV entry either. Its cost is upkeep, and it is a cost only this shape carries: every pin here has to move with the workflow's, so under this list — not under the wildcards in force today — a pin bump's own run fails until the SHA is added here too, a nuisance with a clear message rather than a surprise, and the reason to keep the old SHA off the list once it is gone (see the republish note below, which is the one thing that makes an old pin matter). The `obsidianmd` line floats on purpose, which is also why the switch below, **Require actions to be pinned to a full-length commit SHA**, cannot be turned on: it would block the scan job.

   One thing to settle before anyone switches to that shape: nobody has established whether the allow-list is enforced against the actions a called reusable workflow runs *inside* itself, and the OSV workflow calls five that the tight list does not name — so it may stop the scan. [#48](https://github.com/stavarengo/folia-kanban/issues/48) holds the detail.

   Whichever of the two is in force, keep this section and the setting itself saying the same thing. A document describing a stricter repository than the one configured is what gets discovered during an incident.

## The two scanner checks

The community directory reviews every release with a scanner: Stylelint with its own ruleset, plus ESLint with `eslint-plugin-obsidianmd`. The official tooling exists only as a GitHub Action, so this repo checks itself twice.

`pnpm obsidian-scan:check` (`scripts/obsidian-scan.mjs`, part of `pnpm verify`) reproduces both passes locally and is the gate: it fails on any finding, warning or error, and it is the only signal available before pushing.

The `scan` job in `pipeline.yml` runs the real action, floating on `v1`. It never fails on lint findings and cannot be configured to; it records every finding as a warning and only errors on a broken manifest, a missing README or licence, or a failed tool install. Its value is drift detection: the directory pins its own tool versions, the local script cannot match them, so a finding in that job's log that `obsidian-scan:check` did not produce means `scripts/obsidian-scan.mjs` needs updating.

## The public portal

The listing is at [community.obsidian.md/plugins/folia-kanban](https://community.obsidian.md/plugins/folia-kanban), no login needed. It shows a review rating and an issue count for the latest release; the itemised findings are only on the maintainer's own account page.

Some findings are permanent and informational, not things to fix: the AGPL-3.0 copyleft notice, "vault enumeration" (inherent to a plugin that reads every card), and "malware/obfuscation scan not available".

When the portal lags behind GitHub, the maintainer's account page has a manual trigger: `GET https://community.obsidian.md/account/plugins/folia-kanban/check-release`, sent with the browser's logged-in session (open the plugin's page under Account → Plugins and use its check-for-releases action, or replay that request with the session cookie). It answers "This entry was refreshed in the last few minutes. Please wait before trying again." when called inside its cooldown, so one call per few minutes is the most it accepts. Nothing public or unauthenticated exists (researched in August 2026 across the docs, blog, the `obsidianmd` org and the forum), and Obsidian's own commitment is only that a passing release appears within about a day. If the trigger does not pick it up, wait that day, then ask staff on the forum or the plugin-review channels; do not debug the release pipeline over a stale version number. Precedent: [one stuck listing](https://forum.obsidian.md/t/plugin-submission-portal-stuck-on-no-release-matches-your-manifest-version-despite-correct-releases/114686) was cleared by staff by hand, [another](https://forum.obsidian.md/t/no-release-matches-your-manifest-version/116025) resolved itself after a day.
