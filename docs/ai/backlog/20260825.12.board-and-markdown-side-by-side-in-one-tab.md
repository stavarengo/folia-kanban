# Show a board note as the board and as a Markdown editor side by side, in one tab

## What is asked

A board note opens as the board, and a header button swaps that tab to the plain Markdown editor and back. What is still missing is the arrangement Rafa originally wanted most: **both at once, in a single tab** — a narrow Markdown editor down one side, the board taking the rest of the width — so editing the note's frontmatter and watching the board react is one glance rather than two tab switches.

The hard constraint is his: one tab, not two editors, and not an Obsidian split of two separate tabs. If it cannot be one tab, it is not this.

Concretely, this would become a third value of the existing **Board notes — open as** setting (`board` / `markdown` today, plus `split`), and a third state for the per-note `folia-view` frontmatter override.

## How to observe where this stands

The board-vs-Markdown half shipped: open a board note from the file explorer, it comes up as the board; the tab header button swaps it to Markdown and back. The `split` value simply does not exist in the setting.

## What was already established

A spike ran against the live Obsidian (1.7.2 API, `examples` vault) while implementing the board/Markdown half. It settled the feasibility question, and the answer is "technically yes, cleanly no".

A `WorkspaceLeaf` carries a single `view`, so two views in one tab can only mean the board's own view drawing both panes inside itself. That much was known. What the spike added is that a live, editable Markdown editor **can** in fact be hosted inside an arbitrary DOM container: constructing a leaf, attaching its `containerEl` to a plain `div`, and calling `setViewState({ type: 'markdown', state: { file } })` produced a real `MarkdownView` with a working `editor`. Typing into it and calling `view.save()` wrote the bytes to disk, and re-parenting the container left the editor intact.

Two findings are why it was not shipped anyway:

- **There is no public way in.** The only route to a leaf is `new (someLeaf.constructor)(app)` — a minified runtime constructor. Nothing in `obsidian.d.ts` exposes leaf construction, so this is an undocumented internal that can change in any release, in a plugin intended for the community store.
- **The resulting editor is half-inert.** The leaf is not in the workspace tree: `app.workspace.getLeavesOfType('markdown')` does not contain it, so `getActiveViewOfType(MarkdownView)` cannot see it either. Obsidian's own editor commands and hotkeys, and every plugin that acts on "the active editor" (Templater and friends), would not reach that pane. It would look like an editor and behave like one only for typing.

On top of that, the deferred-leaf behaviour recorded in `AGENTS.md` — Obsidian defers background leaves, so an off-screen board stays empty until focused — applies to whatever hosts the two panes.

Worth re-checking before picking this up: whether a later Obsidian release has made leaf creation or editor embedding part of the public API, or whether `app.embedRegistry.embedByExtension.md` (which exists and is what Canvas-style embeds go through) has grown a supported editable mode. Both would change the answer.

## What the outcome should be

Either a `split` mode built on an API Obsidian actually supports, where the embedded editor is a first-class editor (hotkeys, commands, other plugins) — or a decision that this stays out, recorded so nobody spikes it a third time.
