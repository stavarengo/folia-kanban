# A checklist line's `[status:: …]` can be overwritten by a click decided before it was written

## What happens

Ticking a checklist line is two writes: the checkbox (`toggleSubtask`), then the line's `[status:: …]` claim (`applyMove` with `setSubtaskStatus`, from `syncSubtaskClaim` in `src/model/board.ts`). Both are now guarded against landing on the wrong LINE — the caller names the line by its text as well as its index, and the write refuses when the note no longer reads that way (`subtaskStillReads`, `src/model/card.ts`).

That guard compares the line's text with the inline field stripped off, because that is how every caller read it (`SubItem.text` never contains the field). So a line whose `[status:: …]` changed underneath still passes: it is the same line by every word the guard can see, and the write lands, carrying the claim derived from the reading the caller was holding — overwriting the value somebody else just wrote. The same shape reaches the column dropdown in the detail panel and the drag of a placed todo, both of which decide the new claim from a board read that may be older than the note.

A second, milder residue of the same guard: two checklist lines carrying identical text are indistinguishable to it, so a write meant for one can land on the other if a third identical line appears above them. For identical lines the outcome is hard to tell apart, which is why it is recorded here rather than treated as the same defect.

Found by an unprimed review of the line-identity fix (Codex, 2026-09-09), by inspection — no test was run for it.

## How to reproduce

Open a board with a card holding `- [ ] Deploy [status:: todo]` under `## Subtasks`. With the card drawn, edit the note in another pane (or another app, or a sync pull) so the line reads `[status:: doing]`. Then tick the line's checkbox from the board or the detail panel. The box is written, and the claim goes to the value derived from the board's old reading rather than being left alone or refused.

## Expected outcome

A write that carries a field's new value should not silently replace a different value written in between. Either the write is decided against what the note says at the moment it is made, or it refuses the way a line that has moved already does — and either way the person is told, rather than finding the value they set replaced by one nobody chose.
