# A release can be cut from a main that is not level with origin

## What happens

`pnpm dev:helpers:release` and the Create Release workflow both run release-it from `.release-it.json`. Running it on a branch other than `main` is refused (`requireBranch`), and the workflow only runs on `main`. Nothing checks that the local `main` matches `origin/main` before the bump.

Behind origin: release-it fetches but never compares, so the version bump, the changelog section, the release commit and the tag are all created locally, and the push at the end fails as non-fast-forward. Because `requireCleanWorkingDir` is off, release-it's own rollback (which would reset the commit and delete the local tag) is never armed, so the half-made release stays on `main` for a person to unwind by hand.

Ahead of origin: unpushed local commits ride into the release and are published with it.

Two Create Release dispatches fired close together are not serialised either: `ci.yml` has a `concurrency` block, `create-release.yml` does not, so two runs can race on the same base commit.

Found on 2026-09-10 by a read-only investigation of the release path after 0.1.0 was cut locally.

## How to observe

Create a throwaway commit on a clone of `main` without pushing it, or fetch a newer `origin/main` without merging, then run `pnpm dev:helpers:release --dry-run` and read what it would do: no step refuses.

## Expected outcome

A release started from a `main` that is behind or ahead of `origin/main` stops before it bumps anything, saying why. Two overlapping Create Release runs cannot both proceed.
