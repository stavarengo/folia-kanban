# `pnpm doctor` runs pnpm's own diagnostic, not this project's preflight

## What happens

`package.json` defines a `doctor` script (`node scripts/doctor.mjs`), `pnpm verify` starts with `pnpm doctor`, and step 1 of AGENTS.md's "Way of Working" tells every agent to run `pnpm doctor` before changing code. None of those actually run `scripts/doctor.mjs`.

`doctor` is a built-in pnpm command, and a built-in wins over a same-named script unless it is invoked as `pnpm run doctor`. Verified side by side in a clean worktree on 2026-08-26:

- `pnpm doctor` prints pnpm's own report — pnpm/Node versions, global bin directory, cache directory, filesystem capabilities, registry connectivity, an install smoke test. It ends with "All checks passed with 1 warning(s)" (the warning being that `~/.local/share/pnpm/bin` is not on `PATH`).
- `node scripts/doctor.mjs` prints the project preflight — Node >= 24, pnpm version, lockfile present, dependencies installed, no merge-conflict markers, project prerequisites (manifest, entry, styles, build config) — ending in `doctor: OK`.

So the project's first gate has never run in `pnpm verify` or in any agent session following AGENTS.md. It reports success either way, which is why nobody noticed. Worse, pnpm's version does a live registry request and an install smoke test, so `pnpm verify` currently depends on network reachability at its very first step for no reason.

Nothing is known to have slipped through as a result — the checks it skips are largely covered later in `verify` — but the preflight's whole point is failing fast and legibly before anything else runs.

## Expected outcome

`pnpm verify` and AGENTS.md's step 1 run the project's own preflight. The fix has to hold for every entry point that names it, and it should not be possible to reintroduce silently: a script name that cannot collide with a pnpm built-in would do it, as would invoking it as `pnpm run doctor` everywhere.
