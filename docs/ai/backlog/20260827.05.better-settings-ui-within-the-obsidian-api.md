# A better settings UI within what the Obsidian API offers

## What is asked

Rafa asked on 2026-08-27 for a better settings UI/UX, on the explicit condition that it keeps using only the Obsidian settings API (`PluginSettingTab`, `Setting`, and what they provide) rather than a custom rendered surface.

## Current behaviour

`KanbanSettingTab` in `src/main.ts` renders a single flat list of fourteen rows in the order `settingDefinitions()` (`src/settingsDefinitions.ts`) returns them: board-note default view, detail presentation, side panel layout, side panel width, add-card flow, add-card open mode, next todos preview, subitems default, your name, history scope, board pan, three board-setup toggles, and the version. Grouping is carried only by naming convention ("Side panel — …", "Board setup — …") in the row names, not by any visual structure. Rows that only apply under another row's value (side panel layout when presentation is modal; add-card open mode when the flow is inline) are disabled in place rather than hidden or explained. Descriptions carry a lot of text for what are mostly two- or three-way choices, and the "Your name" row sits between card-appearance and history settings although it is about identity.

## How to observe

Open Settings → Community plugins → Folia Kanban and read the tab top to bottom, then change "Card details — presentation" to modal and watch how the dependent row reacts.

## Expected outcome

A settings tab that reads as a few clearly separated groups with short names and descriptions that explain a choice's consequence rather than restate its options, where dependent settings make their dependency obvious, and where the most consequential choices come first. Everything must still be built from the Obsidian settings API (headings, `Setting` rows, dropdowns, toggles, sliders, text, and the 1.13+ settings-search integration the tab already supports) so the tab behaves like a native one, respects the user's theme, and stays searchable. The implementing session should survey what the API provides (section headings, `setHeading`, `setClass`, extra buttons, collapsible patterns other well-regarded plugins use within the same constraints) and pick from that, rather than adding a custom React surface.
