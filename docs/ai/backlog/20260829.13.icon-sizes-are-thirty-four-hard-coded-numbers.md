# Icon sizes are thirty-four hard-coded numbers in seven values, beside the app's icon size scale

## What is asked

Findings 01-10 and 02-14 of the audit of 2026-08-29 ([section 01](../reports/20260829.what-obsidian-already-provides/01.ui-components-and-primitives.md), [section 02](../reports/20260829.what-obsidian-already-provides/02.styling-theme-and-design-language.md)) found the plugin's icon geometry decided per call site rather than by the app's `--icon-size` scale.

## Current behaviour

`src/ui/icons.tsx:142` takes a `size?: number` defaulting to 16 and writes it straight to the SVG's `width` and `height`, with `strokeWidth={2}` fixed. Call sites pass 34 explicit sizes across `src/ui/*.tsx` in seven distinct values: 11 (four times), 12 (twice), 13 (eleven), 14 (seven), 15 (five), 16 (four) and 20 (once). `.folia-icon` in the stylesheet carries only `flex` and vertical alignment, so nothing central decides how large an icon is.

Nothing sees these numbers: `scripts/audit-raw-values.mjs` polices raw values in the stylesheet, not numeric props in TSX, so all 34 are invisible to the guard that exists for exactly this class of value (see also finding 02-10 and the entry it produced). Finding 01-10 reads the mechanism as a small clear win and 02-14 splits it: driving size from a container rule is free, while collapsing seven values onto a five-rung scale changes several card tiles and is a visual judgement. Whether the icons themselves should come from `setIcon` is a separate question, dismissed in this triage; this stands either way.

## How to observe

Grep `size={` in `src/ui/*.tsx` for the 34 sites, then change Obsidian's own icon size on a theme and watch nothing in the board respond.

## Expected outcome

Icon size decided in one place that the app can influence, with a deliberate answer for the values that do not land on Obsidian's scale — kept as an exception on purpose, or moved and the tiles reviewed.
