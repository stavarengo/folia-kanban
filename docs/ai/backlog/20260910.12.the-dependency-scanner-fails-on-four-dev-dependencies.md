# The dependency scanner fails on four dev dependencies

## What happens

`osv-scanner-scheduled.yml` runs OSV on every push to `main` and monthly, with `fail-on-vuln: true`. Since 2026-09-10 it fails on every push, after passing on 2026-09-01: four advisories against four packages in `pnpm-lock.yaml`, all dev-only.

| Package | Installed | Fixed in | Severity | Pulled in by |
| --- | --- | --- | --- | --- |
| `vitest` and `@vitest/mocker` | 3.2.6 | 4.1.11 | moderate (5.9) | direct dev dependency |
| `js-yaml` | 4.3.1 | 4.3.2 | high (7.5) | stylelint through cosmiconfig |
| `smol-toml` | 1.6.1 | 1.7.1 | high (8.2) | knip and markdownlint-cli2 |

The plugin's runtime dependencies are clean, so nothing vulnerable shipped in 0.1.0. The cost is a red job on every push, which is what teaches people to stop reading it before the day a runtime dependency is hit.

Two of the fixes are patch bumps within the lockfile; the `vitest` one is a major upgrade that touches the test configuration.

## How to observe

`gh run list --workflow=osv-scanner-scheduled.yml` shows the failures; the run log lists the four advisories with their OSV ids.

## Expected outcome

The scanner is green on `main` because the advisories are resolved, not because dev dependencies were excluded from it. `pnpm verify` stays green through the vitest major.

## Decided on 2026-09-12

Rafa asked what the common practice is and agreed with this shape. A vulnerability scanner is a time-varying check, so it does not join `pnpm verify` and does not fail `main` for advisories the commit did not introduce. The pull-request scan stays blocking in diff mode, failing only when a change adds a vulnerable dependency. On `main`, findings are reported rather than failed: enable the `npm` ecosystem in `.github/dependabot.yml` so Dependabot alerts and security-update PRs cover it, and make the scheduled OSV scan non-failing or retire it in favour of those alerts. The release job in `pipeline.yml` gates on runtime dependencies only, with `pnpm audit --prod --audit-level=high`, since only what the bundle ships reaches users; dev-only advisories such as the four above never block a release. Any advisory judged unreachable is waived in the scanner's config file with a reason and an expiry date, never by muting the scan. The four current advisories are fixed by bumping, the vitest major included.
