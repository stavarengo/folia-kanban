# An agent reading a card through MCP sees only its frontmatter tags

## What is asked

The board learned to count a tag written in a card's body (`#tag` in the text) as one of that card's tags, the way Obsidian does: the adapter puts them on `Card.bodyTags` during `loadBoard`, and `tagValues` in `src/ui/cardView.ts` unions them with `area` and the `tags` property. That closed the entry 20260829.24 for the board's own `tag:` filter, its free-text search and its tile chips.

The MCP tools were left where they were, deliberately, because widening them is a different change with a different audience. Decide whether an agent should see the same union, and if so, give it one.

## Current behaviour

`get_card` (`src/mcp/boardTools.ts`) reports `frontmatter: card.frontmatter` verbatim, and `cardSummary` reports no tags at all. Neither reads `Card.bodyTags`, so an agent asking "which cards are tagged `#home`" gets a different answer from the board sitting next to it — and gets no signal that a second set of tags exists. The MCP tools also do not run the board's filter grammar (nothing outside `src/ui/` imports `matchToken`), so this is not a case of one shared code path drifting; it is two separate readers that now disagree.

## How to observe

Take a card with a tag in its body and none in its frontmatter. Filter the board by that tag: the card matches. Call `get_card` on the same path: nothing in the response mentions the tag.

## Expected outcome

A judgement, then whatever follows from it. If an agent should see the union, the shape matters and is not obvious: a separate `bodyTags` field is honest about where each tag came from, while a merged `tags` field is what an agent would naturally reach for and is a change to what `frontmatter` in the response means. Whichever wins, `docs/mcp.md` should say which reading the tools use, since right now it says nothing about tags at all.
