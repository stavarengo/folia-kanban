# The "Your name" setting could be inferred instead of typed

## What is asked

Rafa asked on 2026-08-27 whether the "Your name" setting (`userName`, `src/settings.ts`, labelled in `src/settingsLayout.ts`) could be filled in on a best-effort basis so users do not have to type it.

## Current behaviour

`DEFAULT_SETTINGS.userName` is the empty string and nothing ever populates it. Until the user opens the settings tab and types a name, comments written from the board are unsigned, the plugin cannot tell its own comments from other people's, and the unread logic (`src/model/unread.ts`) works without an author to compare against. Most users will never discover the field, so the signing and unread features are effectively off by default.

## Expected outcome

Once, and only once, when the field is empty, the plugin tries to infer a reasonable value and stores it; a field that already holds a value is never recomputed, and a value the user later clears stays cleared (the inference must not fight the user). The moment to try is on installation and after an update, since those are the two times the field can be empty for someone who has not chosen to leave it so.

What "best effort" can draw on is for the implementing session to explore and judge against Obsidian's plugin constraints (a plugin runs inside the Obsidian sandbox, so anything that reads the operating system's user account has to be checked for availability on desktop and on mobile, and for what the community-plugin guidelines allow). Candidates worth checking include the vault's own signals (an author or name property that already appears in the user's notes, a git identity if the vault is a repository), and whatever the Obsidian or platform APIs expose about the account or the machine. Whatever is picked, the user must be able to see where the name came from and change it.

## Status (2026-08-29)

On hold by Rafa's decision of 2026-08-29: the inference waits until the state-vs-settings brainstorm (20260827.10) settles who "the person" behind a vault actually is, because inferring a name means deciding what that name identifies before anything writes one down. Nothing here is blocked technically — 20260827.09 has since landed, so the settings file stores only what someone actually set and `plugin.isSet("userName")` distinguishes a name typed and then cleared from one nobody ever typed, which is exactly the distinction a once-only inference needs to avoid fighting the user. Pick this up after that conversation, not before.

## Why it matters

The name is the key to two features that only work when it is set, and the "assign to myself" request (20260827.03) will make it a third. A once-only, never-overwriting inference removes the setup step without taking control away from the user.
