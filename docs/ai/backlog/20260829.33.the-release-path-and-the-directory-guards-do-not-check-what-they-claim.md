# The release path and the community-directory guards do not check what they are assumed to check

## What is asked

Seven findings of the audit of 2026-08-29 ([section 07](../reports/20260829.what-obsidian-already-provides/07.guidelines-mcp-build-and-the-rest.md)) are one subject with two halves: what the release workflow verifies before publishing, and what the local reproduction of the directory scanner actually runs. They are 07-03, 07-04, 07-12, 07-13, 07-14, 07-15 and 07-17.

## Current behaviour

The release path:

- Nothing compares the git tag of a release against `manifest.json`'s `version` (07-12). The `release` job in `.github/workflows/pipeline.yml` refuses a tag that is not plain semver or not reachable from `origin/main`, then builds, attests and uploads — and a mismatch would be a silent portal failure rather than a red build. Narrowed on 2026-09-10: on the ordinary path release-it writes the same string into the tag and the manifest in the same job, so the two can only drift on the republish path, where an existing tag is checked out and trusted.
- Two halves of this were closed on 2026-09-10 by the single-pipeline rework: `pnpm verify` (typecheck included) now runs in the same run, on the commit the release is cut from (07-13), and `dist/manifest.json` is attested beside `dist/main.js` and `dist/styles.css` (07-17). What verify still never sees is the `chore(release)` commit release-it writes on top — the manifest and `versions.json` rows it generates are checked only by the bump script that writes them, which is the half of 07-12 that survives above.
- `scripts/bump-plugin-version.mjs:38` writes a `versions.json` row on every bump, where the documentation asks for one only when `minAppVersion` changes; the file now holds twenty rows, eighteen of them identical (07-15). Inert today, actively misleading the moment `minAppVersion` moves — which two other entries in this backlog would do.
- The bundle targets `es2018`, three editions below the sample plugin, downlevelling for a runtime no user is on (07-14). What that costs in bytes is one of the report's unverified items.

The guards:

- `scripts/obsidian-scan.mjs:246-247` switches `validate-manifest` and `validate-license` off, faithfully copying the scanner's own config, and `eslint.config.mjs` cannot run them either. Finding 07-04 establishes why this is not a one-line config change: those two rules need a JSON language and a plain-text language respectively, which the recommended preset does not wire up. What the remote workflow action actually checks is one of the report's unverified items.
- One consequence is already sitting there: `manifest.json`'s description contains an em dash, which both the submission requirements and the manifest rule reject (07-03). One character, no behaviour — but nothing in the repository can see it, so the only route by which it is ever noticed is a human reviewer at submission time.

## How to observe

Read the `release` job in `.github/workflows/pipeline.yml` beside `package.json`'s scripts, and `scripts/obsidian-scan.mjs:240-250` beside `eslint.config.mjs`. Run `pnpm obsidian-scan:check` and note that it passes while two of the scanner's own rules never execute.

## Expected outcome

A release cannot publish an artefact whose version, types or provenance were never checked, and the local scan either runs the two rules it is assumed to run or says plainly that it cannot. The em dash is the first thing the second half would catch.
