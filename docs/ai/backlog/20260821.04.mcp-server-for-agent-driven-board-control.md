# Expose the board to agents through an MCP server inside the plugin

## What is asked

A user-enabled flag that turns on an MCP server hosted inside the Folia Kanban plugin, so any agent can drive a board the way a person drives the UI: create cards, set fields, move things, everything that is possible by hand.

The motivation is concrete and current. Agents driving a board today edit the card files directly, and they do not follow the plugin's rules. Cards end up without their history lines because the agent never knew a history entry was owed. The point of the MCP is that the rules stop depending on the agent knowing them.

The architectural requirement: one implementation behind both entry points. A manual edit through the UI and an MCP request must run the same code, not two copies of the same logic.

One line of the request reads two ways. It asks for agents to stop editing files directly, and also for "editing the files and everything else" to be exposed through the MCP. Most likely that means the MCP can perform anything the UI can, including operations that rewrite file content, rather than offering a raw write-this-file tool. Worth confirming before anyone builds it.

## What already exists

The seam he is asking for is largely already there. `CardRepository` in `src/model/repo.ts` is described in its own header as "the contract the UI depends on": `VaultRepo` implements it against Obsidian, the tests implement it in memory, and the UI never touches the vault directly. What is missing is a second caller of that contract, not an architecture to put behind it.

The seam is not complete, though, and this is the sharp part. `App.tsx` composes the pure `moveCard` reducer from `board.ts` with `repo.applyMove` (lines 154, 187 and 296), so the fractional-order computation for a move lives in the UI layer, above the contract. A caller that reached only `CardRepository` would not inherit it.

The missing history has two causes, not one. `history.ts` owns whether a given event is allowed to emit a line and the adapter owns when to write it, and the default scope is `moves` — under which field edits, comments and subtask changes emit nothing at all. So part of what Rafa is seeing is agents bypassing `VaultRepo` entirely, and part is the configured scope. A fix aimed at only one half will look broken.

The plugin cannot prevent direct file edits. Obsidian's own plugin-security documentation states that plugins inherit the app's access level and that Obsidian cannot reliably restrict them; nothing gives a plugin a lock on the vault. The board's live-reload echo guard exists precisely because outside edits happen. "Agents are not allowed to edit files directly" is therefore a convention Rafa enforces on his agents, not something the plugin can enforce on them.

`manifest.json` declares `isDesktopOnly: false` and the README promises desktop and mobile. Hosting a server inside the plugin has to reckon with that promise.

This shape is proven in the ecosystem. The [Local REST API with MCP](https://github.com/coddingtonbear/obsidian-local-rest-api) community plugin already ships an MCP server that runs inside Obsidian, over Streamable HTTP on `127.0.0.1:27124`, authenticated with a bearer token and a self-signed certificate. Community plugins doing this are accepted in the store, under the Developer Policies and behind Restricted Mode as the user-facing gate.

## Undecided

- Which operations the MCP exposes, given that some `CardRepository` members (`renderMarkdown`, `openCard`) mean nothing to an agent.
- Where the move and ordering logic now living in `App.tsx` has to sit so both callers genuinely share it.
- Transport, authentication, and what the enable flag defaults to.
- Whether the flag is per-vault or per-board, and how an agent picks a board when the vault has several.
- Whether the server runs while no board view is open, and what happens on mobile, where the plugin currently claims support.
- Whether history and the echo guard behave correctly when writes originate outside the UI.
- Whether the MCP surface becomes a documented, versioned public contract, given that this is a published community plugin.
