# Guided board setup picks its card folder non-atomically

## What happens

The guided board actions in [`src/main.ts`](../../../src/main.ts) (`Create board`, `Convert this note into a board`, and their menu entries) give each new board a card folder of its own: `cardFolderFor` in [`src/boardNote.ts`](../../../src/boardNote.ts) walks `Cards`, `Cards 1`, `Cards 2`… and returns the first path that does not exist yet. `makeBoard` then writes that path into the note's `card-folder` property and only afterwards creates the folder.

The check and the claim are separated by an `await` (`FileManager.processFrontMatter`). Two board setups that interleave across that await — both in the same parent folder, and the first not yet past its `createFolder` — both see `Cards` as free, both write `card-folder: ./Cards` into their own note, and end up sharing one folder. Each board then shows the other's cards, and adding a card on one makes it appear on the other, with nothing on either board saying why: [`src/obsidian/vaultRepo.ts`](../../../src/obsidian/vaultRepo.ts)'s `cardFolderWarning` only fires when the folder is missing or when a `card-folder` has two competing readings, and a note-relative `./Cards` has exactly one.

This was found by review, not observed. It is judged unlikely to be reachable by hand — each setup is a separate user gesture (a palette confirmation or a menu click), and the window between them is a single `await` — so it was consciously left as it is rather than paid for with an atomic-claim rewrite of a path whose value is its simplicity. The sequential case, "create two boards in the same folder one after the other", is handled correctly: the second gets `Cards 1`.

The unit tests in [`test/boardNote.test.ts`](../../../test/boardNote.test.ts) exercise `cardFolderFor` against a static `exists` predicate, so they cover the naming and not the check-then-create sequence, and would keep passing if this were ever hit.

## Expected outcome

Two guided board setups cannot end up on the same card folder, whatever their timing. Whether that is worth doing at all is part of the question: the trigger may be out of reach for a human, in which case the right outcome is a decision recorded here rather than code.
