# The MCP bearer token is kept in the plugin's synced data file in the clear

## What is asked

Finding 07-02 of the audit of 2026-08-29 ([section 07](../reports/20260829.what-obsidian-already-provides/07.guidelines-mcp-build-and-the-rest.md)), with finding 05-11 naming the same key from the settings side.

## Current behaviour

The token that authorises an agent to drive the board (`src/settings.ts`, minted in `src/obsidian/mcpService.ts:23`) is held as an ordinary settings key and written to `data.json` by `Plugin.saveData` (`src/main.ts:579`). `docs/mcp.md:121` states this plainly, so nothing is hidden — but `data.json` lives inside the vault, and a vault travels: through Sync, through a git remote, through a backup, onto every device the user opens it on. The credential is for a server bound to one machine, so it has no business on the others.

Obsidian added `App.secretStorage` in 1.11.4 and documents it as the answer for exactly this. Two costs are named in the finding: the API is well above the plugin's `minAppVersion` 1.7.2, so it needs either a raised floor or a `requireApiVersion` branch keeping the current storage as the fallback (the shape `src/main.ts:800` already uses), and a token that moves has to be migrated for users who already have one.

## How to observe

Open the plugin's `data.json` in a vault where agent access has been switched on, and note that the value is readable. Then consider where that file is: any synced copy, any backup, any clone of the vault.

## Expected outcome

The token stops travelling with the vault, with a migration for the ones already written. Nothing here needs the token's value to be reproduced anywhere to be understood or verified.
