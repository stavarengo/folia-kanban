# Commands to create a board or convert a note into one

## Problem

The only documented way to get a board note today is to hand-write the frontmatter yourself (see [`README.md`](../../../README.md#set-up-a-board): `folia-board: true`, `card-folder`, `columns`, plus the newer `folia-view` and `priorities` keys). There is no command, menu item, or ribbon action that creates or converts a note — a user has to copy the YAML block correctly, including getting the properties onto the very first lines of the note, which is not obvious to someone new to Obsidian's frontmatter block.

[GitHub issue #1](https://github.com/stavarengo/folia-kanban/issues/1) shows this failing in practice: a new user created a note "as instructed" and the plugin still reported "no board note found" (the message `activateView()` shows in [`src/main.ts`](../../../src/main.ts) when `findBoards()` comes back empty). The likely cause is the properties block not being placed at the very start of the note — a plain onboarding mistake that a guided command would remove entirely, rather than something that needs explaining better in prose.

## Expected outcome

Two new user-facing actions:

- **Create Folia board** — creates a new note already carrying valid board frontmatter (at minimum `folia-board: true`, `card-folder`, `columns`; consider whether `card-title`, `folia-view`, `priorities` need defaults too).
- **Convert note to Folia board** — takes an existing, non-board note and adds the same properties without disturbing its existing content.

Both should be reachable through as much of the Obsidian API surface as makes sense for each: command palette, file explorer context menu (right-click a note; right-click a folder to create a board inside it), the editor context menu, and the ribbon where it fits. Obsidian should also let users pick which integration points are active, one toggle per integration point, since not everyone wants every context menu cluttered.

## Investigation notes (for whoever picks this up)

**Current create/template code:** none exists. [`src/main.ts`](../../../src/main.ts) only registers one command (`folia-open-kanban-board`, "Open board") and one ribbon icon (`layout-grid`, "Open Folia Kanban board" → `activateView()`). There is no `file-menu`, `files-menu`, or `editor-menu` listener anywhere in `src/`, and no note-creation helper — board discovery is entirely read-only (`findBoards()` scans `vault.getMarkdownFiles()` for `folia-board: true`, via [`src/viewMode.ts`](../../../src/viewMode.ts)'s `isBoardFrontmatter()`).

**Board properties today** (from `README.md` "Set up a board" and `isBoardFrontmatter`/`resolveBoardViewMode` in `src/viewMode.ts`):

```yaml
folia-board: true
card-folder: Cards
card-title: auto        # optional: auto | filename | heading
folia-view: board        # optional: board | markdown, per-note override
priorities: [A, B, C]    # optional
columns:
  - todo
  - doing
  - done
```

Only `folia-board: true` is load-bearing for detection; the rest are read with fallbacks (`card-folder` defaults to `Tasks` if omitted, per the README's "Set up a board" section).

**Relevant Obsidian API** (checked against `node_modules/obsidian/obsidian.d.ts` in this repo, API version 1.13.1):

- `Plugin.addCommand({ id, name, checkCallback, editorCheckCallback, callback })` — a `checkCallback`/`editorCheckCallback` can gate visibility (e.g. hide "Convert to board" from the palette when the active file already is one). `Plugin.removeCommand(id)` exists too, so a command can be added/removed at runtime, not just gated inside its callback.
- `Workspace.on("file-menu", (menu, file, source, leaf?) => ...)` — right-click on a single file/folder in the explorer; `file` can be a `TFolder`, which is how "create a board here" on a folder would be wired.
- `Workspace.on("files-menu", (menu, files, source, leaf?) => ...)` — multi-select right-click; probably out of scope for this feature but exists.
- `Workspace.on("editor-menu", (menu, editor, info) => ...)` — the in-editor right-click/gutter menu.
- `Plugin.addRibbonIcon(icon, title, callback)` returns an `HTMLElement`, removable with `.remove()` — so a ribbon icon can be toggled on/off at runtime the same way a command can.
- `FileManager.processFrontMatter(file, fn)` — the safe way to add properties to an existing note without hand-parsing YAML; this is what "convert note to board" should use to avoid disturbing existing content or existing frontmatter keys.
- `Vault.create(path, data)` and `FileManager.getNewFileParent(sourcePath, newFilePath?)` — for "create a board" from the command palette or ribbon (no folder context), `getNewFileParent` resolves Obsidian's own "new file location" setting so the created note lands wherever the user's normal new-note behaviour puts it; the folder-menu case already has the target folder from the `file-menu` event.

**Per-integration toggles:** nothing in the settings today resembles this — `src/settings.ts`'s `KanbanSettings` interface is all view/behaviour preferences, no feature-visibility flags. Two viable mechanisms, both supported by the API above: (a) register/unregister the command, ribbon icon, and menu-event listener when the corresponding setting changes (`addCommand`/`removeCommand`, ribbon element `.remove()`, `registerEvent`/manually calling `app.workspace.offref`), or (b) always register everything and check the settings flag first thing inside each handler/menu callback, which is simpler but leaves an always-present (if inert) palette entry. `file-menu`/`editor-menu` handlers are called fresh on every menu open, so checking a flag there costs nothing.

**Default-open interaction:** `src/main.ts`'s `patchLeafSetViewState()` intercepts every `WorkspaceLeaf.setViewState({ type: "markdown", ... })` call and redirects to the board view when `shouldOpenAsBoard()` is true. Since this patches the leaf-level open path rather than a specific command, a note created and then opened via `Vault.create` + `workspace.getLeaf().openFile(file)` (or any other standard open call) should already come up as the board automatically, the same way any other board note does — no special-casing needed for "just-created" notes, as long as the frontmatter is written before the note is opened.
