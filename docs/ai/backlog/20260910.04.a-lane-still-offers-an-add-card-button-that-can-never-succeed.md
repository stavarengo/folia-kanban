# A lane still offers an Add card button that can never succeed

## What happens

A column carrying a `filter:` rule is a lane: the board fills it from the rule, and a card whose properties the rule rejects is refused rather than filed there (see the **Columns that fill themselves** section of the README). The refusal covers the inline **Add a card** control too — `onAddCard` in [`src/ui/App.tsx`](../../../src/ui/App.tsx) judges the card `createCard` is about to write and declines with the rule quoted.

That is the right answer to "what should happen", and it leaves a smaller wart behind: the control is still drawn on a lane column, and for most rules it can never succeed. The inline flow writes a title and nothing else, so a lane ruled `area:research`, `tag:bug`, `assignee:alex` or `context:Engineering` refuses every card typed into it. The user gets an explanation, but only after clicking a button that was never going to work.

No add-card flow escapes it. The **detail** flow (Settings → *When adding a card*) looks like it might, since it opens the panel — but its create form has one field, the title, and it creates the card before any other field can be filled in. So today the only lane an added card can satisfy is one ruled on `status:`, which is the column id the write sets anyway.

## Why it matters

Small, and only cosmetic in the sense that nothing is lost or written. But an affordance that always fails is a papercut on every board built around lanes, and the refusal message — written to explain a drag — reads oddly as the answer to "add a card here".

## What to work out

Three shapes, none obviously right:

- Hide the add-card control on a lane entirely. Cheapest, and it reads as honest: a lane is a view, and you do not add to a view. It costs the `status:`-ruled lane, where adding does work today.
- Keep the control and pre-fill what the rule asks for, so adding to an `area:research` lane writes `area: research` on the new card. Closest to what someone clicking it means, and it needs a rule-to-frontmatter translation that only exists for the simple `key:value` tokens — nothing sensible to write for `due:overdue` or `is:blocked`. Giving the detail create form the fields the rule names would be the same work, seen from the other end.
- Leave it and reword the refusal for the add case specifically.
