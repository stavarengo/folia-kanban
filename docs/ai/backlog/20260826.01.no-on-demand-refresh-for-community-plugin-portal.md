# No on-demand refresh for the community plugin portal's version display

## Problem

The public listing at `community.obsidian.md/plugins/folia-kanban` lagged behind GitHub: it still showed version `0.0.10` after GitHub already had a tagged release `0.0.17`. There is no documented, official way for a plugin author to force or check the timing of the portal's rescan.

What the official sources actually say:

- [obsidian.md/blog/future-of-plugins](https://obsidian.md/blog/future-of-plugins/): "If your project passes, it will be available to search and download in the app within 24 hours." For a brand-new submission's first automated review: "Typically, you will see the results of your review within a few minutes." Neither statement documents a mechanism (webhook, poll interval, dashboard button) — only an outcome window.
- [docs.obsidian.md — Submit your plugin](https://docs.obsidian.md/Plugins/Releasing/Submit+your+plugin) and [Release your plugin with GitHub Actions](https://docs.obsidian.md/Plugins/Releasing/Release+your+plugin+with+GitHub+Actions): describe tagging a GitHub release matching `manifest.json`'s version, but say nothing about how or when the directory notices a new release for an already-approved plugin.
- `obsidianmd/obsidian-workflows` and the whole `obsidianmd` GitHub org (checked via `gh repo list obsidianmd --limit 100`): no action, no `workflow_dispatch`-able job, and no API client for triggering a portal rescan. The only related automation found is `obsidian-releases/.github/workflows/mirror-community-json.yml`, an hourly cron (`17 * * * *`, plus `workflow_dispatch`) that mirrors `community.obsidian.md/assets/community-plugins.json` back into that repo — the reverse direction (portal → repo), not a way to push a repo change into the portal.
- Real-world reports on the Obsidian forum describe the same symptom with no official fix path: [Plugin submission portal stuck on "No release matches your manifest version"](https://forum.obsidian.md/t/plugin-submission-portal-stuck-on-no-release-matches-your-manifest-version-despite-correct-releases/114686) was resolved only by a staff member's manual intervention ("the problem is fixed now", from a poster with a recognizable Obsidian-team forum handle), with no explanation of cause or a self-serve fix. A second thread, [No release matches your manifest version](https://forum.obsidian.md/t/no-release-matches-your-manifest-version/116025), got no staff reply at all and the reporter says it "resolved itself" after roughly a day.

## Expected outcome

Confirmation (from this research) that there is currently no official self-serve action to take when the portal is slow or stuck: no API endpoint, no dashboard "sync" button, no GitHub Action, no webhook. The only documented lever is time (up to ~24 hours per the blog post), and beyond that the only known recourse is asking Obsidian staff directly (e.g. via the forum or the plugin-review Discord/GitHub) to manually clear a stuck cache, based on the forum precedent above.

This entry exists so a future session does not re-research this from scratch: if the portal is stale again after a release, don't look for a technical trigger — wait roughly 24 hours, and if it's still stale after that, escalate to Obsidian staff rather than debugging the release itself.

This is blocked by [20260826.02](./20260826.02.adopt-official-obsidian-workflows-action.md) because escalating a staleness question to Obsidian only makes sense once the release pipeline itself is confirmed to produce a clean scan — otherwise a stale-looking portal could just be reflecting a real warning that the official action would have caught first.
