# Open a board note as the board, and let one button swap between the board and the Markdown editor

## What is asked

Opening a note that carries `folia-board: true` should land the user in the view they actually want, rather than always in the plain Markdown editor. Which view that is becomes a plugin setting with three choices: the board, the ordinary Markdown editor, or — as the preferred default — both at once, a narrow Markdown editor on the left with the board taking most of the width beside it.

Rafa is explicit that the third option depends on what Obsidian permits. He does not want two editors; he wants one tab showing two views of the same note. If Obsidian cannot host that inside a single tab, the third option is dropped and only the first two remain.

The setting is a default, not a rule. Any individual board note can override it from its own frontmatter, so one vault-wide preference can coexist with boards that always open a particular way. A note without the property falls back to the plugin setting.

The last part is a toggle. When a board note is open in the Markdown editor there should be a button in the view's header, up in the top right where Obsidian already puts the reading/editing controls and the three-dot menu, that switches that tab to the board. When the board is open, a button in the same position switches back to the Markdown editor. Both buttons appear only for notes carrying the board flag.

## What already exists

Obsidian's API settles the third option, and the answer is mostly no. A workspace leaf — one tab — carries a single `view` property, one View and not a collection. Two views side by side therefore means two leaves, which Obsidian presents as a split rather than as one tab. The only route left to the arrangement described is the board's own view drawing both panes inside itself. Whether a custom view can host a live, editable Obsidian Markdown editor was not established either way here — the pages checked were the Views guide and the `WorkspaceLeaf` and `MarkdownView` references, none of which cover editor embedding, and the plugin's existing markdown rendering goes through `MarkdownRenderer`, which is read-only. That question needs a spike before the option is promised, and by Rafa's own rule the option is dropped if it turns out to be impossible.

The button, by contrast, is squarely supported. `addAction(icon, title, callback)` is declared on `ItemView` and inherited by `MarkdownView`, so one API call places a header action in both the Markdown editor and the board view. A `WorkspaceLeaf` also exposes `isDeferred` and `loadIfDeferred()`, which is the documented face of the deferred-leaf behaviour noted below.

The mechanics of the swap are already in the codebase. `KanbanView` is a registered `ItemView` under the type `folia-kanban-view`, and `openBoard` in `main.ts` already calls `leaf.setViewState({ type: VIEW_TYPE_KANBAN, active: true, state: { boardPath } })` — a leaf being retargeted at the board view is the existing, working path, not something new.

Board detection already exists too: `isBoard` reads `folia-board === true` straight from the metadata cache, and `findBoards` scans the vault with it. A "does this note get the button" test is that same predicate.

What is missing is the entry point. Today a board opens only through the ribbon icon or the "Open board" command; clicking the note in the file explorer opens plain Markdown, and nothing observes file-open events. Also worth knowing before implementing: `openBoard` reuses the *first* existing board leaf rather than the leaf holding the file, so "open this note as a board" is not quite the behaviour that function has today.

The settings side is a well-trodden path. `KanbanSettings` plus `DEFAULT_SETTINGS` in `settings.ts` and the dropdown rows in the settings tab are an established pattern, and `updateSettings` already persists a change and pushes it live into every open board without a reload.

One caution recorded in the repository's own working notes: Obsidian 1.12 defers background leaves, so a board opened in a leaf that is not focused stays empty until it gets focus. Any arrangement that puts the board beside something else has to survive that.

## Undecided

- How a leaf carries the file's identity across a toggle: `KanbanView` stores `{ boardPath }` in its view state, not a file, so switching that same leaf back to `markdown` has no file to open. The round trip needs a piece that does not exist yet.
- The frontmatter property's name on the board note, and its accepted values.
- Whether the setting also governs notes opened by a link or by search, or only direct opens.
- What the toggle does to unsaved editor state and to scroll position when a tab switches view.
- Whether switching a tab to the board is recorded in Obsidian's navigation history, so Back returns to the editor.
- Which icon the button uses in each direction, and its accessible label.
- What happens when a note gains or loses the board flag while it is open.
