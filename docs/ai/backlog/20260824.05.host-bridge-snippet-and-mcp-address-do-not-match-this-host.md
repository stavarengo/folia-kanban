# The Obsidian host-bridge snippet and the MCP browser URL do not match this host's network

## What happens

`AGENTS.md` tells an agent inside a container to have the human run `socat TCP-LISTEN:9222,bind=CONTAINER_IP,fork,reuseaddr TCP:127.0.0.1:9222` on the host, and `.mcp.json` points the `chrome-devtools-obsidian` server at `http://172.17.0.1:9222`.

On the TUXEDO laptop, run through `ccw`, neither works as written. The host does not own the container's address, so `bind=CONTAINER_IP` fails and socat never listens; the working bind is the host side of the link, `10.254.254.1`. And the host has no `172.17.0.1` at all: its `docker0` is `10.254.254.1/24`, so the MCP server can never reach Obsidian without editing `.mcp.json` locally and reconnecting.

Observed on 2026-08-24 while trying to check the card-title feature in the real Obsidian: Obsidian was up with `--remote-debugging-port=9222` on `127.0.0.1`, socat had silently failed, and the MCP server kept reporting "Could not connect to Chrome". The workaround was `bind=10.254.254.1` on the host plus a temporary `.mcp.json` edit, which was reverted afterwards.

## Expected outcome

An agent in a container follows `AGENTS.md`, the human runs the snippet as given, and the MCP server reaches Obsidian on the first try, on this host and in the devcontainer alike. The setup should derive the right addresses (the container's default gateway is the host side of the link) instead of hard-coding `172.17.0.1`, or document both networks explicitly.
