# The Obsidian host-bridge snippet and the MCP browser URL assume one network layout

## What happens

`AGENTS.md` tells an agent running inside a container to have the human run `socat TCP-LISTEN:9222,bind=CONTAINER_IP,fork,reuseaddr TCP:127.0.0.1:9222` on the host, and `.mcp.json` points the `chrome-devtools-obsidian` server at a hard-coded `http://172.17.0.1:9222`.

Both assume Docker's default bridge. On a host with a different bridge subnet, or where the host does not own the container's address, `bind=CONTAINER_IP` makes socat fail silently and the MCP server keeps reporting "Could not connect to Chrome", even though Obsidian is up with `--remote-debugging-port=9222`. The only way through is to bind socat to the host side of the link and edit `.mcp.json` locally, then revert it.

## Expected outcome

An agent in a container follows `AGENTS.md`, the human runs the snippet as given, and the MCP server reaches Obsidian on the first try regardless of the bridge subnet. The setup should derive the addresses (the container's default gateway is the host side of the link, and that is also what socat should bind to) instead of hard-coding `172.17.0.1`, or document how to find both values.
