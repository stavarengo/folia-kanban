# Property names in the detail panel should autocomplete the way Obsidian's frontmatter editor does

## What is asked

Rafa asked on 2026-08-27 for the property fields of the card detail panel to offer the same autocomplete Obsidian gives when typing a property name in a note's YAML frontmatter, integrated with the Obsidian API, and with the suggestions grouped in a specific order.

## Current behaviour

The "New property name" input in `src/ui/CardDetail.tsx` (the `folia-prop-add` block) is a bare text field: no suggestions, no knowledge of what keys exist on the board or in the vault. The panel already uses `<datalist>` suggestions for the priority value and the relationship targets, but not for property names. Meanwhile the set of keys the plugin itself understands is written down in at least three places that must agree by hand: `EDITED_KEYS` in `CardDetail.tsx` (keys the panel edits through dedicated controls), `RESERVED_KEYS` in `src/model/relationships.ts` (keys that can never be relationship keys), and the typed fields of `CardFrontmatter` in `src/model/types.ts`; the README's description of the note format is a fourth.

## Expected outcome

Typing in the property-name field suggests names, using the mechanism Obsidian exposes for this rather than a home-grown popup, so it looks and behaves like the frontmatter editor's suggestions. The suggestions come in three groups, in this order:

1. The properties Folia Kanban itself defines (the note format the README documents: status, priority, due, order, title, the relationship keys the board declares, and so on). These come from one list in the codebase that is the single source of truth for "what keys does Folia Kanban know", and the places that currently keep their own copy of that knowledge read from it too, so the list cannot drift.
2. Properties that are not in the first group but appear on notes inside the board's card folder, obtained from Obsidian's metadata rather than by parsing files ourselves, and offered even when nothing outside that folder uses them.
3. Every other property used anywhere in the vault.

## Why it matters

A property typed into the panel lands in the note's frontmatter, so a misspelt key (`Priority`, `due-date` next to an existing `due`) creates a second property that the board silently ignores. Suggesting the plugin's own vocabulary first, then the board's, then the vault's, makes the right key the easy one and keeps a board's properties consistent without a schema. Consolidating the key list is the precondition, and it removes a duplication that already exists.
