# A release is tagged before anything verifies the commit, and the local path is the only one that verifies at all

## What happens

Both ways of cutting a release create the tag first and check afterwards. The **Create Release** workflow checks out the tip of `main` and runs `release-it --ci`, which bumps, writes the changelog, commits, tags and pushes; nothing in that job runs `pnpm verify`, `pnpm test` or a build, and nothing consults the CI run for the commit it tags. The tag push then starts the **Release** workflow, which runs `pnpm test` and `pnpm build` only, two of verify's nineteen checks and not the typecheck, before attesting and publishing. A red check there leaves a tag on origin and a release commit on `main` with no GitHub release behind it; re-running the workflow tests the same commit and fails the same way, so the recovery is deleting the tag by hand or publishing the next number.

The local path, `pnpm dev:helpers:release`, is the only one that verifies before a tag exists, and only by accident: release-it's push runs the lefthook pre-push hook, which runs the full verify. That is the hook 20260910.09 has decided to remove, and 20260910.07 and 20260910.08 describe two more ways the local path goes wrong that a runner cannot.

Observed on 2026-09-10 while cutting 0.2.0: the gate had to be done by hand, by waiting for the CI run on the commit to go green before dispatching Create Release.

## Decided on 2026-09-10

All releases go through CI. Create Release runs the full `pnpm verify` on the exact commit it is about to tag, and only then hands over to release-it, so a red check costs one workflow run and leaves the repository as it was. Release keeps test and build as a sanity pass and stays re-runnable (it already checks whether the GitHub release exists and uploads with clobber). Create Release gets a concurrency group so two dispatches cannot race on one base commit. `requireCleanWorkingDir: false` leaves `.release-it.json`, since a runner is always clean. The local script stays but only dispatches the workflow through the `gh` CLI and watches the run, failing with the install or login instruction when `gh` is missing or not authenticated. A tag ruleset restricting `*.*.*` tags to the workflow's identity closes the local path by policy; that is a GitHub repository setting, so it is Rafa's step.

## How to observe

Read `.github/workflows/create-release.yml` and `.github/workflows/release.yml` beside `package.json`'s `verify` script, and note where `pnpm verify` runs relative to the `release-it` step. `tmp/release-routine.today.mmd` and `tmp/release-routine.proposed.mmd` (git-ignored, from the 2026-09-10 session) draw both flows.

## Expected outcome

A version cannot be tagged unless the full verify passed on the commit being tagged, the tag can only be created by the workflow, and a release started from the local machine is the same workflow dispatched remotely. With that in place, 20260910.09 can drop the pre-push hook without removing the last verify before a tag, and 20260910.07 and 20260910.08 shrink to whatever remains of them for ordinary commits.
