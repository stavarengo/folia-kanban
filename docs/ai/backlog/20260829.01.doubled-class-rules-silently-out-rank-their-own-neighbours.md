# The doubled-class convention silently out-ranks the plugin's own single-class rules

## What is asked

`src/styles.css` names a class twice — `.folia-link.folia-link` — whenever a rule has to beat Obsidian's `button:not(.clickable-icon)`, which sits at specificity (0,1,1). That convention works, and `scripts/check-button-styles.mjs` enforces it. It has a side effect nobody is watching: a doubled rule at (0,2,0) also beats every ordinary single-class rule at (0,1,0) that the plugin writes for the same element, so a plugin rule can lose to another plugin rule and go on looking correct in the file and in every test.

## Current behaviour

Two live examples, both found on 2026-08-29 while fixing 20260827.02, both measured in the running Obsidian:

- `.folia-title-reason` (`src/styles.css`) asks for `--folia-font-size-xs` (11px) and renders at 12px, because `.folia-muted.folia-muted` sets `--folia-font-size-sm` later in the file at (0,2,0), and the element carries both classes.
- `.folia-title-why` asks for the same 11px and renders at 13px, because `.folia-link.folia-link` expands `font: inherit` at (0,2,0), later in the file.

A third sits on `.folia-title-value` in the same block: its `font-size`, `font-weight`, `color` and `text-align` all lose to `.folia-link.folia-link`, so the row renders as a normal-weight link-coloured line rather than the semibold body-coloured title the stylesheet asks for. Fixing that one by moving the declarations to an element `.folia-link` does not match was tried during 20260827.02 and reverted, because it coloured the glyphs without colouring the underline the button paints around them — which is itself a fact worth carrying into whatever fixes this: the underline is drawn from the *button's* `currentColor`, and `text-decoration-color` is not available in this repo (`src/styles.css` records that Obsidian's community-directory scan flags every `text-decoration-*` longhand). All three were left as they are, because beating a (0,2,0) rule that comes later in the file needs the class repeated a third time, and doing that deserves its own decision.

Nothing catches any of this, and it is worth being precise about why, because the obvious guess is wrong. `check-button-styles.mjs` does have a loop for "one plugin rule out-ranks another", and that loop already looks at every property, not only the colour ones `CONTESTED` lists — the colour list gates a different loop. Three separate things stop it firing here. It reports only the case where the *earlier* rule wins, which is the mirror image of what happens. It compares property names literally, so a `font-size` never matches the `font` shorthand `.folia-link.folia-link` writes. And it enumerates `<button>` opening tags in `src/ui/**` only, so `.folia-title-reason`, which is a `<p>`, is outside its world entirely under any comparison. jsdom sees none of it either, since the tests read the stylesheet as text.

## How to reproduce

Open the card detail panel in the real Obsidian and read the computed `font-size` of `.folia-title-reason` and `.folia-title-why` against what `src/styles.css` declares for them. More generally: for each element in the live plugin DOM, compare every declaration a single-class plugin rule makes against the value that actually computes, and list the ones a later doubled-class plugin rule overrode.

## Expected outcome

Two things a future session should settle together. First, whether the known cases should render what their rule asks for, and any others the sweep turns up. Second, whether this class of collision should be caught mechanically — the existing guard is the obvious place, and the three reasons above are what it would have to grow past, none of which is a small change to it — or whether the convention itself should change so that a rule written to beat the theme cannot also silently beat its own neighbours.
