# The adapter takes the long way round the vault API in eight places, all of them one-liners

## What is asked

Eight findings of the audit of 2026-08-29 are individually small, sit almost entirely in one file, and would be done in one sitting: 04-07, 04-08, 04-10, 04-11, 04-18 and 07-07 (with 07-09 pointing at the file-lookup half), plus 05-07 in `src/view.tsx`. They are grouped for that reason, not because they share a cause.

## Current behaviour

Each with its location, from [section 04](../reports/20260829.what-obsidian-already-provides/04.vault-files-and-metadata.md), [section 05](../reports/20260829.what-obsidian-already-provides/05.workspace-views-commands-and-settings.md) and [section 07](../reports/20260829.what-obsidian-already-provides/07.guidelines-mcp-build-and-the-rest.md):

- `src/obsidian/vaultRepo.ts:189` and `:191` and `src/boardNote.ts:34` read `fm["card-folder"] ?? fm["card_folder"]` by hand, where a RegExp key matches both spellings and the capitalisations nobody wrote down (04-07).
- `src/obsidian/vaultRepo.ts:240` walks the vault's entire markdown list to find the notes inside one folder whose path it already knows, and `src/obsidian/mcpService.ts:59` does the same for a single known path (04-08, 07-09). The community-directory lint has a rule for this shape; its matcher does not happen to fire on these.
- Eight `getAbstractFileByPath` call sites, five of which then narrow with `instanceof`, where `getFileByPath` and `getFolderByPath` exist (04-10); one of the five, `shouldOpenAsBoard` in `src/main.ts:340`, has a better target still.
- `src/obsidian/vaultRepo.ts:567` takes a basename apart with `split("/").pop()` and a regex while holding a `TFile` that answers directly (04-11).
- `src/boardNote.ts:60` and `:72` assemble vault paths by string concatenation with no `normalizePath`, although that file may import `obsidian` and the adapter already uses it three times (04-18).
- `renderMarkdown`'s cleanup closure clears its container with `el.innerHTML = ""` (`src/obsidian/vaultRepo.ts:682`) where the same function already prefers `el.empty()` on entry at `:663`. Finding 07-07 is precise about why the obvious fix is not enough: copying the guard leaves a second literal `innerHTML` in the file that a reviewer grepping for the property still finds.
- `KanbanView.setState` types its result parameter by hand as `{ history: boolean }` (`src/view.tsx:63`) instead of importing the exported `ViewStateResult` (05-07).

## How to observe

Open each location above and read it beside the API member the finding names.

## Expected outcome

These eight read the way the adapter's own neighbouring code already reads. None of them changes behaviour except 04-08, which stops walking the vault, and 04-07, which starts accepting spellings the schema already declares.
