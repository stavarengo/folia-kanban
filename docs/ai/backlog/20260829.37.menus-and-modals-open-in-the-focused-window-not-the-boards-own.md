# Menus and dialogs open in whichever window has focus, not in the window that owns the board

## What happens

Finding 06-04 of the audit of 2026-08-29 ([section 06](../reports/20260829.what-obsidian-already-provides/06.interaction-and-input.md)), confirmed live during the report's verification pass: with the Settings window focused, a Folia column popover rendered into that window.

`src/ui/CardContextMenu.tsx:63` and `src/ui/ColumnMenu.tsx:52` portal into `activeDocument` and measure against global window geometry; `src/ui/ColumnEditModal.tsx:276` portals into `activeDocument.body`; several listeners and measurements in `src/ui/CardDetail.tsx` (`:1099`, `:1192`, `:1209`) do the same. `activeDocument` follows whichever window currently has focus, which is not necessarily the window the board is rendered in. Obsidian's own guidance for a plugin that can appear in a popout window is to use the element's owner document and owner window, which are always the board's own.

Anyone who pops a board out into its own window, or opens a second window at all, can hit this: a menu opens in the wrong window, or its position is measured against the wrong viewport.

## How to reproduce

Open a board, move it into a popout window (drag the tab out), then focus the main window and interact with the board's column menu or context menu from the popout. The finding's own live reproduction used the Settings window for the same effect.

## Expected outcome

Every surface the board portals or measures uses the document and window that own the board. The finding is explicit that this changes nothing about Folia's custom interaction — it is the same code reading the right document.
