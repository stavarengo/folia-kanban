# Let a card's displayed title come from somewhere other than its file name

## What is asked

Some people name card files as numbered slugs — `01-fix-the-export-path.md`, `02-rename-the-widget-helpers.md` — because the number carries the order and the slug keeps the folder readable. Folia Kanban shows that slug as the card title, which is not what the card is called. The note's own first heading usually is.

The default behaviour asked for is automatic: when the file name looks like a slug rather than a name, take the title from the first heading after the frontmatter, whether it is an H1 or an H2, since there is no telling which line it lands on. If that heading does not look like a real title either — a bare `Question`, `Answer`, `To Do` — keep looking. Both of those judgements must be shape-based. Rafa was explicit that this is not a list of forbidden words: the code decides whether a heading *looks like* a title the same way it decides whether a file name *looks like* a name. If nothing suitable turns up, fall back to the file name.

A second part, which he labelled a nice-to-have, makes the source configurable on the board note's frontmatter — the same frontmatter that already declares the board and its card folder. One property, one value, not a list of preferences. The values he sketched: always the file name; always the first heading; the first heading with the file name as fallback; or the card's frontmatter. When the property is set, the guessing stops: "always the first heading" means the first heading is used whenever it is non-empty, even if it is a single word. A configured source that yields nothing still falls back to the next obvious source.

A card-level override completes it: a frontmatter key on the card itself (`card_title`, or just `title` — the name is an implementation decision) that wins outright, with no guessing, for that card.

The framing behind all of it is Folia's freedom principle. The plugin should not impose a naming convention; it should cope with whichever one the person already uses.

## What already exists

The file's base name is not merely how a card is *displayed* — it is what a card *is*. It appears as the card face title, the detail panel heading, the drag overlay label, every accessibility label, the text the inline rename edits, the search haystack, and the alphabetical tiebreak when cards sort. Renaming a card renames the `.md` file through Obsidian's link-aware rename, which is why the card's path changes on rename.

More consequentially, the base name is identity. Subcard parentage is resolved by matching a `[[link]]` against card base names, and `board.ts` deliberately resolves a duplicated base name to nothing rather than binding the wrong card. So introducing a displayed title that differs from the file name splits two things that are currently one: what a card is called, and what other cards link to when they name it.

The groundwork for reading a heading is already in place and unused. `parseBody` already extracts the first H1 into `CardBody.title`, and nothing in the UI reads it. `loadBoard` already calls `cachedRead` on every card and parses its body for stats, so headings are available at load time without any extra file reads.

Card frontmatter is a free-form string-keyed mapping, so a per-card title key needs no schema change to be accepted and preserved.

## Undecided

- What makes a file name a slug rather than a name, and a heading a real title rather than a section label, given both must be judged by shape and not by a word list.
- Whether a detected title replaces the base name only for display, or also for search, for sorting, for accessibility labels, and for `[[wikilink]]` resolution.
- What the inline rename control edits once the displayed title and the file name can differ.
- The board property's name and accepted values, and what happens when the configured source comes back empty.
- The card-level key's name, and confirmation that it outranks the board setting.
- Whether headings below H2 count, since the request names H1 and H2.
- How a card gets renamed at all once its title comes from a heading: `renameCard` is the only title write path today and it renames the file, while `setDescription` deliberately preserves the H1 it sits under. Retitling such a card is an operation the repository contract does not currently have.
- Whether two cards displaying the same title is a problem, given that links still match by base name.
