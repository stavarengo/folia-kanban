# Folia carries a second parsing layer over files Obsidian has already parsed

## What is asked

Five findings of the audit of 2026-08-29 ([section 04](../reports/20260829.what-obsidian-already-provides/04.vault-files-and-metadata.md), with 07-16 pointing at the first from [section 07](../reports/20260829.what-obsidian-already-provides/07.guidelines-mcp-build-and-the-rest.md)): 04-04, 04-05, 04-16 and 04-17. The app parses every note into a metadata cache and exposes `parseYaml` and `stringifyYaml`; the plugin parses the same notes again.

## Current behaviour

- A second YAML parser is bundled into the shipped plugin: `src/model/card.ts:12` imports `parse` from the `yaml` npm package, which is a runtime dependency and is not marked external in `esbuild.config.mjs`, so it is compiled into `dist/main.js` (04-04). What it actually costs in the bundle is one of the report's unverified items; measuring it needs a build with and without.
- Frontmatter is cut off the file with `FRONTMATTER_RE` (`src/model/card.ts:18`, `splitFrontmatter` at `:56`) rather than with the offsets Obsidian already computed, and every byte-stable body edit is built on that split (04-05).
- Headings are found with three different regexes in three places — `src/model/cardTitle.ts:64`, `src/model/card.ts:91` and a stricter H1-only pattern at `:140` — although the cache lists them (04-16).
- Code fences are tracked by a hand-written CommonMark scanner, the whole of `src/model/fences.ts`, so that Folia's own format quoted inside a note stays inert (04-17).

All four sit in `src/model/**`, which may not import `obsidian`, and the findings agree on the shape that unblocks them: a parser or a parsed result injected at the adapter boundary, with the tests supplying their own. They also agree on what must stay text-based: the write path needs the raw text, so the parsers do not disappear, and a second reading path that is not the one the writer uses only adds a way for two readings to disagree.

## How to observe

Read `package.json`'s dependencies beside `esbuild.config.mjs`, then grep `src/model/` for `FRONTMATTER_RE`, `HEADING_RE` and `fences.ts` and compare each against what `app.metadataCache.getFileCache()` returns for the same note.

## Expected outcome

One parse per file wherever a read is being served, with the text-based write path kept deliberately and the duplicate readers gone or reduced to it. The bundled YAML package is the concrete first question: whether the plugin ships a second parser at all.
