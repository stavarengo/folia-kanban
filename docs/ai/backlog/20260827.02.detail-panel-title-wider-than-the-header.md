# The detail panel's title has no answer for a title wider than the header

## What is asked

Rafa asked on 2026-08-27 to test and settle how the detail panel's title behaves when the title in use is too big for the space available.

## Current behaviour

The header is a flex row (`.folia-detail-header`, `src/styles.css`) with the title as a `flex: 1 1 auto` `<h2>` (`.folia-detail-title`) beside the action buttons. There is no rule for overflow: no `overflow`, `text-overflow`, `word-break`, or line clamp. A long title wraps onto as many lines as it needs, so the sticky header grows and pushes the body down; a single unbroken token (a long slug-style file name, a URL used as a title) does not wrap at all and can push the action buttons out of view or widen the panel. The behaviour has not been checked in the three panel modes (modal, side, and the narrow side panel after resizing) nor with the header being `position: sticky`.

## How to reproduce

Give a card a `title:` override of a few hundred characters, and separately one made of a single long word without spaces (or name the file that way). Open it in each panel mode, and resize the side panel to its minimum width. Observe the header height, whether the close/done/open/delete buttons stay reachable, and whether the sticky header hides a meaningful part of the body while scrolling.

## Expected outcome

A defined, tested behaviour for both the wrapping and the unbreakable case in every panel mode: the actions stay reachable, the panel does not grow wider than its mode allows, and the full title remains recoverable (a tooltip, a wrap, or a clamp that expands). Add a test that pins whichever behaviour is chosen so it does not regress. If 20260827.01 moves the title out of the header and into a field, this entry applies to that field's rendering and to whatever remains in the header.

## Status (2026-08-28)

Implemented and merged on `main`. `92f61b6` (*fix(detail): give the panel an answer for a title wider than it is*) settled both cases: the header `<h2>` (`.folia-detail-title`) clamps to two lines with `overflow-wrap: anywhere` and carries the full title as its `title` tooltip, the action buttons are pinned `flex: 0 0 auto` so they keep their width whatever the title does, and the complete title lives in the **Resulting display title** row below, clamped to three lines with a click-to-expand button. `b756a18` is what put that row there in the first place.

Automated coverage lives in `test/ui.test.tsx` (the long-title and unbreakable-token cases) and `test/visual-regression.test.tsx` with its snapshot in `test/__snapshots__/visual-regression.test.tsx.snap`.

**Live verification in Obsidian has not been done.** Line clamping, sticky-header behaviour and the side panel's real minimum width are exactly the things jsdom cannot answer.

## Status (2026-08-29)

Live verification in the real Obsidian ran the "To finish" checklist and found step 4's third **Pass** bullet failing: the **Resulting display title** row rendered as one clipped line in every panel mode (modal 640px, side 380px, side at its 280px minimum), for both the ordinary-words title and the unbreakable token, and clicking to expand did not help.

The cause was Obsidian's own `app.css`, which dresses every `button` with two declarations the clamp cannot survive, neither of them visible from jsdom because no Obsidian stylesheet is loaded there. `white-space: nowrap` means the text never wraps at all, and `height: var(--input-height)` pins the box to one text input's worth of height (30 device-independent pixels in this vault), so with the plugin's own `overflow: hidden` on the same button everything past the first line was clipped away. Read out of the running app: `button { ...; height: var(--input-height); ...; white-space: nowrap; }`.

A third observation is worth writing down because it is easy to misread. The element's computed `display` is `flow-root` rather than the `-webkit-box` the stylesheet asks for. That is **not** what broke the row: measured in the Chromium a current Obsidian ships (142), a clamp written straight on the button still clips to three lines, and a plain `<div>` computes `flow-root` for `-webkit-box` too. The fix still keeps the clamp off the button, because whether a button's inner display carries a clamp is exactly the thing that does not hold on the older Chromium behind this plugin's `minAppVersion` of 1.7.2, and nothing here needs to depend on it.

Fixed by `63693ef`. The row stays a button, because it is a control. The title text moved into a plain `<span class="folia-title-value-text">`, which is where the clamp is now written, so it needs no assumption about how a browser treats a button's inner display (on the engine a current Obsidian ships both placements clamp; this is a precaution for the older ones, which cannot be measured from here); the button itself declares `white-space: normal` and `height: auto` to undo what the theme did. Nothing else about the row changed — an earlier attempt also moved its type and colour onto the span, which made those declarations apply for the first time and left grey glyphs under a link-coloured underline, so that was taken back out.

Verified in the running Obsidian against the built plugin, after the watch build picked the change up and the plugin was reloaded: the row's own span computes the clamp, and the button computes `white-space: normal` with a content-sized height. Collapsed, a ~420-character title clamps to three lines (client height 51, scroll height 84) and clears the reason paragraph below it by 2px; the 200-character unbreakable token wraps into the same three lines; expanded, the row grows to the full 84 and the button grows with it; the text and its underline stay the same colour and weight they were before. **The full checklist below has not been re-run end to end in the app**, so leave this entry until it has.

Three declarations in the same block ask for something the cascade never gives them, and were deliberately left alone because fixing them means repeating a class name a third time, which deserves its own decision: this row's own `font-size`, `font-weight` and `color` (out-ranked by `.folia-link.folia-link` later in `src/styles.css`), `.folia-title-reason` asking for 11px and rendering 12px, and `.folia-title-why` asking for 11px and rendering 13px. `scripts/check-button-styles.mjs` cannot see any of them. Recorded as [20260829.01](./20260829.01.doubled-class-rules-silently-out-rank-their-own-neighbours.md). The undo this fix applies to the one row is also missing from every other `.folia-link` button, where a long inline subcard link already overflows the panel body; that is [20260829.02](./20260829.02.every-other-folia-link-still-wears-the-theme-button-shape.md).
