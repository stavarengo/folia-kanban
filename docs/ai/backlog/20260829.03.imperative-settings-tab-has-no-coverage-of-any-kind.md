# The settings tab Obsidian below 1.13 draws has no coverage of any kind

## What is wrong

The settings tab has two renderings. Obsidian 1.13 and later builds it from `getSettingDefinitions()`; anything below that calls `display()`, which runs `render()` and, under it, `renderRow()`, `writeRow()` and `renderTokenRows()` in `src/main.ts`. On 2026-08-29 the tab was reworked into headed sections (`4c3c067`, finished by `737db70`), and that rework rewrote the imperative half wholesale: the longhand row-by-row code was replaced by a loop over `SETTING_GROUPS` with a control dispatch.

Nothing checked the result. `src/main.ts` cannot be imported by the test suite — it pulls in the Obsidian runtime, which only exists inside the app, which is why `test/settingsDefinitions.test.ts` reads it as text rather than calling it. And the live run that closed the work happened on Obsidian 1.13.7, which takes the declarative path, so the imperative one was never drawn. Every claim about it — that both tabs offer the same sections in the same order, that a dependent row greys the same way, that the version row sits under its own heading, that the held port and bind-address fields still commit on blur and snap back when refused — rests on reading the code.

`manifest.json` declares `minAppVersion: 1.7.2`, so this is not dead code: it is what every user below 1.13 sees.

## How to observe

Install the plugin in an Obsidian older than 1.13 (any version from 1.7.2 up), open Settings → Folia Kanban, and read the tab top to bottom. Then exercise the parts that only exist there: change "Show details in" and watch the rows under it, switch agent access on and off, and type into the port and bind-address fields, leaving each one to see what it keeps and what it puts back.

## Expected outcome

Either the path is confirmed to work on an Obsidian that actually takes it, with the same behaviour the 1.13 tab shows, or the project decides that supporting it is no longer worth it and raises `minAppVersion` so the code can go. Both are answers; what is not an answer is leaving a rendering path shipped, reachable and unexamined.

## Why it matters

A settings tab is where a user changes how the plugin behaves, and a broken one is not obvious from the outside: rows in the wrong section, a heading standing over nothing, a field that quietly fails to save. The two paths are meant to be one tab drawn by whichever API is present, and right now only one of them has ever been seen.
