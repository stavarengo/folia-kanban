# A board's own priority scale renders as undifferentiated grey badges

## Problem

A board can now use any priority vocabulary it likes: the priority field and the right-click chips suggest the values the board itself uses, remembered in the board note's `priorities` property. The colour of a priority badge did not follow.

Badge colour comes from a fixed lookup of value → severity tone in `src/ui/cardView.ts` (`PRIORITY_TONE`), which knows the letter scale `a`–`d`, the word scale `urgent`/`high`/`medium`/`low`, and `p0`–`p4`. Anything outside that map gets the `muted` tone.

So a board whose scale is, say, `blocker` / `normal` / `whenever` gets three identical grey badges. The scale is learned, offered and sorted correctly, but reads as unranked at a glance — which is most of what a priority badge is for.

## How to observe

Open `examples/feature-showcase/`. The `someday` card already shows this: it sits beside `A`–`D` cards with a grey badge while the others are colour-ramped. Set two more cards to invented values (`blocker`, `whenever`) and all three become indistinguishable.

## Expected behavior

A board's own scale should read as a ranked scale visually, the way `A`/`B`/`C` does, without the user having to adopt a vocabulary the plugin already knows. The board note's `priorities` order already expresses the ranking the user intends, so the information needed is present.

Colour is only one way to carry that; whoever picks this up should decide how far to take it, including whether a per-value colour override belongs in the board note and how it interacts with the existing four-tone ramp and its design tokens.
