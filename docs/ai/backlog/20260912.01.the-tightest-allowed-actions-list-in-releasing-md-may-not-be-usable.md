# The tightest allowed-actions list in releasing.md may not be usable

## What happens

`docs/releasing.md`, in the threat-model section, offers a "tighter" shape for the repository's Actions allow-list: untick both sub-options (GitHub-owned actions, verified creators) and name only the pinned actions the workflows run, one line per `uses:`. It presents that list as "exactly what these workflows run today and nothing else could start".

The OSV pull-request scan is a reusable workflow, and the list names it by its own pin. That workflow calls further actions of its own at commit `6e4298eb` (v2.5.1): `google/osv-scanner-action/osv-scanner-action` and `osv-reporter-action`, both at a different SHA (`baa4139e`), `github/codeql-action/upload-sarif@5595ccaf`, `actions/checkout` and `actions/upload-artifact`. Nobody has established whether GitHub enforces the allow-list against actions nested inside a called reusable workflow, and if it does, none of the nested ones is on the list, so the documented tight setting would break the scan that is now the only blocking dependency check.

## How to observe

`gh api "repos/google/osv-scanner-action/contents/.github/workflows/osv-scanner-reusable-pr.yml?ref=6e4298ebc4db23e847df9b2e2de2939d6f066c67" --jq .content | base64 -d | grep uses:` lists the nested actions; compare with the fenced list under "Actions permissions" in `docs/releasing.md`. The repository currently runs the broader setting (both sub-options ticked plus four wildcard patterns), so nothing is broken today.

Since 2026-09-12 the document itself carries the caveat, in the paragraph under the fenced tight list, and points back at this entry. That is a warning, not an answer: the question below is still open.

## Expected outcome

The document either lists a tight setting that has been shown to let the pull-request OSV scan run, or stops offering one. Surfaced by the reviewer of the 2026-09-12 dependency-scanning change and left as found, since that change only grazed the paragraph.
