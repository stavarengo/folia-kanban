# A second install of the same vault silently ends up with a different agent token, and nothing says so

## What is asked

The MCP bearer token moved out of `data.json` into `App.secretStorage` on 2026-09-10 (the entry that asked for it, 20260829.32, is closed; the change is commits `4361bcd`…`4e9f16c`). Moving it was right, and the decision was explicit that there is no `data.json` fallback. What the move left behind is a class of failure that only shows up as "my agent stopped working", with nothing anywhere saying why.

## Current behaviour

The token is now per install rather than per vault. Two consequences, both reachable by an ordinary user and neither surfaced:

**A second install mints its own token, quietly.** Open the same vault on a second computer with agent access already on. Secret storage there is empty, so the load mints a fresh token. That is the intended design — the server that machine would host is its own — and `docs/mcp.md` says so. But whether that second install *inherits* the old token or mints a new one comes down to timing: it inherits only if it reads a `data.json` that still carries the pre-move key, and Sync may well have already delivered the healed file. Either way no notice fires and the settings tab shows nothing, so an agent configured against that machine starts returning `401` with no visible cause.

**During a mixed-version upgrade, the older install re-mints on every cycle.** While one computer is on this version and another is still on a build that kept the token in `data.json`, the old one writes its token back into the file and the new one takes it out again. Each time the old one re-reads a file with agent access on and no token, it mints a *new* token and restarts its server — so its own configured client is not merely stale but locked out afresh every cycle, and both machines keep writing to the vault. `docs/mcp.md` warns about this in prose ("What it does not protect you from"), which is the whole of the telling.

## How to observe

For the first: open a vault with agent access on, on a second machine, and call any MCP tool with the token the first machine gave you. For the second: run two installs on different builds against one synced vault and watch `data.json` gain and lose `mcpToken` while the older install's token changes each time. Nothing in either case needs the token's value to be reproduced anywhere to be understood.

## Expected outcome

A user whose agent stops working can tell why from inside Obsidian. What that costs, and whether it is a notice, something the settings tab shows about this install's token, or something else entirely, is for whoever takes this on. The mixed-version half may also simply be judged an upgrade window worth living with — but that judgement should be made rather than inherited.
