# Folia resolves and writes wikilinks by its own rules, so it can write a link it cannot read back

## What is asked

Four findings of the audit of 2026-08-29 ([section 04](../reports/20260829.what-obsidian-already-provides/04.vault-files-and-metadata.md)) are one subject: 04-01, 04-02, 04-03 and 04-19, with 03-04 in [section 03](../reports/20260829.what-obsidian-already-provides/03.editor-rendering-search-and-dates.md) pointing at the first. Obsidian's `MetadataCache` already answers "which note does this link name", and `FileManager` already answers "how should a link to this note be written".

## Current behaviour

`src/model/board.ts:164` (`linkResolver`) builds a basename index over the board's cards and resolves `[[A]]`, `[[A#Notes]]`, `[[A|see this]]` and `[[Sub/A]]` against it. It has no `sourcePath`, so it cannot apply Obsidian's shortest-path or relative rules; it never consults `aliases`; and it refuses to bind a basename two cards share, which means a relationship silently disappears the moment a second note takes the same name.

The write side has the same shape from the other direction. `src/model/card.ts:459` (`addSubcard`) writes `- [ ] [[${link}]]` with the link text derived as a bare basename by the adapter at `src/obsidian/vaultRepo.ts:567`, and `src/model/relationships.ts:125` writes `[[${relationTarget(target)}]]` into relationship frontmatter. So Folia can write a link that Folia itself cannot resolve as soon as two notes share a name — and the format ignores whatever link style the user has configured.

Two smaller members of the same family: relationship links are re-extracted from raw frontmatter by regex (`src/model/relationships.ts:156`, `:164`) although the cache already holds them parsed, and the MCP tools resolve a card reference with a third hand-written matcher (`src/mcp/tool.ts:94`) whose basename and `.md` branches duplicate `linkResolver`.

The architecture is the reason none of this is a one-line change: `src/model/**` and `src/mcp/**` cannot import `obsidian`, so the resolution has to happen in the adapter and arrive as data. The findings note two things a swap must not lose: the forgiving unbracketed reading of relationship values is a stated product decision, and the MCP matcher's title match has no Obsidian equivalent.

## How to observe

Create two cards with the same basename in different folders, link one as a subcard of a third, and watch the relationship vanish. Separately, give a card an alias and link it by that alias: Obsidian resolves it in the editor, the board does not.

## Expected outcome

One answer to "which note does this link name", shared by the board, the relationships and the MCP tools, and links written in a form the user's own vault settings would produce.
