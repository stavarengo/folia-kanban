# The board takes over markdown opens by patching a core Obsidian prototype, and the reasoning lives only in a code comment

## What is asked

Findings 05-01 and 05-04 ([section 05](../reports/20260829.what-obsidian-already-provides/05.workspace-views-commands-and-settings.md)) and 07-06 ([section 07](../reports/20260829.what-obsidian-already-provides/07.guidelines-mcp-build-and-the-rest.md)) of the audit of 2026-08-29. The report calls the patch the single highest-risk thing it found and the clearest missing entry in `docs/decisions.md`.

## Current behaviour

`patchLeafSetViewState` (`src/main.ts:201`) replaces `WorkspaceLeaf.prototype.setViewState` for the whole application, for the plugin's lifetime, with a wrapper that rewrites a markdown open into a board open whenever `shouldOpenAsBoard` says so. It is a global mutation of a core prototype: every plugin's leaf, not only Folia's, goes through Folia's wrapper while the plugin is loaded, and it can break silently on any Obsidian release. The teardown is careful, and the report is equally clear that every documented alternative is either wrong (taking over the whole markdown extension) or visibly worse (swapping the view after it opens, which flashes the editor first).

Alongside it, `NavigableViewState` (`src/main.ts:73`) widens the public `ViewState` with a `popstate?: boolean` field Obsidian does not declare, set by `showBoardIn` (`:311`) and `showMarkdownIn` (`:321`) so a swap stays out of the navigation history and Back still means "the previous note". There is no public way to say that, and the lint rule that would flag unsupported API cannot see it, because it reports on member expressions rather than on object literal keys. Losing it degrades gracefully; not knowing it exists does not.

Nothing sees any of this. `pnpm obsidian-scan:check` reproduces the community-directory lint and `eslint-plugin-obsidianmd`'s recommended set runs over `src/`, and neither has a rule about prototype patching. The justification for both exists only as a comment in the code, so a reviewer, a future maintainer or an Obsidian release meets them with no written position.

## How to observe

Read `src/main.ts:201-236` and `src/main.ts:73` with `docs/decisions.md` open beside them, and note that the file has no entry for either.

## Expected outcome

The position on both is written where a reader looks for positions rather than in a comment: what the patch does, which alternatives were rejected and why, what would make it untenable, and the same for the undeclared `popstate` field, including what breaks if a future Obsidian removes it. Whether the patch itself stays is a separate question this entry does not prejudge.
