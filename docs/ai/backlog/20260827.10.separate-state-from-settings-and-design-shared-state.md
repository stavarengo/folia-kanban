# Separate state from settings, and design how shared state travels between people and devices

> **Hard stop.** This entry is done with Rafa, in conversation. It is not a task to implement, and an agent given autonomy over the backlog must not pick it up alone: it should stop here and report that this item requires a brainstorming session with the user. The output of the work is that conversation and the architectural design it produces; implementation, if any, becomes new entries afterwards.

## What is asked

Rafa raised this on 2026-08-27: the plugin keeps state in the same file as its settings, and different pieces of that state belong to different scopes. He wants the two separated, and a generic design for the state that should be shared, worked out together rather than delivered.

## Current behaviour

`KanbanSettings` (`src/settings.ts`) is one flat object saved as `data.json`, and it mixes three kinds of things:

- Preferences the user chooses in the settings tab (`detailPresentation`, `historyScope`, `boardPan`, the toggles, …).
- State that is really about one person on one device: `collapsedCards` (per-card collapse override, keyed by path) and arguably `detailWidth` (the side panel width, dragged rather than configured).
- State about a person's relation to a card, independent of the device: `commentsSeen` (per card, the timestamp of the newest comment already read) and `commentsBaseline` (the install-time marker everything older is judged against).

All of it is written by the same `saveSettings` call, so a synced vault (Obsidian Sync with plugin settings on, or a git-synced `.obsidian`) shares one person's collapse state and read markers with every other person and machine, while a non-synced vault loses the read markers the moment the same person opens the vault elsewhere. `src/model/unread.ts` states the opposite assumption in its header ("has Rafa seen this is personal to one install"), so the code and Rafa's intent already disagree on which scope `commentsSeen` belongs to. The path-keyed maps also need hand-written care on every rename and delete (`App.tsx` around lines 366–437, and `migratePathKeyedSettings` in `settings.ts`), which is a cost of keying state by path in a file that is not the note.

## What the conversation needs to settle

- Which existing keys are settings and which are state, and for each state key, its scope: this device, this person on every device, or everyone who shares the vault. `collapsedCards` reads as device-scoped; `commentsSeen` reads as person-scoped across devices, which requires knowing who the person is (see 20260827.04); `commentsBaseline` is ambiguous.
- Where device-scoped state lives. Rafa's starting position is a separate file next to `data.json` (`state.json` or similar, name not important) so that several such things share one home; how it stays out of vault sync is part of the question.
- Where person-scoped, cross-device state lives. Rafa's instinct is that read markers belong with the note itself rather than in plugin data, which raises how per-person information is written into a shared note without polluting it, how it survives edits by other tools, and how it is keyed to a person.
- A generic shape for "state of this kind", so the next thing that needs to travel between devices or people reuses the same mechanism rather than inventing another map. Assignment, which 20260827.03 asked for, shipped on 2026-08-29 as a plain `assignee` key on the card note — the one shared-state mechanism that already existed — so it is no longer waiting on this conversation; it is an example of the shape, not a candidate for it. Who "me" is when that key is compared against a person is still the **Your name** setting, and still this entry's question.
- What happens to the state already frozen in existing `data.json` files.

## Why it matters

Each new feature that remembers something per card is currently forced into the settings file, which is the one place with the wrong scope for all of them. Deciding the scopes and their homes once turns every later feature of this kind into a routine addition instead of a fresh architectural question.
