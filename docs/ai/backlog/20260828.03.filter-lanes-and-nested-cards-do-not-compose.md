# Filter lanes and nested cards do not compose

## What happens

A column can carry its own `filter:` rule, which turns it into an auto-populated lane: instead of showing the cards whose `status` names it, it pulls every TOP-LEVEL card on the board matching the rule, from wherever they live (`src/ui/Column.tsx`, `topLevelPaths`/`lanePaths`). Nested subcards were never part of that population, and two visible oddities follow from it.

**A matching subcard whose inherited column is a lane is still surfaced nowhere.** When a search or quick filter matches a nested subcard whose immediate parent does not match, the board lifts it to the top level of the column it would otherwise inherit — unless that column is a lane, where the lift is deliberately refused (the lane's rule was never run against the subcard, so lifting it in would show a card the lane itself never vetted). This is the last surviving case of `docs/ai/backlog/20260826.10` (fixed 2026-08-28 for plain columns): the card matches, the board shows it nowhere, and the toolbar correctly declines to count it.

**A top-level card can sit in a lane's bucket and be counted while nothing draws it.** `buildBoard` places a card into the bucket named by its own `status`, including a lane's id. The lane column then ignores its own bucket and pulls by rule, so a card whose `status` says `research` but whose properties fail `area:research` is drawn by no column at all — while `filterVisiblePaths` (`src/model/board.ts`) treats every bucket member as rendering somewhere, and the toolbar's "N of M" credits it as a match. Pre-existing, and the same assumption now also decides whether that card's nested children count.

## How to reproduce

1. Give a board a lane column, e.g. `{ id: "research", title: "Research", filter: "area:research" }`, alongside a plain `todo`.
2. Create a card with `status: research` and `area: home` — it fails the lane's own rule. Give it a `## Subtasks` line linking a subcard with no `status` of its own.
3. Search for a word only the subcard has: nothing appears anywhere, though the card matches.
4. Search for a word both have: still nothing on screen, and the toolbar counts both as matches.

## Why it matters

The first case is a promise the README does not make (it names the lane exception), so it is a gap rather than a lie — but it is the shape of question a user hits once they start using lanes for anything nested. The second is a count that disagrees with the screen, the exact failure the shared `filterVisiblePaths` helper exists to prevent; it survives only because the model layer cannot evaluate a lane's rule (the filter grammar lives in `src/ui/cardView.ts`, above the model).

## Likely code areas

- `src/ui/Column.tsx` — `topLevelPaths`/`lanePaths` (what a lane pulls) and the `columnFilter == null` scope on the lift.
- `src/model/board.ts` — `filterVisiblePaths`, whose "a bucket member always renders somewhere" branch is the assumption that breaks.
- Whether the fix is to teach lanes about nested cards, to stop `buildBoard` placing a card into a lane bucket its rule rejects, or to hand the visibility helper a way to ask "does this column draw this card" is the open design question. All three change what a lane means, so this deserves a decision before code.
