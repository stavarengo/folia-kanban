# Consider adopting the official `obsidianmd/obsidian-workflows` action alongside the local scan

## Problem

This repo reproduces the community directory's review scan locally (a worker under `scripts/`, wired into `pnpm verify` as `obsidian-scan:check`) because, at the time that work started, no official equivalent was known. One now exists and is maintained by Obsidian itself: [`obsidianmd/obsidian-workflows`](https://github.com/obsidianmd/obsidian-workflows) (tags `v1` / `v1.1.0` at the time of this research). Its own description: "A GitHub Action that validates, lints, builds, and releases Obsidian plugins and themes. Matches the community directory's validation and scanner expectations so your submissions pass on the first try."

Confirmed from the repo's `README.md` and `action.yml` (both read directly, not summarized):

- In `release` mode (or with `scanner-lint: true`), it runs "the same lint configurations used by the Obsidian community directory scanner": Stylelint with the scanner's ruleset, and ESLint with `eslint-plugin-obsidianmd` (type-aware when `tsconfig.json` is present) — the same two tools our local worker reproduces.
- It also validates `manifest.json`/`versions.json` schema, README/license presence, auto-detects and runs the build, checks release-asset presence, checks manifest consistency between `HEAD` and the tag, generates a build-artifact attestation, and opens a **draft** GitHub release (never auto-publishes).
- Two integration shapes, both official:
  - PR/CI check, any branch:

    ```yaml
    - uses: actions/checkout@v7
    - uses: obsidianmd/obsidian-workflows@v1
    ```

  - Release, on tag push, either as a step or as a single reusable workflow:

    ```yaml
    uses: obsidianmd/obsidian-workflows/.github/workflows/release.yml@v1
    permissions:
      contents: write
      id-token: write
      attestations: write
    ```

    (the step form additionally wants `env: GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`; no other token is required — `GITHUB_TOKEN` is the ambient Actions token, not a new secret to create).
- Relevant inputs: `type` (`auto`/`plugin`/`theme`), `mode` (`pr`/`release`), `build` (override or `false` to skip), `lint` (`true`/`false`), `scanner-lint` (`false` by default in `pr` mode, forced `true` in `release` mode), `node-version` (default `24`, minimum enforced `20`).
- No documented local/npm CLI form — the scanner rulesets are only exposed through this GitHub Action, not as a standalone package a developer can `pnpm dlx` locally. So the local worker in `scripts/` remains the only way to see these findings before pushing a commit; the official action would only cover CI.

## Expected outcome

A decision (not made here) on whether to add `obsidianmd/obsidian-workflows` in this repo, and if so, how it relates to the existing local worker:

- As a PR-mode check (`obsidianmd/obsidian-workflows@v1` with default `mode: pr`) to catch lint/manifest/build regressions on every PR — likely with `scanner-lint: true` so it actually runs the same rulesets as the community scanner, since that's opt-in outside release mode.
- As a genuine replacement for `.github/workflows/release.yml`'s own logic, either fully (`uses: obsidianmd/obsidian-workflows/.github/workflows/release.yml@v1`) or as one step inside the existing release job — trading some control (it creates its own **draft** release and its own attestation) for staying in sync with whatever the community directory scanner checks next, without this repo having to track scanner changes by hand.
- Or: keep the local worker as the pre-push/local-dev signal (since the official action has no local/CLI mode) and layer the official action on top in CI as a second, independently-maintained check — accepting the redundancy as a safety net against local/official drift.

Whoever picks this up should re-diff `src/lint.ts` in `obsidianmd/obsidian-workflows` (or just re-run the action) against the local worker's ruleset before deciding, since both are living code and either could have moved since 2026-08-26.
