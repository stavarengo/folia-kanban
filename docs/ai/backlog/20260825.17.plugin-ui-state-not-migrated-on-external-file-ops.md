# Plugin UI state (selection, subitems-collapse) isn't migrated on external file rename/delete

## What is asked

Nobody asked for this directly — it surfaced while implementing [20260825.03 — collapse/expand subitems in columns](./20260825.03.collapse-expand-subitems-in-columns.md) (now closed) and its unprimed reviewers flagged it as a real gap worth tracking rather than fixing inline.

## Current behaviour

Three pieces of path-keyed UI state exist today: the selected card (`App.tsx`'s `selected` state), `settings.collapsedCards` (persisted plugin data keyed by card path, from the collapse-subitems feature) and `settings.commentsSeen` (the same shape, from the unread-comments feature — the marker of the newest comment already read on each card; a card without one is judged against the install-time `settings.commentsBaseline`).

All three are handled correctly when a rename/delete happens **through the plugin's own UI** — `actions.renameCard` follows the new path for `selected`, `collapsedCards` and `commentsSeen`; `actions.remove` clears them for the deleted path.

None of them is migrated when the underlying file is renamed, moved, or deleted **from outside the board** — Obsidian's file explorer, another plugin, or editing the file directly. `VaultRepository.onChange` (`src/obsidian/vaultRepo.ts`) only schedules a generic board reload on `vault.on("rename"/"delete"/...)`; it never touches `selected`, `collapsedCards` or `commentsSeen`.

Concretely:

- Rename a card's file from the file explorer while it is selected in the board → the detail panel silently closes or points at a path that no longer resolves to that card (selection was never re-pointed).
- Rename a card's file from the file explorer after collapsing its subitems → the card reopens at the board-wide default state; the override is stranded under the old path in `data.json`.
- Delete a card's file from the file explorer after collapsing its subitems, then later create an unrelated card at the exact same path → the new card silently inherits the old card's collapsed/expanded state.
- Rename a card's file from the file explorer after reading its comments → everything commented on it since the install baseline counts as unread again, because the read marker is stranded under the old path. Delete it and reuse the path, and the reverse happens: a genuinely new card's comments arrive already marked as read.

## Expected outcome

Some documented, deliberate answer for what happens to path-keyed plugin UI state when a file operation bypasses the plugin's own actions — either migrate it (hook `vault.on("rename")`/`on("delete")` the same way `onChange` already does, and reconcile `selected` + `collapsedCards` + `commentsSeen`), or explicitly accept the staleness as a known limitation with a stated reason, rather than leaving it as an unexamined gap that grows with every future piece of path-keyed state.
