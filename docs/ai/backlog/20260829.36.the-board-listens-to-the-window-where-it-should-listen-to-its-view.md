# The board listens to the window where the host view already offers the signal

## What is asked

Findings 06-05, 06-06 and 06-11 of the audit of 2026-08-29 ([section 06](../reports/20260829.what-obsidian-already-provides/06.interaction-and-input.md)). Three board-level integrations reach for the window or the document where Obsidian gives the view itself the same information.

## Current behaviour

- `src/ui/App.tsx:230` queries `.status-bar` in the DOM, measures it, and writes the result into a `--folia-statusbar-clearance` custom property that `src/styles.css:447` and `:1376` consume, to keep board and detail content clear of the fixed status bar. Obsidian publishes a scroll-clearance variable for that (06-05).
- `src/ui/App.tsx:798` installs a `keydown` listener on the owning document and decides for itself whether `/` should focus the search box. The view has a keymap scope with a lifecycle and a focus boundary already, and a document listener means a board in a background leaf inspects keys typed at another one (06-06).
- `src/ui/CardDetail.tsx:1122` derives the description preview's maximum height from a `window.resize` listener, so resizing a split — which does not resize the window — leaves the preview measured for the old width (06-11). The finding notes the view's own `onResize` lifecycle as the signal, rather than a workspace-wide event.

All three sit in `src/ui/**`, which cannot import `obsidian`, so each needs the value or the signal to arrive from the view or the adapter.

## How to observe

Drag the divider of a split holding a board and watch the description preview keep its old height. Focus another leaf and press `/`, and note which board's search decides to react. Toggle Obsidian's status bar and watch what the board measures.

## Expected outcome

Board chrome follows the leaf it lives in rather than the window it happens to be in, and the one board-level shortcut goes through the host's own keymap.
