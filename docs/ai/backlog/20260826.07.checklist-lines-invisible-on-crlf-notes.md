# Checklist lines are invisible on a note saved with CRLF line endings

## What happens

`CHECKBOX_RE` in `src/model/card.ts` ends in `(.*)$` with no `m` flag. The card engine splits a note on `\n`, so on a CRLF file every line keeps a trailing `\r`, and `.` does not match `\r`. The regex therefore matches no checklist line at all on such a note.

Everything built on that regex goes quiet together: `parseSubtasks` returns nothing, so the card shows no subtasks, no subcards (its `[[Child]]` lines are never read, so the child renders as a top-level card), a progress bar of `0/0`, and no next todos. Every write keyed on a checklist line (`setSubtaskDone`, `setSubtaskStatus`, `setSubcardDone`, `removeSubtask`) finds no line and returns the note byte-identical, with no error.

`setSubtaskStatus` carries CR-preserving code (`const cr = line.endsWith("\r") ? "\r" : ""`) that can never run, which suggests the regex was believed to match.

## How to reproduce

Take any showcase card, convert it to CRLF (`unix2dos`), reload the board. The card's checklist is gone from the tile and the detail panel; its subcards appear as top-level cards.

Unit level: `CHECKBOX_RE.test("- [ ] foo\r")` is `false`.

## Why it matters

Windows editors and some sync tools write CRLF. A person on such a setup sees a plugin that silently drops a whole section of their notes and refuses every edit to it without saying so.

## Likely code areas

- `src/model/card.ts` — `CHECKBOX_RE`, and the same pattern is worth checking in `TS_LINE_RE` / `TS_LINE_LEGACY_RE` (`[\s\S]*` there may already tolerate it)
- `test/card.test.ts` — the "CRLF files round-trip byte-stably" block covers comments only
