# Subtask and comment edits apply a line index taken from an earlier read, with no check inside the write

## What happens

Finding 04-12 of the audit of 2026-08-29 ([section 04](../reports/20260829.what-obsidian-already-provides/04.vault-files-and-metadata.md)), listed third among the whole report's top findings.

`toggleSubtask` (`src/obsidian/vaultRepo.ts:447`), `removeSubtask` (`:458`), `updateComment` (`:435`), `removeComment` (`:439`) and `applyMove`'s subtask branch (`:373`) each take an `index` produced by an earlier board or body read and apply it inside `editBody` → `vault.process` (`:358`). `vault.process` exists precisely so a read-modify-write sees the current content, and the callback here does not re-check that the line at that index is still the line the caller meant. If the note changed between the read and the write — by hand, by sync, by another tool, or by a second call in flight — the edit lands on whatever line now holds that position.

The riskiest caller is not a person: the MCP tool `set_subtask_done` can be driven in a loop by an agent, which is exactly the pattern that produces several writes against one stale read. The correct pattern is already written a few dozen lines above in the same file, where `setSubcardDone` matches by the item's own link text rather than by position.

## How to reproduce

Open a card with several subtasks, and while the detail panel is open, add or delete a line above them in the note itself (in another pane or another app). Then tick a subtask from the board and read the note: the tick lands on the wrong item. The same shape is reachable through repeated `set_subtask_done` calls against one board read.

## Expected outcome

A write that cannot apply to the wrong line: the item is identified by something that survives an edit elsewhere in the file, or the write refuses when the line no longer looks like what the caller described. The related entry 20260828.02 is the same hazard one layer up, in the view's own reads.
