# An agent can read a list-valued card property but cannot write one back

## What is asked

While assignment was being built on 2026-08-29 (the entry that became `assignee`, since deleted), an unprimed reviewer noticed that the MCP tool surface can report a frontmatter value it has no way to send back.

## Current behaviour

`propertyValue` in `src/mcp/cardTools.ts` is `z.union([z.string(), z.number(), z.boolean(), z.null()])`, so every value an agent writes through `update_card`'s `properties` map is a scalar. The read side has no such limit: `get_card` returns the whole frontmatter, and `get_board`'s per-card summary reports `assignee` raw, both of which hand back a YAML list when the note holds one.

`assignee` is where this now bites, because a card really can name several people — written by hand, by another tool, or by the board's own **Assign to me** button, which adds a name to a card that already has one. An agent handed `["alex", "ana maria"]` has no faithful write available: it can assign one person and drop the other, or write `"alex, ana maria"`, which the board reads as one person whose name contains a comma and which then stops matching `assignee:alex`. The same gap applies to any list-shaped key a vault uses, `tags` being the obvious other one.

`docs/mcp.md` now states the asymmetry plainly, so nothing is misleading — but the gap is real and it is stated, not solved.

## How to observe

Assign a card to two people (the showcase vault ships one: `examples/feature-showcase/Cards/Review PR - accessibility.md`). Call `get_board` and see the list come back. Then try to write it back with `update_card`'s `properties`, and the call is refused by the published schema before it reaches the board.

## Why it matters

The tools are meant to be as capable as a person at the board, and here they are not: a person can put two names on a card and an agent cannot, nor can it leave one alone while changing something else about the card. It also means an agent that reads a card, edits it and writes it back — a natural shape for automation — quietly narrows any list it touches.

## Expected outcome

An agent can write the shapes it can read, or is told at the point of the call which shapes it cannot and why. Whatever the answer, it is a deliberate change to a frozen tool contract: the input schema in `test/__snapshots__/mcpContract.test.ts.snap` moves, and the session that makes it says so. Worth deciding at the same time whether the keys the board refuses through `properties` should change with it.
