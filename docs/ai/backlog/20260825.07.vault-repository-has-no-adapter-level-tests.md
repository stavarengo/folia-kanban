# `VaultRepository` has no tests, so every Obsidian-facing behaviour is unverified

## What happens

`src/obsidian/vaultRepo.ts` is the only place the plugin touches a real vault, and nothing in `test/` ever constructs it. `test/fakeRepo.ts` implements the `CardRepository` interface from scratch instead, so the UI tests exercise a parallel implementation and never the real one. `grep -rn "VaultRepository" src test` returns exactly two hits, both in `src/`.

Everything that lives only in that file is therefore untested: which `card-folder` reading wins against a live vault, the `TFolder`-versus-`TFile` distinction, the "card folder was not found" and "matches both …" notices, `createCard` re-reading the config before writing, `uniquePath`'s collision loop, and the `cachedRead`-instead-of-`metadataCache` freshness rule. A regression in any of it leaves the whole suite green.

Two independent reviewers of the `card-folder` resolution work (landed as `20260821.08`, now deleted) raised this same gap unprompted, each pointing at the pure/adapter split: the resolution logic itself is now a pure function in `src/model/board.ts` with unit tests, and the wiring around it is the part nobody can see fail.

## What already exists

The plugin's `obsidian` dependency ships only a `.d.ts`, no runtime, so there is nothing to import in a test — a mock or a fake `App`/`Vault` has to be built. The repo has no `vi.mock` anywhere and `test/setup.ts` sets up only jsdom and `@testing-library/jest-dom`, so this is new test infrastructure, not a new test file against existing scaffolding.

`test/fakeRepo.ts` is a useful reference for the behaviour a vault fake would have to reproduce, but it fakes the repository, not the vault, so it cannot be reused directly.

## Expected outcome

The behaviours that only exist in `VaultRepository` should be verifiable without opening Obsidian by hand, so a change to path resolution, card creation, or the freshness rules fails a test instead of failing in someone's vault.
