# An external rename remounts the open detail panel and throws away what was typed in it

## What is asked

Nobody asked; an unprimed reviewer found it while reviewing the change that makes the selection follow a card file renamed from outside the board (session `W8`, 2026-08-26).

## Current behaviour

With a card's detail panel open and something half-typed in it — a comment, a description edit, a new todo, a subcard title, a property key/value, or a delete confirmation waiting — rename or move that card's file from the file explorer, from another plugin, or by a sync pull. Everything typed is gone when the panel comes back.

Two events arrive, and they cannot arrive together. `VaultRepository.onFileOp` (`src/obsidian/vaultRepo.ts`) calls back synchronously from the vault event, so the selection moves to the new path immediately; `VaultRepository.onChange` debounces the board reload by 150ms, so for that window `board.cards` still only knows the old path. `App.tsx` computes `detailOpen` as "a card exists at the selected path", which is false in between, so `<CardDetail>` unmounts and then remounts fresh once the reload lands. `CardDetail` keeps roughly fifteen pieces of uncommitted local state (`descDraft`, `editingDesc`, `newComment`, `newTodo`, `newSubcard`, `newBlocks`, `newPropKey`/`newPropVal`, `confirmDelete`, …), and unmounting discards all of them.

This is not new — before the selection followed the rename, the panel simply closed and stayed closed, so the drafts were lost then too. What is new is that the panel now visibly comes back, which makes the loss look like a bug rather than like the panel having been closed.

The same window exists for an in-app rename, which goes through the same two paths.

## Expected outcome

Editing a card while its file is renamed underneath does not lose what was typed. Whatever keeps the panel's identity across the gap between "the file moved" and "the board has reloaded" would do it; there is no requirement that the panel keep rendering during that window, only that the drafts survive it.

## Status (2026-08-28)

Implemented and merged on `main`. `aac41cf` (*fix(detail): keep the open panel across a rename of its own note*) keeps the panel mounted across the window between the rename event and the debounced board reload; `dca8ae4` (*fix(detail): stop the panel from losing drafts and renaming a file twice*) closed the remaining draft loss and the double-rename it exposed once the file name became an editable field.

Automated coverage lives in `test/ui.test.tsx` (rename-while-open cases), with the rename plumbing exercised through `test/fakeRepo.ts` and `test/vaultRepo.test.ts`.

**Live verification in Obsidian has not been done.** The change was merged from a session with no reachable Obsidian instance, so the real vault-event timing — which is the whole subject of this entry — has never been observed.
