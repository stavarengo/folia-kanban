# Audit everything Folia built in-house that Obsidian already provides

## What is asked

Rafa asked on 2026-08-29 for a research pass, not a code change: go through the whole of Folia and list every place where the plugin does something its own way that Obsidian already offers to plugin developers, so that each one can later be judged on its own.

The deliverable is a report of findings. Nothing in this entry asks for code to be fixed or replaced; deciding what to adopt, and how, is a separate step for a later session.

## Current behaviour

Folia is a React-based plugin, and its source (`src/ui`, `src/obsidian`, `src/model`, `src/mcp`, `src/main.ts`, `src/view.tsx`, `src/settings*.ts`, and a 2,000-plus-line `src/styles.css`) mixes three kinds of code without a visible line between them: code that goes through Obsidian's API, code that reimplements something Obsidian has, and code that Obsidian could never provide. Nobody has ever inventoried which is which. The inventory drifts every time a feature ships, because each new control copies whichever neighbour it sits beside (20260829.06 records one such split already: three browser `<datalist>` inputs beside one `AbstractInputSuggest` popup).

The plugin declares `minAppVersion` 1.7.2 and depends on `obsidian ^1.7.2`, while the installed typings at the time of writing are `obsidian@1.13.1`. Anything the API gained between those versions is invisible to the code as written and to a reader who only checks what the manifest promises.

## Scope of the research

"Anything Obsidian provides" is meant literally, at every size, across every layer. The pass must cover at least the following areas, and should not stop at them:

- **UI components and primitives.** Modals, menus, context menus, suggesters (`SuggestModal`, `FuzzySuggestModal`, `AbstractInputSuggest`), `Setting`/`SettingTab` builders, notices, toggles, dropdowns, sliders, text areas, buttons, icons (`setIcon`, `addIcon`, the Lucide set), tooltips (`setTooltip`), progress bars, and whatever Folia draws with its own JSX or CSS instead.
- **Styling, theme and design language.** Obsidian's CSS variables (colours, spacing, radii, typography, shadows, `--interactive-*`, `--background-*`, `--text-*`, size and font tokens), its utility and component classes (`mod-cta`, `clickable-icon`, `nav-*`, `setting-item*`, `menu*`, `modal*`, `suggestion-*`, `is-active`, `mod-warning`, and so on), light/dark and theme-override behaviour, mobile and touch variants, and the accessibility affordances that come for free with the native classes. Every hard-coded colour, pixel size, font, or transition in `src/styles.css` and in inline styles is a candidate.
- **Editor and rendering.** `MarkdownRenderer.render`, `MarkdownRenderChild`, the CodeMirror 6 editor extensions Obsidian exposes, `Component` lifecycle for rendered markdown, link resolution and `app.workspace.openLinkText`, hover previews (`hover-link` event / page preview), embeds, and anything Folia's `src/ui/Markdown.tsx` or its own text handling re-does.
- **Vault, files and metadata.** `Vault` and `FileManager` (`processFrontMatter`, `renameFile`, `trashFile`, `getAvailablePathForAttachment`, atomic writes with `vault.process`), `MetadataCache` (frontmatter, tags, links, resolved links, `getFileCache`, `getFirstLinkpathDest`), `app.metadataTypeManager` and the property registry, `normalizePath`, `parseYaml`/`stringifyYaml`, `parseFrontMatterEntry` and friends, `getAllTags`, `iterateCachedFiles`, and the file-event stream (`create`, `modify`, `delete`, `rename`) against whatever Folia's `src/obsidian/vaultRepo.ts`, `src/model/pathOps.ts`, `src/model/fences.ts`, `src/model/schemas.ts`, and `src/boardNote.ts` implement on their own (YAML handling, frontmatter parsing and rewriting, path logic, file watching, title derivation, link text).
- **Workspace, views and navigation.** `ItemView`/`FileView`/`TextFileView` and their state persistence (`getState`/`setState`, `getViewType`, `getDisplayText`, `getIcon`), leaf management, view registration and file-extension association (`registerExtensions`), `workspace.on(...)` events, `revealLeaf`, split and tab handling, the ribbon, status bar items, and the commands palette (`addCommand`, hotkeys, `checkCallback`, editor commands), against Folia's `src/view.tsx`, `src/viewMode.ts`, `src/main.ts`, and any navigation it wires by hand.
- **Settings and state.** `loadData`/`saveData`, `PluginSettingTab`, `Setting` builders and their headings, descriptions, and validation, against `src/settings.ts`, `src/settingsDefinitions.ts`, `src/settingsLayout.ts`, and what 20260827.10 discusses about state versus settings.
- **Interaction and input.** Drag and drop, keyboard handling and `Scope`/`Keymap` for hotkeys and focus traps, `Platform` detection (desktop, mobile, OS), `Menu` positioning, `debounce`, `requestUrl`, `Notice` durations, `Events`/`EventRef` and `registerEvent`/`registerDomEvent`/`registerInterval` for cleanup, against whatever Folia binds and unbinds itself.
- **Search, sorting and fuzzy matching.** `prepareFuzzySearch`, `prepareSimpleSearch`, `fuzzySearch`, `renderMatches`, `renderResults`, `sortSearchResults`, against any ranking or filtering Folia wrote.
- **Dates, times and locale.** Obsidian's bundled `moment`, `getLanguage`, the daily-notes interface and its date formats, against `src/model/dates.ts` and any formatting done by hand.
- **Community-plugin guidelines and conventions.** The official developer policies and the review checklist (no inline styles, no `innerHTML`, sentence-case UI text, no console noise in production, `Platform` over user-agent sniffing, `normalizePath` for paths, `vault.process` for read-modify-write, no hard-coded `.obsidian` paths, unloading everything registered, and the rest). Each convention Folia violates or side-steps is a finding even when no API call is involved.
- **Everything else.** The `MCP` host (`src/mcp`, `src/obsidian/mcpHttpServer.ts`, `src/obsidian/mcpService.ts`) and any Node or Electron access it takes directly where Obsidian offers a sanctioned route; the build (`esbuild.config.mjs`, `manifest.json`, `versions.json`) against the sample-plugin conventions; icons in `src/ui/icons.tsx` against Lucide via `setIcon`; column colours in `src/ui/columnColors.ts` against theme tokens; history and undo in `src/model/history.ts` against whatever Obsidian offers; anything else the researcher notices.

The comparison side is Obsidian as it stands today, not as of `minAppVersion`. Sources to read, not recall: the official developer docs (docs.obsidian.md), the `obsidian` typings actually installed under `node_modules/obsidian/obsidian.d.ts`, the changelogs since 1.7.2 for API additions, the sample plugin, and the plugin-review guidelines. The `rfst-specialist-obsidian` skill is the source of truth for Obsidian questions and should be used rather than pre-trained memory.

## Expected outcome

A written report, in the repository, with one finding per place where Folia does something its own way that Obsidian provides. Each finding names the Folia location (file and line or symbol), the Obsidian facility that covers it (API member, CSS variable, class, convention, or guideline, with the version it appeared in when that is after 1.7.2), what the in-house version does differently, and the researcher's honest read on whether adopting the Obsidian route is a clear win, a trade-off, or not worth it, so the later decision can be made per item without redoing the research. Findings should be grouped by area (the list above is a reasonable skeleton) and ordered within a group by how much the gap costs today, not by how easy the fix looks.

Places where Folia deliberately diverged and wrote the reason down (`docs/decisions.md`) are still listed, marked as decided, so the report is complete rather than pre-filtered.

The report changes no code. A finding that turns out to be worth acting on becomes its own backlog entry; this entry is done when the report exists and its findings have been triaged into those entries or explicitly dismissed.

## Why it matters

Everything Folia reimplements is something it now has to maintain, theme, test, and keep accessible by itself, and every place it bypasses the native route is a place where a theme, a mobile build, an Obsidian update, or the plugin-review process can break it without warning. Nobody knows the size of that surface. A full inventory turns an unknown into a list of individual, sized decisions, and it stops the drift by giving the next feature something to check against.
