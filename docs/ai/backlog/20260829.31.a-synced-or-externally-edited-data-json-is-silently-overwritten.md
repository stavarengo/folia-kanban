# A `data.json` changed by Sync or by hand is silently overwritten with what this instance had in memory

## What happens

Finding 05-10 of the audit of 2026-08-29 ([section 05](../reports/20260829.what-obsidian-already-provides/05.workspace-views-commands-and-settings.md)), listed second among the whole report's top findings.

The plugin holds its settings in memory (`this.stored`, `src/main.ts:101`), reads `data.json` exactly once at load (`loadSettings`, `:537`), and writes the whole in-memory object back on every settings change and on every vault rename or delete that touches a path-keyed map (`saveSettings`). Obsidian calls `Plugin.onExternalSettingsChange` when that file changes underneath a running plugin, which is what Sync does on another device and what a person does editing the file by hand. Folia does not implement it, so the change is never read, and the next write from this instance replaces it with the older picture.

What is lost is not only preferences: `data.json` also holds per-card collapse state, comment read markers and the detail panel width (see the related entry 20260827.10, which asks the larger question of what belongs in that file at all, and which is a hard stop that must be settled with Rafa rather than by an implementing session).

The finding is honest about the limit of the obvious fix: re-reading on the callback turns "silently clobbered" into "picked up", but a change made in two places at once still resolves last-write-wins.

## How to reproduce

With a vault synced between two machines (or simply by editing `.obsidian/plugins/.../data.json` by hand while Obsidian runs), change a Folia setting on one side, then change any setting on the other: the second write carries the first away.

## Expected outcome

An external change to the plugin's own data file is noticed by a running instance rather than overwritten.
