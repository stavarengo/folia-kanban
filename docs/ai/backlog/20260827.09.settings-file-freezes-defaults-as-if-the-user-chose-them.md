# The settings file freezes every default as if the user had chosen it

## What is asked

Rafa asked on 2026-08-27 to investigate whether Obsidian can tell the plugin which settings the user actually changed, so that `data.json` holds only those and a later version can still tell a deliberate choice from an untouched default.

## What the investigation found

Obsidian offers nothing for this. The whole plugin-data API is two methods on `Plugin` (`node_modules/obsidian/obsidian.d.ts`): `loadData(): Promise<any>` and `saveData(data: any)`, a raw JSON blob in the plugin folder's `data.json`, plus `onExternalSettingsChange` to notice edits from outside. There is no per-setting "has a value" flag, no default registry, and the `Setting` controls in the settings tab have no notion of "unset"; a dropdown or toggle always shows some value. Whatever distinction between "chosen" and "default" the plugin wants, it has to keep itself.

## Current behaviour

The plugin follows the documented Obsidian convention, which is precisely what erases the distinction. `hydrateSettings` (`src/settings.ts`) does `Object.assign({}, DEFAULT_SETTINGS, loaded)` and `saveSettings` (`src/main.ts`) writes `this.settings`, the merged whole, back. Since `loadSettings` saves immediately on first run to stamp `commentsBaseline`, every default is written to `data.json` on the very first launch, and from then on a value that reads `historyScope: "moves"` is indistinguishable from a user who picked it. Two consequences follow: changing a default in a later release never reaches an existing install, and any setting that should be "computed once when the user has not set it" (the name inference in 20260827.04, or a future migration that rewrites an untouched value) has no reliable way to know whether it may.

## How to observe

Install the plugin fresh, open no settings, and read `.obsidian/plugins/folia-kanban/data.json`: every key of `DEFAULT_SETTINGS` is present with its default value.

## Expected outcome

`data.json` holds only what the user (or the plugin's own state-keeping, such as `collapsedCards` and `commentsSeen`) actually set, and the in-memory settings still resolve to the full shape with defaults filled in at read time. A future version that changes a default, or that wants to compute a value for an untouched setting, can then tell the two cases apart. Existing installs, whose files already contain frozen defaults, need a stated rule for what happens to them (a value equal to the old default is the ambiguous case), and the settings tab should still show and behave the same. The `onExternalSettingsChange` hook is unrelated to the question but worth knowing about for the same file.
