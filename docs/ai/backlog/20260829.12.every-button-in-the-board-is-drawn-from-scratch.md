# Every button in the board is drawn from scratch, and the specificity fight that follows is now a documented hazard

## What is asked

Findings 01-08 and 02-30 of the audit of 2026-08-29 ([section 01](../reports/20260829.what-obsidian-already-provides/01.ui-components-and-primitives.md) and [section 02](../reports/20260829.what-obsidian-already-provides/02.styling-theme-and-design-language.md)) read the same decision from two sides: the component choice, and the stylesheet that follows from it.

## Current behaviour

Thirteen button classes are listed together at `src/styles.css:128-149`, each named twice so the rule out-specifies Obsidian's own `button:not(.clickable-icon)`, purely to reset the theme's raised button face. `.folia-btn`, `.folia-btn-primary`, `.folia-btn-danger` and `.folia-icon-btn` (`1205-1260`) then rebuild padding, radius, background and colour from `--folia-*` tokens. On the component side, nothing in the plugin goes through `ButtonComponent`; the three shapes that have an exact native equivalent (primary, danger, icon-only) are drawn by hand alongside ten that are Folia's own vocabulary and have no equivalent.

The doubling convention is enforced by `scripts/check-button-styles.mjs`, which also refuses any `<button>` in `src/ui/**` carrying no `folia-*` class — so "drop the class and let the theme dress it" fails the guard as written today. Two live consequences of the same convention were fixed on 2026-09-10 without touching the convention: the doubled base rules for `.folia-link` and `.folia-muted` moved above the rules that refine them, those refinements were doubled to match, and the theme's `white-space: nowrap` and fixed height are now undone once on `.folia-link` for every link the board draws. The guard learned to expand shorthands and to look at every element the plugin dresses rather than only its `<button>`s, so a `font: inherit` can no longer swallow a `font-size` unseen on a `<p>` either. What that did NOT settle is this entry: the resets exist at all only because the plugin draws every button itself, and one shape of the collision — a refinement written above its base — is still caught by habit rather than by a check, because it cannot be told apart from a variant class legitimately overriding a base one. Worth weighing when this is picked up: `@layer` would dissolve the doubling convention entirely, since a plugin layer declared after the theme's wins on layer order and no class would need naming twice. It is already admissible here — `scripts/obsidian-scan.mjs` puts `css-cascade-layers` on the browser-feature ignore list and allows the at-rule — so the question is the refactor's size, not its legality.

The findings are explicit that a wholesale swap is not the answer: a kanban board legitimately wants denser controls than the app's settings buttons, and `mod-cta` cannot express a chip or a 26px icon button. What they identify as recoverable without touching the design is the radius, the interactive background variables and the three shapes that already exist natively.

## How to observe

Read `src/styles.css:128-149` and count how many rules exist only to undo the theme, then compare a Folia primary button against a `mod-cta` button in Obsidian's own settings on the same theme. `pnpm check:button-styles` shows what the guard currently requires.

## Expected outcome

An explicit boundary between the buttons that are Folia's own vocabulary and the ones that are Obsidian's control wearing a different coat, with whatever the guard needs to allow the second group written into it. Closing this is what would remove the resets, and with them the specificity fight, rather than keeping it survivable.
