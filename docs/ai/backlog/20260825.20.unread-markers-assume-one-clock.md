# Unread markers assume every comment writer shares the reader's clock

## What is asked

Nobody asked; an unprimed reviewer of the unread-comments feature raised it (session `impl-unread2`, 2026-08-25).

## Current behaviour

Comment timestamps are written by `stamp()` (`src/model/dates.ts`) in local time with no timezone, and read-state (`commentsSeen` and `commentsBaseline` in plugin data) compares those minute strings as text (`src/model/unread.ts`). Every writer is assumed to share the reader's clock.

A writer in another timezone, or an agent on a UTC server writing straight into the note, produces stamps systematically behind or ahead of the reader's marker:

- Reader in UTC+2 opens a card at 14:00 local (marker `… 14:00#n`); an agent on UTC writes `- _2026-08-25 12:30 @agent:_ …` (which is 14:30 for the reader). It sorts below the marker and never lights the tile or gets a `new` tag.
- The opposite offset makes fresh comments light up and then leaves already-read ones showing as unread after the marker moves past them.

The README's "out of order" caveat covers sync latency, not this systematic offset.

## Expected outcome

Either a documented decision that same-clock writers are the supported case (a README caveat naming the agent-on-a-server scenario), or a design for carrying enough time information in the line to order comments across clocks without breaking the existing `- _YYYY-MM-DD HH:mm @name:_` grammar and every note already written in it.
