# A pale accent colour paints white text on a near-white button

## What happens

Finding 02-01 of the audit of 2026-08-29 ([section 02](../reports/20260829.what-obsidian-already-provides/02.styling-theme-and-design-language.md)) — the report's top-listed styling bug.

`src/styles.css:75` declares `--folia-on-accent` as `var(--text-on-accent, #fff)`, and that token is the only foreground the plugin ever puts on an accent or danger fill: `.folia-btn-primary` (`1189-1193`), `.folia-btn-danger` (`1202-1206`), `.folia-column-count.is-over-limit` (`431-434`) and the toast. Obsidian defines a second variable for exactly this case, `--text-on-accent-inverted`, which themes and the app use when the accent is light enough that white text stops being readable. Folia never reads it, so a user who picks a pale accent colour gets white text on a near-white button, and the plugin has no way to detect that it happened.

Nothing guards it: `scripts/check-a11y-exceptions.mjs` and the raw-value audit both look at source shapes, not computed contrast, and `tracking/waivers/0002-automated-a11y-gate.md` records that there is no automated a11y gate at all.

## How to reproduce

In Obsidian's appearance settings, set the accent colour to a pale value (a light yellow or a pale mint), then open a board and read the primary button, the over-limit column count and any toast.

## Expected outcome

Text on Folia's accent and danger fills stays readable whatever accent the user picks. Worth knowing before starting: the finding notes that Obsidian's docs describe both variables but do not say who is responsible for choosing between them, so part of the work is establishing the mechanism rather than only applying it.
