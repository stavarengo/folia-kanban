# A board read before a change can land after it, and the view believes it

## Current behaviour

`App`'s `load` in `src/ui/App.tsx` calls `repo.loadBoard()` and hands whatever comes back to `setBoard`, with no record of which request it came from. Every vault change fires the repository's change listener, which calls `load` again, so several reads can be in flight at once. `VaultRepository.loadBoard` in `src/obsidian/vaultRepo.ts` reads the board note, then the card folder, then each card's frontmatter, awaiting between each — an earlier read can therefore finish after a later one, and the state it leaves behind is the older picture.

Nothing in the view checks. The last write to `setBoard` wins regardless of which read produced it, so after a burst of changes the board can settle on a snapshot that predates the newest one until some later change happens to trigger another reload.

The detail panel's rename window is the one place that already defends itself: `renamedTo` holds the path a rename moved the open card to, and it is only cleared by a board that can actually answer for that path (one that has the card there, or no longer has it under the old path either). That guard was added because a stale board arriving mid-rename used to unmount the panel and take every draft in it with it. It protects that one transition; the general problem is untouched.

## Expected outcome

A board that was read before a newer read started never replaces the newer one. The natural shape is a sequence number taken when a read is issued and checked when it resolves, dropping any result that is not the latest — the same guard `CardDetail` already applies to its own per-card body reads. With that in place, the `renamedTo` window becomes a smaller thing: it would still exist to cover the gap between the vault reporting a file operation and the debounced reload that knows about it, but it would no longer have to defend against out-of-order arrivals.

## Why it matters

The visible symptoms are mild and intermittent — a card that briefly shows its old status or title after a quick sequence of edits, a column that flickers back — which is exactly why it is easy to dismiss and hard to reproduce on demand. The severity is in what a stale board can take with it: anything the view keys off `board` identity. That already cost the detail panel its drafts once, and the fix for that case was a local guard rather than ordering, so the next thing to hang state off a board reload inherits the same hazard with no warning.
