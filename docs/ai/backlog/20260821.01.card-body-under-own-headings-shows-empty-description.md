# A card note whose body lives under its own headings shows an empty description

## What happens

Some notes carry their whole content under headings the plugin does not know about, typically `## Question` and `## Answer`, with only a stray line (or nothing at all) sitting between the H1 title and that first heading. Open such a note as a card on the board and the Description box in the detail panel shows nothing of what the note says. The note's text is intact on disk; it just never reaches the panel.

The same note most likely loses its comments too. It has a `## Comments` section with content, but that content is written as prose rather than as the timestamped bullet the plugin expects, so the comments list should come up empty as well. That second half is derived from reading the parser, not from watching the UI, and is worth confirming in the same pass.

Notes shaped like this are not exotic. They are what agents and note-taking workflows produce when they write an issue-style note, so the board will keep meeting them.

## How to reproduce

Save the file below into the card folder of any board, then open it as a card and look at the Description box and the comments list. The original that prompted this entry lives in a private vault and cannot be copied here, so this is a faithful reconstruction of its shape with neutral content. Keep every oddity when reproducing: the unusual `type` value, a `status` that matches no column on the board, the empty `blocked-by` list, exactly one prose line between the H1 and the first H2, the two unrecognized H2 sections, and a `## Comments` body written as bold prose instead of a `- [timestamp] text` bullet. Any one of them could be the trigger, and dropping it may hide the bug.

```markdown
---
type: task-afk
status: resolved
order: 2
created: 2026-08-20
blocked-by: []
---

# Rename the widget factory helpers

Context: [overview.md](../overview.md)

## Question

Three renames were agreed in the last review. Apply the ones that still stand:

1. `makeThing` becomes `createWidget`.
2. `thingOpts` becomes `WidgetOptions`.
3. Delete the unused `legacyThing` shim.

Resolved when all three are applied and the status file no longer lists them as pending.

## Answer

All three renames landed. The shim turned out to have no remaining callers.

## Comments

**2026-08-21** — Applied and checked against the test suite.
```

## What I already checked

Reading the card engine at `src/model/card.ts`, three boundaries look relevant, and they are offered as places to start rather than as a diagnosis:

- `parseBody` treats the description as only the region between the H1 and the first `##` line, so nothing under any H2 can appear in the Description box.
- The `SECTION` constant recognizes exactly three section names, `Subtasks`, `Comments` and `History`. Anything else in the note has no home in the panel.
- `parseTimestamped`, which feeds the comments list, skips any line that does not start as a `-` or `*` bullet, which is why the note's comment is expected to vanish.

One thing does not line up, and it is worth resolving before assuming the obvious story. Running the description slice over the real file by hand produced a non-empty result: the single line that sits between the H1 and the first `##`. Yet the box was reported as showing nothing. So "everything below the first H2 is dropped" may not be the whole explanation. Whoever picks this up should first open the example above in the UI and record what the Description box actually shows, rather than reasoning from the parser alone.

Frontmatter is not the cause. `FrontmatterSchema` accepts any string-keyed mapping, so `type: task-afk`, `status: resolved` and `blocked-by: []` all decode cleanly and no corruption error is raised.

## Expected outcome

Opening a card should let the person read what the note says. A note whose content is entirely under its own headings should not look empty on the board.

What the Description box should show when a note's content lives under sections the plugin does not recognize is a product decision, not a detail to settle here. The session that takes this on should choose deliberately, with Rafa, and should decide the comments-parsing gap in the same pass, since it is the same underlying question of how much of a hand-written note the board is willing to understand.
