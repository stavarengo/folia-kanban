# Lane membership is known only to the board view

## What happens

A column carrying a `filter` rule is not a filtered view of its own status bucket — it is an auto-populated lane. [`src/ui/Column.tsx`](../../../src/ui/Column.tsx) pulls every top-level card on the board matching the rule, wherever that card's `status` says it lives, and a card can appear in several lanes as well as in its own status column.

That rule is resolved with `parseFilter` and `matchCard` from [`src/ui/cardView.ts`](../../../src/ui/cardView.ts), so lane membership exists only above the `CardRepository` port. Anything reading the board through the port — today that is the MCP server in [`src/mcp/`](../../../src/mcp/), which the architecture forbids from importing `src/ui` — cannot ask which cards a lane actually holds. `get_board` therefore reports the column's plain status bucket, which for a lane is a different set from what the person looking at the board sees.

The write side has the same root. A card's visibility comes from its `status` matching a column, and for a lane column, from matching the rule instead. `create_card` and `move_card` set `status` — so a card sent to a lane whose rule it does not match is drawn in no column at all. The board view has the same wart and accepted it deliberately (`#1.6` in `Column.tsx`), on the grounds that a person dragging a card watches it happen; an agent gets no such feedback.

Both are currently handled by telling the caller rather than by fixing the asymmetry: `get_board` marks a filtered column with a `lane` note saying the listing is the status bucket and not the lane, and `create_card` / `move_card` return a `warning` when the target column has a rule. That is honest, and it is not the same as correct — an agent still cannot see a lane's contents, and still cannot tell a safe move into a lane from one that makes a card vanish.

## Expected outcome

One definition of lane membership, asked the same way by the board view and by anything else reading through the port — most likely by moving the filter parsing and card matching down into `src/model/` and having `Column.tsx` consume it from there. With that in place, `get_board` can report a lane as drawn, and a write that would leave a card invisible can be refused with the reason rather than warned about.

Worth pairing with a decision about whether the underlying behaviour is right at all: a column that shows cards by rule while also being a status a card can be assigned to is two things at once, and the invisible-card case is what that costs.
