# Connect cards to each other with typed relationships, starting with "blocks"

## What is asked

The ability to declare a relationship between two items and have the board understand it. The first and only type in scope is **blocking**: item A blocks item B. Other types ("a result of", and eventually user-defined ones) are explicitly future work, but the shape chosen now should not make them impossible later.

Rafa also raised, without deciding it, that a relationship type could carry implications. Blocking is the obvious case: it could mean something for whether a card may move to a given column.

His constraint, in his words: Folia Kanban aims to be a free Kanban framework based on Markdown, and "we don't want to enforce any particular usage or workflow. Everything should remain up to the user." Flexibility comes first; the feature provides basic Kanban management, not a process.

## What already exists

One relationship is already first-class, and it is hierarchical: a card is a subcard of P if and only if P's `## Subtasks` section links to it with `- [ ] [[Child]]`. It renders nested under its parent, in the parent's column. So what is new here is the **non-hierarchical, typed** link between two cards, not linking as such.

Answering Rafa's direct question: the plugin defines no rules at all about which card may move to which column. Soft WIP limits are the only rule-shaped thing that exists, and they are purely visual — `Column.tsx` adds an `is-over-limit` class and an "over the WIP limit" label; nothing refuses a drop. The README states the same posture: the board "nudges (never blocks)".

Frontmatter is free-form. `FrontmatterSchema` is a plain string-keyed record, so a card can already carry a key like `blocked-by: []` today and the plugin will accept it, ignore it, and preserve it. That key is not hypothetical: it is the convention Rafa already writes by hand in issue notes elsewhere.

A board's cards are the Markdown files under its `card-folder`. Anything outside that folder is not a card and has nowhere to appear on the board.

## Undecided

- What can be on the other end of a relationship: another card, any note in the vault, or an item in an external tracker? Rafa said "an external file" and repeatedly said "tickets"; those are materially different features.
- Where the relationship is recorded in the note, given that it must stay legible and hand-editable rather than living in a hidden index.
- Whether the plugin writes both ends of the pair or only one, and what it does when a hand-edited note has only one end.
- What "blocking" is allowed to do when a card is dragged, in a project whose only existing rule nudges rather than refuses.
- How, and where, a relationship becomes visible: on the card, in the detail panel, or both.
- Whether relationship changes are recorded in `## History`, and under which of the existing history settings.
- What a target that does not exist, or stops existing, should look like.
- How custom types arrive later without invalidating the files written by this first version.
