# Styling, theme and design language

What Folia styles by hand against the design language Obsidian already ships as CSS variables and classes. This section covers the `--folia-*` token layer and every rule that consumes it in `src/styles.css` (2,278 lines on 2026-09-20; it was 2,198 when the findings below were measured), the eight-colour palette in `src/ui/columnColors.ts`, the inline `style=` props in `src/ui/*.tsx`, the token JSON under `tokens/source/`, and the guards that police raw values: `scripts/audit-raw-values.mjs`, `scripts/raw-value-allowlist.json`, `scripts/check-tokens.mjs`, `scripts/check-button-styles.mjs`, `scripts/check-portal-scope.mjs`, plus `tracking/waivers/0001-raw-value-debt.md` and `0003-visual-regression-automation.md`. Which component gets drawn is section 01's question; this section is about how it is painted once drawn.

One thing shapes the whole section and is worth stating up front. Obsidian's **CSS variables** are documented exhaustively in `Reference/CSS variables/`, so every variable claim below is sourced. Obsidian's **class names** are almost undocumented: of `mod-cta`, `mod-warning`, `mod-muted`, `clickable-icon`, `is-active`, `is-disabled`, `nav-*`, `setting-item*`, `menu*`, `prompt*`, `suggestion-*`, `tree-item*`, `search-input-container`, `checkbox-container`, `is-mobile`, `is-phone` and `is-tablet`, only `u-pop` appears in the developer docs (`Plugins/User interface/Settings.md:935`), and `clickable-icon` appears there only as the variable `--clickable-icon-radius` (`Reference/CSS variables/Foundations/Icons.md`). The class claims in this section were therefore settled a second way, by reading the stylesheet of a running Obsidian 1.13.7 through the DevTools bridge on 2026-08-29 (`app://obsidian.md/app.css`, 3,672 rules; see "Verified live" at the end for the method and the per-class evidence). Every class in that list exists there with the behaviour its name suggests, with one exception: **`mod-muted` matches no rule at all** and should not be treated as an Obsidian class. Reading the running app's own stylesheet is not the same as an API promise — these names are still undocumented and Obsidian can move them — so findings below say "observed in Obsidian 1.13.7 `app.css`", never "documented".

## Colour

### 02-01. A light accent paints white text on a light button, because `--text-on-accent-inverted` is never used

- **Folia:** `src/styles.css:110` (`--folia-on-accent`) resolves to `var(--text-on-accent, #fff)` and is the only foreground the plugin ever puts on an accent or danger fill: `.folia-btn-primary` (`src/styles.css:1264-1268`), `.folia-btn-danger` (`1277-1281`), `.folia-column-count.is-over-limit` (`505-508`), and the toast, which hard-codes `color: #fff` outright (`src/styles.css:260`).
- **Obsidian:** `--text-on-accent` is documented as "Text on accent background when accent is dark" and `--text-on-accent-inverted` as "Text on accent background when accent is light" (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Text foreground colors`). The accent itself is user-chosen: "can be overridden by the user under **Settings → Appearance**" (same file, `#Accent color`).
- **Differs:** Folia treats "text on accent" as one colour. Obsidian splits it in two precisely because the accent is a user setting that can land anywhere on the lightness range. No rule in `src/styles.css` branches on accent lightness (no `--text-on-accent-inverted` anywhere in `src/`), so a user with a pale yellow or pale green accent gets a primary button and an over-limit badge whose label is white on near-white.
- **Read:** **clear win** — one variable swap behind a lightness condition, on a small number of rules, fixing a contrast failure the plugin cannot otherwise detect. Honest caveat: the docs describe the two variables but do not say who is responsible for choosing between them, so the exact mechanism (a `color-contrast()`-style pick, or reading `--accent-l`) needs a decision.
- **Guard:** none. `scripts/check-a11y-exceptions.mjs` and the raw-value audit both look at source shapes, not computed contrast; `tracking/waivers/0002-automated-a11y-gate.md` covers the absent automated a11y gate.
- **Correction, 2026-09-10 — the symptom does not happen, and the read above was wrong about where the choice is made.** Obsidian does not branch between the two variables in CSS at all; it rewrites `--text-on-accent` to point at `--text-on-accent-inverted` in the inline style of `<body>` when the user's accent is light. Folia's token block inherits from that body, so it follows without any code of its own: with the accent set to `#f5f3a0` in the live app, `button.mod-cta` and `.folia-btn-primary` both computed `rgb(0, 0, 0)` on `rgb(245, 243, 158)`, and a popout window carried the same override. What the finding correctly identifies is a fragility rather than a bug — the override reaches only rules that inherit from `<body>`, so the declaration must never be hoisted to `:root`, where it would freeze on its `#fff` fallback. See `docs/decisions.md`, "Folia does not decide for itself what colour goes on a pale accent". The rest of this section's reading is left as it stood.

### 02-02. The eight column colours are fixed hexes where Obsidian ships eight theme-aware ones

- **Folia:** `src/ui/columnColors.ts:3-12` (`COLUMN_COLORS`) is the single source of truth for the colours a column can take — eight literal hexes (`#4c9aff`, `#8fd14f`, `#ffab00`, `#9c8cff`, `#ff5c5c`, `#57d9a3`, `#f78fb3`, `#9aa0a6`), mirrored into `tokens/source/color.tokens.json` and applied as `--folia-col-accent`, which drives the column's top border, dot, subcard group frame and focus outline.
- **Obsidian:** the extended palette is exactly eight named colours — `--color-red`, `--color-orange`, `--color-yellow`, `--color-green`, `--color-cyan`, `--color-blue`, `--color-purple`, `--color-pink` — and each carries a different value in light and dark mode (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Extended colors`), themable by the user's theme.
- **Differs:** Folia's eight are one value each. They were picked to read on a dark surface (they are pastel-bright), so in a light theme the same accents sit on white with much less separation, and a theme that recolours the whole app leaves the board's column colours untouched. Against that, a stored column colour is user data: it is written into the board note as a hex, so the palette has to survive as a stable value, and `var(--color-blue)` is not a value that can be round-tripped through a note the way `#4c9aff` is.
- **Read:** **trade-off** — the theme-awareness is real, but the migration needs a stored form (a palette key resolved to a variable at render time) and a rule for hexes already written into existing board notes. Worth it if column colour is meant to be part of the theme; not worth it if it is meant to be a fixed product palette.
- **Guard:** `scripts/check-tokens.mjs` direction 2 asserts the eight hexes match `tokens/source/color.tokens.json` in order; all eight are allowlisted in `scripts/raw-value-allowlist.json` and named in `tracking/waivers/0001-raw-value-debt.md` as accepted residuals.
- **Adopted 2026-09-21 in 81bb84e, with the stored form the Read asked for.** A column stores the NAME of one of Obsidian's eight extended colours and `columnAccent` in `src/ui/columnColors.ts` resolves it to `var(--color-<name>)` at render time, so a name round-trips through a note exactly as a hex did while the colour itself follows the theme and its light/dark pair. `COLUMN_COLORS` is those eight names; rule F in `scripts/check-theme.mjs` now checks the mirror against names rather than hexes, and additionally that every name is a colour the registry documents, so a ninth colour cannot be invented here and resolve to nothing.
  - **A hex already in a board note is not touched and not migrated.** Anything that is not one of the eight names is passed through unchanged, so such a column paints exactly what it always did. There is one narrow exception, and it is deliberate: the eight names are also CSS colour keywords, so a hand-written `color: red` or `color: cyan` is read as the palette name it spells and now resolves to `var(--color-red)` rather than to pure `#ff0000`. That is the only path on which this change alters what an existing note renders, it is pinned by a test, and it is the answer a board asking for "red" should get. The column menu and the edit modal show a legacy value as a ninth, unpickable swatch marked active, so the colour the column carries is visible in the row rather than absent from it. Picking any of the eight replaces it with a name. `examples/feature-showcase/Showcase Board.md` keeps its Parked column on `#9aa0a6` on purpose, as the live example of that path — the grey it used has no counterpart among the eight, which is the one slot with no honest translation.
  - **Verified live 2026-09-21**, examples vault, Obsidian 1.13.7, both modes. The board read back `next → var(--color-green)`, `doing → var(--color-orange)`, `review → var(--color-purple)`, `focus → var(--color-red)`, `done → var(--color-cyan)` from the names in the note; `parked → #9aa0a6`, the stored hex passed through untouched; and `todo → var(--color-pink)` from `autoColor`, the note assigning it nothing. The column menu on Parked showed the eight theme swatches, then that hex as a ninth, ringed active and disabled, then the clear button. Screenshots were kept at `tmp/screenshots/phase1-colour/`, which is gitignored — they are evidence of that run on that machine, not something a later reader can open from the repository, so what they showed is written out here instead.
  - **The order of the eight is the old palette's, hue for hue.** `autoColor` hashes a column id into the array to colour a column the board note never assigned, so re-ordering would have changed the colour of every auto-coloured column on every existing board with nothing stored to explain it. A column that auto-coloured itself blue is still blue. Two slots move further than the rest, because the old palette had colours the eight do not: the eighth was a neutral grey and becomes yellow, and the sixth was a mint green (`#57d9a3`) that lands on cyan, green being taken by the second.
  - **Two things this finding's surrounding notes got wrong.** There is no column-colour surface in `src/mcp` — the MCP tools never read or wrote the field — and the Zod side needed nothing: `ContextFrontmatterSchema`'s `color` is a context colour, a different field, and a column's colour is carried as free text by `normalizeColumns`/`serializeColumns`, which is exactly what lets a legacy hex survive. `test/columns.test.ts` now pins the resolution, the case handling, the passthrough and the round-trip.

### 02-03. Every theme colour is read through a hard-coded hex fallback that can only ever be wrong

- **Folia:** `src/styles.css:85-117` declares the priority ramp and status colours through six distinct fallbacked variables — `var(--color-red, #e5534b)`, `var(--color-orange, #d9882f)`, `var(--color-yellow, #c2a312)`, `var(--color-blue, #5b8def)`, `var(--color-purple, #a882e0)`, `var(--color-green, #4caf7d)` — written eight times in all (red at `85` and `111`, blue at `88` and `115`), plus `var(--text-on-accent, #fff)` at line 110 — nine fallback literals across nine declarations. The same fallback strings are preserved verbatim in `tokens/source/color.tokens.json` (`color.primitive.*`) and enforced byte-for-byte by `scripts/check-tokens.mjs`.
- **Obsidian:** all seven are documented variables Obsidian defines itself — the six extended colours in `developer-docs: Reference/CSS variables/Foundations/Colors.md#Extended colors`, `--text-on-accent` in the same file under `#Text foreground colors`. Their documented defaults differ per mode: `--color-red` is `#e93147` in light and `#fb464c` in dark, `--color-yellow` is `#e0ac00` light and `#e0de71` dark, and so on.
- **Differs:** the fallbacks never fire in Obsidian, so they are inert weight in the normal case. In the abnormal case they are worse than nothing: each is a single value where Obsidian's is a light/dark pair, so a fallback that ever did fire would be both off-palette and theme-blind, and `#c2a312` against `#e0de71` is not a near miss. They also travel: `tokens/source/color.tokens.json` preserves each fallback string verbatim as the token's `$value` (and, for the referencing tokens, as its `resolvedValue`), so the wrong constant is recorded in the design-token source of truth as part of what "red" means here.
- **Read:** **clear win** — dropping the fallbacks is a pure deletion (`var(--color-red)`), removes nine wrong-in-two-ways literals across nine declarations. The only cost is that a jsdom test reading the stylesheet as text sees a bare `var()`, which it already does for the dozens of unfallbacked ones.
- **Guard:** none of the nine is allowlisted, because none is seen: all nine sit on `--folia-*` token-declaration lines, which `scripts/audit-raw-values.mjs` exempts wholesale via `TOKEN_DECL` (line 74). The `#fff` entry in `scripts/raw-value-allowlist.json` is a different occurrence — the toast's `color: #fff` at `src/styles.css:260` (02-01) — so deleting these fallbacks changes neither the allowlist nor the audit's count.
- **Fixed 2026-09-21 in 7242a58 (c2b6ee3 for the guard rule that made them findable).** All nine literals are gone from `src/theme/tokens.css`: the four priority rungs, `--folia-danger`, `--folia-unread`, `--folia-unread-reply` and `--folia-success` now read the extended colours bare, and `--folia-on-accent` reads `--text-on-accent` bare. All nine are recorded as plain aliases in `src/theme/tokens/color.tokens.json`, so the wrong constants no longer travel in the token source either. The guard change that preceded this made a fallback part of the alias rather than a reason to own the token, which is what turned "find the literals" into a metadata query; the two `--layer-*` fallbacks survive it, because `z-index` does not inherit and an unresolved `var()` there computes to `auto`. `--folia-border-strong` also keeps its fallback, which is a second variable rather than a literal and so is not one of this finding's nine.

### 02-04. Status colours are rebuilt from the palette instead of the semantic variables Obsidian defines for them

- **Folia:** `src/styles.css:111` sets `--folia-danger` to the red primitive and `:117` sets `--folia-success` to the green one; `--folia-prio-2` (orange) doubles as the warning colour for `.folia-chip-warn` (`1075`), `.folia-card-folder-notice` (`414-421`) and `.folia-desc-behind` (`1741-1748`). Error and success surfaces are then built by mixing those into the background (`.folia-detail-confirm`, `1464`; `.folia-menu-danger:hover`, `680`).
- **Obsidian:** `--text-error`, `--text-warning`, `--text-success` are documented text colours, and `--background-modifier-error`, `--background-modifier-error-hover`, `--background-modifier-success`, `--background-modifier-message` are documented surfaces for exactly these states (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Surface colors` and `#Text foreground colors`). The plugin guidelines' own example of correct styling uses `--background-modifier-error` for a warning container (`developer-docs: Plugins/Releasing/Plugin guidelines.md#No hardcoded styling`).
- **Also:** the toast (`src/styles.css:250-269`) is the plugin's message surface, filled with `--folia-success`/`--folia-danger` and white text, while `--background-modifier-message` ("Messages background", same page) appears nowhere in `src/styles.css`.
- **Differs:** Folia derives semantic states from hue primitives, so a theme that recolours the error state — the thing a user actually perceives as "error red" in the rest of the app — does not reach the board. Folia does use `--text-error` where the text is plainly an error (`.folia-error` at `404-406`, `.folia-desc-refusal` at `408-412`), so the divergence is confined to the fills, badges and chips.
- **Read:** **trade-off** — for the chips the mixing percentages were tuned for contrast (see 02-09) and a semantic variable would have to be re-tuned; for the plain surfaces (`.folia-detail-confirm`, `.folia-card-folder-notice`, `.folia-desc-behind`) the swap is close to free and buys theme consistency.
- **Fixed 2026-09-21 in 4f57106, with two departures from the obvious reading.** `--folia-text-error`, `--folia-text-warning` and `--folia-text-success` alias the three documented text colours and `--folia-error-bg` aliases `--background-modifier-error`. The confirm bar keeps a 10% mix and changes what it mixes: the palette red that also fills the danger button, replaced by `--background-modifier-error` itself, so a theme that recolours the error state now reaches it. The first pass took the surface whole, on the strength of the pairing `Plugins/Releasing/Plugin guidelines.md:330-336` shows — `--text-normal` on `--background-modifier-error`. Measuring it retired that reading: the variable is `#fb464c`, a saturated red, and `--text-normal` is `#dadada`, so the documented pairing is a red band with near-white text, which is a button face rather than a notice bar. The variable is right and the proportion is the board's. The foregrounds that were painted with a fill move to the text colours: `.folia-action-done:hover`, `.folia-action-delete:hover`, `.folia-menu-danger` and its hover tint, and the progress meta's done state. The first two had to be doubled to render at all — they weigh the same as `.folia-icon-btn:hover` and `index.css` imports their file first, so the base rule was winning on source order and had been since before this phase; the tint they were supposed to draw had never appeared.   `.folia-error` and `.folia-desc-refusal` already read `--text-error` and now read it through the token, so the layer is not half-direct.
  - **The folder notice and the "behind" bar take `--text-warning` as their hue, not a surface variable.** Obsidian documents no warning background — `--background-modifier-error`, `-error-hover`, `-success` and `-message` are the whole set — so there is nothing to swap in. The real divergence this finding names is that both surfaces were built out of `--folia-prio-2`, the *priority ramp's orange*, which is a different semantic object from "warning"; re-sourcing the mix onto `--text-warning` fixes that without inventing a variable.
  - **Verified live 2026-09-21** in the examples vault on Obsidian 1.13.7, dark and light: the five columns written as names resolve to `var(--color-green)`, `orange`, `purple`, `red` and `cyan`, the Parked column's stored `#9aa0a6` passes through untouched, and the column with no colour at all auto-colours to `var(--color-pink)` — see 02-02.
  - **The toast keeps `--folia-success`/`--folia-danger` as its fill.** The documented pairing for `--background-modifier-error` is `--text-normal`, which says the variable is a surface text sits on, not a saturated pill. The toast is a saturated pill with a white label, and `docs/decisions.md` records that its `#fff` is deliberate and must not follow an unrelated appearance setting. Filling it with a surface variable while keeping white text would be exactly the mismatch that decision exists to prevent, and the contrast cannot be checked without the running app. Left as a surface to verify live.
  - `--folia-danger` and `--folia-success` stay on the palette, because they are fills — the danger button, the toast, the over-limit badge — and Obsidian publishes no variable for a danger fill. Keeping one token for both duties would have recreated 02-06's bug in a different hue.
  - The tinted chips keep their mixes, as the Read asks. The comment on the rule in `src/theme/chips.css` now says why in terms of this finding rather than only in terms of contrast.

### 02-05. Ten `var(--text-faint, var(--text-muted))` fallbacks for a variable Obsidian always defines

- **Folia:** ten occurrences in `src/styles.css` — `.folia-column-empty` (`538`), `.folia-menu-label` (`603`), `.folia-prop-key` (`1544`), `.folia-title-step-source` (`1663`), `.folia-ts` (`2013`), `.folia-muted` (`219`), `.folia-card-group-heading` (`2051`), `.folia-field-label` (`2148`), `.folia-field-hint` (`2152`), `.folia-card-next-todo-mark` (`1167`).
- **Obsidian:** `--text-faint` is a documented text foreground colour alongside `--text-normal` and `--text-muted` (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Text foreground colors`).
- **Differs:** nothing functionally — the fallback is unreachable. It costs readability of the stylesheet and it quietly says "this variable may not exist", which is the opposite of what the reader should conclude. The same pattern appears on `--font-monospace` (`src/styles.css:389`) and `--interactive-accent-hover` (`1273`). `--font-monospace` turns out to be a real Obsidian variable — `app.css` declares it on `body` as `var(--font-monospace-override), var(--font-monospace-theme), var(--font-monospace-default)`, the composed value that already ends in the platform's monospace stack — so that fallback is unreachable too, exactly like the ten above.
- **Read:** **clear win**, in the sense of cheap and unambiguous. Ten one-token deletions, no visual change.
- **Fixed 2026-09-21 in 7242a58.** All ten `--text-faint` fallbacks are gone, now spread across six of the section files Phase 0 split `styles.css` into (`base.css`, `board-columns.css`, `next-todos.css`, `column-config.css` ×3, `detail-panel.css` ×3, `column-menu.css`). `--font-monospace` and `--interactive-accent-hover` went with them: `--folia-font-mono` is a bare alias of `--font-monospace`, which `src/theme/host/observed.json` records as real-but-undocumented, and `.folia-btn-primary:hover` reads `--interactive-accent-hover` bare. The `--font-ui-small` fallback this finding's family implies no longer exists — Phase 0 had already made `--folia-font-size-md` a bare alias of it.

### 02-06. Accent text is painted with the interactive-element accent, not the text accent

- **Folia:** `src/styles.css:338` (`.folia-filter-chip.is-on`) sets `color: var(--folia-accent)`, and `.folia-link` falls back to the same token when `--link-color` is missing (`203`); `--folia-accent` is `var(--interactive-accent)` (`89`). The accent is also the colour of the focus ring, the progress fill and every "selected" border.
- **Obsidian:** the two are separate documented variables. `--interactive-accent` is "Background for accented interactive elements" under `#Interactive colors`, while `--text-accent` and `--text-accent-hover` are "Accent text" under `#Text foreground colors` (`developer-docs: Reference/CSS variables/Foundations/Colors.md`).
- **Differs:** Folia uses the *background* accent as a *foreground* colour. At the default theme they are close, but they are separate variables precisely so a theme can darken accent text for legibility while keeping bright accent fills; a theme that does exactly that leaves Folia's accented text at the fill colour, on a background it was never meant to sit on.
- **Read:** **clear win** — two declarations, and it is the difference between "accent" meaning one thing and meaning two.
- **Fixed 2026-09-21 in aeaa437.** `--folia-text-accent` and `--folia-text-accent-hover` alias `--text-accent` and `--text-accent-hover`, and every foreground that was painted with the fill now reads one of them: `.folia-filter-chip.is-on` (`toolbar.css`), `.folia-filter-suggest-key` (`filter-suggest.css`), and `.folia-card-parent-ref:hover` (`subitem-columns.css`), which takes the hover variant because that is what it is. `--folia-accent` keeps its own meaning and its own jobs — the focus ring, the progress fill, every "selected" border, and the accent-tinted background and border of that same `is-on` chip, which 02-07 argues for keeping. `.folia-link`'s accent fallback went with the link work in 02-31.

### 02-07. Active and selected states are mixed by hand where the theme has a variable for them

- **Folia:** `.folia-filter-chip.is-on` (`src/styles.css:335-339`) mixes 16% accent into transparent for the background and 45% for the border; `.folia-swatch.is-active` (`639-642`) and `.folia-menu-prio.is-active` (`725-727`) draw two-tone rings; `.folia-column-body.is-over` mixes 9% (`528-530`).
- **Obsidian:** `--background-modifier-active-hover` is documented as "Active hovered elements" alongside `--background-modifier-hover` (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Surface colors`), and `--nav-item-background-active`/`--nav-item-background-selected` cover the same states for list items (`Components/Navigation.md`).
- **Differs:** Folia takes the theme's hover colour (see the aligned list) and then invents the active and selected steps beside it, so a theme that gives active elements a distinct treatment reaches the board's hover state and nothing beyond it.
- **Read:** **trade-off** — the accent-tinted "on" chip is a deliberate signal that a plain active background would flatten; the swatch and priority rings are shape, not colour, and are fine as they are. The one clear candidate is `.folia-column-body.is-over`, a plain highlighted surface.
- **Also:** the same page documents `--background-secondary-alt`, "Background for surfaces on top of secondary background" (`Colors.md#Surface colors`). `.folia-column-header` (`src/styles.css:468-475`) fills itself with `--folia-col-bg`, the same `--background-secondary` as the column body it sits on top of — precisely the stacking that variable exists for.
- **Fixed 2026-09-21 in 3d0bc96 for the two the Read names; the other three stand by design.** `--folia-drop-target-bg` aliases `--background-modifier-active-hover` and `.folia-column-body.is-over` takes it in place of its 9% accent mix, so the board's drop target is now whatever the theme makes an active surface. `--folia-col-header-bg` aliases `--background-secondary-alt` and `.folia-column-header` takes it, which is the stacking the variable exists for; the over-limit header tint mixes into the new base rather than the old one, so the two still agree. The filter chip's "on" state keeps its accent tint — an active filter is a statement about what the whole board is showing, and a neutral active background would flatten it into the same grey as a hovered row — and the swatch and priority rings stay shape rather than colour, since there is no host variable for "this is the chosen swatch" and a colour marker would vanish on the swatch whose colour it matched. `docs/decisions.md` carries both arguments.

### 02-08. Form fields are painted with the page background instead of the form-field background

- **Folia:** every input, textarea and select in the plugin sets `background: var(--background-primary)` — the search box (`src/styles.css:295`), the menu field (`610`), the add-column input (`791`), the card add textarea (`1342`), the detail fields (`1499`), the property input (`1559`), the comment editor (`1936`), the modal fields (`2162`) — or `transparent` for the inner search input (`306`).
- **Obsidian:** `--background-modifier-form-field` is documented as "Form field background" (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Surface colors`).
- **Differs:** Folia's inputs are the same colour as the surface behind them and rely entirely on their border to read as fields. Obsidian ships a distinct fill for exactly this, which many themes use to make inputs recessed or tinted; on those themes every Folia input reads as flat where the app's read as a field.
- **Read:** **clear win** — one variable swap across eight rules, and it is what makes an input look like an input on the user's theme rather than on the plugin author's.
- **Fixed 2026-09-21 in f00ca0a.** `--folia-field-bg` aliases `--background-modifier-form-field` and nine rules take it: the search box (`toolbar.css`), the menu field (`column-menu.css`), the add-column input (`add-column.css`), the card and inline add inputs (`inline-add-inputs.css`), the detail fields and the property input, the description textarea and the comment editor (`detail-panel.css` ×4), and the modal fields (`column-config.css`). The description textarea is the ninth the finding's rule catches but its line list did not name. The inner `.folia-search input` stays `transparent` — the container it sits in carries the fill. Two inputs deliberately keep `--background-primary`: `.folia-card-title-input` and `.folia-column-title-input` replace text in its own slot and are meant not to read as fields; `docs/decisions.md` carries the argument.

### 02-09. Fifty-four `color-mix(in srgb, …)` tints against a palette the app mixes in OKLCH

- **Folia:** 54 occurrences across `src/styles.css`, all `color-mix(in srgb, …)`. - **Fixed 2026-09-21 in 9291766 for the free half.** Recounted against the split bundle and after this phase's other commits, there are 53 mixes rather than 54: the column drop target lost one to `--background-modifier-active-hover` (02-07), and that one mixed into `transparent`. ### 02-17. The detail panel's resize handle reinvents the app's divider

- **Folia:** `.folia-detail-resize` (`src/styles.css:1410-1418`) is a 6px-wide absolutely positioned strip at `left: -3px` with `cursor: col-resize` and no colour at all; the panel's own edge is a separate `border-left: 1px solid var(--folia-border-strong)` (`1369`).

- **Differs:** Folia's handle never changes appearance on hover, so there is no feedback that the edge is draggable until the pointer changes; Obsidian's dividers widen and recolour on hover through the `-hover` variables. The plugin is drawing the app's most familiar drag affordance in a way that does not behave like it.
- **Read:** **clear win** — a handful of declarations (`--divider-color-hover` on hover, `--divider-width`) to make an existing affordance behave the way the same affordance behaves everywhere else in the window.
- **Phase 3, 2026-09-21. Half resolved, and the other half is blocked by the panel's structure.** The resting line is now the app's: `.folia-detail` draws `border-left: var(--divider-width) solid var(--divider-color)`, which measured moves the edge from `--background-modifier-border-hover` (`#3f3f3f`) to `#333333`, both 1px, so it is slightly dimmer than before.
  The hover half is **not** adopted, and the reason is worth keeping because it caught a real bug. `.folia-detail-resize` is `position: absolute; top: 0; bottom: 0` inside `.folia-detail`, which is `overflow-y: auto` — so it is exactly one viewport tall and scrolls with the content. Measured in the running app on a docked panel with 1736px of content in a 675px viewport: at `scrollTop: 600` the handle's box ends 200px down the screen, and `document.elementFromPoint` finds `.folia-detail-body` rather than the handle over the lower 89% of the panel's edge. Its top is painted over by the sticky header, which carries the same `z-index`. Anything the handle draws therefore vanishes on a scrolled panel, which is most panels — a first attempt at this finding moved the resting line onto the handle and did exactly that. The line has to be the panel's own border, and a border cannot be recoloured from a descendant's `:hover` without `:has()`. The upstream community scan warns about `:has()` on performance grounds, and this repository fails on every scanner finding rather than only on the ones upstream calls errors, so a warning is a refusal here.
  What did get fixed is the grab target. The handle sat at `left: -3px`, and `overflow-y: auto` makes the computed `overflow-x` `auto` too, so its outer half was clipped — not painted, not hit-testable. The 6px strip has only ever been 3px wide. It is now at `left: 0` and the full width works wherever it is visible.

### 02-19. Dropdowns get no dropdown styling at all

- **Folia:** `.folia-fields select` (`src/styles.css:1496-1506`) and `.folia-field select` (`2154-2164`) are styled exactly like text inputs — same border, radius, padding and background — with focus rules at `1353` and `2166`.

Adopting it on a control that cannot draw a chevron would leave a wide empty gutter with nothing in it, which is worse than either the old look or the platform's. The select uses the board's own symmetric padding instead.
- **Phase 3 — not adopted.** The chevron is an inline data-URI SVG on the undocumented `.dropdown` class (`.theme-dark .dropdown` swaps it for a light one); `--dropdown-background-position`, `--dropdown-background-size` and `--dropdown-background-blend-mode` are that image's three background layers and paint nothing without it. No variable publishes the glyph, so the only route is wearing `.dropdown`, which the owner's decision 5 rules out. The board's selects therefore still have no dropdown indicator — a state this phase inherited rather than created, and the one real cost of that decision. Recorded in `docs/decisions.md`.

### 02-41. The property rows reimplement Obsidian's own property editor

- **Folia:** `.folia-prop-key` (`src/styles.css:1542-1550`) is a fixed `86px` uppercase label with `0.03em` tracking at the smallest font size, and `.folia-prop-input` (`1554-1565`) is a text input with its own border, radius, padding and focus ring; together they render a card's frontmatter properties as label-and-value rows.
- **Obsidian:** the metadata property editor is a documented component with roughly 35 variables (`developer-docs: Reference/CSS variables/Editor/Properties.md`), including `--metadata-label-width`, `--metadata-label-font-size`, `--metadata-label-font-weight`, `--metadata-label-text-color`, `--metadata-label-text-color-hover`, `--metadata-input-height`, `--metadata-input-font-size`, `--metadata-input-background`, `--metadata-input-background-hover`, `--metadata-divider-color`, `--metadata-gap`, `--metadata-border-radius`.
- **Differs:** this is the closest match in the whole section between a Folia surface and an Obsidian one: the same object (a note's properties), edited the same way (label plus typed value), styled by two unrelated sets of values. A user editing the same frontmatter in the note's own property editor and in the board's detail panel sees two different controls. Folia's label column is a fixed 86px where Obsidian's is `--metadata-label-width`.
- **Read:** **trade-off** — adopting the label and input variables aligns the two views for a handful of declarations, but the detail panel is much narrower than an editor pane, and `--metadata-label-width` is sized for the latter. The label geometry may have to stay Folia's even if the colours and type do not. Whether the panel should host Obsidian's property editor outright is section 01's question.
- **Phase 3, 2026-09-21.** Resolved as the read describes. `.folia-prop-key` takes `--metadata-label-font-size` and `--metadata-label-text-color`, with a hover on `--metadata-label-text-color-hover`; `.folia-prop-input` takes `--metadata-input-font-size` and `--metadata-input-text-color`; its corner is `--input-radius`. Measured in 1.13.7: the label goes 10px → `0.875em` (11.4px) and `#b3b3b3`, the input 12px → 11.4px, its text `--text-normal` → `#dadada`, its radius 4px → 5px.
  The line this finding draws, after three attempts at the radius: the row's *identity* — the type and colour of the label and of the value — comes from the metadata family, because that is what makes the board's rows read as the same object the note's own property editor edits. The *box* around the value stays the board's. `--metadata-input-background` is `transparent`, which works in an editor pane that has other lines to place a field against and reads as no field at all in a panel this narrow, over `--folia-col-bg` behind a `#333333` hairline; the fill therefore stays `--background-primary`, and its divergence from the host's form-field colour belongs to 02-08. `--metadata-input-background-hover` goes with it. For the same reason the corner is `--input-radius` (5px): with a border, this element is a text input. `--metadata-border-radius` is the *container's* corner and `--metadata-property-radius` is the *row's* — the row here is `.folia-prop-row`, and this is the value inside it.
  The radius took three attempts and the third is the honest one. `--metadata-border-radius` is the *container's* corner (`0`, paired with `--metadata-border-width: 0`) and was wrong. `--metadata-property-radius` (6px) is the *row's* corner, and the row here is `.folia-prop-row` — this element is the value inside it, so that was wrong too. What this element actually is, once the board keeps a border on it, is a text input, so it takes `--input-radius` (5px), which is what Obsidian rounds a text input to. `--metadata-label-text-color-hover` resolves to its resting value in the default theme, so that rule paints nothing today and exists so a theme that lifts a property row on hover reaches these rows too. The label also gains `white-space: nowrap`, without which the `text-overflow: ellipsis` beside it never fired and the now-larger label wrapped inside its fixed column instead of truncating.
- **Phase 3 — not adopted, with reasons.** `--metadata-label-width` is `9em` (about 117px), sized for an editor pane; this panel is around 380px wide and its label column stays the board's 88px. `--metadata-label-font-weight` computes to the empty string — declared, never shipped — so reading it would paint nothing. `--metadata-divider-color` and `--metadata-divider-width` have nothing to draw: these rows have no dividers between properties, they are separated by a gap. `--metadata-gap` is `3px` against the board's own 6px, which would crowd rows that carry a label, an input and sometimes a button; `--metadata-input-height` (`calc(16px * 1.75)`, 28px) is not taken either, because the input is sized by its type and padding here and pinning a height would fight the row's `align-items: center`. The input keeps Folia's 1px border although Obsidian's property inputs have none: with a transparent fill and no border, a row in this panel would be invisible between edits, where the editor pane has surrounding lines to place it against. The uppercase label and its tracking also stay — they are what distinguishes a property row from the form fields above it in the same panel.
