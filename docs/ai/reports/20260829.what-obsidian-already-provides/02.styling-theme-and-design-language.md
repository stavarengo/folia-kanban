# Styling, theme and design language

What Folia styles by hand against the design language Obsidian already ships as CSS variables and classes. This section covers the `--folia-*` token layer and every rule that consumes it in `src/styles.css` (2,198 lines), the eight-colour palette in `src/ui/columnColors.ts`, the inline `style=` props in `src/ui/*.tsx`, the token JSON under `tokens/source/`, and the guards that police raw values: `scripts/audit-raw-values.mjs`, `scripts/raw-value-allowlist.json`, `scripts/check-tokens.mjs`, `scripts/check-button-styles.mjs`, `scripts/check-portal-scope.mjs`, plus `tracking/waivers/0001-raw-value-debt.md` and `0003-visual-regression-automation.md`. Which component gets drawn is section 01's question; this section is about how it is painted once drawn.

One thing shapes the whole section and is worth stating up front. Obsidian's **CSS variables** are documented exhaustively in `Reference/CSS variables/`, so every variable claim below is sourced. Obsidian's **class names** are almost undocumented: of `mod-cta`, `mod-warning`, `mod-muted`, `clickable-icon`, `is-active`, `is-disabled`, `nav-*`, `setting-item*`, `menu*`, `prompt*`, `suggestion-*`, `tree-item*`, `search-input-container`, `checkbox-container`, `is-mobile`, `is-phone` and `is-tablet`, only `u-pop` appears in the developer docs (`Plugins/User interface/Settings.md:935`), and `clickable-icon` appears there only as the variable `--clickable-icon-radius` (`Reference/CSS variables/Foundations/Icons.md`). The class claims in this section were therefore settled a second way, by reading the stylesheet of a running Obsidian 1.13.7 through the DevTools bridge on 2026-08-29 (`app://obsidian.md/app.css`, 3,672 rules; see "Verified live" at the end for the method and the per-class evidence). Every class in that list exists there with the behaviour its name suggests, with one exception: **`mod-muted` matches no rule at all** and should not be treated as an Obsidian class. Reading the running app's own stylesheet is not the same as an API promise — these names are still undocumented and Obsidian can move them — so findings below say "observed in Obsidian 1.13.7 `app.css`", never "documented".

## Colour

### 02-01. A light accent paints white text on a light button, because `--text-on-accent-inverted` is never used

- **Folia:** `src/styles.css:75` (`--folia-on-accent`) resolves to `var(--text-on-accent, #fff)` and is the only foreground the plugin ever puts on an accent or danger fill: `.folia-btn-primary` (`src/styles.css:1189-1193`), `.folia-btn-danger` (`1202-1206`), `.folia-column-count.is-over-limit` (`431-434`), and the toast, which hard-codes `color: #fff` outright (`src/styles.css:175`).
- **Obsidian:** `--text-on-accent` is documented as "Text on accent background when accent is dark" and `--text-on-accent-inverted` as "Text on accent background when accent is light" (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Text foreground colors`). The accent itself is user-chosen: "can be overridden by the user under **Settings → Appearance**" (same file, `#Accent color`).
- **Differs:** Folia treats "text on accent" as one colour. Obsidian splits it in two precisely because the accent is a user setting that can land anywhere on the lightness range. No rule in `src/styles.css` branches on accent lightness (no `--text-on-accent-inverted` anywhere in `src/`), so a user with a pale yellow or pale green accent gets a primary button and an over-limit badge whose label is white on near-white.
- **Read:** **clear win** — one variable swap behind a lightness condition, on a small number of rules, fixing a contrast failure the plugin cannot otherwise detect. Honest caveat: the docs describe the two variables but do not say who is responsible for choosing between them, so the exact mechanism (a `color-contrast()`-style pick, or reading `--accent-l`) needs a decision.
- **Guard:** none. `scripts/check-a11y-exceptions.mjs` and the raw-value audit both look at source shapes, not computed contrast; `tracking/waivers/0002-automated-a11y-gate.md` covers the absent automated a11y gate.

### 02-02. The eight column colours are fixed hexes where Obsidian ships eight theme-aware ones

- **Folia:** `src/ui/columnColors.ts:3-12` (`COLUMN_COLORS`) is the single source of truth for the colours a column can take — eight literal hexes (`#4c9aff`, `#8fd14f`, `#ffab00`, `#9c8cff`, `#ff5c5c`, `#57d9a3`, `#f78fb3`, `#9aa0a6`), mirrored into `tokens/source/color.tokens.json` and applied as `--folia-col-accent`, which drives the column's top border, dot, subcard group frame and focus outline.
- **Obsidian:** the extended palette is exactly eight named colours — `--color-red`, `--color-orange`, `--color-yellow`, `--color-green`, `--color-cyan`, `--color-blue`, `--color-purple`, `--color-pink` — and each carries a different value in light and dark mode (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Extended colors`), themable by the user's theme.
- **Differs:** Folia's eight are one value each. They were picked to read on a dark surface (they are pastel-bright), so in a light theme the same accents sit on white with much less separation, and a theme that recolours the whole app leaves the board's column colours untouched. Against that, a stored column colour is user data: it is written into the board note as a hex, so the palette has to survive as a stable value, and `var(--color-blue)` is not a value that can be round-tripped through a note the way `#4c9aff` is.
- **Read:** **trade-off** — the theme-awareness is real, but the migration needs a stored form (a palette key resolved to a variable at render time) and a rule for hexes already written into existing board notes. Worth it if column colour is meant to be part of the theme; not worth it if it is meant to be a fixed product palette.
- **Guard:** `scripts/check-tokens.mjs` direction 2 asserts the eight hexes match `tokens/source/color.tokens.json` in order; all eight are allowlisted in `scripts/raw-value-allowlist.json` and named in `tracking/waivers/0001-raw-value-debt.md` as accepted residuals.

### 02-03. Every theme colour is read through a hard-coded hex fallback that can only ever be wrong

- **Folia:** `src/styles.css:70-82` declares the priority ramp and status colours through six distinct fallbacked variables — `var(--color-red, #e5534b)`, `var(--color-orange, #d9882f)`, `var(--color-yellow, #c2a312)`, `var(--color-blue, #5b8def)`, `var(--color-purple, #a882e0)`, `var(--color-green, #4caf7d)` — written eight times in all (red at `70` and `76`, blue at `73` and `80`), plus `var(--text-on-accent, #fff)` at line 75 — nine fallback literals across nine declarations. The same fallback strings are preserved verbatim in `tokens/source/color.tokens.json` (`color.primitive.*`) and enforced byte-for-byte by `scripts/check-tokens.mjs`.
- **Obsidian:** all seven are documented variables Obsidian defines itself — the six extended colours in `developer-docs: Reference/CSS variables/Foundations/Colors.md#Extended colors`, `--text-on-accent` in the same file under `#Text foreground colors`. Their documented defaults differ per mode: `--color-red` is `#e93147` in light and `#fb464c` in dark, `--color-yellow` is `#e0ac00` light and `#e0de71` dark, and so on.
- **Differs:** the fallbacks never fire in Obsidian, so they are inert weight in the normal case. In the abnormal case they are worse than nothing: each is a single value where Obsidian's is a light/dark pair, so a fallback that ever did fire would be both off-palette and theme-blind, and `#c2a312` against `#e0de71` is not a near miss. They also travel: `tokens/source/color.tokens.json` preserves each fallback string verbatim as the token's `$value` (and, for the referencing tokens, as its `resolvedValue`), so the wrong constant is recorded in the design-token source of truth as part of what "red" means here.
- **Read:** **clear win** — dropping the fallbacks is a pure deletion (`var(--color-red)`), removes nine wrong-in-two-ways literals across nine declarations. The only cost is that a jsdom test reading the stylesheet as text sees a bare `var()`, which it already does for the dozens of unfallbacked ones.
- **Guard:** none of the nine is allowlisted, because none is seen: all nine sit on `--folia-*` token-declaration lines, which `scripts/audit-raw-values.mjs` exempts wholesale via `TOKEN_DECL` (line 74). The `#fff` entry in `scripts/raw-value-allowlist.json` is a different occurrence — the toast's `color: #fff` at `src/styles.css:175` (02-01) — so deleting these fallbacks changes neither the allowlist nor the audit's count.

### 02-04. Status colours are rebuilt from the palette instead of the semantic variables Obsidian defines for them

- **Folia:** `src/styles.css:76` sets `--folia-danger` to the red primitive and `:82` sets `--folia-success` to the green one; `--folia-prio-2` (orange) doubles as the warning colour for `.folia-chip-warn` (`1000`), `.folia-card-folder-notice` (`329-336`) and `.folia-desc-behind` (`1649-1656`). Error and success surfaces are then built by mixing those into the background (`.folia-detail-confirm`, `1373`; `.folia-menu-danger:hover`, `606`).
- **Obsidian:** `--text-error`, `--text-warning`, `--text-success` are documented text colours, and `--background-modifier-error`, `--background-modifier-error-hover`, `--background-modifier-success`, `--background-modifier-message` are documented surfaces for exactly these states (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Surface colors` and `#Text foreground colors`). The plugin guidelines' own example of correct styling uses `--background-modifier-error` for a warning container (`developer-docs: Plugins/Releasing/Plugin guidelines.md#No hardcoded styling`).
- **Also:** the toast (`src/styles.css:165-184`) is the plugin's message surface, filled with `--folia-success`/`--folia-danger` and white text, while `--background-modifier-message` ("Messages background", same page) appears nowhere in `src/styles.css`.
- **Differs:** Folia derives semantic states from hue primitives, so a theme that recolours the error state — the thing a user actually perceives as "error red" in the rest of the app — does not reach the board. Folia does use `--text-error` where the text is plainly an error (`.folia-error` at `319-321`, `.folia-desc-refusal` at `323-327`), so the divergence is confined to the fills, badges and chips.
- **Read:** **trade-off** — for the chips the mixing percentages were tuned for contrast (see 02-09) and a semantic variable would have to be re-tuned; for the plain surfaces (`.folia-detail-confirm`, `.folia-card-folder-notice`, `.folia-desc-behind`) the swap is close to free and buys theme consistency.

### 02-05. Ten `var(--text-faint, var(--text-muted))` fallbacks for a variable Obsidian always defines

- **Folia:** ten occurrences in `src/styles.css` — `.folia-column-empty` (`464`), `.folia-menu-label` (`529`), `.folia-prop-key` (`1453`), `.folia-title-step-source` (`1573`), `.folia-ts` (`1928`), `.folia-muted` (`1932`), `.folia-card-group-heading` (`1971`), `.folia-field-label` (`2068`), `.folia-field-hint` (`2072`), `.folia-card-next-todo-mark` (`1092`).
- **Obsidian:** `--text-faint` is a documented text foreground colour alongside `--text-normal` and `--text-muted` (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Text foreground colors`).
- **Differs:** nothing functionally — the fallback is unreachable. It costs readability of the stylesheet and it quietly says "this variable may not exist", which is the opposite of what the reader should conclude. The same pattern appears on `--font-monospace` (`src/styles.css:304`) and `--interactive-accent-hover` (`1198`). `--font-monospace` turns out to be a real Obsidian variable — `app.css` declares it on `body` as `var(--font-monospace-override), var(--font-monospace-theme), var(--font-monospace-default)`, the composed value that already ends in the platform's monospace stack — so that fallback is unreachable too, exactly like the ten above.
- **Read:** **clear win**, in the sense of cheap and unambiguous. Ten one-token deletions, no visual change.

### 02-06. Accent text is painted with the interactive-element accent, not the text accent

- **Folia:** `src/styles.css:253` (`.folia-filter-chip.is-on`) sets `color: var(--folia-accent)`, and `.folia-link` falls back to the same token when `--link-color` is missing (`1780`); `--folia-accent` is `var(--interactive-accent)` (`74`). The accent is also the colour of the focus ring, the progress fill and every "selected" border.
- **Obsidian:** the two are separate documented variables. `--interactive-accent` is "Background for accented interactive elements" under `#Interactive colors`, while `--text-accent` and `--text-accent-hover` are "Accent text" under `#Text foreground colors` (`developer-docs: Reference/CSS variables/Foundations/Colors.md`).
- **Differs:** Folia uses the *background* accent as a *foreground* colour. At the default theme they are close, but they are separate variables precisely so a theme can darken accent text for legibility while keeping bright accent fills; a theme that does exactly that leaves Folia's accented text at the fill colour, on a background it was never meant to sit on.
- **Read:** **clear win** — two declarations, and it is the difference between "accent" meaning one thing and meaning two.

### 02-07. Active and selected states are mixed by hand where the theme has a variable for them

- **Folia:** `.folia-filter-chip.is-on` (`src/styles.css:250-254`) mixes 16% accent into transparent for the background and 45% for the border; `.folia-swatch.is-active` (`565-568`) and `.folia-menu-prio.is-active` (`650-652`) draw two-tone rings; `.folia-column-body.is-over` mixes 9% (`454-456`).
- **Obsidian:** `--background-modifier-active-hover` is documented as "Active hovered elements" alongside `--background-modifier-hover` (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Surface colors`), and `--nav-item-background-active`/`--nav-item-background-selected` cover the same states for list items (`Components/Navigation.md`).
- **Differs:** Folia takes the theme's hover colour (see the aligned list) and then invents the active and selected steps beside it, so a theme that gives active elements a distinct treatment reaches the board's hover state and nothing beyond it.
- **Read:** **trade-off** — the accent-tinted "on" chip is a deliberate signal that a plain active background would flatten; the swatch and priority rings are shape, not colour, and are fine as they are. The one clear candidate is `.folia-column-body.is-over`, a plain highlighted surface.
- **Also:** the same page documents `--background-secondary-alt`, "Background for surfaces on top of secondary background" (`Colors.md#Surface colors`). `.folia-column-header` (`src/styles.css:383-390`) fills itself with `--folia-col-bg`, the same `--background-secondary` as the column body it sits on top of — precisely the stacking that variable exists for.

### 02-08. Form fields are painted with the page background instead of the form-field background

- **Folia:** every input, textarea and select in the plugin sets `background: var(--background-primary)` — the search box (`src/styles.css:210`), the menu field (`536`), the add-column input (`716`), the card add textarea (`1251`), the detail fields (`1408`), the property input (`1468`), the comment editor (`1851`), the modal fields (`2082`) — or `transparent` for the inner search input (`221`).
- **Obsidian:** `--background-modifier-form-field` is documented as "Form field background" (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Surface colors`).
- **Differs:** Folia's inputs are the same colour as the surface behind them and rely entirely on their border to read as fields. Obsidian ships a distinct fill for exactly this, which many themes use to make inputs recessed or tinted; on those themes every Folia input reads as flat where the app's read as a field.
- **Read:** **clear win** — one variable swap across eight rules, and it is what makes an input look like an input on the user's theme rather than on the plugin author's.

### 02-09. Fifty-four `color-mix(in srgb, …)` tints against a palette the app mixes in OKLCH

- **Folia:** 54 occurrences across `src/styles.css`, all `color-mix(in srgb, …)`. They carry the priority chips (`995-1001`), the urgency card tints (`765-776`), the drag and drop washes (`455`, `791`), the unread comment tints (`1883-1901`), the filter-chip "on" state (`250-254`), the subcard group frame (`880-881`) and the focus ring token itself (`src/styles.css:67`, `--folia-ring`).
- **Obsidian:** "As of Obsidian 1.13, colors use the OKLCH color space for mixing", and the documented replacement for the deprecated RGB variables is `color-mix(in oklch, var(--color-red) 20%, transparent)` (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Extended colors`, the deprecation callout).
- **Differs:** the doc does not forbid `in srgb`; it states the app's own mixing space and writes its replacement idiom in OKLCH. How much that costs was measured in the running app on 2026-08-29 (see "Verified live") and it is much less than the principle suggests. Thirty-nine of the 54 mixes have `transparent` as their second colour, and mixing a colour into `transparent` is pure alpha: `color-mix(in srgb, #fb464c 20%, transparent)` and the OKLCH form rasterise to exactly the same pixel, at every percentage tested. The remaining fifteen mix two opaque colours — twelve into `var(--text-normal)`, two into `var(--folia-col-bg)`, one into `var(--folia-border)` — and there the two spaces do diverge, by at most 10 of 255 per channel (about 4%) at the 55–60% the chips use, and by 2 to 6 at the ends of the range. The comment at `src/styles.css:993-994` records that those percentages were hand-tuned for WCAG AA in both themes, which is exactly the tuning a space change would perturb.
- **Read:** **not worth it** as a visual correction, and only a consistency-of-idiom argument as a change. The measurement removes the "the chips land somewhere else" argument: 39 of the 54 mixes are identical in either space, and the other fifteen differ by a few units per channel, below what the contrast tuning at `src/styles.css:993-994` would notice. What remains is that Folia writes `in srgb` where the app writes `in oklch`, which matters for the next person editing the stylesheet rather than for what anyone sees. The 39 transparent mixes can be switched with no risk at all; the fifteen opaque ones would want re-checking against the contrast target, and there is no visual-regression harness to catch drift (`tracking/waivers/0003-visual-regression-automation.md`). The version attribution rests on `Colors.md` alone: `node_modules/obsidian/CHANGELOG.md` stops at v1.7.2 and never mentions OKLCH.
- **Guard:** none. `scripts/audit-raw-values.mjs` detects `rgb()`/`hsl()` literals but has no detector for `color-mix`, its mixing space, or its percentages.

## Spacing, size and radius

### 02-10. The raw-value audit is blind to most of what it exists to police

- **Folia:** `scripts/audit-raw-values.mjs:52-72` is the whole detector list: nine regular expressions (hex, `rgb()`/`hsl()`, `box-shadow`, `font-family`, `z-index`, px lengths, `font-weight`, bare `opacity`, half-pixel lengths). The spacing detector is `/\b\d{2,}px\b/` — **two or more digits** (line 64, with the comment "1px hairlines and 0 are fine"). Consequences, measured in the current `src/styles.css` with comments stripped: 233 unsigned single-digit `px` lengths exist (240 counting the seven negative-signed ones at `66`, `516`, `922`, `1141`, `1321`, `1617`, `1944`), of which 164 sit in layout declarations (margin, padding, gap, inset, the four offsets, width/height and their min/max forms, counting one declaration per line), and **none of them is seen by the audit or listed in the allowlist**. There is no detector at all for durations (`animation: folia-toast-in 220ms …`, line 181; `transition-duration: 0.01ms`, line 2117), for `em` lengths (`2em`, `0.5em`, `0.25em`, `0.15em`), for `letter-spacing` (`0.03em`, `0.04em`, `0.05em`), for bare `line-height` numbers (13 declarations across five distinct values), for viewport lengths (`60vw`, `92vw`, `85vh`, three `100vh` arithmetic expressions and a fourth inside a comment), for `border-radius: 3px` (line 1093), for transforms (`scale(1.1)`, `scale(1.03)`, `rotate(1.5deg)`), for `backdrop-filter: blur(2px|3px)` (three), or for `color-mix` percentages (54).
- **Obsidian:** the values these would be checked against are all documented — `--size-2-*`/`--size-4-*` (`developer-docs: Reference/CSS variables/Foundations/Spacing.md`), `--radius-*` (`Radiuses.md`), `--line-height-normal`/`--line-height-tight` (`Typography.md#Line heights`), `--border-width` (`Borders.md`).
- **Differs:** the guard's documented promise — "Raw design values that should be design tokens … a RATCHET: existing debt is tolerated, new debt is blocked" (`scripts/audit-raw-values.mjs:1-6`) — reads much wider than those nine regular expressions deliver, and `tracking/waivers/0001-raw-value-debt.md` retires the waiver on the strength of that promise ("nothing remains to migrate"). Two narrower gaps the waiver already confesses (2026-08-26 and 2026-08-28 corrections): a count is a ceiling that spare headroom can be spent against, and a value named in a comment counts as an occurrence — `90px` is allowlisted with `count: 1` and that one occurrence is entirely the arithmetic comment at `src/styles.css:840`, so the first real `90px` declaration anywhere in the file would pass unnoticed.
- **Read:** **trade-off** — widening the detectors is easy, but every new detector produces a large first baseline (164 single-digit px lengths in layout declarations alone), and the honest question is which of those categories has a token home worth having. The value of writing it down now is that the waiver currently reads as "fully covered" and is not.
- **Guard:** this finding is about the guard.
- **Backlog:** `docs/ai/backlog/20260828.01.raw-value-count-ceiling-does-not-shrink-on-paydown.md` covers the ceiling half.

### 02-11. A parallel radius ladder that no theme can reach

- **Folia:** `src/styles.css:34-38` declares `--folia-r-sm: 6px`, `--folia-r: 8px`, `--folia-r-lg: 10px`, `--folia-r-xl: 14px`, `--folia-r-pill: 999px`, consumed by roughly every surface in the file (cards, columns, menus, the modal, inputs, chips, buttons).
- **Obsidian:** `--radius-s: 4px`, `--radius-m: 8px`, `--radius-l: 12px`, `--radius-xl: 16px` (`developer-docs: Reference/CSS variables/Foundations/Radiuses.md`), plus per-component radii a theme can move independently: `--button-radius` (`Components/Button.md`), `--input-radius` (`Components/Text input.md`), `--modal-radius` (`Components/Modal.md`), `--tag-radius` (`Editor/Tag.md`), `--checkbox-radius` (`Components/Checkbox.md`), `--clickable-icon-radius` (`Foundations/Icons.md`), `--toggle-radius`, `--slider-thumb-radius`.
- **Differs:** the ladders overlap on one rung (8px) and disagree on the other three (6 vs 4, 10 vs 12, 14 vs 16). A user on a sharp-cornered theme that sets `--radius-*: 0` gets an app with square corners and a board with 6–14px rounding. `--folia-r-xl` is declared and, at the time of writing, used nowhere in the file.
- **Read:** **trade-off** — remapping to `--radius-s/m/l` is a small edit with a visible result (every corner in the plugin changes by 2px), which is exactly what there is no harness for (`tracking/waivers/0003-visual-regression-automation.md`). The theming win is real and permanent; the cost is a one-time visual review. `--folia-r-xl` should go regardless.
- **Guard:** `scripts/check-tokens.mjs` asserts the five radius tokens match `tokens/source/radius.tokens.json`; nothing compares them to Obsidian's ladder.

### 02-12. Around 140 hard-coded gaps and paddings land exactly on Obsidian's 4-pixel grid without using it

- **Folia:** counting px lengths in layout properties only (margin, padding, gap, inset, the four offsets, width, height and their min/max forms), comments stripped, unsigned lengths only, one declaration per line, `src/styles.css` holds 233 such lengths. 140 of them land exactly on a documented Obsidian size: `2px` (16), `4px` (16), `6px` (40), `8px` (43), `12px` (8), `16px` (4), `20px` (1), `24px` (8), `48px` (3), `72px` (1). The remaining 93 are off-grid: `1px` (12), `3px` (9), `5px` (10), `7px` (7), `9px` (11), `10px` (16), `11px` (3), `14px` (10), `18px` (3), `22px` (1), `26px` (2), `30px` (2), `92px` (1), plus the one-off component widths `220px`, `224px`, `280px`, `440px` (twice) and `640px`. One of the off-grid values is a load-bearing token: `--folia-gap: 10px` (`src/styles.css:41`); `--folia-pad: 12px` (line 42) is already on the grid.
- **Obsidian:** "Obsidian uses a 4-pixel grid to structure UI elements … all elements should use the predefined `--size` CSS variables for spacing and dimensions properties", with `--size-2-1: 2px`, `--size-2-2: 4px`, `--size-2-3: 6px`, `--size-4-2: 8px`, `--size-4-3: 12px`, `--size-4-4: 16px`, `--size-4-6: 24px` (`developer-docs: Reference/CSS variables/Foundations/Spacing.md`). The stated reason is scaling across high and low DPI screens.
- **Differs:** Folia's spacing is a hand-tuned rhythm around 10px that happens to touch the grid about 60% of the time. Adopting the variables for the 140 that already match is a rename with no visual change; the other 93 (and `--folia-gap` itself) would have to move by 1–2px to join the grid, which is a design change, not a refactor.
- **Read:** **trade-off** — the free 60% is a genuine win (the board then scales with the app when Obsidian changes the grid); the rest is a redesign of the board's density and should be judged as one.
- **Guard:** the single-digit half of this is invisible to `scripts/audit-raw-values.mjs` (see 02-10); `10px`, `11px`, `12px`, `14px`, `16px`, `18px`, `24px` and `92px` are allowlisted with counts, justified in `scripts/raw-value-allowlist.json`'s note as "one-off component-dimension px lengths … with no semantic token home".

### 02-13. Thirty-one hand-written `1px solid` borders where the app has a border-width variable

- **Folia:** 31 `1px solid` declarations in `src/styles.css` (columns, cards, chips, every input, the menu, the modal, the toolbar and detail-panel rules), plus four `1px dashed` borders at the same width (`466`, `691`, `1662`, `1795`), `border-left: 2px` on the subcard group (`880`) and the comment quote rules (`1810`), `border-top: 3px` on the column accent (`378`), and two `1.5px` hairlines (`802`, `1092`).
- **Obsidian:** `--border-width: 1px` (`developer-docs: Reference/CSS variables/Foundations/Borders.md`), with `--input-border-width` (`Components/Text input.md`), `--modal-border-width` (`Components/Modal.md`), `--prompt-border-width` (`Components/Prompt.md`), `--divider-width` (`Window/Divider.md`), `--tag-border-width` (`Editor/Tag.md`), `--toggle-border-width`, `--slider-thumb-border-width` for the specific cases.
- **Differs:** a theme that thickens or removes borders app-wide leaves the board's 31 hairlines exactly where they are. Folia does route the border *colour* through the theme (`--folia-border` is `--background-modifier-border`, `src/styles.css:55`), so only the width is unreachable.
- **Read:** **clear win** for the 35 plain `1px` cases (solid and dashed) — a mechanical substitution with no visual change at the default value, and the component-specific variables can follow later where a rule is plainly an input or a modal.
- **Guard:** none; `1px` is single-digit and below the audit's `\d{2,}px` threshold, and `1.5px` is allowlisted (count 2).

### 02-14. Icon dimensions are seven hard-coded numbers instead of the icon size scale

- **Folia:** `src/ui/icons.tsx:142-155` (`Icon`) writes `width={size}` / `height={size}` (lines 150-151) with `size = 16` by default and `strokeWidth={2}` fixed (line 155); callers pass 34 explicit sizes across `src/ui/*.tsx` in seven distinct values (11, 12, 13, 14, 15, 16, 20). `.folia-icon` in CSS carries only `flex` and `vertical-align` (`src/styles.css:338-341`).
- **Obsidian:** `--icon-size` is the "shorthand for icon width and length" and `--icon-stroke` for stroke width, with the scale `--icon-xs: 14px`, `--icon-s: 16px`, `--icon-m: 18px`, `--icon-l: 18px`, `--icon-xl: 32px` and matching `--icon-*-stroke-width` values, of which three are `1.75px` or `1.25px`, not `2px` (`developer-docs: Reference/CSS variables/Foundations/Icons.md`). The changelog records the design intent: the `size` parameter was **removed** from `setIcon` in v1.1.0 and "This is now configurable via CSS. You can add override the CSS var `--icon-size` on the parent class of your element" (`node_modules/obsidian/CHANGELOG.md:238`, under the v1.1.0 heading at line 201).
- **Differs:** Folia sizes icons in JSX, per call site, in seven values, none of which is on Obsidian's scale except 14 and 16; stroke width never varies, so a small Folia icon is proportionally heavier than a small Obsidian one. Obsidian removed exactly this parameter from its own API and moved the decision into CSS, where a theme can reach it.
- **Read:** **clear win** for the mechanism (drive size from `--icon-size` on the container rule, drop the per-call numbers), **trade-off** for the values, since collapsing seven sizes onto a five-rung scale changes several tiles. Whether the icons should come from `setIcon` at all is section 01's call; this finding stands either way.

### 02-15. Control heights are invented rather than taken from `--input-height`

- **Folia:** the search box and every filter chip are pinned to `height: 30px` (`src/styles.css:207`, `235`); `.folia-icon-btn` is `26px` square (`1216-1217`), `.folia-mini` and the column menu button `24px` (`1233-1234`, `392-393`); inputs get `padding: 6px 8px` or `7px 9px` and no height at all (`532-533`, `1255`, `2079`).
- **Obsidian:** `--input-height` (`developer-docs: Reference/CSS variables/Components/Text input.md`) and `--prompt-input-height` (`Components/Prompt.md`). The search box in particular has its own set: `--search-icon-color`, `--search-icon-size`, `--search-clear-button-color`, `--search-clear-button-size` and `--search-result-background` (`Plugins/Search.md`), the last of which is what `.folia-filter-suggest-item` (`src/styles.css:285-302`) hand-paints with `--background-modifier-hover`. Folia's own stylesheet already records that Obsidian applies `height: var(--input-height)` to every `button` in `app.css` (`src/styles.css:1510-1514`), which is why `.folia-title-value` has to undo it.
- **Differs:** the board's controls are 30px and 26px whatever the app's control height is, so a theme that enlarges inputs for touch or accessibility produces a board whose controls stay small next to the rest of the window. The plugin is already exposed to `--input-height` in the one place it fights it.
- **Read:** **trade-off** — adopting it aligns the board with the app but hands its row heights to the theme, which is a real loss of layout control on a dense board (the toolbar row and the chip row are sized to each other). Worth doing for the search input at least, which is the control users read as an input.

### 02-16. Scrollbars are asked for by width only, ignoring the scrollbar variables

- **Folia:** `scrollbar-width: thin` on five scrolling surfaces (`src/styles.css:354`, `451`, `1284`, `1630`, `2042`) and `scrollbar-gutter: stable` on the card context menu (`628`); nothing else.
- **Obsidian:** `--scrollbar-bg`, `--scrollbar-thumb-bg`, `--scrollbar-active-thumb-bg`, with the note that "Custom scrollbars are only used on Windows and Linux" (`developer-docs: Reference/CSS variables/Window/Scrollbar.md`).
- **Differs:** `scrollbar-width: thin` is a platform-neutral standard property, so on Windows and Linux the board's scrollbars are thin but coloured by the browser default rather than by the theme's scrollbar colours; on macOS the declaration is close to inert. It is not wrong, it is simply narrower than what the app exposes.
- **Read:** **not worth it** on its own — the visible difference is small and only on two platforms. It becomes worth it if a user reports the board's scrollbars looking foreign against a strongly coloured theme.

### 02-17. The detail panel's resize handle reinvents the app's divider

- **Folia:** `.folia-detail-resize` (`src/styles.css:1319-1327`) is a 6px-wide absolutely positioned strip at `left: -3px` with `cursor: col-resize` and no colour at all; the panel's own edge is a separate `border-left: 1px solid var(--folia-border-strong)` (`1278`).
- **Obsidian:** `--divider-color`, `--divider-color-hover`, `--divider-width`, `--divider-width-hover`, `--divider-vertical-height`, documented as "CSS variables for dividers and resize handles between sidebars, tabs, and split panes" (`developer-docs: Reference/CSS variables/Window/Divider.md`) — the same object, including the hover-thickening behaviour Obsidian's own split handles have.
- **Differs:** Folia's handle never changes appearance on hover, so there is no feedback that the edge is draggable until the pointer changes; Obsidian's dividers widen and recolour on hover through the `-hover` variables. The plugin is drawing the app's most familiar drag affordance in a way that does not behave like it.
- **Read:** **clear win** — a handful of declarations (`--divider-color-hover` on hover, `--divider-width`) to make an existing affordance behave the way the same affordance behaves everywhere else in the window.

### 02-18. Colour swatches reinvent the colour-input geometry

- **Folia:** `.folia-swatch` (`src/styles.css:549-561`) is a `24px` square with `--folia-r-pill`, a `2px` transparent border and `background-clip: padding-box`, scaling to `1.1` on hover; the fill comes in inline from the palette (`ColumnMenu.tsx:126`, `ColumnEditModal.tsx:150`).
- **Obsidian:** `--swatch-radius`, `--swatch-height`, `--swatch-width` and `--swatch-shadow`, on a page whose intro reads "CSS variables for color inputs, such as the accent color picker" (`developer-docs: Reference/CSS variables/Components/Color input.md`) — the same object, in the same role: picking a colour from a row of round chips.
- **Differs:** Folia's swatches are 24px pills whatever the app's colour picker looks like, so the plugin's colour row and the theme's accent picker in Settings → Appearance are visibly different controls doing the same job.
- **Read:** **clear win** for the geometry (`--swatch-height`, `--swatch-width`, `--swatch-radius`), which changes nothing at the default values and follows the theme thereafter. The selected-state ring stays Folia's, since no swatch variable covers it.

### 02-19. Dropdowns get no dropdown styling at all

- **Folia:** `.folia-fields select` (`src/styles.css:1405-1415`) and `.folia-field select` (`2074-2084`) are styled exactly like text inputs — same border, radius, padding and background — with focus rules at `1262` and `2086`.
- **Obsidian:** `--dropdown-background`, `--dropdown-background-hover`, `--dropdown-background-blend-mode`, `--dropdown-background-position`, `--dropdown-background-size`, `--dropdown-padding`, on a page titled "CSS variables for dropdowns and `select` elements" (`developer-docs: Reference/CSS variables/Components/Dropdowns.md`).
- **Differs:** Obsidian gives `select` its own background, hover background, blend mode, background position and size — a set that only makes sense for a control whose background carries something (the variable names are all the doc gives; what Obsidian actually paints there is not documented). Folia's selects are styled exactly like its text inputs and otherwise fall back to the platform's own select rendering, so on the same panel a select and a text input differ only by whatever the operating system draws.
- **Read:** **clear win** — six variables exist for this control and the plugin uses none of them, so whatever Obsidian's dropdowns look like on the user's theme, the board's do not. Nothing in the board's design wants a select to look like a text field.

### 02-20. Icon buttons pick their own icon colours beside the icon colour variables

- **Folia:** `.folia-icon-btn` (`src/styles.css:1213-1228`) hard-codes `color: var(--text-muted)` at rest and `var(--text-normal)` on hover, with `background: var(--background-modifier-hover)` behind it; `.folia-card-subitems-toggle` (`1103-1118`) and `.folia-column-menu-btn` (`391-401`) repeat the pattern, the latter also animating `opacity` from 0.
- **Obsidian:** the same table 02-14 cites for sizing also documents `--icon-color`, `--icon-color-hover`, `--icon-color-active`, `--icon-color-focused`, `--icon-opacity`, `--icon-opacity-hover`, `--icon-opacity-active` and `--clickable-icon-radius` (`developer-docs: Reference/CSS variables/Foundations/Icons.md`). For the collapse chevron specifically — `.folia-card-subitems-toggle`, rotated `-90deg` at `src/styles.css:1125` — Obsidian has `--nav-collapse-icon-color` and `--nav-collapse-icon-color-collapsed` (`Components/Navigation.md`), a pair whose whole purpose is to colour a collapsed state differently from an expanded one, which Folia does not distinguish at all.
- **Differs:** Folia expresses icon state as text colours, Obsidian as icon colours and icon opacities — a theme that dims icons through `--icon-opacity` and leaves text colours alone changes every icon in the window except the board's. `--icon-color-focused` has no Folia equivalent at all; the board's icon buttons show focus only through the generic `:focus-visible` outline.
- **Read:** **clear win** — a direct substitution on three rules, no layout change, and it picks up a focus state the plugin currently does not express.

## Typography

### 02-21. A nine-rung font-size ladder shadows Obsidian's four UI sizes

- **Folia:** `src/styles.css:85-93` declares `--folia-font-size-xxs: 10px`, `-xxs-plus: 10.5px`, `-xs: 11px`, `-sm: 12px`, `-sm-plus: 12.5px`, `-md: 13px`, `-md-plus: 13.5px`, `-lg: 15px`, `-xl: 16px`, consumed by 62 declarations (21 of them `-xs`, 14 `-sm`, 12 `-md`).
- **Obsidian:** "Use `--font-ui-*` (fixed) variables for UI elements": `--font-ui-smaller: 12px`, `--font-ui-small: 13px`, `--font-ui-medium: 15px`, `--font-ui-large: 20px`, alongside the relative `--font-smallest`/`--font-smaller`/`--font-small` for editor content (`developer-docs: Reference/CSS variables/Foundations/Typography.md#Font size`).
- **Differs:** three of Folia's rungs are Obsidian's (12, 13, 15) and six are not, including three half-pixel sizes that exist to make nested and secondary text read slightly smaller than the text above it. A user who enlarges the interface font in the theme moves the whole app and leaves the board where it is — except for `.folia-scope`'s own base, which does follow `--font-ui-small` (`src/styles.css:31`, and see the aligned list).
- **Read:** **trade-off** — mapping `-sm`/`-md`/`-lg` onto `--font-ui-smaller`/`--font-ui-small`/`--font-ui-medium` is free and makes three quarters of the text theme-responsive; the 10px/11px small print has no Obsidian equivalent at all (the smallest UI size is 12px), so those rungs would have to stay as `calc()` off a variable or stay raw. The `-plus` rungs are the ones to question first: three of them, six uses between them — `-xxs-plus` twice, `-sm-plus` once, `-md-plus` three times.
- **Guard:** `scripts/check-tokens.mjs` asserts all nine against `tokens/source/typography.tokens.json`; the audit's `\d{2,}px` detector sees them only as allowlisted `10px`/`11px`/`12px`/`13px`/`14px`/`16px` entries.

### 02-22. Two font weights hard-coded beside Obsidian's named weight scale

- **Folia:** `src/styles.css:96-97` — `--folia-font-weight-medium: 500`, `--folia-font-weight-semibold: 600` — used 24 times.
- **Obsidian:** the full numeric scale is exposed by name, `--font-thin` through `--font-black`, with `--font-medium: 500` and `--font-semibold: 600` exactly matching Folia's two (`developer-docs: Reference/CSS variables/Foundations/Typography.md#Font weight`).
- **Differs:** nothing at the default value. The difference appears in a theme that shifts its weight scale (a theme with a light body weight typically drops the whole ladder), where the board keeps 500/600 and reads heavier than the app around it.
- **Read:** **clear win** — a two-line token change (`--folia-font-weight-medium: var(--font-medium)`), no visual change at defaults, no call-site edits at all.

### 02-23. Thirteen line heights, five values, written as literals

- **Folia:** `line-height` is written literally thirteen times in `src/styles.css`: `1.5` (five, on the description editor, the rendered description, the comment body and the comment editor), `1.4` (four, card title and list rows), `1.35` (two, detail title and rendered headings), `1.3` (one, the parent reference), `1` (one, the unread mark).
- **Obsidian:** `--line-height-normal: 1.5` and `--line-height-tight: 1.3`, the latter documented as "Used in search results, tree items, tooltips, and other smaller spaces" (`developer-docs: Reference/CSS variables/Foundations/Typography.md#Line heights`).
- **Differs:** Folia's `1.5` is Obsidian's normal and its `1.3` is Obsidian's tight, so six of the thirteen are the app's values written as literals. The remaining `1.4` and `1.35` sit between the two rungs. Several of the `1.5`s are load-bearing in a way the comments record: the editor and the rendered preview must match so the height does not jump on the view/edit toggle (`src/styles.css:1599-1601`, `1848-1850`), which is an argument for one shared value, and a variable is a better shared value than four copies of a literal.
- **Read:** **clear win** for the six that already match; **trade-off** for `1.4`/`1.35`, which would move if snapped to the scale.
- **Guard:** none — the audit has no line-height detector (see 02-10).

### 02-24. Completed-item styling ignores the checklist-done variables

- **Folia:** `.folia-done` (`src/styles.css:1798-1802`) sets `text-decoration: line-through` and `color: var(--text-muted)`, with a comment explaining the single-keyword shorthand is deliberate because Obsidian's community-directory CSS scan flags `text-decoration-*` longhands.
- **Obsidian:** `--checklist-done-decoration` ("Checked text decoration") and `--checklist-done-color` ("Checked text color") (`developer-docs: Reference/CSS variables/Components/Checkbox.md`) are the variables the app itself uses for the text of a completed task, which is the same semantic object as a done card or subtask.
- **Differs:** a theme that renders finished tasks as faded-not-struck, or struck in a specific colour, reaches every checklist in the vault and not the board. Using the variables also sidesteps the scan problem the comment describes, since the value comes from the variable rather than from a longhand.
- **Read:** **clear win** — two declarations, and it removes a workaround.

## Shadows, layers and motion

### 02-25. Folia's z-index ladder sits in the same numeric space as Obsidian's, with five exact collisions

- **Folia:** `src/styles.css:99-108` — base 1, raised 2, sticky 30, toast 50, scrim 55, menu 60, popover 70, modal 80, top 90 — applied to the card context menu (80, `620`), the detail panel float (55, `1294`), the modal backdrop portalled to `<body>` (90, `1999`), the column popover (60, `501`), the detail panel's modal backdrop (70, `1301`) and the toast (50, `179`). Three of those surfaces are portalled to the document body, outside the plugin's own subtree.
- **Obsidian:** `--layer-cover: 5`, `--layer-sidedock: 10`, `--layer-status-bar: 15`, `--layer-popover: 30`, `--layer-slides: 45`, `--layer-modal: 50`, `--layer-notice: 60`, `--layer-menu: 65`, `--layer-tooltip: 70`, `--layer-dragged-item: 80` (`developer-docs: Reference/CSS variables/Foundations/Layers.md`).
- **Differs:** the two ladders are not merely parallel, they overlap on five numbers: Folia's sticky layer is 30 and the app's popover layer is 30; Folia's toast is 50 and the app's modal layer is 50; Folia's menu is 60 and the app's notice layer is 60; Folia's popover is 70 and the app's tooltip layer is 70; Folia's modal is 80 and the app's dragged-item layer is 80. For a surface that stays inside the board's own stacking context this is harmless. For the three that are portalled to `<body>` it means the plugin's menus and dialogs are competing directly with Obsidian's notices, tooltips and menus on the same numbers, and the winner is then decided by document order.
- **Read:** **trade-off** — mapping the portalled surfaces onto `--layer-menu`/`--layer-modal`/`--layer-notice` puts them in the app's own order deliberately instead of by coincidence; the in-board layers (base, raised, sticky) have no Obsidian equivalent and should stay. The comparison is real rather than theoretical: opening the column popover in the running app puts `.folia-menu` in the document body as a `position: fixed` sibling of `.app-container`, at `z-index: 60`, in the same root stacking context as Obsidian's own body-level overlays, so the two ladders are read off the same axis and ties fall to document order. Hovering a card-count badge while that popover was open drew Obsidian's tooltip (`z-index: 70`) over it, which is the collision this finding predicts — screenshot at [`assets/03-tooltip-over-folia-menu.png`](./assets/03-tooltip-over-folia-menu.png).
- **Guard:** `scripts/check-tokens.mjs` asserts the ladder against `tokens/source/zindex.tokens.json`; `scripts/check-portal-scope.mjs` knows which surfaces are portalled out of the root, which is exactly the list this finding cares about.

### 02-26. The elevation set is tuned for dark mode and applies unchanged in light

- **Folia:** `src/styles.css:62-66` declares five shadows over literal black — `0 1px 2px rgba(0,0,0,0.16)`, `0 4px 14px rgba(0,0,0,0.22)`, `0 14px 36px rgba(0,0,0,0.4)`, `0 6px 20px rgba(0,0,0,0.28)`, `-8px 0 24px rgba(0,0,0,0.18)` — under the comment "elevation (subtle in dark, structure carried by borders)". `--folia-scrim: rgba(0,0,0,0.45)` (line 59) backs both dialog backdrops.
- **Obsidian:** Obsidian exposes no general elevation scale: the Foundations tree covers borders, colours, cursor, icons, layers, radiuses, spacing and typography, and the only shadow variables anywhere in `Reference/CSS variables/` are six component-specific ones — `--swatch-shadow` (`Components/Color input.md`), `--tab-stacked-shadow` (`Components/Tabs.md`), `--embed-block-shadow-hover` (`Editor/Block.md`) and three Bases shadows (`Editor/Bases.md`). None of them is a reusable card, popover or overlay elevation. What Obsidian does document is the convention for values that must differ by scheme: define them under `.theme-light` and `.theme-dark`, and reserve `body` for values that stay the same ("Only use `.theme-dark` or `.theme-light` selectors if you want the styles to change when switching between light and dark themes" — `developer-docs: Themes/App themes/Build a theme.md`, step 6 tip; `Themes/App themes/Theme guidelines.md#Use CSS variables` puts the same rule as "Override general variables under `body`, and colors under `.theme-light` or `.theme-dark`").
- **Differs:** owning an elevation scale is legitimate, since Obsidian ships none. Declaring one set of black shadows for both schemes is the part that diverges: a 40% black overlay shadow reads as a soft lift on a dark ground and as a hard smudge on white, and the token block itself says the values were chosen for dark. `.folia-scope` is a single flat rule, so there is no light/dark split anywhere in the plugin.
- **Read:** **clear win** for the split (redeclare the five shadow tokens and the scrim under `.theme-light`, which is additive and cannot affect the current dark rendering), independent of whether the values themselves change.
- **Guard:** the five declarations themselves are exempt from the audit as `--folia-*` token lines (`TOKEN_DECL`, `scripts/audit-raw-values.mjs:74`); what the allowlist holds is the consuming `box-shadow: var(--folia-shadow-*)` lines. `scripts/check-tokens.mjs` asserts the five values against `tokens/source/shadow.tokens.json`.

### 02-27. One animation duration escapes the motion tokens

- **Folia:** `src/styles.css:181` — `animation: folia-toast-in 220ms var(--folia-ease)` — while `--folia-dur-fast: 110ms` and `--folia-dur: 170ms` sit in the token block at `50-51` and every other animation and transition in the file uses them.
- **Obsidian:** no motion or duration variable is documented anywhere in `Reference/CSS variables/`, so the token layer itself is Folia's to own; the divergence is internal.
- **Differs:** one surface animates at a duration nothing else can reach, and the audit cannot see it because it has no duration detector (02-10). It is the only raw duration in the file besides the `0.01ms` in the reduced-motion block.
- **Read:** **clear win** — either use `--folia-dur`, or add a `--folia-dur-slow` token so the value has a home.

## Component and utility classes

### 02-28. Thirteen `cursor: pointer` declarations against Obsidian's explicit no-pointer convention

- **Folia:** thirteen `cursor: pointer` declarations in `src/styles.css` — filter chips (`243`), suggestion items (`297`), swatches (`558`), menu items (`592`), priority and column chips (`647`, `675`), the add-column tile (`696`), the column add button (`489`), buttons (`1182`), icon buttons (`1221`), links (`1781`), the parent reference (`932`), the subitems toggle (`1113`).
- **Obsidian:** "Obsidian follows operating system conventions for cursors, which means interactive elements use the arrow cursor instead of the pointer cursor", with `--cursor: default` for interactive elements and `--cursor-link: pointer` reserved for links (`developer-docs: Reference/CSS variables/Foundations/Cursor.md`).
- **Differs:** the board is the one region of the window where the cursor turns into a hand over a button. Of the thirteen, only `.folia-link` is a link in Obsidian's sense and would keep `pointer` (as `var(--cursor-link)`); the other twelve are controls, where the app's convention is the arrow. Folia does route the cursors it invents itself correctly (`grab`/`grabbing` on draggables, `col-resize` on the handle, `help` on the missing-link marker, `text` on the description view), so this is specifically the pointer-on-controls case. Three rules go the other way and write `cursor: default` literally (`600`, `708`, `826`) — the documented default value of `--cursor`, spelled out instead of read.
- **Read:** **clear win** — a mechanical substitution to `var(--cursor)` and `var(--cursor-link)`, zero layout risk, and it is the single most visible "this plugin is not part of the app" tell in the whole stylesheet. The counter-argument (users expect a hand on clickable things) is exactly the one the Obsidian doc answers, and the variable leaves the choice with the theme in either case.

### 02-29. Every input suppresses the focus outline and redraws its own ring

- **Folia:** eight `outline: none` declarations in `src/styles.css` (`224`, `540`, `720`, `1264`, `1476`, `1858`, `2087`, `2197`). Six are paired directly with `border-color: var(--folia-accent)` and `box-shadow: var(--folia-ring)`; line `224` sits on the base `.folia-search input` rule, with the ring supplied one level up by `.folia-search:focus-within` (`214-217`); and line `2197`, on `.folia-column-title-input:focus`, suppresses the outline and adds nothing, so focus is **not distinguished from rest** — the field's base rule (`2185-2195`) already carries an accent border, and focusing it changes nothing. The ring is `0 0 0 2px color-mix(in srgb, var(--folia-accent) 30%, transparent)` (`67`). Separately, `.folia-scope :focus-visible` draws a `2px` accent outline at `2px` offset over everything else (`1938-1942`), with pill-shaped exceptions (`1948-1952`) and a column-coloured variant on the column title (`2166-2170`).
- **Obsidian:** `--background-modifier-border-focus` is documented in the variable reference itself as "Border color (focus)" (`developer-docs: Reference/CSS variables/Foundations/Colors.md#Surface colors`) — the exact property the six paired rules set to `var(--folia-accent)`. Beyond it, `--input-focus-border-color` and `--input-focus-outline` are the variables the app uses for the outline, and the theme documentation shows them declared on `:root` with system-keyword defaults (`--input-focus-border-color: Highlight; --input-focus-outline: 1px solid Canvas;` — `developer-docs: Themes/App themes/Build a theme.md`, step 6, and repeated in `Themes/App themes/Theme guidelines.md#Use CSS variables`). `Highlight` and `Canvas` are the operating system's own focus colours.
- **Differs:** Folia's focus indication is the plugin's accent, always, at a fixed 2px. Obsidian's default resolves to the OS highlight colour, which is what a user running a high-contrast or forced-colours mode has configured their machine to use for focus. Suppressing `outline` and substituting a `box-shadow` is also the specific pattern that disappears entirely under forced-colours rendering, where box shadows are dropped and outlines are not. Folia's `:focus-visible` rule is a genuine strength — the plugin has one, applies it everywhere, and rounds it per shape — so this is about which colour and which property, not about whether focus is visible.
- **Read:** **trade-off** — adopting `--background-modifier-border-focus` for the border and `--input-focus-outline` for the outline is close to free and puts focus on the user's own colour, and `.folia-column-title-input` needs a focus state that differs from its resting state either way; keeping the accent ring on the non-input controls is defensible. The forced-colours half deserves its own look and is not something this audit can measure.
- **Guard:** `scripts/check-a11y-exceptions.mjs` polices documented a11y exceptions in the JSX, not computed focus styling; `tracking/waivers/0002-automated-a11y-gate.md` records that there is no automated a11y gate.

### 02-30. The entire button face is rebuilt, and the specificity fight that follows is now a documented hazard

- **Folia:** `src/styles.css:117-137` lists thirteen classes that must be reset to `box-shadow: none` so they do not inherit the theme's raised button face, each named twice to out-specify Obsidian's own rule; `.folia-btn`, `.folia-btn-primary`, `.folia-btn-danger` and `.folia-icon-btn` (`1173-1236`) then rebuild padding, radius, border, background, colour, hover and transition from scratch. `scripts/check-button-styles.mjs` exists solely to keep the doubling honest, and the stylesheet header (`6-12`) explains the trap.
- **Obsidian:** the documented route to a primary button face is the API method `ButtonComponent.setCta()` (`obsidian.d.ts:1346`, used in `developer-docs: Plugins/User interface/Modals.md`), and `--button-radius` is the button's themable radius (`Reference/CSS variables/Components/Button.md`); button colours come from the interactive colour set, `--interactive-normal`, `--interactive-hover`, `--interactive-accent`, `--interactive-accent-hover` (`Foundations/Colors.md#Interactive colors`). What Obsidian's own `app.css` puts on every `button:not(.clickable-icon)` was read directly out of the running 1.13.7 build and matches what Folia records: exactly `color: var(--text-color)`, `background-color: var(--interactive-normal)` and `box-shadow: var(--input-shadow)` on desktop, with `padding` added only under `.is-tablet` (`scripts/check-button-styles.mjs:29-37`), plus `white-space: nowrap` and `height: var(--input-height)` (`src/styles.css:1510-1514`).
- **Differs:** Folia's buttons are a complete parallel implementation, and the cost is not the CSS but the arms race it started: thirteen classes must be reset, every colour rule must be doubled, a bespoke guard script exists to enforce the doubling, and the doubling now out-ranks the plugin's own single-class rules in ways nothing catches. Folia does use `--interactive-accent` (through `--folia-accent`) and `--interactive-accent-hover`, so the accent path is theme-aware; the neutral face is not. `--interactive-normal` and `--interactive-hover` appear nowhere in `src/styles.css` at all, and the neutral interactive face they describe is hand-painted from `--background-primary` plus `--background-modifier-hover` on the filter chip (`238`, `247`), the button (`1180`, `1186`), the add-column tile (`690`, `700`), the column add button (`482`, `494`) and the menu item (`596`) — so this is a divergence across every control the plugin draws, not only the buttons.
- **Read:** **trade-off** — a kanban board legitimately needs denser controls than the app's settings buttons, and `mod-cta` cannot express a chip or a 26px icon button. But three specific pieces are recoverable without touching the design: `--button-radius` for the radius, `--interactive-normal`/`--interactive-hover` for the neutral face, and undoing the theme's inherited `white-space`/`height` once in a shared rule rather than per element, which `src/styles.css:1507-1523` currently does for `.folia-title-value` alone.
- **Guard:** `scripts/check-button-styles.mjs` (the doubling); `scripts/check-portal-scope.mjs` (the token scope those buttons need when portalled).
- **Backlog:** `docs/ai/backlog/20260829.01.doubled-class-rules-silently-out-rank-their-own-neighbours.md` — the doubling beating the plugin's own rules, with three live examples.

## Theme, mobile and accessibility variants

### 02-42. There is no mobile, tablet or touch variant anywhere in the stylesheet

- **Folia:** `src/styles.css` contains exactly one media query, `@media (prefers-reduced-motion: reduce)` at line 2110, and no `is-mobile`, `is-phone` or `is-tablet` selector at all. - **Obsidian:** the app varies its own controls by platform through body classes, observed in Obsidian 1.13.7's `app.css`: 253 rules are keyed on `.is-phone`, 156 on `.is-mobile` and 15 on `.is-tablet` — including the `.is-tablet button:not(.clickable-icon)` padding override Folia already records (`scripts/check-button-styles.mjs:15`, `33-35`), `.is-mobile .clickable-icon` sizing, `.is-mobile .search-row > .clickable-icon` at `var(--touch-size-s)`, and the whole phone treatment of menus and modals described in section 01. `manifest.json:9` sets `"isDesktopOnly": false` explicitly, so the plugin declares itself installable on mobile (`developer-docs: Plugins/Getting started/Mobile development.md#Disable your plugin on mobile devices`), and mobile support is a checklist item in the plugin self-critique (`developer-docs: Obsidian October plugin self-critique checklist.md#Mobile support`).
- **Differs:** the board ships one layout, tuned for a pointer and a wide window, to a plugin that declares itself mobile-capable. The hover-driven affordances are the sharp end: on a phone, the card's quick actions, the column menu button, the description pencil and the comment edit/delete controls are all invisible until something focuses.
- **Read:** **trade-off** — a full mobile layout is a large piece of work with no device harness here, but the hover-driven reveals are a usability problem rather than a styling preference and can be addressed on their own. What would make the full treatment worth it is a decision that the plugin supports phones; if it does not, `isDesktopOnly` says so honestly.
- **Guard:** none — no script or test in the repository exercises a mobile viewport or platform class.

- **Read:** **not worth it** to change — the media query is the right mechanism, and as of 1.13.7 it is the only one. It would become worth revisiting only if a later Obsidian adds an animation-disable class of its own.

## Inline styles

### 02-44. Two inline styles carry a colour; the rest are values CSS cannot know

- **Folia:** thirteen `style=` props exist across `src/ui/*.tsx`. Eleven are values only the runtime has: CSS custom-property passthroughs (`Board.tsx:416` `--folia-col-accent`, `CardItem.tsx:189` `--folia-ctx-color`, `CardDetail.tsx:1735` `--folia-desc-max-h`), measured geometry (`CardDetail.tsx:1260` `panelStyle`, used at `1291`/`1363`/`1436`; `ColumnMenu.tsx:97` and `CardContextMenu.tsx:141` menu `top`/`left` with `visibility: hidden` before measurement), the dnd transform (`Column.tsx:405`), the progress fill percentage (`CardItem.tsx:270`) and the preserved editor height (`CardDetail.tsx:1652`). Two carry a colour: `ColumnMenu.tsx:126` and `ColumnEditModal.tsx:150`, both `style={{ background: c }}` on a palette swatch.
- **Obsidian:** the guideline shows `el.style.color = 'white'` as the counter-example and a class plus a stylesheet rule as the fix (`developer-docs: Plugins/Releasing/Plugin guidelines.md#No hardcoded styling`, lines 317 and 334); the checklist puts it as "Don't assign styles via JavaScript or in HTML" (`developer-docs: Obsidian October plugin self-critique checklist.md:21`), codified as the ESLint rule `obsidianmd/no-static-styles-assignment` ("Disallow setting styles directly on DOM elements, favoring CSS classes instead", enabled in `recommended` — `eslint-plugin/docs/rules/no-static-styles-assignment.md`). Obsidian's own API path for the legitimate cases is `setCssStyles(styles)` / `setCssProps(props)` (`obsidian.d.ts:105-106`, and again at `117-118`). Conditional styling is documented as `element.toggleClass('danger', status === 'error')` (`developer-docs: Plugins/User interface/HTML elements.md#Conditional styles`).
- **Differs:** the rule and the guideline both target *static* styling assigned from code, which is not what eleven of these are — a measured pixel width or a user-chosen accent has no static class to be. React's `style` prop is also a third mechanism that neither the rule (which matches `el.style.x =` assignment) nor `setCssStyles` covers, so the local `pnpm obsidian:scan` reproduction would not flag any of them. The two swatch fills are the only genuine colour-from-code case, and they render eight user-choosable palette values that cannot be enumerated as classes without generating eight rules from the same array.
- **Read:** **trade-off**, and a mild one — the swatch fills could become a `--folia-swatch-color` custom property set inline and consumed by a class rule, which is the same passthrough shape as the other eleven and moves the last literal colour out of the components. Everything else here is correct as it stands.
- **Guard:** `scripts/obsidian-scan.mjs` runs the community-directory ESLint and Stylelint passes locally, including `obsidianmd/no-static-styles-assignment`; `src/ui` is in scope for it.

## Verified live

Checked on 2026-08-29 against the running Obsidian 1.13.7 desktop build (Linux, the repository's `examples` vault) through the Chrome DevTools bridge. The stylesheet was read as `app://obsidian.md/app.css` — the installed build's own file, 3,672 rules, 1,186 of them matching the classes this section asks about — and computed values were read with `getComputedStyle(document.body)`. This is an observation of one shipped build, not an API guarantee.

- Every class this section names exists in `app.css` with the behaviour its name implies, except `mod-muted`, which matches no rule and is not an Obsidian class. Rule counts: `clickable-icon` 52, `mod-cta` 12, `mod-warning` 6, `is-active` 68, `is-disabled` 19, `checkbox-container` 31, `search-input-container` 42, `tree-item` 80, `setting-item` 141, `suggestion-` 85, `menu` 53, `modal` 218, `prompt` 21, `nav-` 42, `dropdown` 22, `slider` 19, `tooltip` 56, `status-bar` 15, `markdown-rendered` 95, `u-pop` 1.
- `.clickable-icon` gives an element the full interactive treatment for free: `var(--clickable-icon-radius)` and `var(--cursor)`, a `@media (hover: hover)` hover that paints `var(--background-modifier-hover)` and switches to `var(--icon-color-hover)`, an `:active` and a `.has-active-menu` state at `var(--icon-color-focused)`, an `.is-active` state at `var(--icon-color-active)`, a `:focus-visible` ring of `0 0 0 3px var(--background-modifier-border-focus)`, an `[aria-disabled="true"]` treatment at 0.4 opacity, a `.mod-warning` variant, and separate `.is-mobile` transition and touch sizing.
- `button.mod-cta` sets `background-color: var(--interactive-accent)` and `--text-color: var(--text-on-accent)`, with hover, focus-visible and `.mobile-tap` states, and composes with `.mod-destructive` for the error colour; `button.mod-warning` paints `var(--background-modifier-error)` and is re-styled again under `.is-mobile`. `.checkbox-container` is the toggle: `.is-enabled`, `.is-disabled`, a `:focus-visible` outline and a thumb animation, sized from `--toggle-*`.
- `--font-monospace` is declared on `body` as `var(--font-monospace-override), var(--font-monospace-theme), var(--font-monospace-default)` and computes to the user's monospace font ahead of the platform stack, so `src/styles.css:304` names the right variable and its `monospace` fallback is unreachable.
- The `--layer-*` values in the running build match what this section cites (`cover: 5`, `sidedock: 10`, `status-bar: 15`, `popover: 30`, `slides: 45`, `modal: 50`, `notice: 60`, `menu: 65`, `tooltip: 70`, `dragged-item: 80`), and `--background-modifier-form-field` computes to `#2e2e2e` in the current theme. Folia's portalled `.folia-menu` sits in the document body as a `position: fixed` sibling of `.app-container` at `z-index: 60`, in the same root stacking context as Obsidian's own overlays, so the numeric collisions in 02-25 are real comparisons; Obsidian's tooltip (70) was seen drawing over that open menu ([`assets/03-tooltip-over-folia-menu.png`](./assets/03-tooltip-over-folia-menu.png)).
- `prefers-reduced-motion` appears nowhere in `app.css` or `app.js`, and the bundled interface strings contain no reduce-motion setting, so 02-43's premise holds: there is nothing else to use.
- The sRGB versus OKLCH mixing gap was measured by rasterising both forms of each mix through a canvas. Mixing into `transparent` is identical in the two spaces at 7%, 20%, 55%, 60% and 92% — which covers 39 of Folia's 54 mixes. For the fifteen that mix two opaque colours the largest per-channel difference was 10 of 255 (at 55–60% of `--color-red` into `--text-normal`), falling to 2–6 at the ends of the range. 02-09 was rewritten around this.
