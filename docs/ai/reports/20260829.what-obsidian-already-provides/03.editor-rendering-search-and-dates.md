# Editor, rendering, search and dates

This section covers Folia's rendered Markdown, card-link navigation, board filtering and suggestion matching, plus its hand-written date and unread-comment clock logic. Four of the nine findings below turned out to be the same gap another section owns from the side of the facility itself — suggestions (01-06), link navigation and hover preview (05-02, 05-03) and link resolution (04-01) — so they keep their ids and their bodies are a cross-reference plus whatever this section established that the primary lacked, which has been moved into the primary as well. It read `src/ui/Markdown.tsx`, `src/ui/cardView.ts`, `src/ui/CardDetail.tsx`, `src/ui/CardItem.tsx`, `src/model/fences.ts`, `src/ui/Toolbar.tsx`, `src/ui/App.tsx`, `src/ui/Board.tsx`, `src/model/properties.ts`, `src/obsidian/propertySuggest.ts`, `src/model/priorities.ts`, `src/model/dates.ts`, `src/model/unread.ts`, `src/model/board.ts`, and the vault adapter.

## Editor and rendered Markdown

### 03-01. The toolbar reimplements Obsidian input suggestions — covered by 01-06

- Same gap as 01-06, which owns `AbstractInputSuggest` and counts all five suggesting inputs in the plugin, of which the toolbar box is the largest. `src/ui/Toolbar.tsx:59` (`suggestionsFor`) and `:96` (`Toolbar`) implement token completion, listbox state, arrow/Enter/Tab/Escape handling, pointer selection and the popup's blur lifecycle around a controlled React input; `AbstractInputSuggest` (`obsidian.d.ts:287`, `:325`, `:330`, with a public `limit`) supplies all of it except the caret-aware replacement and the custom result layout. `src/obsidian/propertySuggest.ts:20` is the working proof that the controlled-input bridge is possible. See also 06-10 for the same box read from the interaction side.

### 03-02. Direct note opening bypasses standard link navigation — covered by 05-02

- Same gap as 05-02, which owns leaf targeting and traces the click through all five signatures between the card and the leaf. `src/obsidian/vaultRepo.ts:658` (`openCard`) opens a known `TFile` through `app.workspace.getLeaf(false).openFile(...)`, and the "Open note" call sites drop the click event, so `Keymap.isModEvent` (`obsidian.d.ts:3661`) never reaches `getLeaf` or `openLinkText` (`obsidian.d.ts:7914`). The caveat this section added and 05-02 now records: the change belongs to the external "Open note" buttons only, not to Folia's in-panel navigation for relationship and subcard rows.

### 03-03. Card links do not participate in Obsidian page preview — covered by 05-03

- Same gap as 05-03, which owns `Plugin.registerHoverLinkSource` and spells out both halves of the fix. The link-bearing React sites this section identified are now listed there: `RelationRow` (`src/ui/CardDetail.tsx:564`), the subcard link rendering (`:1793`) and the card face's "Open note" action (`src/ui/CardItem.tsx:388`). `developer-docs: Plugins/Guides/Build a Bases view.md#Step 4: Display list items` is the guide that shows a custom view emitting `hover-link` and implementing `HoverParent`.

## Search, sorting and fuzzy matching

### 03-04. Folia parses card-link targets instead of using Obsidian's resolver — covered by 04-01

- Same gap as 04-01, which owns `MetadataCache` and goes further: it establishes that Folia has no `sourcePath` at all, never consults `aliases`, and can only see cards inside the board's card folder, and it names the fix shape (resolve in the adapter, keep the "must be a card on this board" filter as a second step in the model). The point this section added and 04-01 now records: `parseLinktext` (`obsidian.d.ts:4793`) exposes only a path and a subpath, so alias extraction stays Folia's work under either route.

### 03-05. Property-name suggestions use substring matching instead of Obsidian's fuzzy result model

- **Folia:** `src/model/properties.ts:152` (`propertySuggestions`) lowercases each candidate and keeps it when `lower.includes(needle)`, preserving Folia, board and vault group order. `src/obsidian/propertySuggest.ts:20` then supplies those rows to `AbstractInputSuggest`.
- **Obsidian:** `prepareFuzzySearch(query)` returns a callback whose `SearchResult` carries a score and match ranges (`obsidian.d.ts:5252`, `obsidian.d.ts:5595`, `obsidian.d.ts:5597`); `renderMatches` and `renderResults` render those ranges (`obsidian.d.ts:5416`, `obsidian.d.ts:5428`). The API changelog says the older `fuzzySearch` function was removed in 1.7.2 and plugins should use `prepareFuzzySearch` (`CHANGELOG.md:17`).
- **Differs:** Folia only accepts contiguous, case-insensitive substrings and does not rank or mark the matching characters. A fuzzy search could find a partially typed property name and show why it matched, but Folia would have to apply it per group so its deliberate group order, deduplication and exclusions survive.
- **Read:** **trade-off** — native fuzzy matching makes a long vault's property vocabulary easier to search, while the current exact-substring rule is predictable and keeps Folia's curated order. It becomes worthwhile when users report difficulty finding properties by partial or non-contiguous input.

### 03-06. The board's query grammar should remain its own matcher

- **Folia:** `src/ui/cardView.ts:388` (`parseFilter`) parses quoted free text and Folia tokens such as `due:`, `assignee:` and `unread:`. `matchCard` at `src/ui/cardView.ts:545` ANDs those semantic predicates with a case-insensitive substring search; filter lanes and the toolbar share the result. `src/ui/Toolbar.tsx:59` adds grammar-aware key and value completion.
- **Obsidian:** `prepareSimpleSearch(query)` creates a matcher for space-separated words, while `prepareFuzzySearch` provides scored fuzzy matching (`obsidian.d.ts:5252`, `obsidian.d.ts:5260`). `SearchComponent` supplies an input and clear button (`obsidian.d.ts:5558`).
- **Differs:** Obsidian's matchers do not know Folia's token grammar, board-specific state such as unread replies, or the requirement that a filter lane and the visible-card tally use exactly the same predicate. `SearchComponent` could replace only the input while leaving that grammar intact, but it would not supply Folia's contextual completion list and needs React controlled-input plumbing.
- **Read:** **not worth it** — the matcher should stay domain-specific, and the native input alone does not remove the toolbar's custom completion work. Revisit the input separately if 01-06 adopts `AbstractInputSuggest` for the toolbar box; 01-12 covers the search field's own chrome against `SearchComponent`.

## Dates, times and locale

### 03-07. Relative due dates use hand-written calendar arithmetic

- **Folia:** `src/ui/cardView.ts:221` (`dayDelta`) parses two `YYYY-MM-DD` values with `Date.parse` at local midnight and divides their milliseconds difference by one day. `dueInfo` at `src/ui/cardView.ts:236` turns that result into the user-facing labels "Yesterday", "Today", "Tomorrow", `in Nd` and `Nd ago`.
- **Obsidian:** Obsidian exports its bundled `moment` instance (`obsidian.d.ts:4561`). The developer guide identifies Moment as a library for date and time work and says a plugin can import it from `obsidian` without adding another copy (`developer-docs: Plugins/Events.md#Date and time`).
- **Differs:** Folia owns both the calendar calculation and the product-specific urgency labels. Using the bundled date-time library would move the parsing and date calculation out of `cardView`, while Folia would still own the labels and urgency thresholds.
- **Read:** **trade-off** — date arithmetic deserves a dedicated date-time library if this logic grows, but the current function is short and the labels are necessarily Folia-specific. It becomes a clear win when due dates gain more accepted input forms or any configurable calendar behaviour. The two calls it would use were exercised in the running app (Moment 2.30.1, see "Verified live"): `moment(value, "YYYY-MM-DD", true)` in strict mode rejects a date that does not exist, and `moment(a).isSame(b, "day")` is the whole-day comparison `dayDelta` open-codes.

### 03-08. Date strings reimplement formatting exposed by Obsidian's bundled Moment

- **Folia:** `src/model/dates.ts:7` (`dateOnly`) and `src/model/dates.ts:11` (`stamp`) manually assemble `YYYY-MM-DD` and `YYYY-MM-DD HH:mm` with `Date` getters and zero-padding.
- **Obsidian:** Obsidian exports its bundled `moment` instance (`obsidian.d.ts:4561`). The developer guide explicitly says plugins can import it from `obsidian` instead of adding another copy, and shows `moment().format(...)` for date formatting (`developer-docs: Plugins/Events.md#Date and time`).
- **Differs:** Folia owns two fixed output formats instead of calling `moment().format(...)`. Both routes produce the local, timezone-free strings its stored note format expects.
- **Read:** **not worth it** — the two small functions are easier to read than adding a formatting abstraction, and they do not add a dependency. Revisit if the plugin gains configurable date formats or needs several date representations.

### 03-09. Unread-comment ordering uses local, timezone-free timestamps by design

- **Folia:** `src/model/dates.ts:11` (`stamp`) writes minute-resolution local timestamps without an offset. `src/model/unread.ts:78` (`sortKey`) pads digit runs; callers such as `seenMarker` at `src/model/unread.ts:101` and `unreadComments` at `src/model/unread.ts:154` compare the normalized strings to decide which comments are unread.
- **Obsidian:** Obsidian exposes its bundled `moment` instance for date and time work (`obsidian.d.ts:4561`; `developer-docs: Plugins/Events.md#Date and time`).
- **Differs:** Folia's note grammar and read markers deliberately store plain local timestamps. Replacing that with a timezone-aware representation would require changing the parser, ordering and every existing note's compatibility story.
- **Read:** **decided** (`docs/decisions.md#Unread-comment ordering assumes one clock`) — same-clock writers are the supported case. Revisit only after an observed cross-timezone failure, not as a mechanical Moment migration.

## Checked and found aligned

- `src/ui/Markdown.tsx:21` delegates rendering to the repository, while `src/obsidian/vaultRepo.ts:662` loads a `Component`, passes it to `MarkdownRenderer.render`, and unloads it on React cleanup, so embeds and post-processors have a managed lifecycle (`obsidian.d.ts:1842`, `obsidian.d.ts:1855`, `obsidian.d.ts:4147`).
- `src/obsidian/propertySuggest.ts:20` already uses Obsidian's `AbstractInputSuggest` for property names; `src/model/properties.ts:152` only owns the domain-specific candidate list.
- `src/ui/cardView.ts:214`, `src/model/board.ts:195`, and `src/obsidian/vaultRepo.ts:712` use `localeCompare` rather than hard-coded locale ordering. There is no hand-written localized date or number formatter to replace with `getLanguage`.
- `src/model/fences.ts:36` protects Folia's structural Markdown parser from code fences; the public API exposes rendering and post-processing, not a public Markdown syntax parser that could replace this model rule.

## Unverified

- `MarkdownEditView` accepts a `MarkdownView` in its public constructor (`obsidian.d.ts:3906`), but this audit did not find a public API for hosting an Obsidian editor inside Folia's React detail panel. The documented one-tab editor decision remains the controlling evidence for those textareas.
- Which strict-parse and formatting calls are the right *prescription* for finding 03-07 is now demonstrable (below), but no source read here documents Obsidian's own conventions for them, so the finding still stops at "this is available", not "do it this way".

## Verified live

Checked on 2026-08-29 against the running Obsidian 1.13.7 desktop build with the repository's `examples` vault open, through the Chrome DevTools bridge.

- Obsidian's bundled Moment is 2.30.1 and is reachable in the app as the global `window.moment`. Strict parsing behaves as 03-07 would need: `moment("2026-02-30", "YYYY-MM-DD", true).isValid()` is `false`, and the whole-day comparison `moment("2026-08-29T23:00").isSame(moment("2026-08-29T01:00"), "day")` is `true`. The app's Moment locale is `en` with the week starting on Sunday, which is the locale a plugin inherits unless it sets its own.
- The daily-notes core plugin is present and enabled but exposes no public interface: it is reachable only as `app.internalPlugins.getPluginById("daily-notes").instance`, whose `options` object holds the user's date format and is `{}` when the user has never changed it — none of which is in the typings. Folia's `dateOnly` format therefore has no supported daily-note format to defer to, and the first Unverified item from the source pass is settled as a genuine absence rather than a gap in this audit's reading.
