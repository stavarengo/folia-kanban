# Vault, files and metadata

Everything Folia does for itself around files, paths, YAML, frontmatter, links, tags and file events, set against what `Vault`, `FileManager`, `MetadataCache` and the exported helper functions already give a plugin. Read for this section: `src/obsidian/vaultRepo.ts`, `src/model/repo.ts`, `src/model/card.ts`, `src/model/cardTitle.ts`, `src/model/board.ts`, `src/model/relationships.ts`, `src/model/fences.ts`, `src/model/pathOps.ts`, `src/model/columns.ts`, `src/model/properties.ts`, `src/model/schemas.ts`, `src/boardNote.ts`, `src/obsidian/mcpService.ts` and `src/mcp/tool.ts` where they look files up, `src/ui/cardView.ts` (its tag reading), the vault-touching parts of `src/main.ts`, `test/obsidianFake.ts`, `package.json`, `esbuild.config.mjs`, `eslint.config.mjs` and `.dependency-cruiser.cjs`.

One architectural fact governs half the verdicts below, so it is stated once here rather than repeated in every finding. `src/model/**` and `src/ui/**` are forbidden from importing the `obsidian` package: `eslint.config.mjs:108-121` (`no-restricted-imports`, scoped by that `files:` glob) makes it a hard error, and `.dependency-cruiser.cjs:22` (`model-is-pure-domain`) keeps the model off the adapter, and `.dependency-cruiser.cjs:38` (`mcp-is-a-port-consumer`) fences `src/mcp/**` off the adapter the same way. That is what lets the whole card engine and board build run headlessly under Vitest. So when an in-house routine lives in `src/model/` or `src/ui/`, swapping in the Obsidian call is not a local edit; it means moving the work to the adapter (`src/obsidian/vaultRepo.ts`) and passing the result in. Those are marked **trade-off**, with the alternative fix shape named. Code that already sits in `src/obsidian/vaultRepo.ts` or `src/main.ts` has no such excuse.

Everything cited in the findings below exists at or before the plugin's `minAppVersion` of 1.7.2, so no finding needs a version caveat.

## Links

### 04-01. Wikilink resolution is hand-written and does not follow Obsidian's own resolution rules

- **Folia:** `src/model/board.ts:164` (`linkResolver`), exposed as `boardLinkResolver` (`src/model/board.ts:190`) — builds a basename index over the board's cards and resolves `[[A]]`, `[[A#Notes]]`, `[[A|see this]]` and `[[Sub/A]]` against it, refusing to bind a basename that two cards share. `src/model/relationships.ts:103` (`relationTarget`) and `:116` (`targetIdentity`) strip the brackets with a regex and then the anchor and the alias with two `split` calls (`src/model/relationships.ts:117`); `linkResolver` repeats the same two splits at `src/model/board.ts:174-176`, and `parseSubItem` does it a third time on body wikilinks at `src/model/card.ts:337`.
- **Obsidian:** `MetadataCache.getFirstLinkpathDest(linkpath, sourcePath)` (`obsidian.d.ts:4411`) resolves a linkpath the way the app itself does, from the perspective of the note that holds the link; `getLinkpath(linktext)` (`obsidian.d.ts:3373`) turns a linktext into that linkpath; `MetadataCache.resolvedLinks` and `unresolvedLinks` (`obsidian.d.ts:4438`, `:4444`) hold the whole resolved graph keyed by source path; `parseLinktext(linktext)` (`obsidian.d.ts:4798`), whose public contract exposes only a path and a subpath, so alias extraction stays Folia's either way — "Parses the linktext of a wikilink into its component parts… returns filepath and subpath (subpath can refer either to a block id, or a heading)" — is the exact counterpart of the two splits, and `resolveSubpath(cache, subpath)` (`obsidian.d.ts:5500`) is what resolves the subpath half Folia discards. `CachedMetadata.links?: LinkCache[]` (`obsidian.d.ts:1406`) is the body-link half of the same story, already parsed per note, which `parseSubItem` re-extracts by regex. `parseFrontMatterAliases(frontmatter)` (`obsidian.d.ts:4775`) reads the `aliases` key.
- **Differs:** Folia has no `sourcePath` at all, so wherever Obsidian's "best match for a linkpath" (its whole documented contract, `obsidian.d.ts:4407`) depends on where the link is written from, Folia cannot reproduce it; on a basename two cards share it refuses to bind and the relationship silently disappears from the board. It never consults `aliases`. It only knows cards inside the board's card folder, so a link out to any other note is unresolved by construction. Against that, the restriction to board cards is deliberate and load-bearing: `boardLinkResolver` is what keeps a relationship row from pointing at a note the board cannot show, and the "ambiguous binds to nothing" rule is a documented choice rather than an oversight.
- **Read:** **trade-off** — the Obsidian resolver is the app's own answer to which note a link names, so by construction it cannot disagree with what the user sees, but it lives behind `app`, and this code is in `src/model/`, which cannot reach it. The honest fix is for the adapter to resolve each link with `getFirstLinkpathDest` at load time and hand `buildBoard` resolved paths, keeping the "must be a card on this board" filter as a second step in the model.

### 04-02. Link text is a bare basename in a hard-coded `[[…]]`, so Folia can write a link Folia cannot resolve

- **Folia:** `src/model/card.ts:459` (`addSubcard`) writes `- [ ] [[${link}]]`, with the link text derived as a bare basename by the adapter at `src/obsidian/vaultRepo.ts:567`; `src/model/relationships.ts:125` (`relationLinkText`) writes `[[${relationTarget(target)}]]` into the card's relationship frontmatter, taking whatever target the panel handed it.
- **Obsidian:** `FileManager.generateMarkdownLink(file, sourcePath, subpath?, alias?)` (`obsidian.d.ts:2931`) — "Generate a Markdown link based on the user's preferences", with `sourcePath` used to compute relative links. For the text alone, `MetadataCache.fileToLinktext(file, sourcePath, omitMdExtension?)` (`obsidian.d.ts:4431`) — "If file name is unique, use the filename. If not unique, use full path."
- **Differs:** the basename is the sharp end. `linkResolver` (`src/model/board.ts:164`) refuses to bind a basename two cards share, so the moment a second card anywhere in the folder takes the same file name, a subtask link or relationship Folia itself wrote stops resolving on Folia's own board, with nothing said. `fileToLinktext` is precisely the answer to that — it widens to the full path when the name is not unique — and both write sites are in the adapter with the `TFile` in hand, so nothing blocks it. Separately, Folia always emits a shortest-form wikilink. A vault set to "Markdown links", or to absolute or relative paths, gets links from Folia in a shape nothing else in that vault uses, and the user's own notes and Folia's notes end up written two different ways. The counterweight is that Folia's readers only understand the wikilink form: `WIKILINK_ONLY_RE` (`src/model/card.ts:21`) and `WIKILINK_RE` (`src/model/relationships.ts:96`) both anchor on `[[…]]`, so emitting a Markdown link today would produce a subtask line Folia itself reads as plain text.
- **Read:** **clear win** for the link text: `fileToLinktext` in the adapter removes a way for Folia to break its own links, and needs no change to the readers. **Trade-off** for the link *format*: writer and reader are self-consistent as they stand, and honouring the user's setting means changing both ends, not just the writer. Worth doing if the goal is that a Folia card looks like every other note in the vault; not worth doing piecemeal, because a half-migrated vault is worse than a consistently wikilinked one.

### 04-03. Frontmatter links are re-extracted by regex although the cache already holds them

- **Folia:** `src/model/relationships.ts:156` (`collectStrings`) and `:164` (`readTargets`) walk the raw frontmatter value for a relationship key, flatten nested sequences, and run each string through `relationTarget` (`:103`) to pull the target out of `[[…]]`.
- **Obsidian:** `CachedMetadata.frontmatterLinks?: FrontmatterLinkCache[]` (`obsidian.d.ts:1458`), added in 1.4.0 (`CHANGELOG.md`, v1.4.0 section: "frontmatter now supports wikilinks. If a value in the frontmatter can be interpreted as a link, it will be cached inside `CachedMetadata.frontmatterLinks`"). `FrontmatterLinkCache` (`obsidian.d.ts:3266`) carries the frontmatter `key` alongside the `Reference` fields, so the entries can be grouped by the property that holds them.
- **Differs:** the cache only records values Obsidian recognises as links. Folia deliberately also accepts a bare, unbracketed value (`blocks: Other card`), documented at `src/model/relationships.ts:98-102` as the shape a person actually types — Obsidian would not cache that as a link at all. Folia additionally de-duplicates by what the target names rather than by how it is spelled, which the cache does not do.
- **Read:** **trade-off** — the cache would give correctly parsed links for free and stay right about escaping and edge cases the regex will eventually get wrong, but it would drop the forgiving unbracketed reading, which is a stated product decision. A hybrid (cache first, regex only for values the cache did not claim) is possible but adds a second code path for a small gain.

## YAML and frontmatter

### 04-04. A second YAML parser is bundled into the plugin

- **Folia:** `src/model/card.ts:12` imports `parse` from the `yaml` npm package and uses it in `parseFrontmatter` (`src/model/card.ts:63`). `yaml` is a runtime dependency (`package.json`, `dependencies`), and `esbuild.config.mjs` does not list it in `external`, so it is compiled into `dist/main.js`. Its unminified browser build is 274 KB of JavaScript source (280,106 bytes across the `.js` files under `node_modules/yaml/browser/dist`, 492 KB as the directory occupies on disk). None of those is the shipped delta, which nothing here measured — see "Unverified".
- **Obsidian:** `parseYaml(yaml: string): any` (`obsidian.d.ts:4817`) and `stringifyYaml(obj: any): string` (`obsidian.d.ts:6815`) are exported from the `obsidian` module, which is already `external` in the build.
- **Differs:** the plugin ships and loads its own parser rather than calling the one already resident in the app. Two parsers over the same bytes can disagree — on a value Obsidian's parser accepts and this one rejects (raised as `DataCorruptionError` at `src/model/card.ts:73`), the board refuses to load a card whose frontmatter Obsidian itself reads without complaint, and vice versa. What Folia gets in return is a parser it can call from a pure module, which is what keeps the whole card engine unit-testable without Obsidian.
- **Read:** **trade-off** — the correctness argument (one parser, the app's) and the size argument both point at `parseYaml`, and the only thing standing in the way is the model-purity rule. The fix shape is a parser injected at the adapter boundary: `VaultRepository` passes `parseYaml` in, and the tests pass the `yaml` package, which `test/obsidianFake.ts:15` already imports and which would then move from `dependencies` to `devDependencies`, where its weight costs nothing.

### 04-05. Frontmatter is split off the file with a regex rather than with the offsets Obsidian computes

- **Folia:** `FRONTMATTER_RE` (`src/model/card.ts:18`) and `splitFrontmatter` (`src/model/card.ts:56`) cut the `---` block off the front of the text; every byte-stable body edit is built on that split (`withBody`, `src/model/card.ts:425`).
- **Obsidian:** `getFrontMatterInfo(content): FrontMatterInfo` (`obsidian.d.ts:3344`), added in 1.5.7 (`CHANGELOG.md`, v1.5.7: "There is now a canonical way to find the offsets of where the frontmatter ends and where the content starts in a file"). It returns `exists`, the raw `frontmatter` text, and the `from` / `to` / `contentStart` offsets (`obsidian.d.ts:3250`). The same boundary is also cached per file as `CachedMetadata.frontmatterPosition` (`obsidian.d.ts:1452`, since 1.4.0).
- **Differs:** functionally these agree on well-formed notes; where they can part company is exactly the input nobody tests, since Obsidian's function is by definition the app's own reading of where the block ends. Folia's version returns the block text itself for verbatim passthrough, which `getFrontMatterInfo` supports just as well through `contentStart`.
- **Read:** **trade-off** — a genuine improvement in fidelity for a small change, blocked by the same purity rule as 04-04, and fixable by the same injection. Lower cost than 04-04 because it ships no extra bytes.

### 04-06. Card tags are read only from the `tags` frontmatter key, so body tags never match a filter

- **Folia:** `src/ui/cardView.ts:269` (`tagValues`) reads `frontmatter.area` and `frontmatter["tags"]`, accepting a list or a single string, and feeds the result to the board's `tag:` filter term and the free-text haystack (`src/ui/cardView.ts:416`).
- **Obsidian:** `getAllTags(cache): string[] | null` (`obsidian.d.ts:3332`) — "Combines all tags from frontmatter and note content into a single array". `parseFrontMatterTags(frontmatter)` (`obsidian.d.ts:4790`) covers the frontmatter half alone, and `CachedMetadata.tags` (`TagCache`, `obsidian.d.ts:6965`) is the body half.
- **Differs:** a card that carries its tags in the note body as `#urgent` — the way a large share of Obsidian users tag things — is invisible to Folia's `tag:` filter and its search box, with nothing telling the user why. Obsidian's own tag pane shows those tags on the same note. `parseFrontMatterStringArray(frontmatter, key)` (`obsidian.d.ts:4785`) is the generic form of the list-or-single-string normalisation `tagValues` open-codes, and which `collectStrings` (`src/model/relationships.ts:156`) open-codes a second time for relationship keys; and its behaviour, read from the running app, is exactly that normalisation: a string becomes a one-element trimmed array, an array is filtered to its string members and each is trimmed, anything else returns `null`.
- **Read:** **trade-off** by location only — the substance is a clear behavioural gap worth closing, but `src/ui/cardView.ts` cannot import `obsidian`. The fix is for `VaultRepository.loadBoard` to call `getAllTags` on each card's cache and put the result on the `Card` object, leaving `tagValues` to read a field instead of guessing at frontmatter shapes.

### 04-07. `card-folder` and `card_folder` are looked up by hand where a RegExp key would do

- **Folia:** `src/obsidian/vaultRepo.ts:189` reads `fm["card-folder"] ?? fm["card_folder"]`; `src/obsidian/vaultRepo.ts:191` does the same for `card-title` / `card_title`; `src/boardNote.ts:34` repeats the pattern; `src/model/schemas.ts:46-49` declares all four keys so the schema accepts either spelling.
- **Obsidian:** `parseFrontMatterEntry(frontmatter, key: string | RegExp)` (`obsidian.d.ts:4780`) accepts a RegExp as the key. The declaration is signature-only, but the implementation in the running app settles what it does: with a string key it is an own-property lookup, and with a RegExp it walks the frontmatter's own property *names* and returns the value of the first name the expression matches (read from Obsidian 1.13.7's `app.js`, see "Verified live").
- **Differs:** the hand-written pair only matches the two spellings someone remembered to write down, in the exact case they wrote them. A single `parseFrontMatterEntry(fm, /^card[-_]folder$/i)` covers the whole family, capitalisation included — that is now read from the implementation rather than inferred from the signature, with the caveat that first-match order is property order in the note, so two spellings in one note resolve to whichever was written first. What is certain either way is that five places currently have to be kept in step rather than one. The fifth is the property registry at `src/model/properties.ts:89-90`, which names `card-folder` and `card-title` in the dashed spelling only. Nothing visible breaks because of that — both entries are `scope: "board"`, and the panel's suggestion list is built from `FOLIA_CARD_KEYS` (`src/model/properties.ts:104`), which filters board keys out — but it is one more copy of a fact stated five different ways.
- **Read:** **clear win, small.** The fact this was pending is now in hand: a RegExp key matches property names, so `/^card[-_]folder$/i` replaces the `??` chain and picks up the capitalisations nobody wrote down. The two reads in `src/obsidian/vaultRepo.ts` and the third in `src/boardNote.ts:34` are all eligible — `eslint.config.mjs:108` scopes the `obsidian` import ban to `src/model/**` and `src/ui/**`, and `src/boardNote.ts` is the plugin shell, so none of the three is blocked. The schema in `src/model/schemas.ts` has to name both keys regardless, so this shrinks the duplication rather than removing it.

## Paths and file lookup

### 04-08. The vault's whole Markdown list is walked to find files whose paths are already known

- **Folia:** `src/obsidian/vaultRepo.ts:240` — `this.app.vault.getMarkdownFiles().filter(f => f.path.startsWith(prefix) && …)` to find the notes inside one folder. `src/obsidian/vaultRepo.ts:699` (`propertyNamesInUse`) walks the same full list, though that one genuinely needs every note and is memoised per board load (`:700`, `:717`, invalidated at `:208`), so it runs once per reload rather than per event. The starkest instance is `src/obsidian/mcpService.ts:59` (`vaultBoardHost.repoFor`): `app.vault.getMarkdownFiles().find((f) => f.path === boardPath)` — a whole-vault walk to find one note whose exact path the caller already supplied.
- **Obsidian:** `Vault.getFolderByPath(path): TFolder | null` (`obsidian.d.ts:7360`) plus `TFolder.children` (`obsidian.d.ts:7141`) or the static `Vault.recurseChildren(root, cb)` (`obsidian.d.ts:7537`) walk one subtree. The guideline is explicit: developer-docs `Plugins/Releasing/Plugin guidelines.md#Avoid iterating all files to find a file by its path` — "This is inefficient, especially for large vaults."
- **Differs:** at `src/obsidian/mcpService.ts:59` there is nothing to weigh: `Vault.getFileByPath(boardPath)` returns the same file in one lookup, and the guideline's own "Don't do this" example is the same shape down to the `find(file => file.path === filePath)` predicate (`Plugin guidelines.md`, same section; it writes `getFiles`, Folia writes `getMarkdownFiles`). For the two folder scans, the cost is proportional to the vault, not to the board. `loadBoard` already re-reads the folder's config and every card body on each reload, and `onChange` (`src/obsidian/vaultRepo.ts:751`) fires that reload — see 04-09 — so in a large vault the whole-vault scan runs repeatedly during ordinary editing. `loadContexts` (`src/obsidian/vaultRepo.ts:282`) shows the shape that avoids it: it takes the folder and walks `root.children`. `propertyNamesInUse`, `findBoards` (`src/main.ts:495`) and `listBoards` (`src/obsidian/mcpService.ts:52`) genuinely need every note and are not what this finding asks to change; `findBoards` says so in a comment (`src/main.ts:496`). The last two are also the same walk with the same `isBoardFrontmatter` predicate written twice — an in-house duplication rather than an Obsidian gap, but worth collapsing at the same time.
- **Read:** **clear win** — `src/obsidian/mcpService.ts:59` is a one-line swap to `getFileByPath` with no argument against it; for `loadBoard`, the code is in the adapter, `getFolderByPath` returns exactly the root it wants, and `loadContexts` already proves the pattern in the same class.
- **Guard:** `eslint-plugin-obsidianmd`'s `vault/iterate` rule codifies this guideline and runs inside the recommended preset that `scripts/obsidian-scan.mjs` reproduces, but its AST matcher only fires on `vault.getFiles().find(f => f.path === X)` (`refs/eslint-plugin/lib/rules/vault/iterate.ts`). Its matcher requires the callee object to be an identifier literally named `vault`, so it sees neither the `getMarkdownFiles().filter(startsWith)` shape nor — despite the near-identical code — the `app.vault.getMarkdownFiles().find(f => f.path === X)` at `src/obsidian/mcpService.ts:59`. The guard names the guideline and catches none of Folia's three instances.

### 04-09. Any change anywhere in the vault reloads the entire board

- **Folia:** `src/obsidian/vaultRepo.ts:766` subscribes to `vault.on("modify" | "create" | "delete" | "rename")` and calls `fireVault(f.path)` (`:757`), which only checks the path against the plugin's own recent-writes guard before scheduling a full `loadBoard`. Nothing filters by the board note or the card folder.
- **Obsidian:** the same events carry the `TAbstractFile` that changed, and `MetadataCache.on('changed', (file, data, cache) => …)` (`obsidian.d.ts:4453`) carries the file and its freshly indexed cache. Both give the plugin everything it needs to ignore a file that is not this board's business.
- **Differs:** typing in an unrelated note in the vault schedules a board reload, which is a full-vault Markdown scan (04-08) plus a `cachedRead` of every card in the folder. The board is correct, just doing the work for nothing. The plugin already has the two predicates it would need — the board path, and the resolved card-folder prefix `loadBoard` computes at `src/obsidian/vaultRepo.ts:239`.
- **Read:** **clear win** — a path check in `fireVault` before scheduling. The one thing to be careful about is a rename that moves a note *into* the card folder, where the incoming path is the one to test, and a delete, where the old path is.
- **Backlog:** `docs/ai/backlog/20260828.02.board-loads-can-land-out-of-order.md` — the same reload path, from the other side: fewer reloads also means fewer chances for two of them to land out of order, though it does not fix the ordering hazard itself.

### 04-10. `getAbstractFileByPath` plus an `instanceof` check where `getFileByPath` / `getFolderByPath` exist

- **Folia:** eight call sites. Five narrow the result with `instanceof`: `src/obsidian/vaultRepo.ts:123` (`file`), `:170` (`isFolder`), `:223` (`loadBoard`'s folder check), `:286` (`loadContexts`) and `src/main.ts:341` (`shouldOpenAsBoard`). Three only test for presence: `src/obsidian/vaultRepo.ts:531` (`uniquePath`), `:538` (`ensureFolder`) and `src/main.ts:490` (`exists`).
- **Obsidian:** `Vault.getFileByPath(path): TFile | null` (`obsidian.d.ts:7351`) and `Vault.getFolderByPath(path): TFolder | null` (`obsidian.d.ts:7360`), added in 1.5.7 for exactly this. The changelog entry names the pattern: "Instead of using `getAbstractFileByPath` then checking if the result is an instance of `TFile` or `TFolder`, now you can just use `getFileByPath` or `getFolderByPath` to automatically do this check" (`CHANGELOG.md`, v1.5.7). The same advice is in developer-docs `Plugins/Releasing/Plugin guidelines.md#Avoid iterating all files to find a file by its path`.
- **Differs:** for the five narrowing sites, behaviourally nothing — it is a line of boilerplate each. The three presence checks are a different matter and must stay generic: all three ask "is anything at this path", and the typed accessors answer `null` for the wrong kind. `uniquePath` would hand back a colliding path if a *folder* named `Name.md` sat there, and `ensureFolder` would call `createFolder` over a *file*. The guidelines bless exactly that reading: "If you aren't sure if the path provided is for a folder or a file, use…" (developer-docs `Plugins/Releasing/Plugin guidelines.md#Avoid iterating all files to find a file by its path`).
- **Read:** **clear win**, small — five of the eight sites, mechanical, removing the `instanceof` narrowings that make the adapter's control flow noisier than it needs to be. The other three are correct as they are. One of the five has a better target still: `shouldOpenAsBoard` (`src/main.ts:340`) looks the file up only to hand it to `resolveMode` (`:334`), which uses it for nothing but `getFileCache` — `MetadataCache.getCache(path)` (`obsidian.d.ts:4422`) answers both in one call from the path.

### 04-11. Paths are taken apart with string surgery where a `TFile` is already in hand

- **Folia:** `src/obsidian/vaultRepo.ts:567` — `(childPath.split("/").pop() ?? "").replace(/\.md$/i, "")` to get a basename; `src/obsidian/vaultRepo.ts:648` uses `file.parent?.path` correctly. The pure helpers `parentFolder` / `baseName` live at `src/model/pathOps.ts:56` and `:62`, with a third copy of `parentFolder` at `src/model/board.ts:58`.
- **Obsidian:** `TFile.basename` (`obsidian.d.ts:7123`) and `TFile.extension` (`:7128`), `TAbstractFile.name` (`:6952`) and `TAbstractFile.parent` (`:6957`).
- **Differs:** at `src/obsidian/vaultRepo.ts:567` the file was created two lines earlier — `createCard` (`:543`) has the `TFile` from `vault.create` and returns only its path — so returning the file instead would let the caller read `.basename`. The sibling case at `src/main.ts:443` looks the same and is not: `createBoard` (`src/main.ts:438`) derives the title from the path *before* the file exists, because the title goes into the file's body, so there is no `TFile` to ask. The `src/model/pathOps.ts` copies are a different case and are not the same finding: they operate on the path strings in a rename or delete event, including paths whose file no longer exists, where there is no `TFile` to ask.
- **Read:** **clear win** for the one adapter site; the `src/model/pathOps.ts` helpers stay, since `TFile` navigation cannot answer for a path that has been deleted. The duplicated `parentFolder` in `src/model/board.ts:58` is a plain in-house duplication, not an Obsidian gap.

## Reading, writing and events

### 04-12. Subtask and comment edits apply a line index taken from an earlier read, with no check inside the write

- **Folia:** `src/obsidian/vaultRepo.ts:447` (`toggleSubtask`), `:458` (`removeSubtask`), `:435` (`updateComment`), `:439` (`removeComment`) and `applyMove`'s subtask branch (`:373`) each take an `index` produced by an earlier board or body read and apply it inside `editBody` → `vault.process` (`src/obsidian/vaultRepo.ts:358`). Nothing in the callback checks that the text it is handed still has the item that index meant. The MCP `set_subtask_done` tool (`src/mcp/cardTools.ts:374`) is the same shape at a higher rate: it locates the subtask by `args.index` against a `readBody` snapshot at `:388` and then writes.
- **Obsidian:** developer-docs `Plugins/Vault.md#Asynchronous modifications` is explicit — "Remember to check that the `data` in the `process()` callback is the same as the data returned by `cachedRead()`. If they aren't the same, that means that the file was changed by a different process, and you may want to ask the user for confirmation, or try again." `Vault.process` (`obsidian.d.ts:7510`) gives the atomicity but cannot supply the check.
- **Differs:** `vault.process` guarantees nobody writes between the read and the write, which is not the same as guaranteeing the index still points at the same line. If the note changed after the board read — a hand edit, a sync, another plugin — the index quietly names a different item, and the tick, the status change or the deletion lands on the wrong line. The codebase already knows the rule: `applyMove`'s parent-lines branch (`src/obsidian/vaultRepo.ts:393-411`) re-derives `pendingSubcardLinks` *inside* the callback and matches by link rather than by position, with a comment explaining that it is looked up twice on purpose.
- **Read:** **clear win** — correctness, in the adapter, with the pattern already written a few dozen lines above. Matching by the item's own text (as `setSubcardDone` matches by link) or bailing when the line no longer looks like what the caller described both close it. An agent driving `set_subtask_done` in a loop is the case most likely to hit it, since it can fire faster than a person can.

### 04-13. Every frontmatter write re-serialises the whole block, and the plugin routes around it by hand

- **Folia:** `src/obsidian/vaultRepo.ts:582` (`rememberPriorities`) reads the board note, decides whether a write is needed, and only then opens `processFrontMatter` — with a comment at `:584-588` stating why: `processFrontMatter` rewrites the whole block whether or not the callback changed anything, so a no-op callback still reflows other properties (it drops the quotes from `filter: "priority:a"`). Every other write path takes the reflow: `writeFrontmatter` (`:327`), `unsetFrontmatterKey` (`:348`), `editRelations` (`:473`), `setColumns` (`:572`), `createCard` (`:551`).
- **Obsidian:** `FileManager.processFrontMatter(file, fn, options?)` (`obsidian.d.ts:2954`) is the blessed route — developer-docs `Plugins/Releasing/Plugin guidelines.md#Prefer FileManager.processFrontMatter to modify frontmatter of a note`: "Instead of extracting the frontmatter of a note, parsing and modifying the YAML manually you should use the `processFrontMatter` function."
- **Differs:** here the in-house work is the *avoidance* of a lossy Obsidian route, not a replacement for a good one. Obsidian's function re-serialises the whole block, which the guideline itself sells as the point — "It will also ensure a consistent layout of the YAML produced" (developer-docs `Plugins/Releasing/Plugin guidelines.md#Prefer FileManager.processFrontMatter to modify frontmatter of a note`) — so key order, quoting style and flow-versus-block layout are not preserved across a call; the typings (`obsidian.d.ts:2954`) promise nothing either way; Folia's answer is a read-decide-then-write dance in one place and acceptance everywhere else. The byte-stability contracts elsewhere in the codebase exist for the same reason — `serializeColumns` (`src/model/columns.ts:111`) emits only non-default keys so a board that gained no new fields serialises to the same shape it had before.
- **Read:** **not worth it** to change, because the current arrangement is already the right one — but it is decided in practice and not in writing: `docs/decisions.md` has no entry for it, and the trade-off is recorded only as a code comment at `src/obsidian/vaultRepo.ts:584`. Keeping `processFrontMatter` is right (hand-editing YAML is what the guideline forbids); what is missing is the decision written down where the next reader of a noisy diff will find it.
- **Backlog:** `docs/ai/backlog/20260829.04.override-title-commit-rewrites-unrelated-frontmatter-lines.md` asks for exactly the fact this finding establishes — the entry says the whole-block re-serialisation is "worth verifying as fact". The documentary evidence is the guideline itself, which sells the reflow as a feature: "It will also ensure a consistent layout of the YAML produced" (developer-docs `Plugins/Releasing/Plugin guidelines.md#Prefer FileManager.processFrontMatter to modify frontmatter of a note`). `obsidian.d.ts:2954` is a bare signature and says nothing about it, and the comment at `src/obsidian/vaultRepo.ts:584-588` is the plugin authors' own observation, not a source. `docs/ai/backlog/20260829.05.mcp-cannot-write-a-list-valued-property.md` is the other end of the same surface: `processFrontMatter` hands the callback plain JS values and will happily take an array back, so the scalar-only limit is Folia's tool schema, not an Obsidian one.

### 04-14. The board's own writes are filtered out of the event stream by a wall-clock window

- **Folia:** `src/obsidian/vaultRepo.ts:102` (`recentWrites`) and `:134` (`markWrite`) stamp a path before each write; `fireVault` (`:757`) drops a vault event for a path written in the last 2500 ms, and `onChange` debounces the survivors by 150 ms (the timer at `:755`). A `metadataCache.on("changed")` subscription (`:774`) re-schedules a reload for those same recently written paths, because the cache catches up a tick after the write.
- **Obsidian:** there is no echo-suppression facility in the API. The 150 ms debounce beside it does have one: `debounce(cb, timeout?, resetTimer?)` (`obsidian.d.ts:2232`) returns a `Debouncer` with its own `cancel()`, which would replace the hand-rolled `window.setTimeout` / `clearTimeout` pair and the manual teardown at `:778`. For the echo guard itself, what exists is the event's own payload (`obsidian.d.ts:4453` — `changed` carries the file, its data and its new cache) and `Vault.process`'s return value (`obsidian.d.ts:7510`), which is the exact text that was written.
- **Differs:** the guard is time-based, so it is right only when the vault is quicker than 2500 ms and the user is not. An external edit to a card landing inside that window after an in-app write is dropped silently; the plugin's own comment at `src/obsidian/vaultRepo.ts:736-739` shows the team already reasoned about this for `onFileOp`, where the guard is deliberately *not* applied. A content-based guard (compare the incoming text or cache against what the write produced) needs no window at all.
- **Read:** **not worth it** as stated — no Obsidian API replaces this, and the current guard is cheap and mostly right. It becomes worth revisiting if 04-09 lands, because once the reload is scoped to the board's own files, the remaining events are few enough that comparing content instead of timing is affordable.

## Markdown structure the metadata cache already parses

### 04-15. Checklist items and their checked state are parsed from text although the cache indexes them

- **Folia:** `CHECKBOX_RE` (`src/model/card.ts:19`), `parseSubtasks` (`src/model/card.ts:345`), `parseSubItem` (`:330`), `cardStats` (`:402`), and `setSubtaskDone` / `tickLine` (`:476`, `:467`) for the write side.
- **Obsidian:** `CachedMetadata.listItems?: ListItemCache[]` (`obsidian.d.ts:1442`). `ListItemCache` (`obsidian.d.ts:3746`) carries `task` — "A single character indicating the checked status of a task. The space character `' '` is interpreted as an incomplete task. Any other character is interpreted as completed task. `undefined` if this item isn't a task" — plus `parent` for hierarchy and, through `CacheItem`, the item's `position`.
- **Differs:** the cache would give Folia the checkbox states and the nesting for free, and would agree with Obsidian's own reading of any checklist a user writes. There is a concrete disagreement today: `CHECKBOX_RE` accepts only `[ ]`, `[x]` and `[X]`, so a custom-status checkbox — `[/]`, `[-]`, `[>]`, the shapes themes and task plugins encourage — is not a checklist item to Folia at all, while Obsidian reads it as a completed task. Such a line is invisible in the card's subtask list and absent from its progress count. It cannot serve the write side, which is where the value is here: every mutation in `src/model/card.ts` runs on the text handed in by `vault.process`, is required to leave every byte it did not change alone, and cannot consult an `app` at all. The cache also lags a write by a tick, so the read side would have to tolerate a stale answer where the current one reads the same bytes it just wrote. Folia's parser also reads a `[status:: …]` inline field the cache knows nothing about (`INLINE_STATUS_RE`, `src/model/card.ts:26`).
- **Read:** **trade-off** — the write engine has to stay text-based, which means the parser stays too, and a second reading path from the cache would only add a way for the two to disagree. The character class is the part worth acting on regardless of the cache: widening `CHECKBOX_RE` to Obsidian's own rule (space means open, anything else means done) is a one-line change in the model that needs no `app`.

### 04-16. Headings are found with a regex although the cache lists them

- **Folia:** `HEADING_RE` (`src/model/cardTitle.ts:64`), `findHeading` (`:93`), `plainHeadingText` (`:77`), `setHeadingTitle` (`:259`); the card parser has a second heading lookup in `headingIndex` (`src/model/card.ts:91`), and `descriptionRange` (`:138`) uses a third, stricter pattern again — `/^#\s+/` at `:140`, H1 only and no indent allowed.
- **Obsidian:** `CachedMetadata.headings?: HeadingCache[]` (`obsidian.d.ts:1418`); `HeadingCache` (`obsidian.d.ts:3378`) carries `heading` (the text) and `level` (1–6), with `position` from `CacheItem`.
- **Differs:** the cache would answer "what is the first heading and what does it say" with Obsidian's own parse, `HEADING_RE` is ATX-only, so a setext heading (`Title` underlined with `===`) is not a title candidate for Folia and such a card falls through to its file name with no explanation; whether `HeadingCache` covers setext headings is not stated in any source read here — `HeadingCache` documents only `heading` and a `level` "Number between 1 and 6", and "setext" appears nowhere in the developer docs — so treat the size of that particular gap as unconfirmed. `plainHeadingText` strips inline markup by regex, where the cache's `heading` string is already the parsed text. Against that, `setHeadingTitle` has to rewrite the heading line while keeping its indent, its `#` marker and its trailing hashes, which needs the raw line, not the parsed text.
- **Read:** **trade-off** — the read side would be more faithful through the cache by construction, since the cache is Obsidian's own parse; the write side needs the text either way, and both live in `src/model/`. The fix shape is the same as 04-01: the adapter resolves the title from the cache and hands `Card.title` in, leaving `setHeadingTitle` to work on text.

### 04-17. Code fences are tracked by a hand-written CommonMark scanner

- **Folia:** the whole of `src/model/fences.ts` — `FENCE_RE` (`:5`), `fenceMarker` (`:8`), `fenceAfter` (`:22`), `fencedLines` (`:36`), `unclosedFence` (`:50`). Every heading and bullet lookup in the card model goes through it so that Folia's own format quoted inside a note stays inert.
- **Obsidian:** `CachedMetadata.sections?: SectionCache[]` (`obsidian.d.ts:1438`); `SectionCache` (`obsidian.d.ts:5668`) has a `type` whose documented values include `'code'`, and a `position` from `CacheItem` giving the block's line range.
- **Differs:** the cache's section list is Obsidian's own reading of where a code block starts and ends, so it can never disagree with what the user sees rendered — which is the exact property `src/model/fences.ts:1-3` says it is trying to achieve by copying CommonMark. Folia's version additionally answers "is there a fence still open at the end", which `appendToSection` (`src/model/card.ts:223`) needs before it can append a new section, and which the cache does not answer directly. It also has to work on text mid-write, before any cache exists for it.
- **Read:** **trade-off** — this is the most carefully specified in-house module in the area and it is genuinely needed for the write path, but it is a second implementation of a parser the app already runs, and any divergence between the two shows up as a section Folia rewrites that the user sees as code. Worth a periodic check against the cache in tests rather than a replacement.

## Path hygiene and name resolution elsewhere in the plugin

### 04-18. The guided board's own paths are built without `normalizePath`

- **Folia:** `src/boardNote.ts:60` (`cardFolderFor`) and `:72` (`uniqueNotePath`) assemble vault paths by string concatenation — `${dir}${name}`, `${dir}${base}.md` — with no normalisation. `normalizePath` appears in exactly three places in `src/`, all in `src/obsidian/vaultRepo.ts` (`:158`, `:529`, `:532`).
- **Obsidian:** `normalizePath(path)` (`obsidian.d.ts:4606`). The guideline is broader than the input side: "Use `normalizePath()` whenever you accept user-defined paths to files or folders in the vault, **or when you construct your own paths in the plugin code**" (developer-docs `Plugins/Releasing/Plugin guidelines.md#Use normalizePath() to clean up user-defined paths`).
- **Differs:** nothing malformed can reach these two today — their inputs are a `TFolder.path` obtained from `FileManager.getNewFileParent` plus the string constants `Cards` and `Board` — so this is a letter-of-the-guideline gap, not a live bug. What it does create is an inconsistency: the same repository normalises the equivalent construction in `uniquePath` (`src/obsidian/vaultRepo.ts:529`) and here does not, so the next person to widen either function has no rule to follow.
- **Read:** **clear win**, small — `src/boardNote.ts` is the plugin shell and may import `obsidian` (`eslint.config.mjs:108` fences only `src/model/**` and `src/ui/**`), so it is two call sites, and it settles the inconsistency. The sharper half of the same guideline is the input side, which nothing covers today: the MCP board path is a bare `z.string()` (`src/mcp/tool.ts:63`), compared raw at `src/obsidian/mcpService.ts:59`, and `resolveCardPath` builds `${ref}.md` from raw agent input (`src/mcp/tool.ts:105`). That is "a user-defined path" in the guideline's own words, and 04-08's swap to `getFileByPath` inherits the gap unless the path is normalised first.

### 04-19. The MCP tools resolve a card name with a third hand-written matcher

- **Folia:** `src/mcp/tool.ts:94` (`resolveCardPath`) matches an agent-supplied `ref` against each card's `title`, its `basename`, or its path with `.md` appended (`:105`), refusing to guess when more than one card answers.
- **Obsidian:** `MetadataCache.getFirstLinkpathDest(linkpath, sourcePath)` (`obsidian.d.ts:4411`) is the app's own name-to-note resolution, and `parseLinktext` (`obsidian.d.ts:4798`) splits the ref into the parts a resolver needs.
- **Differs:** this is the fourth implementation of the family 04-01 describes — `linkResolver` (`src/model/board.ts:164`), `targetIdentity` (`src/model/relationships.ts:116`), `isSelfRelation` (`src/model/relationships.ts:137`, which does its own add-or-strip of `.md` and its own basename compare) and this one — with `.md` hard-coded and a third set of rules. It does one thing the Obsidian route would not, and deliberately: it matches a card's *displayed title*, which is often neither the file name nor anything a wikilink could name, because that is what an agent has actually been shown. Nothing else in Folia resolves a name that way.
- **Read:** **trade-off** — the title match is the point of the function and Obsidian has no equivalent for it, but the basename and `.md` branches duplicate `linkResolver` (`src/model/board.ts:164`) and could share one implementation. `src/mcp/**` is fenced off the adapter by `.dependency-cruiser.cjs:38`, so the fix shape is the same as 04-01's: resolve in the adapter, hand paths in.

## Verified live
