# Interaction and input

This section covers Folia's input, gestures, popup placement, timing, clipboard feedback, and cleanup in `src/ui/App.tsx`, `Board.tsx`, `Column.tsx`, `CardItem.tsx`, `CardDetail.tsx`, `CardContextMenu.tsx`, `ColumnMenu.tsx`, `ColumnEditModal.tsx`, `AddColumn.tsx`, `Toolbar.tsx`, `context.ts`, `src/view.tsx`, `src/main.ts`, and `src/obsidian/propertySuggest.ts`, with the UI tests and Obsidian fake checked for their event assumptions.

Nine of the fifteen findings below turned out to be the same gap section 01 records against the component Obsidian ships (`Menu`, `Modal`, `ConfirmationModal`, `Notice`, `AbstractInputSuggest`, `setTooltip`). Those keep their ids and their headings say which finding owns them; their bodies are a cross-reference plus whatever this section established that 01 did not, which has been moved into 01 as well. The six that stand on their own — 06-04, 06-05, 06-06, 06-11, 06-12 and 06-14 — are about interaction itself: owner documents, keymap scope, view resize, lifecycle cleanup.

## Keyboard, menus, and modal interaction

### 06-01. The card context menu carries known keyboard-access gaps alongside its custom controls — covered by 01-01

- Same gap as 01-01, which owns `Menu` and carries the fuller inventory of what the hand-built popover reimplements. What this section added and 01-01 now records: the public `Menu` contract promises placement (`showAtMouseEvent`, `showAtPosition`) but says nothing about focus restoration, roving focus or dismissal, so a swap inherits the app's behaviour rather than a documented guarantee. The two active access failures — no keyboard route to open the menu, and roving focus skipping the priority radio group — are held in `tracking/waivers/0002-automated-a11y-gate.md#Remaining (why this waiver stays active)` and are cited from 01-01.

### 06-02. The standalone column editor bypasses Obsidian's modal lifecycle and scope — covered by 01-03

- Same gap as 01-03, which owns `Modal` and covers both in-house dialog shells. Read from the interaction side, `ColumnEditModal` alone is a **clear win**: it is only ever a modal editor, and a host modal can mount the same React form in its `contentEl` without giving up the fields or the validation. That reading is recorded in 01-03, along with the correction this section established: `Modal` documents a `scope: Scope` for Escape and the modal keymap, but neither the typings nor the modal guide promises a focus trap or an inert background, so the waiver's open item (`tracking/waivers/0002-automated-a11y-gate.md#Remaining (why this waiver stays active)`) does not close by adoption alone.

### 06-03. The modal detail presentation trades host modal behaviour for one shared panel — covered by 01-03

- Same gap as 01-03. `src/ui/App.tsx:917` renders a custom backdrop around `CardDetail`, whose modal branches are at `src/ui/CardDetail.tsx:1280` and `:1425`. Folia shares one React panel across split, float and modal presentations, which a standalone `Modal` would split into two mount paths — the reason 01-03 recommends trying `Modal` on `ColumnEditModal` first. The modal branch still owns focus behaviour itself and still needs a separately verified focus trap and background treatment, whether it stays in React or moves into a host modal.

### 06-04. Popout interaction uses the focused document instead of the board's owner document

- **Folia:** `src/ui/CardContextMenu.tsx:63` (`CardContextMenu`) and `src/ui/ColumnMenu.tsx:52` (`ColumnMenu`) portal into `activeDocument` and use global window geometry. `src/ui/ColumnEditModal.tsx:276` portals into `activeDocument.body`; `src/ui/CardDetail.tsx:1099`, `src/ui/CardDetail.tsx:1192`, and `src/ui/CardDetail.tsx:1201` read from and listen on `activeDocument`.
- **Obsidian:** `activeWindow` and `activeDocument` refer to the currently focused window and document (`obsidian.d.ts:259`, `obsidian.d.ts:264`). An element's `win` and `doc` identify the window and document that own it, which the popout guide calls the correct route when a different window may be focused (`developer-docs: Plugins/Guides/Support pop-out windows.md#The active window`).
- **Differs:** A background board can re-render while another window is focused. Its portal, focus capture, pointer listener, and viewport geometry can then land in that other window. Folia already uses the board's own document for its drag overlay at `src/ui/Board.tsx:386`; the other surfaces should derive their document and window from the board root or panel element too.
- **Read:** **clear win**. Owner-document and owner-window access fixes a popout correctness bug without changing Folia's custom interaction.

### 06-05. Manual status-bar measurement duplicates Obsidian's scroll-clearance variable

- **Folia:** `src/ui/App.tsx:230` (`BoardApp` status-bar clearance effect) queries `.status-bar` and writes a measured `--folia-statusbar-clearance`; `src/styles.css:447` and `src/styles.css:1376` consume that value to keep board and detail content clear of the fixed bar.
- **Obsidian:** `--status-bar-scroll-padding` is the documented CSS variable for status-bar scroll clearance (`developer-docs: Reference/CSS variables/Window/Status bar.md#CSS variables`).
- **Differs:** Folia measures one status bar only after a board load and reads from the focused document, which repeats host layout work and has the owner-document problem from 06-04. The host variable follows the status bar without Folia querying its height.
- **Read:** **clear win**. Use the host clearance variable in the relevant scrolling layout and delete the measurement effect and plugin-specific variable.

### 06-06. The board search shortcut bypasses the view keymap scope

- **Folia:** `src/ui/App.tsx:798` (`BoardApp` search-shortcut effect) installs a `keydown` listener on the owning document and manually decides whether `/` should focus the search box.
- **Obsidian:** `Scope` and `Keymap` let a view register a focused-scope hotkey, with inherited parent scopes and automatic `preventDefault` when the handler returns `false` (`obsidian.d.ts:3624`, `obsidian.d.ts:3684`, `obsidian.d.ts:5527`, `obsidian.d.ts:5537`, `obsidian.d.ts:5545`). `View.scope` is `Scope | null` and is explicitly for hotkeys while the view has focus (`obsidian.d.ts:7617`; `developer-docs: Reference/TypeScript API/View.md#Properties`).
- **Differs:** Folia checks visibility and editable targets itself because a document listener also runs for other UI in the same document. A `KanbanView` scope would make `/` active only for the focused board leaf and remove that visibility workaround. The React input would still own its local keyboard behaviour.
- **Read:** **clear win**. This is one board-level shortcut with a host lifecycle and focus boundary already available. It also avoids a background board inspecting keys for another leaf.

### 06-07. Detail-field suggestions split between browser datalists and Obsidian type-ahead — covered by 01-06

- Same gap as 01-06, which counts all five suggesting inputs and owns `AbstractInputSuggest`. From the interaction side the cost is that one detail panel presents four suggestion controls with two keyboard and visual models: `src/ui/CardDetail.tsx:160` (`PriorityField`), `:224` (`AssigneeField`) and `:684` (`RelationshipField`) use `<datalist>`, while the property-name input reaches `PropertyNameSuggest` through `propKeyRef` at `:921`. Any consolidation has to preserve free-text entry in the three open-vocabulary fields.
- **Backlog:** [20260829.06 detail panel suggests in two different ways](../../backlog/20260829.06.detail-panel-suggests-in-two-different-ways.md).

### 06-08. Custom destructive confirmations bypass `ConfirmationModal` — covered by 01-13

- Same gap as 01-13, which owns `Modal` and now carries the facility this section found: `ConfirmationModal` (`obsidian.d.ts:1957`, since 1.13.0) extends `Modal` with its own button row, `addButton`, `addCancelButton` and `addCheckbox`, and closes automatically after an action unless the handler returns truthy. Being above Folia's 1.7.2 floor it needs a `requireApiVersion` gate or a fallback, which is the compatibility decision this route turns on. Until then the three bespoke alertdialogs at `src/ui/CardItem.tsx:415`, `src/ui/CardDetail.tsx:1494` and `src/ui/ColumnMenu.tsx:215` need their own focus and dismissal tests.

### 06-09. Board-local status toasts duplicate `Notice` — covered by 01-07

- Same gap as 01-07, which owns `Notice` and inventories every transient message on the board. From the interaction side: `src/ui/App.tsx:143` (`showToast`) holds the state, manages the timer and renders the live region, with 2.2-second success and 4-second error durations, while `src/main.ts:635` (`copyMcpToken`) already raises the same class of message through `Notice` with an explicit duration. A board-local toast does stay inside the board's own popout document, which a host notice would not.

### 06-10. The generic filter suggestion list duplicates Obsidian's input suggester — covered by 01-06

- Same gap as 01-06, which owns `AbstractInputSuggest` and counts the Toolbar box as the plugin's most elaborate reimplementation of an existing control. The interaction detail now recorded in 01-06: `src/ui/Toolbar.tsx:105` (`FilterBar`) replaces a fragment inside a React-controlled query and restores the caret afterwards through a `requestAnimationFrame`, so a host suggester would have to drive that from its own selection callback, the way `PropertyNameSuggest.selectSuggestion` already does for property names.

## Remaining interaction choices

### 06-11. The description preview misses view-resize signals

- **Folia:** `src/ui/CardDetail.tsx:1122` (`CardDetail` description-preview measurement effect) listens to `window.resize`, then derives the preview maximum height from that element's viewport position.
- **Obsidian:** `KanbanView` extends `FileView` at `src/view.tsx:17`, and `View.onResize()` is called when that view's size changes (`obsidian.d.ts:7676`, `obsidian.d.ts:7680`; `developer-docs: Reference/TypeScript API/View/onResize.md#View.onResize() method`).
- **Differs:** A view resize callback cannot replace measuring the React element, but it directly observes this board's split and pane resizing, which a browser window listener does not. The current global-window listener also has the popout defect in 06-04.
- **Read:** **trade-off**. Keep local element measurement, but bridge `KanbanView.onResize()` into React or use a `ResizeObserver` so a split resize recomputes the preview. The view bridge should use the view lifecycle rather than a workspace-wide event.

### 06-12. The inline add-column editor preserves context that a host modal would lose

- **Folia:** `src/ui/AddColumn.tsx:5` (`AddColumn`) replaces the board's add button with an autofocus input and hand-written Enter, Escape, submit, and cancel behaviour.
- **Obsidian:** the modal guide supports user input with `Modal` and `Setting` (`developer-docs: Plugins/User interface/Modals.md#Accept user input`), and `Modal` provides the container and lifecycle hooks (`obsidian.d.ts:4477`, `obsidian.d.ts:4513`, `obsidian.d.ts:4519`, `obsidian.d.ts:4525`).
- **Differs:** A host modal supplies a conventional modal input route, but adding a column is a small board-local action. The inline field keeps the current lanes visible and avoids interrupting the flow of board setup.
- **Read:** **not worth it**. Revisit only if adding a column grows validation or multi-field configuration that no longer fits a short inline edit.

### 06-13. The column options popover cannot be a plain host menu without losing its editable controls — covered by 01-02

- Same gap as 01-02, which owns `Menu` and reaches the same conclusion by a different route: `Menu.showAtPosition` and `showAtMouseEvent` (`obsidian.d.ts:4285`, `:4290`) would improve placement and dismissal, but `MenuItem` (`:4313`) is an action-menu API, not a form container, so the rename input, the WIP field and the swatch grid at `src/ui/ColumnMenu.tsx:45` have nowhere to go inside a native menu. 01-02 adds the part that makes it a decision rather than a refactor: those fields already exist a second time in `ColumnEditModal`.

### 06-14. React effects already clean up the board's transient DOM listeners

- **Folia:** `src/ui/Board.tsx:169` (`Board` pan effect), `src/ui/CardDetail.tsx:1180` (`CardDetail` outside-click effect), and `src/ui/CardContextMenu.tsx:86` (`CardContextMenu` outside-pointer effect) pair their transient React listeners with matching cleanup. `src/ui/App.tsx:162` also clears its pending toast timer on unmount. The settings-tab blur listeners at `src/main.ts:877` and `src/main.ts:982` have no explicit removal, but attach only to input elements discarded when that settings DOM redraws.
- **Obsidian:** `Component.register`, `registerEvent`, `registerDomEvent`, and `registerInterval` detach callbacks, DOM listeners, and intervals when a component unloads (`obsidian.d.ts:1880`, `obsidian.d.ts:1886`, `obsidian.d.ts:1892`, `obsidian.d.ts:1912`). The developer event guide calls `registerEvent` the safest way to detach application events (`developer-docs: Plugins/Events.md#Events`).
- **Differs:** A registration owned by `KanbanView` would outlive a changing React subtree unless that subtree separately owns and unloads a `Component`. React effects already express that changing-subtree lifecycle, and `KanbanView.onClose` unmounts the React root at `src/view.tsx:104`.
- **Read:** **not worth it**. The current effect cleanups cover the lifecycle correctly. Use Obsidian registration for future listeners attached by `KanbanView` or the plugin itself, especially workspace events.

### 06-15. Native title attributes bypass Obsidian's tooltip facility — covered by 01-05

- Same gap as 01-05, which owns `setTooltip` and counts all 36 `title` attributes, splits them into literals and JSX expressions, and records the live observation that Obsidian's own tooltip is driven by `aria-label` and never by `title`. The interaction reading is unchanged: reserve `setTooltip` for controls where placement, touch behaviour or theme consistency matters, and treat titles that merely duplicate an accessible name as low-value migration targets.

## Checked and found aligned

- `src/obsidian/propertySuggest.ts` uses `AbstractInputSuggest` for the property-name field, including Obsidian's popup placement, theme, and keyboard scope.
- `src/main.ts` uses `Platform.isDesktop` instead of user-agent or viewport-width sniffing for desktop-only MCP behaviour.
- `src/main.ts` uses `Notice` with explicit durations for plugin-level notices.
- `src/view.tsx` unmounts the React root in `KanbanView.onClose`, so React effect cleanups run when the view closes.
- `src/ui/Board.tsx` uses dnd-kit and browser pointer capture for sortable cards, columns, panning, and keyboard dragging. Obsidian's public `editor-drop` event is editor-specific and is not an alternative.
- The only two `window.setTimeout` timers in the plugin are `src/ui/App.tsx:156` (the toast, covered by 01-07) and `src/obsidian/vaultRepo.ts:755` (the vault-event debounce). Obsidian's `debounce(cb, timeout?, resetTimer?)` (`obsidian.d.ts:2232`) is the facility for the second, and 04-14 owns that finding; no other hand-rolled debounce exists to replace.
- No `fetch`, `requestUrl`, `setInterval`, `ResizeObserver`, or `MutationObserver` call exists in the reviewed Folia files; there is therefore no route to replace with `requestUrl`, `registerInterval`, or a lifecycle-bound observer.

## Unverified

- Whether Obsidian's own drag machinery would behave acceptably for a kanban board's sortable columns and cards. Its existence is settled below; how it performs against dnd-kit's sortable model is not, and testing that would mean building against an internal API.

## Verified live

Checked on 2026-08-29 against the running Obsidian 1.13.7 desktop build with the repository's `examples` vault open, through the Chrome DevTools bridge.

- `app.dragManager` does exist at runtime, with `dragFile`, `dragFolder`, `dragFiles`, `dragLink`, `handleDrag`, `handleDrop`, `setAction`, `updateSource`, `updateHover`, `showOverlay` and `hideOverlay` on its prototype. None of it appears in `obsidian@1.13.1`'s typings, and its shape is oriented at dragging files and links between the app's own panes rather than at sorting a list, so the conclusion is unchanged: it is not a supported replacement for dnd-kit, and now the reason is that it is internal and file-shaped rather than that its existence was unconfirmed.
- The `obsidian` module in this build exports just over 500 members (506 names in the app bundle's own export table), and none of them is a clipboard helper; the only near-misses are the editor commands `copyLineUp` and `copyLineDown`. `navigator.clipboard.writeText` at `src/ui/App.tsx:465` and `src/main.ts:648` is the only route there is, so this is a genuine absence in the API rather than a limit of the sources read.
