# Guidelines, the MCP host, the build, and the rest

This section covers four things no other section owns: the community-directory conventions (the developer policies, the submission requirements, the plugin guidelines and the codified ESLint rules) checked against the whole codebase; the MCP host (`src/mcp/*`, `src/obsidian/mcpHttpServer.ts`, `src/obsidian/mcpService.ts`, `docs/mcp.md`); the build and release (`esbuild.config.mjs`, `manifest.json`, `versions.json`, `package.json`, `scripts/bump-plugin-version.mjs`, `docs/releasing.md`, `.github/`); and the leftovers (`src/model/history.ts`, `src/model/unread.ts`, `src/model/priorities.ts`, `examples/`, `README.md` claims).

Folia reproduces the community-directory scanner locally in `scripts/obsidian-scan.mjs`, and `pnpm verify` runs it with an empty baseline; running it directly exits 0 with zero findings, so every rule that scanner enables is genuinely guarded today. This section therefore concentrates on what the reproduction does not cover: the rules it explicitly switches off — `validate-manifest` and `validate-license` are the real hole, since of the three `ui/sentence-case` variants it also disables, only `ui/sentence-case` is in `recommended` at all (the other two live in `recommendedWithLocalesEn`, which neither guard uses) and `eslint.config.mjs:219` re-enables that one at `error` for `src/` — plus the guideline items that were never lint rules, and the conventions that live only in prose.

## Manifest, policies and review risk

### 07-01. `isDesktopOnly` is `false` while the plugin imports a Node builtin, against a submission requirement that says "must"

- **Folia:** `manifest.json` declares `"isDesktopOnly": false`; `src/obsidian/mcpHttpServer.ts:270` (`startMcpServer`) does `await import("http")`, behind `if (!Platform.isDesktop) throw` at `:263`, and `esbuild.config.mjs` marks all Node builtins external with `supported: { "dynamic-import": false }` so the import is emitted as a `require` that only runs inside the gate. `src/main.ts:600`–`:603` (`buildMcp`) writes the reasoning down: the board works everywhere, and declaring the whole plugin desktop-only would take it off mobile for a feature that is off by default.
- **Obsidian:** two official documents disagree. `developer-docs: Community directory/Submission requirements for plugins.md#Node.js and Electron APIs are only allowed on desktop` — "If your plugin uses any of these APIs, you **must** set `isDesktopOnly` to `true` in the `manifest.json`." `developer-docs: Obsidian October plugin self-critique checklist.md#Mobile support` opens the section with "Complete this section if you have `isDesktopOnly` set to false" and then tells you how to do exactly what Folia does — "gate the functionality behind `Platform.isDesktopApp` and `require()` them dynamically at runtime". The codified rule sides with the checklist: `obsidianmd/no-nodejs-modules` is switched off entirely when the manifest says `isDesktopOnly` and set to `warn` otherwise (`node_modules/eslint-plugin-obsidianmd/dist/lib/index.js:190`), which only makes sense if a gated Node import in a `false` plugin is a thing the rule expects to see and accept. The app itself reads the flag as being about the Electron shell and nothing else: `enablePlugin` refuses to load a plugin when `!Platform.isDesktopApp && manifest.isDesktopOnly`, and the community-plugin modal marks such a plugin unsupported on the same test (observed in Obsidian 1.13.7's `app.js`, see "Verified live").
- **Differs:** Folia takes the permissive reading. The strict reading would cost every mobile user the board, for a desktop-only feature nobody has to turn on; the permissive reading leaves a line in the submission requirements that a directory reviewer can quote verbatim against the manifest.
- **Read:** **trade-off**, and the one most likely to be raised on review. The gating is correct, the rule that codifies the guideline accepts it, and the alternative is strictly worse for users — but the requirement's wording is unconditional, and nothing in the repository records this as a considered position where a reviewer would look for it. The cheap half of the fix is not a manifest change at all: put the reasoning in `docs/decisions.md` (it is currently only a code comment in `src/main.ts`) so the answer exists before the question is asked.
- **Guard:** `obsidianmd/no-nodejs-modules` is active at `warn` in both `pnpm lint` and `pnpm obsidian-scan:check`, and passes — which is the evidence that the tooling accepts the gated form.

### 07-02. The MCP bearer token is kept in `data.json` in the clear, and Obsidian now has a secret store with a written guide

- **Folia:** `src/settings.ts:94` (`mcpToken`) and `src/obsidian/mcpService.ts:23` (`newMcpToken`) — the token is minted with `crypto.getRandomValues` and held as an ordinary settings key, written to `data.json` by `Plugin.saveData` (`src/main.ts:579`). `docs/mcp.md:121` says so plainly: "The token is stored in the plugin's `data.json`, in the clear, like every other setting."
- **Obsidian:** `App.secretStorage` (`obsidian.d.ts:458`, `@since 1.11.4`) exposes `SecretStorage` (`obsidian.d.ts:5635`) with `setSecret`, `getSecret` and `listSecrets`, all `@since 1.11.4`; `SecretComponent` (`obsidian.d.ts:5613`, `@since 1.11.1`, `setValue`/`onChange` `@since 1.11.4`) is the settings-tab control, attached through `Setting.addComponent<T extends BaseComponent>(cb: (el) => T)` (`obsidian.d.ts:5812`, `@since 1.11.0`). There is a whole guide: `developer-docs: Plugins/Guides/Store secrets.md`, whose "Why use SecretStorage?" section names the exact problem — "**Security**: Secrets are stored in plaintext alongside other plugin data." Its FAQ explains why there is no `Setting.addSecret`: the component needs the `App` instance, which `addText` and friends do not pass. None of this is in `node_modules/obsidian/CHANGELOG.md`, which stops at v1.7.2; the `@since` tags and the guide are the sources.
- **Differs:** two things, in opposite directions. Nothing in Folia's favour is about storage: the guide states "The actual secret is stored in local storage, keyed to the specific vault", so a secret does *not* travel in `data.json` to a second machine — which is precisely the property `docs/mcp.md` and the every-start notice at `src/main.ts:619` (`reportMcpState`) work around today, and precisely what stops mattering once the bind moves off loopback and the token becomes a credential other machines can use. Against adopting it is the shape: `SecretStorage` secrets are named and curated by the user (settings store the *name*, and `SecretComponent` lets the user pick an existing secret or create one), whereas Folia's token is minted by the plugin, copied to a clipboard, and replaced by a button. Nothing in the guide covers a plugin writing a secret the user never typed. Mechanically it is allowed: `setSecret(id, value)` in the running 1.13.7 build validates the id against `/^[a-z0-9-]+$/` up to 64 characters, writes the value through the storage adapter and fires a `changed` event, with no user interaction anywhere in the path — so a plugin-minted token would go in. It also throws `Secure storage is not available` when the platform has no adapter, and the store exposes `isEncryptionAvailable()` for exactly that case, which means any adoption needs the `data.json` fallback anyway rather than only for versions below 1.11.4.
- **Read:** **trade-off.** The storage win is real and the guide argues it in Obsidian's own words. Two costs: the API landed at 1.11.4, well past `minAppVersion` 1.7.2, so it needs either a version bump or a `requireApiVersion("1.11.4")` branch keeping `data.json` as the fallback — the shape `src/main.ts:800` already uses for the 1.13.0 settings API — and the user-facing model would change from "a token the plugin gave you" to "a named secret you manage", which is a bigger design decision than the storage move. The `SecretComponent` half can be taken alone and cheaply: the settings tab currently offers only a "Copy token" button, so a masked field is a plain UI improvement.

### 07-03. The manifest description contains an em dash, which the submission requirements and the official manifest rule both reject

- **Folia:** `manifest.json` — `"description": "A real Kanban board with drag-and-drop, nested subcards, comments, and history — every card is a plain Markdown file."` It is 117 characters, starts with a capital and ends with a period.
- **Obsidian:** `developer-docs: Community directory/Submission requirements for plugins.md#Keep plugin descriptions short and simple` requires the description to "Avoid using emoji or special characters". `obsidianmd/validate-manifest` codifies that as a character allowlist, `/^[A-Za-z0-9\s.,!?'"-]+$/` (`node_modules/eslint-plugin-obsidianmd/dist/lib/rules/validateManifest.js:221`). The em dash is outside that set; running the same regex against the description returns `false`, so the rule would report `descriptionFormat`.
- **Differs:** the description reads well and says nothing wrong; the rule is a blunt allowlist, and the human requirement it encodes is applied by judgement. Replacing the em dash with a colon or a full stop satisfies both without losing a word. The rule's other manifest checks pass: all seven required keys present and correctly typed, no disallowed key, no duplicate, and no forbidden word ("obsidian", "plugin") in `id`, `name` or `description`. The requirement's remaining items — following the Obsidian style guide, correct capitalization of proper nouns — are human judgement, and "Markdown" and "Kanban" are capitalized correctly.
- **Read:** **clear win**, but a smaller one than it looks. One character, no behaviour. It is not, however, closing a finding anybody is about to report: as 07-04 sets out, `validate-manifest` cannot fire on a manifest in the stock preset at all, so the only route by which the dash is ever seen is a human reviewer applying the written requirement. That makes the change cheap insurance rather than a fix for a live failure.
- **Guard:** no guard runs the rule, and none can without hand-wiring. See 07-04.

### 07-04. Neither guard ever runs `validate-manifest` or `validate-license`

- **Folia:** `scripts/obsidian-scan.mjs:246`–`:247` sets `"obsidianmd/validate-manifest": "off"` and `"obsidianmd/validate-license": "off"`, copied faithfully from the scanner's own config. Folia's `eslint.config.mjs` spreads `obsidianmd.configs.recommended` and re-globs its rule blocks onto `src/**/*.{ts,tsx}` (deliberately exempting ignores-only blocks, anything carrying a `language`, and anything targeting `package.json` — `eslint.config.mjs:199`–`:203`), and `pnpm lint` is `eslint src test` (`package.json`), so ESLint is never handed `manifest.json` or `LICENSE` at all. The scanner reproduction could not report them either even with the rules on: `scripts/obsidian-scan.mjs:291` names `manifest.json` in its own `ignores`, and its `LINTABLE` regex (`:306`) requires a file extension, so an extensionless `LICENSE` is never passed to ESLint.
- **Obsidian:** both rules key off the file name — `validateManifest.js:66` returns early unless the linted file's basename ends with `manifest.json`, `validateLicense.js:38` unless it ends with `LICENSE`. Both are part of `recommended` at `warn` (`node_modules/eslint-plugin-obsidianmd/dist/lib/index.js:151`–`:152`). They are also unreachable there: that rule block is merged only into `files: ['**/*.{js,cjs,mjs,jsx}']` (`index.js:227`) and `files: ['**/*.{ts,cts,mts,tsx}']` (`index.js:242`), neither of which matches `manifest.json` or an extensionless `LICENSE`. The preset's remaining file-scoped blocks are `files: ['package.json']` (`index.js:250`, the only one carrying a `language`, at `:251`) and an `eslint-comments` block on the same TS/JS extensions (`index.js:267`). Nothing anywhere in the preset targets `manifest.json`. So Folia's two `"off"` lines switch off something that was never on.
- **Differs:** the effect is that nothing in `pnpm verify` reads the manifest against the submission requirements — 07-03 is the finding that fell through this gap. The `Obsidian community scan` job (declared at `.github/workflows/ci.yml:63`, the action at `:91`, its inputs running to `:101`) runs the real `obsidianmd/obsidian-workflows@v1`, which does carry a manifest and licence check of its own — but not these rules, and not the content 07-03 is about. Read from the action's source: `src/main.ts:58`–`:60` calls `validateManifest` unconditionally in both `pr` and `release` mode, and `src/main.ts:63`–`:64` calls `checkReadme` and `checkLicense` the same way, so all three run on every Folia pull request. `validateManifest` (`src/manifest.ts:246`) is a hand-written JSON check, not the ESLint rule: for a plugin it returns `validatePluginManifest` plus `validateVersionsJson` (`src/manifest.ts:276`–`:279`). `validatePluginManifest` (`:83`) raises an **error** for a missing `id`, `name`, `version` or `description` (`:88`–`:124`), for a `version` or `minAppVersion` that is not `X.Y.Z` (`:10`–`:21`, called at `:113` and `:127`), and for an `authorUrl` or `fundingUrl` that is not an HTTP(S) URL (`:55`–`:81`, `:130`–`:141`); it raises a **warning** for a name containing "obsidian" or "plugin" (`:8`, `:23`–`:38`) and for a description under ten characters (`:40`–`:53`). It never inspects the characters *inside* a description, which is why 07-03's em dash passes this job as well as the local one. `checkLicense` (`src/repo-checks.ts:170`) errors only when no `LICENSE` file exists at the root (`:174`–`:181`) and warns when `package.json` declares a non-OSI SPDX id (`:185`–`:191`); Folia has a `LICENSE` and declares no `license` field, so it passes silently and says nothing about the file's contents. And the failure rule is now confirmed rather than assumed: `src/main.ts:114`–`:119` calls `core.setFailed` only when some result carries severity `error`, so every warning above lands in a log nobody reads.
- **Also worth knowing:** `validateVersionsJson` (`src/manifest.ts:193`) is thinner than its name suggests. It returns an empty result when `versions.json` does not exist (`:197`), so the file is optional to the action; it errors only when the file is not valid JSON or not a JSON object (`:206`, `:215`); and it checks nothing but that every key is semver and every value a semver string, both at **warning** severity (`:227`–`:240`). It never checks that `manifest.json`'s own `version` has a row, nor that a row's value matches `minAppVersion`, which is the invariant 07-15 is about.
- **Also in this hole:** `depend/ban-dependencies` (presets `native`, `microutilities`, `preferred`), which the preset puts at `error` on `files: ['package.json']` (`index.js:250`–`:265`). `pnpm lint` never reaches `package.json`, and `eslint.config.mjs` leaves that block un-re-globbed on purpose, so Folia's own lint does not run it. `pnpm obsidian-scan:check` does — its `LINTABLE` admits `.json` — and it passes. Not a live finding, but it means the two guards do not cover the same rule set, which is the premise the local reproduction rests on.
- **Read:** **trade-off**, not the one-line config block it first looks like. `validateManifest` needs a JSON language to see the file as an `ObjectExpression` (`validateManifest.js:74`–`:80`) and `validateLicense` needs a plain-text language to get `Line` tokens (`validateLicense.js:48`); the recommended preset wires `language: 'json/json'` for `package.json` only (`index.js:249`–`:263`) and nothing at all for `manifest.json` or `LICENSE`, so both languages would have to be configured here by hand. Worth it for the manifest, which has real content to check; near-pointless for `LICENSE`, which is the unmodified AGPL text whose template line reads `Copyright (C) <year>  <name of author>` (`LICENSE:633`) and matches the rule's `Copyright (C) YYYY by NAME` regex nowhere, so that rule can never say anything about this file.

## Code and structure against the checklist

### 07-05. `src/main.ts` is 1020 lines, against a checklist item asking for it to be split

- **Folia:** `src/main.ts` — 1020 lines holding the plugin class, the `setViewState` patch, the board-setup commands, the settings tab and the MCP wiring. `eslint.config.mjs:142`–`:163` switches `max-lines`, `max-lines-per-function` and `complexity` off for this file and fourteen others (`eslint.config.mjs:142`–`:158`), and `tracking/waivers/0004-legacy-file-size-complexity.md` records that as active debt with an expiry of 2026-12-31 and a plan to split.
- **Obsidian:** `developer-docs: Obsidian October plugin self-critique checklist.md#Coding style` — "Do break up your `main.ts` into smaller files or even folders if it gets big to make code easier to find." The related `developer-docs: Plugins/Releasing/Plugin guidelines.md#Consider organizing your code base using folders` is already satisfied (`src/model/`, `src/ui/`, `src/obsidian/`, `src/mcp/`).
- **Differs:** the plugin is well organised everywhere except its entry point, which carries five unrelated responsibilities. The settings tab in particular (`KanbanSettingTab`, declared at `src/main.ts:720`) is a self-contained class whose layout and definitions are already extracted to `src/settingsLayout.ts` and `src/settingsDefinitions.ts`, so the split has a natural first cut.
- **Read:** **clear win**, at real cost. This is not a substitution for an Obsidian facility, it is a structural item the review checklist names outright, and the repository already agrees with it in writing. What makes it a win rather than a preference is that the waiver has an expiry and a plan; what makes it expensive is that it is a refactor, not an edit.
- **Guard:** `tracking/waivers/0004-legacy-file-size-complexity.md` (active, expires 2026-12-31), enforced by the ESLint override block that only relaxes the three rules for the listed legacy files and keeps every new file fully gated.

### 07-06. `WorkspaceLeaf.prototype.setViewState` is monkey-patched, and no written rule covers it

- **Folia:** the patch itself is written up in full as **05-01**, which owns the workspace API and weighs the alternatives; this finding is only about the absence of any written rule covering it. `src/main.ts:215`–`:236` (`patchLeafSetViewState`) takes `WorkspaceLeaf.prototype.setViewState`, replaces it with a wrapper that redirects a board note's `markdown` view state to the Kanban view type, and restores it in a `this.register` teardown that first goes inert (`patchState.redirectToBoard = null`) in case another plugin wrapped it afterwards. The comment at `src/main.ts:197`–`:200` justifies it: every route that opens a file ends in that one call, so patching it is complete and avoids the flash a listener-based swap would give, and it names Kanban and Excalidraw as plugins doing the same.
- **Obsidian:** nothing. `WorkspaceLeaf.setViewState` is public API (`obsidian.d.ts`), but there is no guidance for or against replacing a prototype method: a sweep of the developer-docs clone for prototype patching, private API, internal API and undocumented API returns no policy, and no rule in `eslint-plugin/docs/rules/` touches it. The nearest written rules are about the opposite habit — `obsidianmd/no-view-references-in-plugin` and the guideline against holding references to custom views, both of which Folia already follows.
- **Differs:** there is no Obsidian route being side-stepped here, because Obsidian offers none. What exists instead is exposure: the patch is global, it survives for the plugin's lifetime, and it is the single most review-visible thing in the codebase — a reviewer will stop on it whether or not a rule exists.
- **Read:** **trade-off**, recorded rather than actioned. The alternative Obsidian does provide — a `file-open` or `layout-change` listener that swaps the view after it opens — is what the comment rules out for the flash it causes, and that reasoning is sound. What is missing is that the reasoning lives only in a code comment: this is the clearest candidate in the whole section for an entry in `docs/decisions.md`, which currently records two decisions and not this one.

### 07-07. `renderMarkdown` clears its container with `innerHTML = ""` instead of `el.empty()`

- **Folia:** `src/obsidian/vaultRepo.ts:682` (`renderMarkdown`) — the cleanup closure the caller invokes on unmount does `el.innerHTML = "";`. The same function already prefers the Obsidian route on entry, `if (el.empty) el.empty();` at `:663` with `else el.innerHTML = "";` at `:664` as a fallback for the test environment, which has no `empty()`. The cleanup path has neither the guard nor the fallback.
- **Obsidian:** `developer-docs: Plugins/Releasing/Plugin guidelines.md#Avoid innerHTML, outerHTML and insertAdjacentHTML` — "To cleanup a HTML elements contents use `el.empty();`".
- **Differs:** the two behave the same for clearing; the guideline is categorical about the property rather than about the value assigned to it, and a reviewer greps for the property. `empty()` also detaches children through Obsidian's own helper rather than through an HTML parse of the empty string.
- **Read:** **trade-off**, and worth being precise about, because the obvious fix does not achieve what the guideline is after. Copying the `:663`–`:664` guard onto `:682` makes the cleanup prefer `empty()` in Obsidian while leaving a second literal `innerHTML` in the file, so a reviewer grepping for the property still finds two. The fix that actually clears the file is to give the test environment an `empty()` (a line of jsdom setup) and drop both fallbacks; the cheap fix is the guard, and it is still better than what is there, because today the cleanup path never uses the Obsidian route at all.
- **Guard:** none reaches it. The scanner's `no-unsanitized/property` (`scripts/obsidian-scan.mjs:232`) only fires on a non-literal assignment and `""` is a literal, so the scan is clean over this line and stays clean; running `node scripts/obsidian-scan.mjs` confirms zero findings.

### 07-08. Command ids repeat a prefix Obsidian adds for you — covered by 05-08

- Same gap as 05-08, which owns the command surface and now carries the written requirement this section found: `developer-docs: Community directory/Submission requirements for plugins.md#Don't include the plugin ID in the command ID` — "Obsidian automatically prefixes command IDs with your plugin ID. ## The MCP host

### 07-09. The MCP tools duplicate a file lookup the vault API already does — covered by 04-08 and 04-19

`src/obsidian/mcpService.ts:59` (`repoFor`) walks `app.vault.getMarkdownFiles()` to find one board by its known path, and the MCP card tools resolve a card by name rather than by path. Both are written up as **04-08** and **04-19**; the guideline behind them is `developer-docs: Plugins/Releasing/Plugin guidelines.md#Avoid iterating all files to find a file by its path`, which names `Vault.getFileByPath`. Recorded here only so the MCP host does not read as clean; the findings live in section 04.

### 07-10. The Node gate spells `Platform.isDesktop` where the checklist says `isDesktopApp`, and the lint rule only accepts `isDesktop`

- **Folia:** `src/obsidian/mcpHttpServer.ts:263` (`startMcpServer`) throws unless `Platform.isDesktop`, immediately before the `await import("http")` at `:270`. Five more sites gate on the same flag for the feature rather than the import: `src/main.ts:606` (`buildMcp`), `:547` and `:594` (`mcpTokenPatch`), `:768` (the flag handed to the settings layout) and `:921` (which is what hides the agent-access section from the settings tab).
- **Obsidian:** the two sources contradict each other. `developer-docs: Obsidian October plugin self-critique checklist.md#Mobile support` says "gate the functionality behind `Platform.isDesktopApp`". `obsidianmd/no-nodejs-modules` recognises only the literal `isDesktop` — its `isPlatformIsDesktop` helper tests `expr.property.name === "isDesktop"` (`node_modules/eslint-plugin-obsidianmd/dist/lib/rules/noNodejsModules.js:80`), and its own message says "guarded by Platform.isDesktop". The typings distinguish them: `isDesktop` is "The UI is in desktop mode" (`obsidian.d.ts:4828`), `isDesktopApp` is "We're running the electron-based desktop app" (`obsidian.d.ts:4838`).
- **Differs:** only under mobile emulation, and only in the harmless direction. The desktop boot path sets `isDesktopApp` and `isDesktop` to `true` in the same statement, and the emulation switch is the one place that separates them — it sets `isMobile = true` and `isDesktop = false` while leaving `isDesktopApp` untouched (both observed in Obsidian 1.13.7's `app.js`). So on a real Electron machine under `app.emulateMobile(true)` the server declines to start and the settings section hides itself even though `http` is available, which is a feature going missing rather than a Node import running where Node is absent. The reverse case — `isDesktop` true where Node is not there — would have to come from the mobile build, which the desktop bundle cannot answer for.
- **Read:** **not worth it**, and effectively decided by the tooling, though the checklist's spelling is the one the app agrees with: Obsidian gates `isDesktopOnly` plugins on `isDesktopApp` (see 07-01), which is the flag that means "the Electron shell, so Node exists". Switching `mcpHttpServer.ts:263` to it would nonetheless make `obsidianmd/no-nodejs-modules` report the `http` import in both `pnpm lint` and `pnpm obsidian-scan:check` — the checklist's spelling and the rule's spelling are not interchangeable, and the rule is what actually runs on submission. The five `src/main.ts` sites are invisible to the rule and could be changed freely, but changing them alone would leave the codebase using two spellings for one question.
- **Guard:** `obsidianmd/no-nodejs-modules`, active at `warn` in both guards because the manifest says `isDesktopOnly: false` (`node_modules/eslint-plugin-obsidianmd/dist/lib/index.js:190`), currently passing.

### 07-11. The transport is written with `Promise` constructors and `.then` chains where the guidelines ask for async/await

- **Folia:** `src/obsidian/mcpHttpServer.ts:116` (`readBody`), `:223` (`answerLate`) and `:308` (`listen`) each return a hand-built `new Promise`; the one-at-a-time queue at `:277`–`:290` (`turn = turn.then(work, work)`) and its twin at `src/obsidian/mcpService.ts:124` (`enqueue`) are `.then` chains.
- **Obsidian:** `developer-docs: Plugins/Releasing/Plugin guidelines.md#Prefer async/await over Promise`, echoed in `developer-docs: Obsidian October plugin self-critique checklist.md#Coding style` as "Do use `async` and `await` when you can for readability, instead of using `Promise`".
- **Differs:** the guideline's example is a `.then`/`.catch` chain over a single awaitable call, which none of these are. `readBody` and `listen` adapt Node event emitters, which have no promise form; `answerLate` races a timer against a settled promise; the two queues deliberately keep a chain the caller does not await, so the next call joins the tail rather than the caller's stack.
- **Read:** **not worth it.** Each is a case async/await cannot express, and a rewrite would either lose the behaviour or wrap the same constructor one layer down. The checklist's own wording ("when you can") already allows for this, and the comments at each site say why.

## Build and release

### 07-12. Nothing checks that the release tag matches `manifest.json`'s version

- **Folia:** `.github/workflows/release.yml` refuses a tag that is not plain semver or not reachable from `origin/main`, then tests, builds, attests and uploads the three assets — but it never compares the tag to `manifest.json`'s `version`. The two are kept in step earlier and elsewhere: release-it passes `${tagName}` into `scripts/bump-plugin-version.mjs` (`.release-it.json`), which writes it into the manifest. Nothing re-checks it on the commit the tag actually points at.
- **Obsidian:** `developer-docs: Plugins/Releasing/Submit your plugin.md` — "The 'Tag version' of the release must match the version in your `manifest.json`", restated in the next step: Obsidian downloads the three files "from the GitHub release whose tag matches the `version` in your manifest". It is the one hard requirement in that guide that the release workflow does not enforce. Obsidian's own action already implements the comparison: `validateManifestConsistency` (`obsidian-workflows: src/release.ts:76`) reads the tag out of `GITHUB_REF` (`:19`–`:23`) and reports when `manifest.json`'s `version` differs from it (`:90`–`:96`). Two things blunt it. It runs only in release mode (`src/main.ts:86`–`:89`), and Folia invokes the action once, at `.github/workflows/ci.yml:91`, with `mode: pr` — neither `release.yml` nor `create-release.yml` calls it at all. And the mismatch is raised at severity **warning** (`src/release.ts:94`), which `src/main.ts:114`–`:119` never turns into a failure.
- **Differs:** the invariant is maintained by construction rather than checked, so it holds only as long as every release goes through release-it. A hand-made tag, a re-run against an older commit, or a manual manifest edit produces a release the portal silently will not pick up. `docs/releasing.md` already documents that exact failure — it cites two forum threads about the portal reporting "No release matches your manifest version" — so the repository knows the symptom and has no guard for it.
- **Read:** **clear win**, and now a better-evidenced one. One step in `release.yml` comparing the tag to the manifest's `version` and failing loudly, next to the semver and reachability checks that are already there. It costs nothing and turns a silent portal failure into a red build. Adopting the upstream check instead is not a substitute: running the action in release mode would produce a warning rather than a failure for exactly this mismatch, so a local step that exits non-zero is the stronger guard even where the two overlap.

### 07-13. The build script skips the type check the sample plugin's does

- **Folia:** `package.json:13` — `"build": "node esbuild.config.mjs production"`. Type checking lives in a separate `typecheck` script and runs as part of `pnpm verify`; `.github/workflows/release.yml` runs `pnpm test` and `pnpm build`, and never `pnpm typecheck`.
- **Obsidian:** the sample plugin's `package.json` — `"build": "tsc -noEmit -skipLibCheck && node esbuild.config.mjs production"`. esbuild strips types without checking them, so a build that does not run `tsc` cannot fail on a type error.
- **Differs:** on the release path specifically, a type error reaches a published artefact. `pnpm verify` catches it locally and CI catches it on the PR, so the gap only opens when the release runs against a commit CI has not finished with — which is exactly what a tag push does.
- **Read:** **clear win.** Either add `pnpm typecheck` to the release workflow, or fold `tsc --noEmit` into `build` the way the sample does. The second matches the sample and cannot be forgotten by a future workflow.

### 07-14. The bundle targets `es2018`, three editions below what the sample plugin uses

- **Folia:** `esbuild.config.mjs` — `target: "es2018"`.
- **Obsidian:** the sample plugin's `esbuild.config.mjs` uses `target: 'es2021'`. Folia's own `scripts/obsidian-scan.mjs:90` (`ELECTRON_VERSIONS`) and `:105`–`:113` (`getMinElectronVersion`) copy the directory scanner's mapping, under which `minAppVersion` 1.7.2 resolves to Electron 30; the script prints `manifest.minAppVersion 1.7.2 -> browserslist target "electron >= 30"` on every run, and that is the target the CSS is already checked against.
- **Differs:** two things, and only the first is measurable from the sources. Folia compiles three ECMAScript editions below the sample's default, so esbuild downlevels syntax the sample would emit as written. Separately, the CSS half of the scan is checked against `electron >= 30` while nothing checks the JS target against anything — not the local reproduction, not the real scanner. Worth keeping the two numbers apart: `electron >= 30` is the floor the manifest's `minAppVersion` implies, not what users run. The installed Obsidian 1.13.7 reports Electron 39.8.3, Chromium 142 and Node 22.22.1, so for anyone on a current Obsidian the target is downlevelling against a runtime that is many editions ahead of it; what a machine actually pinned to the 1.7.2 floor can run is still unmeasured — see Unverified.
- **Read:** **trade-off.** Raising it to `es2021` matches the sample and stops the downlevelling for the runtime users are actually on; leaving it means a smaller supported-syntax surface and no reason to think about it again. What is not a trade-off is that one half of the same scan derives a browser target from the manifest and the other half ignores it. What would make the change clearly right is a measured bundle-size or startup difference, which nothing in this repository currently produces.

### 07-15. `versions.json` gets a row on every release, where the doc asks for one only when `minAppVersion` changes

- **Folia:** `scripts/bump-plugin-version.mjs:38` writes `versions[version] = minAppVersion` unconditionally on every bump, so `versions.json` now holds twenty rows: `"0.0.1": "1.12.0"`, `"0.0.2": "1.7.0"`, and eighteen identical `"1.7.2"` rows from `0.0.3` to `0.0.20`.
- **Obsidian:** `developer-docs: Reference/Versions.md` explains the mechanism — Obsidian consults `versions.json` only when the user's app is *older* than the manifest's `minAppVersion`, to find the newest plugin version that still runs — and closes with a callout: "You don't need to list every plugin release in the `versions.json`. You only need to update `versions.json` if you change the `minAppVersion` for your plugin." The sample plugin's `version-bump.mjs` writes a row only when the version is not already present, which is a weaker version of the same idea.
- **Differs:** seventeen of the twenty rows say nothing, and every future release adds another. The first two are not bugs: `CHANGELOG.md` dates 0.0.20 to 2026-08-27 and 0.0.18 to 2026-08-25, roughly one release a day, so 0.0.1 shipped in early August 2026 when Obsidian 1.12.x was current and the manifest genuinely said `1.12.0`. The `0.0.2` row records the step down to 1.7.0, and `0.0.3` the step to 1.7.2. That is honest history and the three rows Obsidian's own rule would keep; rewriting any of them would assert something nothing supports.
- **Read:** **not worth it** on its own; the file is inert today and no guard or reviewer reads it. It becomes worth it the moment `minAppVersion` moves again — 07-02 would move it to 1.11.4, 07-06's settings-tab split invites 1.13.0 — because that is when the accumulated identical rows start actively misleading, claiming every past release needs the new floor. The change is one condition in `bump-plugin-version.mjs`, and the right time is the next `minAppVersion` bump, not before.

### 07-16. A bundled YAML parser duplicates `parseYaml` — covered by 04-04

`src/model/card.ts:12` imports `parse` from the `yaml` package (a runtime dependency in `package.json`, bundled into `main.js`) while Obsidian exports `parseYaml` (`obsidian.d.ts:4817`) and `stringifyYaml` (`:6815`) for free. It is written up as **04-04**; the convention behind it is `developer-docs: Obsidian October plugin self-critique checklist.md#Security` — "Do be mindful of all dependencies you add to your plugin. Remember that less is safer." Recorded here because it is the one dependency in the bundle with a first-party Obsidian equivalent, and the build section would otherwise read as if the dependency list were checked and clean; the finding itself lives in section 04. Worth knowing when triaging it: `src/model/` is deliberately Obsidian-free and that boundary is enforced by `pnpm architecture:check`, so adopting `parseYaml` there means injecting a parser from `src/obsidian/` rather than adding an import.

### 07-17. The bundle carries no "generated file" banner, and the manifest carries no build attestation

- **Folia:** `esbuild.config.mjs` sets no `banner`. Separately, `.github/workflows/release.yml` attests build provenance for `dist/main.js` and `dist/styles.css` but not for `dist/manifest.json`, although all three are uploaded.
- **Obsidian:** the sample plugin's `esbuild.config.mjs` opens with a `banner` constant reading "THIS IS A GENERATED/BUNDLED FILE BY ESBUILD / if you want to view the source, please visit the github repository of this plugin", passed as `banner: { js: banner }`. Nothing in the policies, the submission requirements, the guidelines or the October checklist mentions a banner — a sweep of the developer-docs clone returns nothing — so that half is a sample-plugin convention, not a rule. The attestation half does have a source: `developer-docs: Plugins/Releasing/Release your plugin with GitHub Actions.md` lists three subject paths, `main.js`, `manifest.json` and `styles.css`, and calls the attestation "recommended when you submit a plugin to the community directory".
- **Differs:** anyone opening a released `main.js` lands on minified output with nothing saying where the source lives, and the one asset that carries the plugin's identity is the one nobody can verify came from this repository.
- **Read:** **not worth it** for the banner, since `README.md` and the manifest's `authorUrl` both point at the repository and the release is built from a tagged commit; it becomes worth it only if the plugin is distributed outside the directory, where the manifest does not travel with the file. **Clear win** for the attestation, which is one more path in a list that already has two, and is the half with a written recommendation behind it.

## Documentation and claims

### 07-18. `README.md` says the plugin "makes no network requests at all" under a privacy heading, while the MCP server listens

- **Folia:** `README.md:345` ("Your data stays yours"), whose claim is at `:347` — "there is **no database, no account, no sync service, and no telemetry** — the plugin makes no network requests at all." The MCP server is disclosed properly and at length 32 lines earlier (`README.md:315`, "Agent access (MCP)"), which names the bearer token, the loopback default and the bind-address setting and links `docs/mcp.md`.
- **Obsidian:** `developer-docs: Community directory/Developer policies.md#Disclosures` requires network use to be "clearly indicated in your README", explaining "which remote services are used and why they're needed"; `developer-docs: Obsidian October plugin self-critique checklist.md#Security` carries the same requirement as a checklist line naming "network use, external file access".
- **Differs:** the claim is true as written — nothing in `src/` calls `fetch` or `requestUrl`, so there are no outbound requests — but it sits in the section a privacy-minded reader goes to first, and inbound listening is what that section does not mention. The policy's own wording is about remote services rather than about hosting a socket, so the disclosure duty is discharged by the MCP section; what is at risk is the reader, and a reviewer meeting the two sections in the wrong order. The neighbouring disclosure item, "Accessing files outside of Obsidian vaults", does not apply: the only absolute path the plugin produces is `src/obsidian/vaultRepo.ts:732` (`absolutePath`), which resolves a path inside the vault for the clipboard (`src/ui/App.tsx:465`, documented at `README.md:343`).
- **Read:** **clear win.** A half-sentence in the privacy section pointing at agent access ("except the local server you can switch on for agent access, which never makes an outbound request either") keeps the claim and removes the seam.

### 07-19. Three bundled dependencies ship no licence notice, and nothing in the repository supplies one

- **Folia:** `main.js` bundles seven runtime dependencies (`package.json`: `react`, `react-dom`, the three `@dnd-kit/*` packages, `yaml`, `zod`), all MIT or ISC. `README.md`'s only licence content is its own badge (`:8`) and `AGPL-3.0 © Rafael Stavarengo` (`:389`).
- **Obsidian:** `developer-docs: Community directory/Developer policies.md#Copyright and licensing` — "Comply with the original licenses of any code your plugin or theme makes use of, including attribution in the README if required." MIT requires its copyright notice to travel with substantial portions of the code.
- **Differs:** partly, and less than it first looks. esbuild's `legalComments` defaults to `eof` when bundling, so a production `main.js` does carry the four `@license React` blocks with their Facebook copyright lines — React's notices ship, unasked. `@dnd-kit/*`, `yaml` and `zod` publish no legal comment in their distributed code, so there is nothing for esbuild to relocate and their notices appear nowhere in what ships.
- **Read:** **clear win**, and a small one. The esbuild setting is not the lever: `inline`, `eof` and `external` only move comments that already exist, so changing it does nothing for the three packages that lack them. What reaches those is a "Third-party licences" line in `README.md`, which is also what the policy actually names. Worth noting that the sample plugin sets no `legalComments` either, so this is the ecosystem default rather than a Folia peculiarity.

Every Obsidian member Folia calls unconditionally is `@since` 1.7.2 or earlier; the newest is `Workspace.revealLeaf` (`obsidian.d.ts:8029`, `@since 1.7.2`), and the next few down are `FileManager.trashFile` (1.6.6), `AbstractInputSuggest` (1.4.10), `FileManager.processFrontMatter` (1.4.4), `Vault.createFolder` (1.4.0) and `Vault.process` (`obsidian.d.ts:7510`, 1.1.0). The submission requirements name `SubtleCrypto` as the Web alternative to Node's `crypto` and do not mention `getRandomValues`, but the principle — a Web API rather than the Node module — is the one being followed.

No leaf is detached in unload, which is `obsidianmd/detach-leaves` and the guideline behind it.
- Commands use the right callback type: `callback` for the unconditional "Open board", `checkCallback` for the two board-setup commands that only apply to some notes (`src/main.ts:380`, `:389`). No default hotkey is set anywhere.
- The settings tab uses `new Setting(containerEl).setName(...).setHeading()` for section headings (`src/main.ts:922`, `:929`) rather than raw `<h1>`/`<h2>`, and has no top-level "Settings" heading.

- `scripts/bump-plugin-version.mjs` covers what the sample's `version-bump.mjs` covers and more: it writes the manifest version, the `versions.json` row from `minAppVersion` and the `package.json` version, takes the version from `argv` rather than an `npm version` lifecycle variable, and refuses a non-semver or `v`-prefixed tag and an empty `minAppVersion`. The sample never touches `package.json` and validates nothing. Where it is stricter than Folia's is the `versions.json` row, which it writes only when absent — see 07-14.

The same goes for the transport as a whole — Obsidian provides no sanctioned route for a plugin to *host* a server. `requestUrl` is outbound-only, and no local-REST convention exists in the developer docs, the typings or the ESLint rules, so `mcpHttpServer.ts` is not side-stepping an Obsidian facility, it is filling an absence.

The typing's own comment two lines above sanctions it: "Only implement display() as a fallback for plugins that need to support Obsidian versions older than 1.13.0", which is exactly what `minAppVersion` 1.7.2 requires. The renderer is `MarkdownRenderer.render`, not the deprecated `renderMarkdown` (`obsidian.d.ts:4137`). This is the October checklist's "scan your code for deprecated methods" item, and it is the one deprecation the plugin knowingly carries — worth remembering when 07-05's settings-tab split is done.
- No `process.platform` and no global variables: `src/` contains no `process.` reference and no module-level mutable state, covering two more October checklist lines.

The ribbon tooltip does say "Open Folia Kanban board" (`src/main.ts:138`), but a ribbon tooltip is not a command name and neither rule reaches it.
- The release uploads the three files the directory expects as separate assets — `dist/main.js`, `dist/manifest.json`, `dist/styles.css` (`.github/workflows/release.yml`) — and tags plain semver with no `v` prefix (`.release-it.json`, re-checked in `release.yml`), which is `developer-docs: Plugins/Releasing/Submit your plugin.md`.

Nothing in this section is marked **decided**, but 07-01 and 07-06 are both arguably owed an entry, and the release decision shows the project already writes them somewhere other than `docs/decisions.md`.

## Verified live

Checked on 2026-08-29 against the running Obsidian 1.13.7 desktop build with the repository's `examples` vault open, through the Chrome DevTools bridge. Runtime values were read from the app's own objects; where `app.js` is cited, the app's bundle was read from `app://obsidian.md/app.js` and is minified, so what is quoted is behaviour read off the implementation rather than a documented contract.

- Obsidian enforces `isDesktopOnly` against `Platform.isDesktopApp`, not `Platform.isDesktop`: `enablePlugin` returns early when `!isDesktopApp && manifest.isDesktopOnly`, and the community-plugin modal shows its "unsupported" warning on the same test.
