# UI components and primitives

Every place Folia draws a control with its own JSX or DOM code where Obsidian ships a component, a primitive or a helper that does the same job: menus, modals, suggesters, setting rows, notices, icons, tooltips, buttons, progress bars. Read for this section: all of `src/ui/*.tsx` (`AddColumn`, `App`, `Board`, `CardContextMenu`, `CardDetail`, `CardItem`, `Column`, `ColumnEditModal`, `ColumnMenu`, `Markdown`, `Toolbar`, `icons`), `src/ui/cardView.ts`, `src/ui/context.ts`, `src/obsidian/propertySuggest.ts`, `src/settings.ts`, `src/settingsLayout.ts`, `src/main.ts` where it builds UI, `src/view.tsx`, plus the guards `test/a11y.axe.test.tsx`, `scripts/check-a11y-exceptions.mjs`, `scripts/check-portal-scope.mjs` and `scripts/check-button-styles.mjs`.

## The constraint every finding here runs into

`src/ui/**` contains no import from `obsidian` at all. Every Obsidian import in the plugin lives in `src/main.ts`, `src/view.tsx`, `src/viewMode.ts`, `src/settingsDefinitions.ts` and `src/obsidian/**`; the React tree reaches the app only through the `CardRepository` port (`src/model/repo.ts`), which is why `test/ui.test.tsx`, `test/a11y.axe.test.tsx` and `test/visual-regression.test.tsx` can render the real `<App/>` under jsdom against `test/fakeRepo.ts`. A component that called `new Menu()` or `new Notice()` directly would not render there.

So for a finding inside `src/ui`, "use the Obsidian component" always means one of two things, and each finding says which: add a port method on `CardRepository` (the pattern `src/obsidian/propertySuggest.ts` already proves — the native class lives in `src/obsidian/`, the UI calls `repo.suggestProperties(el, source)` declared at `src/model/repo.ts:163`, and `test/fakeRepo.ts:420` supplies a no-op), or break that boundary and give the tests an Obsidian stub. The port route is the cheap one and it has precedent; it is still a new method plus a fake per component. Findings in `src/main.ts` and `src/view.tsx` carry none of this cost, because those files already import from `obsidian`.

Obsidian's own `CHANGELOG.md` in the installed package stops at 1.7.2 (its newest heading is `:5`), so "which version added this" is read from the `@since` tags in `obsidian.d.ts` instead. Anything without a version note here predates the plugin's `minAppVersion` 1.7.2 (`manifest.json`) and is available unconditionally.

The version floor is not advisory. `eslint.config.mjs:198` spreads `obsidianmd.configs.recommended` over `src/**`, and that preset enables `obsidianmd/no-unsupported-api` — "Disallow usage of Obsidian APIs not available in the plugin's minimum app version", which reads `minAppVersion` straight out of `manifest.json`. So every member marked here as `since 1.8.7` or later is a lint error the moment it is written, unless it goes behind the pattern `src/main.ts:902` already uses: `requireApiVersion("1.13.0")` with a fallback for older builds. Each finding says where that applies.

## Menus and popovers

### 01-01. The card context menu is a hand-built popover where `Menu` is the native answer

- **Folia:** `src/ui/CardContextMenu.tsx:39` (`CardContextMenu`) — a ~235-line component (the file is 273 lines) that portals a `role="menu"` div to `activeDocument.body`, measure and clamp it to the viewport (`:70-71`), close it on a document `pointerdown` (`:90`), roll their own arrow-key roving focus over `.folia-menu-item:not(:disabled)` (`:95`), restore focus to the opener unless an item ran (`:78`), and draw dividers (`.folia-menu-divider`), section labels (`.folia-menu-label`), a danger item (`folia-menu-danger`, `:120`) and two radio grids (`role="menuitemradio"`, `:165` and `:219`) by hand.
- **Obsidian:** `Menu` (`obsidian.d.ts:4245`) with `addItem` (`:4269`), `addSeparator` (`:4275`), `showAtMouseEvent` (`:4285`), `showAtPosition` (`:4290`), and `Menu.forEvent(evt)` (`:4307`, since 1.6.0); `MenuItem` (`obsidian.d.ts:4313`) with `setTitle`, `setIcon`, `setChecked` (`:4336`), `setDisabled` (`:4341`), `setWarning` (`:4348`, "title and icon will become red, or whatever colour a theme applies to `is-warning`"), `setIsLabel` (`:4353`) and `setSection` (`:4367`). `developer-docs: Plugins/User interface/Context menus.md` documents exactly this shape, including the `showAtPosition` tip. `Menu.setUseNativeMenu` (`:4262`) additionally lets the desktop app draw an OS-native menu.
- **Differs:** every affordance in the hand-built version maps onto one of those: the danger item onto `setWarning`, the section labels onto `setIsLabel`/`setSection`, the radio grids onto `setChecked`, the dividers onto `addSeparator`, and the placement onto `showAtMouseEvent`/`showAtPosition`. Placement is the only one of those the typings actually promise: nothing in the `Menu` contract documents focus restoration, roving focus or viewport clamping, so a swap inherits the app's own menu behaviour rather than a documented guarantee (see 06-01). What the hand-built version has that `Menu` does not is layout: the priority row and the column row are grids of chips, several per line, drawn with the board's own priority tones, whereas `Menu` is a single vertical column of rows. Converting them to `setChecked` items would make the menu much taller and lose the colour coding. It also renders inside the React tree, where the plugin's own tests could reach it — though today's axe gate opens only the board and the detail panel (`test/a11y.axe.test.tsx:77-105`), so the menu is not actually covered by it either.
- **Read:** **trade-off.** The item list — open, rename, mark done, assign, copy path ×4, move up/down, add subcard, delete — is a plain `Menu`. What that demonstrably gains is the app's own look, its phone presentation (`.is-phone .menu` is a bottom sheet, observed in the 1.13.7 stylesheet) and the OS-native option, while dropping the viewport math, the roving-focus loop and the focus-restore ref. What it gains in keyboard behaviour and dismissal is the app's implementation rather than a promise: the typings document neither, so a swap has to be tested for them rather than assumed to fix them. The two chip grids are the real cost: as `setChecked` items they become long flat lists, so the honest shape is a native `Menu` for the items plus something else for priority and column, which is more surfaces, not fewer. Also needs a `CardRepository` port method and a `FakeRepo` no-op.
- **Guard:** `tracking/waivers/0002-automated-a11y-gate.md` holds two open behavioural gaps that are directly this finding: "the card context menu is pointer-only, leaving keyboard users without a path to it", and "arrow-key navigation inside `CardContextMenu` doesn't reach the priority radio group". A native `Menu` shown from a keyboard handler via `showAtPosition` answers the first; the second would rest on the app's own menu keymap, which the typings do not describe. `scripts/check-portal-scope.mjs` separately requires the `folia-scope` class on the portalled root (`src/ui/CardContextMenu.tsx:135`) so the `--folia-*` tokens resolve outside the board. Unlike `ColumnMenu`, this file needs no a11y waiver in `eslint.config.mjs:28-41`: its root carries `role="menu"` and `tabIndex={-1}`, so `jsx-a11y` sees an interactive element.

### 01-02. The column popover is a menu with form fields in it, so only half of it is a `Menu`

- **Folia:** `src/ui/ColumnMenu.tsx:33` (`ColumnMenu`) — a `role="dialog"` popover portalled to the body, positioned against the trigger's rect with a hard-coded `MENU_W = 224` (`:15`), closed on a document `mousedown` (`:66`), returning focus to the trigger on unmount (`:71`). It holds a rename input (`:101`), a colour swatch grid (`:119`), a WIP-limit number input (`:144`), six menu items with dividers, and an inline delete confirmation (`:220`, guarded from `:215`).
- **Obsidian:** `Menu`/`MenuItem` as in 01-01, plus `Setting` (`obsidian.d.ts:5695`) with `addText` (`:5807`) and `addColorPicker` (`:5837`) for the field half, and the popover CSS variables (`developer-docs: Reference/CSS variables/Components/Popover.md`) that a native menu already honours.
- **Differs:** `MenuItem.setTitle` takes a `string | DocumentFragment` and `onClick` — it is a row that fires, not a container that can host a live text input the user types into and that commits on blur. The rename field, the WIP field and the swatch grid have no `Menu` equivalent, so a native menu here means either splitting the popover in two (a `Menu` for the actions, a `Modal` for the fields — but `ColumnEditModal` already exists and already holds all of them) or keeping a custom popover.
- **Read:** **trade-off, leaning towards deleting the overlap.** The six action rows (edit, collapse all, expand all, move left, move right, delete) are a textbook `Menu`, and the fields duplicate `ColumnEditModal` (`src/ui/ColumnEditModal.tsx:128`, `:142`, `:170`) which the popover's own "Edit column…" item opens. The version worth having is probably a native `Menu` whose fields moved into the modal that already has them — that removes the second copy of title/colour/WIP as well as the popover code — but it is a UX change (two clicks to rename instead of one), not a mechanical swap, so it is a decision rather than a refactor. Same port cost as 01-01.
- **Guard:** `scripts/check-a11y-exceptions.mjs` re-runs `jsx-a11y/no-noninteractive-element-interactions`, which `eslint.config.mjs:31` switches off for this file and the two others named at `:30`, and requires the waiver comment at `src/ui/ColumnMenu.tsx:90` — the popover's root is a `role="dialog"` with an `onKeyDown`, which is exactly the shape a native `Menu` would not have. `scripts/check-portal-scope.mjs` requires the `folia-scope` class on the portalled root (`:92`).

## Modal and setting rows

### 01-03. The edit-column modal builds its own dialog shell where `Modal` provides one

- **Folia:** two shells, not one. `src/ui/CardDetail.tsx` is the larger: three `role="dialog"` returns (`:1285` the create form, `:1357` the card-not-found state, `:1430` the card itself), each with `aria-modal={mode === "modal"}`, `tabIndex={-1}`, a hand-written Escape handler (`:1242`) and focus capture/restore (`:1098-1102`), and in modal mode a backdrop portalled by `src/ui/App.tsx:917-927`. `src/ui/ColumnEditModal.tsx:49` (`ColumnEditModal`) is the smaller and the more mechanical: `createPortal` into `activeDocument.body` (`:276`) of a `.folia-modal-backdrop` that closes on a backdrop `pointerdown` (`:105`), wrapping a `role="dialog" aria-modal="true"` div with a hand-written Escape handler (`:93`), a hand-written focus-on-open (`:55`), a header with its own close button (`:120`) and a footer with Cancel/Save (`:266`).
- **Obsidian:** `Modal` (`obsidian.d.ts:4477`), with `containerEl`/`modalEl`/`titleEl`/`contentEl`, `open()`/`close()`, `setTitle` (`:4538`), `setContent` (`:4542`), `setCloseCallback` (`:4548`, since 1.10.0, above the 1.7.2 floor — see the preamble), `shouldRestoreSelection` (`:4508`) and — the part that matters most — a `scope: Scope` (`:4485`) that owns Escape and the modal keymap. `developer-docs: Plugins/User interface/Modals.md` shows the shape, including a `Modal` whose body is built from `Setting` rows. Theme-facing variables: `developer-docs: Reference/CSS variables/Components/Modal.md` (`--modal-background`, `--modal-width`, `--modal-radius`, `--modal-max-height`, …), with `Dialog.md` and `Prompt.md` covering the two narrower shapes Obsidian builds on the same shell.
- **Differs:** the in-house shell reimplements the backdrop, the scrim, the Escape key, the dialog roles and the width/height constraints, and it is styled from `--folia-*` tokens rather than the `--modal-*` ones, so a theme that restyles Obsidian's modals leaves this one alone. What it gains is that its children are React components reading React context (`useBoardActions`). A native `Modal` can host a React root in its `contentEl`, so that is solvable, but the mount then lives outside the component tree. It does *not* gain a focus trap: `tracking/waivers/0002-automated-a11y-gate.md` records, as an open item, that "modal dialogs (`ColumnEditModal`, modal `CardDetail`) declare a modal role without a real focus trap or background `inert`, so focus can escape behind the dialog" — which adopting `Modal` does not by itself settle. `Modal` documents a `scope: Scope` (`obsidian.d.ts:4485`) that owns Escape and the modal keymap, and the app's own dialogs behave as modal dialogs, but neither the typings nor `developer-docs: Plugins/User interface/Modals.md` promises a focus trap or an inert background. Moving to `Modal` therefore hands that behaviour to the app's implementation rather than to a contract, and it still needs checking (see 06-02 and 06-03).
- **Read:** **trade-off, and the closest thing here to a clear win.** Both shells are duplication of `Modal`, including the keyboard behaviour that `Scope` gives away; hosting a React root in `contentEl` keeps the bodies as they are. `ColumnEditModal` is the one to try it on, and 06-02 reads that half alone as a clear win: it is always a dialog, whereas `CardDetail` is a dialog only in one of its three presentation modes and is a side panel in the other two, so a native `Modal` there would mean two mount paths for one component. The cost is real and specific: a port method plus a fake, and `scripts/check-portal-scope.mjs:30-32` only recognises two container shapes — anything matching `/(^|\.)body$/`, and `rootRef.current` — and *errors* on anything else. A native `Modal`'s `contentEl` is neither, so the script would have to be taught it. (A body-shaped container is already fine: `src/ui/Board.tsx:451` portals to `boardRef.current.ownerDocument.body` and passes.)
- **Guard:** `scripts/check-a11y-exceptions.mjs` covers the `jsx-a11y/no-noninteractive-element-interactions` waiver at `src/ui/ColumnEditModal.tsx:109` (off for this file at `eslint.config.mjs:31`, for the three files named at `:30`); `scripts/check-portal-scope.mjs` requires the `folia-scope` class at `:104`.

### 01-04. The edit-column fields are label/input pairs where `Setting` and its components exist

- **Folia:** `src/ui/ColumnEditModal.tsx:126-263` — nine controls built as `<label className="folia-field">` wrappers: a text input for the title (`:128`), a swatch grid for the colour (`:142`), a `type="number"` WIP limit (`:170`), a text filter rule with a hint span (`:182`), two `<select>` dropdowns for group and sort (`:196`, `:207`), two `type="range"` sliders for opacity and hover reveal (`:221`, `:238`), and a bare `<input type="checkbox">` for "Park aside" (`:251`). The same pattern recurs elsewhere: `src/ui/CardDetail.tsx` has a `<select>` for status at `:1530` and a second for each subtask's column at `:1824`, an `<input type="date">` at `:1565` and an `<input type="checkbox">` per subtask at `:1778`. Four bare `<textarea>` elements sit in the same category — `src/ui/CardDetail.tsx:329` (edit a comment), `:1647` (the description editor), `:1992` (write a comment) and `src/ui/Column.tsx:598` (the inline add-card box).
- **Obsidian:** `Setting` (`obsidian.d.ts:5695`) with `setName`, `setDesc`, `setHeading` (`:5781`), `setDisabled` (`:5786`, since 1.2.3), `setErrorMessage` (`:5743`, since 1.13.0 — above the floor, so it needs the `requireApiVersion` gate the plugin already uses at `src/main.ts:902`), and the control builders `addText` (`:5807`), `addTextArea` (`:5822`), `addDropdown` (`:5832`), `addToggle` (`:5802`), `addSlider` (`:5847`), `addColorPicker` (`:5837`, since 0.16.0), `addButton` (`:5792`), `addExtraButton` (`:5797`), `addSearch` (`:5817`), `addProgressBar` (`:5842`, since 1.4.4) and `addComponent` (`:5812`, since 1.11.0, also above the floor). The underlying classes are also usable on their own: `ToggleComponent` (`:7155`), `SliderComponent` (`:6722`), `DropdownComponent` (`:2299`), `TextComponent` (`:7030`), `ColorComponent` (`:1647`). Theme variables for what they render: `developer-docs: Reference/CSS variables/Components/Toggle.md`, `Checkbox.md`, `Slider.md`, `Dropdowns.md`, `Text input.md` and `Color input.md`.
- **Differs:** the "Park aside" checkbox is the sharpest case. `Setting.addToggle` renders Obsidian's own switch — the thing every other toggle in the app looks like, sized by `--toggle-width`/`--toggle-thumb-*` and given a larger touch target on mobile — while `<input type="checkbox">` is the browser's box, which no Obsidian theme styles and which reads as foreign inside the app. The two range sliders lose `--slider-track-*`/`--slider-thumb-*` the same way, the four selects lose the dropdown styling, and the four textareas lose what `TextAreaComponent`/`addTextArea` render. The description editor is the one textarea worth arguing about separately: it is a full markdown editing surface with its own save/revert/refusal flow, which `addTextArea` would only wrap, not replace. The colour swatch grid is *not* a match for `addColorPicker`: it offers a fixed palette from `src/ui/columnColors.ts`, and `ColorComponent` is a free colour input, so swapping it would change what the control does. The in-house rows do carry things `Setting` does not offer directly: the hint text under the filter field (`:188`) and the live "Opacity — 55%" label that updates as the slider moves (`:220`).
- **Read:** **trade-off, worth taking for the toggle and the sliders specifically.** Those three controls are the ones users can see are not Obsidian's, and `src/main.ts:939-983` already drives `addToggle`/`addDropdown`/`addSlider`/`addText` correctly, so the plugin knows the API. Adopting them inside `src/ui` needs 01-03's answer first, since a `Setting` wants a container element and the natural container is a native `Modal`'s `contentEl`. The swatch grid should stay as it is.
- **Backlog:** `docs/ai/backlog/20260827.10.separate-state-from-settings-and-design-shared-state.md` touches the same modal from the state side, not the control side.

## Tooltips, suggestions and notices

### 01-05. Thirty-six `title` attributes where `setTooltip` renders Obsidian's own tooltip

- **Folia:** 36 `title` attributes across `src/ui/*.tsx` — 24 written as literals and 12 as JSX expressions (`title={…}`, e.g. `CardItem.tsx:248`/`:254`/`:264`/`:302`/`:361`/`:404`, `CardDetail.tsx:269`/`:513`/`:604`/`:1453`/`:1827`, `Column.tsx:464`), which matters because an expression site is a different mechanical swap from a literal — 20 in `CardDetail.tsx` (for example `:470` explaining what the file-name field renames, `:1470` "Open note in Obsidian", `:1308` "Close (Esc)"), 9 in `CardItem.tsx` (`:248` the context label, `:264` the subtask progress, `:361` the parent reference), 2 each in `Column.tsx` (`:436` "Drag to reorder, click to rename", `:464` the WIP count) and `CardContextMenu.tsx`, and one each in `ColumnMenu.tsx`, `ColumnEditModal.tsx` and `Toolbar.tsx`.
- **Obsidian:** `setTooltip(el, tooltip, options?)` (`obsidian.d.ts:6711`, since 1.4.4) and `displayTooltip` (`:2258`), with `TooltipOptions` (`:7201`) carrying `placement`, `delay` (since 1.4.11) and `classes`/`gap` (both since 1.8.7, above the floor). `setTooltip` itself (1.4.4) and `placement` are below it; `displayTooltip` is `@since 1.8.7` and is not. Obsidian's tooltip is a real element in the app's own layer stack — `--layer-tooltip: 70` in `developer-docs: Reference/CSS variables/Foundations/Layers.md`, and `--line-height-tight` is documented as used in tooltips in `Typography.md`. Every component class also exposes it directly (`ButtonComponent.setTooltip` at `:1376`, `ToggleComponent.setTooltip` at `:7187`, `Setting.setTooltip` at `:5776`).
- **Differs:** a `title` attribute is drawn by the OS/browser, not by Obsidian: it appears after the browser's own delay, in the browser's own chrome, with no theme, no placement control and no way to sit in the app's layer stack. Observed in Obsidian 1.13.7: the app's tooltip is a `div.tooltip` appended to the document body at `z-index: 70`, and it is driven by `aria-label`, not by `title` — hovering a Folia element that carries only `aria-label` produced it, hovering one that carries only `title` did not (see Verified live). That also means the 93 rendered board elements that carry both attributes already get Obsidian's tooltip from their `aria-label`, so the `title` there is redundant rather than the only tooltip they have. Inside a plugin view, next to controls whose tooltips are Obsidian's, the difference is visible. `setTooltip` takes an `HTMLElement`, so in React each of the 36 sites becomes a ref plus an effect (or one small `useTooltip` hook doing both), which is why the count matters more than any single site.
- **Read:** **trade-off.** Visually and behaviourally the native tooltip is the right one and a single hook would cover all 36 sites, but the hook has to reach `setTooltip`, which is an `obsidian` import inside `src/ui` — so it is the same port question as everything else here, for a payoff that is cosmetic rather than functional. Note the sites are not interchangeable: several `title` values duplicate an `aria-label` that is already the accessible name verbatim (`CardItem.tsx:264`/`:265` and `:302`/`:303`), and those are about the pointer only.

### 01-06. Five suggesting inputs, four of them not Obsidian's

- **Folia:** five inputs in the plugin offer suggestions as you type, and they answer the keyboard four different ways. The board's search box in `src/ui/Toolbar.tsx:184-250` is a hand-built combobox — `role="combobox"` with `aria-expanded`/`aria-controls`/`aria-activedescendant` (`:194`), a `role="listbox"` (`:226`) of `role="option"` buttons (`:233`), its own arrow/Enter/Tab/Escape handling (`:147`), its own highlight index and its own `onMouseDown`-before-blur commit trick (`:238`), over the filter grammar in `suggestionsFor` (`:59`). Three `<datalist>` elements back the rest: priority (`src/ui/CardDetail.tsx:187`), assignee (`:279`), and one shared list (`:1926`, built once because every relationship field offers the same cards — see the comment at `:856`) consumed by the relationship input at `:698`, which renders once per relationship type the board declares. So three datalists, but more than three inputs behind them on a board with several relationship types. Only the property-name field goes through Obsidian: `src/obsidian/propertySuggest.ts:20` (`PropertyNameSuggest extends AbstractInputSuggest`), reached from `src/ui/CardDetail.tsx:924` via the `suggestProperties` port.
- **Obsidian:** `AbstractInputSuggest<T>` (`obsidian.d.ts:294`), which takes an `<input>` or a contenteditable div, with `getSuggestions` (`:325`), `renderSuggestion` (via `PopoverSuggest`, `:5219`), `selectSuggestion` (`:330`, since 1.6.6), `onSelect` (`:336`, since 1.4.10) and `limit` (`:301`, since 1.4.10). The official community lint has a codified rule for this: `obsidianmd/prefer-abstract-input-suggest` ("Disallow Liam's frequently copied `TextInputSuggest` implementation in favor of the built-in `AbstractInputSuggest`", warns in `recommended`).
- **Differs:** `AbstractInputSuggest` gives the popup Obsidian's `suggestion-*` markup and theming, its keyboard scope and its placement, and lets a row carry a secondary note — `propertySuggest.ts:53-58` uses exactly that (`mod-complex`, `suggestion-content`, `suggestion-title`, `suggestion-note`). The `<datalist>` popups are the browser's, and the Toolbar combobox is a third look with a third set of key handlers. The one genuine obstacle — that `AbstractInputSuggest` writes the picked value straight into the input, which a React-controlled field reverts — is already solved in the repository: `propertySuggest.ts:68` overrides `selectSuggestion` to hand the value to the caller's state instead. So the mechanical objection is answered by working code, though the Toolbar has one wrinkle the property field does not: it replaces a fragment inside a controlled query and restores the caret afterwards through a `requestAnimationFrame`, which any host suggester would still have to drive from its own selection callback.
- **Read:** **clear win for the Toolbar box, trade-off for the datalists.** The Toolbar's ~80 lines of combobox are the plugin's most elaborate reimplementation of a control that exists, and nobody has counted it: entry `20260829.06` names the three datalists and the one native popup and stops there. The datalists are cheaper as they are and their own entry already frames the choice; what is new here is that there are five suggesting inputs, not four, and that the official lint has a rule about it.
- **Backlog:** `docs/ai/backlog/20260829.06.detail-panel-suggests-in-two-different-ways.md` covers the three `<datalist>` fields and the property-name popup; it does not cover the Toolbar.

### 01-07. The board draws its own toast where `Notice` exists

- **Folia:** `src/ui/App.tsx:143` holds `toast` state, `showToast` (`:153`) sets it with a `window.setTimeout` of 4000 ms for errors and 2200 ms otherwise and clears the previous timer, a cleanup effect clears it on unmount (`:161`), and `:928-937` renders a `role="status" aria-live="polite"` div with an icon and the text, at `--folia-z-index-toast: 50`. `reportError` (`:158`) funnels every board and panel write failure through it, and `BoardActions.reportError` (`src/ui/context.ts:175`) is how the detail panel reaches it. Three more user-facing messages bypass it entirely and are drawn in place: `src/ui/App.tsx:895` (`role="status"`, the card-folder warning) and `src/ui/CardDetail.tsx:1675` (`role="alert"`, why a description was refused) and `:1687` (`role="status"`, the note moved on while you were editing). Two whole-surface states replace the board rather than message over it: `src/ui/App.tsx:816` ("Couldn't load the board") and `:817` ("Loading board…").
- **Obsidian:** `Notice` (`obsidian.d.ts:4613`), constructed with `message: string | DocumentFragment` and a `duration` in milliseconds where `0` means "until dismissed", plus `setMessage` (`:4643`) and `hide` (`:4649`), and `containerEl`/`messageEl` (both `@since 1.8.7`, i.e. above the floor and therefore gated — `noticeEl` is deprecated in favour of `messageEl`). `src/main.ts` already uses it in thirteen places (`:299`, `:355`, `:446`, `:455`, `:625`, `:635`, `:645`, `:649`, `:660`, `:671`, `:679`, `:682`, `:887`).
- **Differs:** the toast stacks nothing (a second message replaces the first), lives inside the board's own DOM so it is bounded by the view and needs `--folia-statusbar-clearance` to sit clear of the status bar, and is styled entirely by the plugin. `Notice` renders in the app's notice container, stacks, is dismissible by click, and takes a `DocumentFragment`, which is how the icon-plus-text shape would survive the move — built with Obsidian's own `createFragment` helper, the one `obsidianmd/prefer-create-el` asks for. The constructor's fragment argument carries no version floor; only `messageEl`/`containerEl` would need a gate. Against that: the toast is inside the React tree and the plugin controls its position relative to the board. Note the axe gate never sees it — `test/a11y.axe.test.tsx:77-105` renders four states, none of which raises a failure — so "we would lose test coverage of the live region" is not an argument available here.
- **Read:** **trade-off, and the cleanest port candidate in the section.** Every transient message already funnels through one function, so the port method is a single `repo.notify(text, tone)` and a `FakeRepo` no-op — smaller than any other swap here. The three in-place messages above are a different case and should stay where they are: each is anchored to the control it is about (the refusal names the offending line under the editor that produced it), and a `Notice` in the corner of the app would lose that anchoring. The two whole-surface states at `App.tsx:816-817` have no native equivalent either — the typings carry no empty-state or spinner component — though the load failure is the one message here that `main.ts` would have raised as a `Notice`, so a board that fails to load could reasonably do both. What is lost is the in-view placement — a board message would appear wherever Obsidian puts notices rather than over the board; what is gained is consistency with the notices `main.ts` already raises for the same plugin, which today look nothing like the board's.

## Buttons, icons and small components

### 01-08. Every button is drawn from scratch instead of going through `ButtonComponent`

- **Folia:** thirteen button classes listed together in `src/styles.css:123-135` (`folia-add-column`, `folia-btn`, `folia-card-subitems-toggle`, `folia-column-add`, `folia-desc-empty`, `folia-filter-chip`, `folia-filter-suggest-item`, `folia-icon-btn`, `folia-link`, `folia-menu-column`, `folia-menu-item`, `folia-menu-prio`, `folia-swatch`), plus the modifiers `folia-btn-primary` (`:1189`) and `folia-btn-danger` (`:1202`). Every one of them is dressed by plugin rules and named twice in its selector to out-specify Obsidian's own `button:not(.clickable-icon)`.
- **Obsidian:** `ButtonComponent` (`obsidian.d.ts:1325`) builds the app's own button and carries the two variants by name: `setCta()` (`:1346`) for a primary action and `setDestructive()` (`:1366`, since 1.13.0, above the floor) for one that deletes or is hard to undo, composable as `setDestructive().setCta()`; `setWarning()` (`:1358`) is the deprecated spelling of the second. `ExtraButtonComponent` (`:2841`) is the icon-only button, with `setIcon` (`:2868`) and `setTooltip` (`:2861`) — the exact shape of the eighteen `folia-icon-btn` sites — `src/ui/ColumnEditModal.tsx:120`, `src/ui/Toolbar.tsx:214`, `src/ui/Column.tsx:484`, `src/ui/CardItem.tsx:377`/`:389`/`:402` and twelve in `src/ui/CardDetail.tsx` (`:140`, `:347`, `:358`, `:596`, `:1306`, `:1367`, `:1459`, `:1468`, `:1476`, `:1484`, `:1751`, `:1863`) — each of which pairs an `<Icon>` with an `aria-label` and a `title` by hand. Obsidian's theme excludes icon buttons from the plain-button face by class — `--clickable-icon-radius` is the documented variable for them (`developer-docs: Reference/CSS variables/Foundations/Icons.md`) — and `--button-radius` is the button variable (`developer-docs: Reference/CSS variables/Components/Button.md`), with interactive colours in `Foundations/Colors.md`.
- **Differs:** `folia-btn-primary` is `setCta()` reimplemented, `folia-btn-danger` is `setDestructive()`, and `folia-icon-btn` is `ExtraButtonComponent`. The concrete price is `scripts/check-button-styles.mjs`: 269 lines of CSS-specificity arithmetic whose only job is to keep the plugin's own button rules winning against a theme rule they would otherwise silently lose to in the real app — a class of bug jsdom cannot see, which is why the script exists at all. Wearing the native classes removes that whole class of bug. Against it: the board deliberately has its own visual system (`src/styles.css:1-24`); menu items, chips and swatches genuinely have no native counterpart; and `setDestructive` is 1.13.0, so the danger button would need the `requireApiVersion` gate or the deprecated `setWarning()`. `src/ui/AddColumn.tsx:19` and `:43-58` are the same pattern in miniature — an icon-plus-label button, then a `folia-btn-primary`/`folia-btn` action pair, all hand-drawn.
- **Read:** **trade-off, and the boundary is worth drawing explicitly.** The three that have an exact native equivalent (primary, danger, icon-only) are where adopting the native route pays for itself in guard surface; the rest are Folia's own vocabulary and should stay. This finding is about the *component* choice; the wider inventory of Obsidian CSS variables and classes belongs to section 02, which overlaps here.
- **Guard:** `scripts/check-button-styles.mjs` — it also refuses any `<button>` in `src/ui/**` that carries no `folia-*` class, so "just drop the class and let the theme dress it" fails the check as written today.
- **Backlog:** `docs/ai/backlog/20260829.02.every-other-folia-link-still-wears-the-theme-button-shape.md` and `docs/ai/backlog/20260829.01.doubled-class-rules-silently-out-rank-their-own-neighbours.md` are both consequences of this choice.

### 01-09. Twenty-three Lucide icons redrawn by hand where Obsidian bundles Lucide

- **Folia:** `src/ui/icons.tsx` — a 23-entry `IconName` union (`:5-28`) and a `PATHS` record of hand-written SVG path data (`:30-135`), rendered by an `Icon` component (`:142`) that emits a `24×24` viewBox SVG with `stroke="currentColor"`, `strokeWidth={2}`, round caps and joins, `aria-hidden`, `focusable="false"` and a `folia-icon` class. The file's own header says the geometry is Lucide's.
- **Obsidian:** the app bundles the Lucide library — "Obsidian uses the Lucide icon library, which includes more than 800 icons" (`developer-docs: Reference/CSS variables/Foundations/Icons.md`), capped at Lucide v0.446.0 (`developer-docs: Plugins/User interface/Icons.md`). `setIcon(parent, iconId)` (`obsidian.d.ts:5689`) appends one into an element, `getIcon(iconId)` (`:3351`) returns a detached `SVGSVGElement | null`, `getIconIds()` (`:3357`) lists every registered id, and `addIcon(id, svg)` (`:393`) registers a custom one — the same route `src/main.ts:138` and `src/view.tsx:54` already use for the ribbon icon and the view icon (`layout-grid`).
- **Differs:** `getIcon` returns a real element rather than JSX, so a React wrapper is `useRef` plus an effect calling `replaceChildren` — mechanically fine, but it re-introduces an imperative node inside every tile, chip and button, and every icon then depends on the bundled Lucide version rather than on committed path data. What the in-house version buys is exactly that determinism: the icons render identically in jsdom, which is what `test/visual-regression.test.tsx` snapshots, and they cannot change under the plugin when Obsidian updates Lucide. The names are Folia's own vocabulary (`close`, `alert`, `more`, `message`), not Lucide ids, so a swap is also a rename.
- **Read:** **not worth it as a wholesale swap; worth it for the sizing.** Twenty-three small path constants are cheap to maintain and the visual-regression snapshots depend on them. What would change the answer is any of: needing an icon the file does not have (each new one is hand-drawn path data), wanting the user's icon pack or a theme's icon overrides to apply, or the count growing past what a reviewer can eyeball. The sizing half is a separate, cheaper fix — see 01-10.
- **Guard:** none. Nothing checks that `IconName` entries correspond to anything, or that the geometry stays faithful to Lucide.

### 01-10. Icon sizes are hard-coded pixel props instead of `--icon-size`

- **Folia:** `src/ui/icons.tsx:142` takes `size?: number` defaulting to 16 and writes it to the SVG's `width` and `height`; call sites pass seven distinct literals across `src/ui/*.tsx` — `11` (×4), `12` (×2), `13` (×11), `14` (×7), `15` (×5), `16` (×4) and `20` (×1).
- **Obsidian:** icon size is a CSS variable, not a prop. `--icon-size` is "shorthand for icon width and length", with the preset ramp `--icon-xs: 14px`, `--icon-s: 16px`, `--icon-m: 18px`, `--icon-l: 18px`, `--icon-xl: 32px` and matching `--icon-*-stroke-width` values (`developer-docs: Reference/CSS variables/Foundations/Icons.md`); `developer-docs: Plugins/User interface/Icons.md:24-30` shows the intended usage (`div { --icon-size: var(--icon-size-m); }`), and the changelog entry below shows the same idea as `.parent-element { --icon-size: var(--icon-xs) }`. The API changelog records that `setIcon`'s `size` parameter was *removed* in favour of the variable (`node_modules/obsidian/CHANGELOG.md:238`, in the v1.1.0 "Improved" list at `:235`).
- **Differs:** thirty-four hard-coded pixel values instead of one CSS variable per container. Sizes that are not on Obsidian's ramp (11, 12, 13, 15, 20) are also not sizes any theme can adjust, so an icon in the board stays 13px while every icon around it follows the user's theme.
- **Read:** **clear win, small.** `Icon` can keep its `size` prop for the odd case and otherwise inherit `width: var(--icon-size)`; the call sites become CSS on their containers. No port method needed — it is CSS and one component, entirely inside `src/ui`. It does touch `scripts/audit-raw-values.mjs` territory, and the raw-value inventory belongs to section 02.
- **Guard:** `scripts/audit-raw-values.mjs` and `scripts/raw-value-allowlist.json` police raw values in the stylesheet, not numeric props in TSX, so these thirty-four are invisible to it.

### 01-11. The subtask progress bar is hand-drawn where `ProgressBarComponent` exists

- **Folia:** `src/ui/CardItem.tsx:261-278` — a `.folia-progress` div holding a `.folia-progress-track` and a `.folia-progress-fill` whose `width` is an inline `style` computed as a percentage, plus a `.folia-progress-label` showing `done/total` and a check icon when complete, with `title` and `aria-label` both set to "N of M subtasks done".
- **Obsidian:** `ProgressBarComponent` (`obsidian.d.ts:5291`), constructed on a container element, with `setValue(0-100)`; also reachable as `Setting.addProgressBar` (`obsidian.d.ts:5842`, since 1.4.4).
- **Differs:** `ProgressBarComponent` is a bar and nothing else — no label, no completion state, no accessible name, confirmed by reading its constructor in the running app: it creates `div.setting-progress-bar > div.setting-progress-bar-inner` and `setValue` writes a percentage into the inner element's inline `width`, with no `role`, no `aria-valuenow` and no ARIA of any kind (Obsidian 1.13.7 `app.js`). The Folia version carries all three, and the `is-complete` class drives a different colour. Swapping would mean keeping the label and the naming anyway and gaining only the theme's track styling, at the price of an imperative node inside a memoised card tile that re-renders per card.
- **Read:** **not worth it.** What would change it: if Obsidian's bar gained a label or a value/max accessible pairing, or if the plugin needed a progress bar somewhere the card tile's own layout is not already deciding the geometry.
- **Guard:** the `obsidianmd/no-static-styles-assignment` rule ("Disallow setting styles directly on DOM elements, favoring CSS classes instead", error in `recommended`, enabled here by `eslint.config.mjs:198`) is the nearest thing watching the inline `width` at `:270`. It passes today, so either the rule does not reach a JSX `style` prop or a percentage computed per render counts as dynamic; either way the guard is not the reason this is fine — the reason is that a bar's fill has to be computed.

### 01-12. The search box's chrome is hand-built where `SearchComponent` is the same control

- **Folia:** `src/ui/Toolbar.tsx:186-221` — a `.folia-search` wrapper holding a magnifier `<Icon name="search" size={15} />`, the `<input type="text">` itself, and a conditional "Clear search" button (`:212`) that empties the query. The wrapper carries `role="search"` on the toolbar above it (`:185`).
- **Obsidian:** `SearchComponent` (`obsidian.d.ts:5558`), constructed on a container element, extending `AbstractTextComponent<HTMLInputElement>` (so it has `setPlaceholder`, `setValue`, `onChange`, `inputEl`) and exposing a `clearButtonEl` (`:5563`, since 0.9.21) — Obsidian's own search field with its own clear affordance. Reachable as `Setting.addSearch` (`:5817`) too.
- **Differs:** the two are the same control: a search input with a clear button. Folia's adds the leading magnifier icon and, more importantly, is the anchor for the suggestion listbox in 01-06, which reads the input's `selectionStart` on every render (`:112`) to work out the fragment under the caret. `SearchComponent` gives back `inputEl`, so the caret reading survives; what would need re-plumbing is the React-controlled `value`, since the component owns the element.
- **Read:** **not worth it on its own; only alongside 01-06.** As a standalone swap it trades one input for another and gains the theme's search chrome, which is a small win for a real amount of re-plumbing in the most stateful component in `src/ui`. If the Toolbar's suggester moves to `AbstractInputSuggest`, the input is being rebuilt anyway and this comes almost free.

### 01-13. Three inline confirmations built as `role="alertdialog"` instead of a `Modal`

- **Folia:** `src/ui/CardItem.tsx:417` (delete card / remove todo), `src/ui/ColumnMenu.tsx:220` (delete column) and `src/ui/CardDetail.tsx:1495` (delete card) each render a `role="alertdialog"` div with a sentence, a danger button and an autofocused Cancel button, in place inside the surface the user was already looking at.
- **Obsidian:** `ConfirmationModal` (`obsidian.d.ts:1957`, since 1.13.0) is the dedicated facility: a `Modal` subclass with its own button row (`buttonContainerEl`), `addButton` (`:1989`), `addCancelButton` (`:1994`), `addCheckbox` (`:1984`) and buttons that auto-close unless the handler returns truthy. Being 1.13.0 it is above the 1.7.2 floor, so it is an `obsidianmd/no-unsupported-api` error unless it goes behind the `requireApiVersion` gate `src/main.ts:902` already uses. Below that floor the shape is plain `Modal` (`obsidian.d.ts:4477`) with `setTitle`/`setContent`, a `scope` for the keyboard and two `Setting.addButton` rows, as `developer-docs: Plugins/User interface/Modals.md` demonstrates. For the two of these three that delete a *file*, there is a narrower and much cheaper answer: `FileManager.promptForDeletion(file)` (`obsidian.d.ts:2911`, since 0.15.0, so below the floor and needing no gate) — "Prompt the user to confirm they want to delete the specified file or folder", returning `true` when confirmed (`developer-docs: Reference/TypeScript API/FileManager/promptForDeletion.md`). It raises the app's own delete confirmation, the one the user already knows from the file explorer, and it respects the same trash preference as `FileManager.trashFile`, which `src/obsidian/vaultRepo.ts:613` (`deleteCard`) already calls.
- **Differs:** an inline confirmation keeps the answer next to the thing being deleted and never covers the board; a `Modal` steals focus for a whole-window dialog. The three in-house ones also do not trap focus (`tracking/waivers/0002-automated-a11y-gate.md`); `ConfirmationModal` inherits `Modal`'s `scope` and close lifecycle, which is more than they have today, though as 01-03 notes the typings stop short of promising a focus trap.
- **Read:** **trade-off.** Against the swap: these are deliberately in-place, not dialogs, and turning them into whole-window modals would make three common actions heavier. For it: `ConfirmationModal` is the exact facility, it brings a close lifecycle and a keyboard scope the three hand-written ones do not have, and the a11y waiver's open item about them is otherwise Folia's to fix by hand. The nearest thing to a deciding case is that a confirmation should survive its container unmounting — the column popover closes out from under its own confirm today — where a real modal is the right owner. The two card deletions are a separate and much easier call than the column one: `promptForDeletion` costs no version gate, needs no dialog built, and gives the user the same confirmation Obsidian shows when they delete the note from the file explorer. It would have to be reached through the port like everything else in `src/ui`, and it confirms a *file* deletion, which is what those two actions do; the column confirmation deletes no file and has no equivalent. (Section 06 reached the same trade-off from the interaction side and named the version floor as the gating question; see 06-08.)

### 01-14. Viewport layout decided by raw pixel maths where `Platform` says what the device is

- **Folia:** three surfaces clamp themselves against `window.innerWidth`/`innerHeight` with hard-coded 8px gutters — `src/ui/CardContextMenu.tsx:70-71`, `src/ui/ColumnMenu.tsx:55` (against a fixed `MENU_W = 224`) and `src/ui/CardDetail.tsx:1209` (the fallback right edge of the panel's own resize drag — the splitter itself has no Obsidian counterpart, so only the fallback is in scope here). Nothing in `src/ui/**` reads `Platform`, and the detail panel's presentation is chosen from a setting (`detailPresentation`) rather than from the device.
- **Obsidian:** `Platform` (`obsidian.d.ts:4823`) exposes `isDesktop`, `isMobile`, `isPhone`, `isTablet` and the OS flags, and the community lint has `obsidianmd/platform` ("Disallow use of navigator API for OS detection", error in `recommended`, enabled here by `eslint.config.mjs:198`). `Menu` and `Modal` do branch by device themselves, observed in Obsidian 1.13.7's `app.css`: `.is-phone .menu` is anchored to the bottom of the screen inside the safe-area insets with rounded top corners and a `.menu-grabber` handle, `.is-phone .menu-item` grows to `padding: var(--size-4-3) var(--size-4-4)`, and `.is-phone .modal` becomes a full-width sheet whose header buttons are sized `var(--touch-size-m)` — 253 rules in that stylesheet are keyed on `.is-phone`, 156 on `.is-mobile` and 15 on `.is-tablet`.
- **Differs:** a fixed 224px popover clamped to an 8px gutter is a desktop shape applied everywhere. Folia is not sniffing the user agent — the lint rule has nothing to complain about, and `src/main.ts:547`, `:594`, `:606`, `:768` and `:921` all gate correctly on `Platform.isDesktop` — so this is an absence rather than a violation: the board's own surfaces make no device distinction at all.
- **Read:** **trade-off, and mostly downstream of 01-01 and 01-03.** Reading `Platform` inside `src/ui` costs the same port hop as everything else here, for layout tuning nobody has yet reported as broken. Since the menus and the modal would branch by device on their own once they are native, going native mostly dissolves this finding; if they stay in-house, `Platform.isPhone` is the honest way to give them a phone shape.
