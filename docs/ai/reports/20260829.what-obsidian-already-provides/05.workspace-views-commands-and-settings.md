# Workspace, views, commands and settings

This section covers how Folia takes part in the Obsidian workspace — the board's view class, how a board note gets opened as the board, leaf targeting, the ribbon, the command palette, the file and editor context menus, workspace events — and how the plugin's settings tab is built and its data persisted. It read `src/view.tsx`, `src/viewMode.ts`, `src/main.ts`, `src/settings.ts`, `src/settingsDefinitions.ts`, `src/settingsLayout.ts`, `src/boardNote.ts`, `src/obsidian/vaultRepo.ts` and `src/model/repo.ts` (the leaf and markdown-render calls outside `main.ts`), `src/ui/context.ts`, `src/ui/App.tsx`, `src/ui/Markdown.tsx`, `src/ui/CardItem.tsx`, `src/ui/CardDetail.tsx` and `src/ui/CardContextMenu.tsx` (the call sites that reach them), `test/settingsDefinitions.test.ts`, `test/settings.test.ts`, `test/viewMode.test.ts`, `manifest.json`, `versions.json`, `package.json`, `eslint.config.mjs`, `AGENTS.md`, `docs/decisions.md` and the backlog entries `20260827.10` and `20260829.03`.

Findings are cost-ordered **within each of the two groups below**, which are ordered independently of each other. Read across both groups, the three most expensive are 05-01 (the prototype patch), 05-10 (external settings changes silently clobbered) and 05-02 (modifier-clicks ignored on every card).

Not covered here: which UI component is drawn inside a settings row or a card menu (section 01), CSS (02), markdown rendering and search (03), vault, frontmatter and file operations (04), keyboard and drag-and-drop mechanics (06), community-directory guidelines and build (07).

## Workspace, views and navigation

### 05-01. The board takes over markdown opens by patching `WorkspaceLeaf.prototype.setViewState` on the prototype

- **Folia:** `src/main.ts:201` (`patchLeafSetViewState`) replaces `WorkspaceLeaf.prototype.setViewState` for the whole app with a wrapper that rewrites `{ type: "markdown", state: { file } }` into `{ type: VIEW_TYPE_KANBAN, ... }` whenever `shouldOpenAsBoard(filePath)` (`src/main.ts:340`) says so — which needs `resolveBoardViewMode` (`src/viewMode.ts:25`) to answer `"board"`, so a note carrying `folia-board: true` alongside `folia-view: markdown`, or opened while the vault-wide default is the editor, is left alone. Teardown is registered (`src/main.ts:232`) and goes inert before restoring, so a second plugin wrapping on top leaves an inert wrapper rather than a live one.
- **Obsidian:** `Plugin.registerExtensions(extensions, viewType)` (`obsidian.d.ts:4985`) is the supported way to say "files with this extension open in my view", paired with `FileView` (`obsidian.d.ts:3130`) and `canAcceptExtension` (`obsidian.d.ts:3186`). There is no public API that associates a *subset* of one extension — a per-note predicate — with a view type; `developer-docs: Plugins/User interface/Views.md` documents only `registerView` plus explicit `setViewState` calls by the plugin itself.
- **Differs:** `registerExtensions(["md"], VIEW_TYPE_KANBAN)` would route **every** markdown file in the vault to the board, which is the opposite of what Folia wants — `resolveBoardViewMode` returns `null` for every non-board note precisely so ordinary notes never notice the plugin. The patch also carries three behaviours no Obsidian route offers: it respects a per-leaf "the user sent this tab to the editor" record (`markdownTabs`, `src/main.ts:109`), it declines when the open targets a place in the text — a heading link, a block link, a search hit (`targetsAPlaceInTheText`, `src/main.ts:87`) — and it declines in the sidebars (`isEditingSurface`, `src/main.ts:531`). The alternative Obsidian *does* support, listening on the `file-open` event and swapping the view afterwards, would show the markdown editor for a frame before replacing it; the code comment at `src/main.ts:194` names exactly that.
- **Read:** **trade-off**. The patch is a global mutation of a core prototype that could break silently on any Obsidian release, and it is the single highest-risk thing this section found — but every documented route is either wrong (whole-extension takeover) or visibly worse (post-hoc swap with a flash). The teardown is careful and the risk is bounded to one method. What would remove the trade-off is a public per-file view association, which does not exist in 1.13.1.
- **Guard:** `pnpm obsidian-scan:check` reproduces the community-directory lint (`scripts/obsidian-scan.mjs`, wired into `pnpm verify` in `package.json:43`), and `eslint-plugin-obsidianmd` 0.4.1's recommended set is applied to `src/` (`eslint.config.mjs:198`, dependency at `package.json:72`). Neither has a rule about prototype patching, and both pass on `src/main.ts` today. `no-unsupported-api` in particular resolves `minAppVersion` from the manifest and reports on member expressions, so it genuinely checks against 1.7.2 — and it structurally cannot see a prototype assignment. The risk is real and uncodified: no bot will flag it on submission.

### 05-02. Opening a card note ignores the modifier keys every other Obsidian surface honours

- **Folia:** `src/obsidian/vaultRepo.ts:658` (`openCard`) is `this.app.workspace.getLeaf(false).openFile(this.file(path))` — always the current tab. The call sites drop the click event that would say otherwise: `src/ui/CardItem.tsx:394` binds `onClick={(e) => { e.stopPropagation(); actions.openNote(notePath); }}` and passes nothing on; `src/ui/CardDetail.tsx:1471` ignores the event React hands it; `src/ui/CardContextMenu.tsx:206` goes through an `item()` helper typed `() => void`, so there is no event to pass.
- **Obsidian:** `Keymap.isModEvent(evt)` (`obsidian.d.ts:3661`) returns a `PaneType | boolean` designed to be handed straight to `Workspace.getLeaf(newLeaf?: PaneType | boolean)` (`obsidian.d.ts:7892`) or to `Workspace.openLinkText(linktext, sourcePath, newLeaf)` (`obsidian.d.ts:7914`). `developer-docs: Plugins/Guides/Build a Bases view.md` gives the canonical shape for a custom view opening a note: `const modEvent = Keymap.isModEvent(evt); void app.workspace.openLinkText(path, '', modEvent);`.
- **Differs:** Folia's "Open note" affordance — on every card face, in the detail panel and in the card context menu — is the one place in the app where a modified click behaves the same as a plain one: no new tab, no split, no new window. Because the board sets `navigation = false` (`src/view.tsx:27`), `getLeaf(false)` from a board tab cannot land in the board's own tab, so the note goes to some other main-area tab chosen by Obsidian, with no way for the user to say which.
- **Read:** **clear win**, but not a one-liner: the path from click to leaf runs through five signatures — the board-actions context (`openNote(path: string): void`, `src/ui/context.ts:181`, wired at `src/ui/App.tsx:454`), the model port (`src/model/repo.ts:136`), `src/obsidian/vaultRepo.ts`, the fake repository the tests use, and the context-menu `item()` helper. `getLeaf(Keymap.isModEvent(evt)).openFile(file)` and the documented `openLinkText` form are equivalent here — Folia already holds the `TFile`, so `openFile` keeps the resolution it has. The change is confined to the "Open note" affordances, which are explicitly meant to leave the board; Folia's own in-panel navigation for relationship and subcard rows is a different route and stays as it is.

### 05-03. The detail panel's rendered markdown offers no hover preview, because the view is never registered as a hover-link source

- **Folia:** comment text and card descriptions are rendered with `MarkdownRenderer.render` and a real `sourcePath` (`renderMarkdown`, `src/obsidian/vaultRepo.ts:662`, reached through `src/ui/Markdown.tsx` from `src/ui/CardDetail.tsx:345` and `:1745`), so the detail panel carries live internal links. Card faces render no markdown, so this is the panel's gap, not the whole board's. The link-bearing sites are `RelationRow` (`src/ui/CardDetail.tsx:564`), the subcard link rendering (`:1793`) and the "Open note" action on the card face (`src/ui/CardItem.tsx:388`), each a React button that navigates on click. Neither `registerHoverLinkSource` nor a `hover-link` trigger appears anywhere in `src/`.
- **Obsidian:** `Plugin.registerHoverLinkSource(id, info)` (`obsidian.d.ts:4980`, `@since 1.1.0`) registers a view with the Page preview core plugin, and `HoverLinkSource` (`obsidian.d.ts:3446`) carries the `display` name shown in Page preview's own settings and a `defaultMod` flag saying whether the Mod key is required. Registration alone is not enough: the view must also emit the event, `app.workspace.trigger('hover-link', { event, source, hoverParent, targetEl, linktext })` on `mouseover`, which `developer-docs: Plugins/Guides/Build a Bases view.md` spells out for a custom view.
- **Differs:** in a markdown note, hovering an internal link shows the note's preview; inside the detail panel, the same link is inert. Folia has not built its own preview either — the behaviour is simply absent, which makes the panel feel unlike the rest of Obsidian in a way users notice without being able to name.
- **Read:** **clear win**, with the caveat that it is two halves and half of it does nothing on its own: `registerHoverLinkSource(VIEW_TYPE_KANBAN, { display: "Folia Kanban", defaultMod: true })` in `onload`, plus a `mouseover` handler that triggers `hover-link` on each rendered link. `hoverParent` needs a `HoverParent` (`obsidian.d.ts:3464`), which the view can be, and the popover it holds is a `HoverPopover` (`obsidian.d.ts:3476`).

### 05-04. The view swap depends on `popstate`, a `ViewState` field Obsidian does not declare

- **Folia:** `NavigableViewState` (`src/main.ts:73`) widens the public `ViewState` with `popstate?: boolean`, and both `showBoardIn` (`src/main.ts:311`) and `showMarkdownIn` (`src/main.ts:321`) set it so a board-to-editor swap stays out of the navigation history and Back still means "the previous note".
- **Obsidian:** the public `ViewState` interface (`obsidian.d.ts:7705`) declares exactly `type`, `state`, `active`, `pinned` and `group`. `popstate` appears nowhere in `obsidian.d.ts` 1.13.1, and nothing in the developer docs mentions it.
- **Differs:** the field is understood by the runtime but not by the API, so the swap's history behaviour rests on an undeclared implementation detail — the same class of dependency as 05-01, in the code path 05-01's replacement would be built on. The comment at `src/main.ts:70` says so honestly.
- **Read:** **trade-off**. There is no public way to say "this view change is not a navigation", and losing `popstate` degrades gracefully — Back would replay swaps instead of notes, which is annoying rather than broken. Worth knowing it exists, because `no-unsupported-api` cannot see it: it reports on member expressions, and this is a type widening, not an API call.

### 05-05. The board note's editor and the board cannot be shown side by side in one tab

- **Folia:** the shipped answer is the swap — `showBoardIn` / `showMarkdownIn` (`src/main.ts:307`, `src/main.ts:320`) flip one leaf between `VIEW_TYPE_KANBAN` and `markdown` on the same file, with the tab-header buttons at `src/view.tsx:95` and `src/main.ts:248`.
- **Obsidian:** `Workspace.createLeafBySplit` (`obsidian.d.ts:7845`) and `createLeafInParent` (`obsidian.d.ts:7839`) are public but both put the new leaf in the workspace tree; `WorkspaceSplit` (`obsidian.d.ts:8426`) has no public constructor; `MarkdownEditView` (`obsidian.d.ts:3917`) takes `constructor(view: MarkdownView)`, which needs a leaf; there is no `embedRegistry`, `EmbedCreator` or `registerEmbed` anywhere in the typings.
- **Differs:** the in-house answer is one view per tab and a button that swaps which one, rather than one view hosting two panes.
- **Read:** **decided** (`docs/decisions.md#The board and a Markdown editor side by side, in one tab`). Recorded 2026-08-26 and re-checked against 1.13.1; it stays out until Obsidian exposes a public way to create a leaf outside the workspace tree, or a supported editable markdown embed. The entry names the four typings facts above as the ones to re-check before spiking again, and all four still hold.

### 05-06. The tab-header button on board notes is tracked by a marker class and a `querySelector` sweep that ignores the event's own payload

- **Folia:** `syncMarkdownActions` (`src/main.ts:241`) walks every `markdown` leaf, asks `view.containerEl.querySelector('.view-actions .folia-open-as-board')` whether the button is already there, calls `view.addAction(...)` and tags the returned element with `BOARD_ACTION_CLASS` (`src/main.ts:68`), or calls `existing.remove()`. It is re-run from four workspace and metadata events (`src/main.ts:150`, `:151`, `:152`, `:157`), from `onLayoutReady` (`src/main.ts:184`), from `showMarkdownIn` (`src/main.ts:328`), and once more as `removeMarkdownActions` on unload (`src/main.ts:260`).
- **Obsidian:** `ItemView.addAction(icon, title, callback)` (`obsidian.d.ts:3604`) returns the `HTMLElement` it created and is the documented way to add a tab-header action; there is no `removeAction`, and no API for attaching an action to another view type conditionally. But three of the four events hand the callback the thing that changed and are written as `() => this.syncMarkdownActions()` anyway: `metadataCache.on('changed', ...)` supplies the `TFile` (`obsidian.d.ts:4453`), `workspace.on('active-leaf-change', ...)` supplies the `WorkspaceLeaf | null` (`obsidian.d.ts:8071`), and `workspace.on('file-open', ...)` supplies the `TFile | null` (`obsidian.d.ts:8078`). Only `layout-change` (`obsidian.d.ts:8084`) genuinely carries no payload.
- **Differs:** the identity scheme (a marker CSS class, a DOM query as the "does it exist" test) is forced, since Obsidian gives no handle back. The full sweep on every event is not: any note in the vault changing re-walks every open markdown leaf, when the event already says which file or leaf it was.
- **Read:** **trade-off**. The `addAction` bookkeeping stays as it is until Obsidian offers a `removeAction` or an id — nothing better exists. Narrowing `changed` and `active-leaf-change` to their payloads is small and self-contained and does not need a measurement to justify itself. `file-open` is the murky one: it names the file, but what actually changed is which leaf is bound to it, so the sweep may still be the right shape there.

### 05-07. `setState` types its result parameter by hand instead of using the exported `ViewStateResult`

- **Folia:** `src/view.tsx:63` (`KanbanView.setState`) declares `result: { history: boolean }`.
- **Obsidian:** `ViewStateResult` is exported (`obsidian.d.ts:7733`) and is the declared parameter type of `FileView.setState` (`obsidian.d.ts:3167`).
- **Differs:** a structural type that happens to match today rather than the named one. It compiles because the shapes are identical; a field added to `ViewStateResult` in a later release would leave the override silently narrower than the base signature.
- **Read:** **clear win**. One import, no behaviour change, and the reference then survives an API addition.

### 05-08. Command ids repeat a prefix Obsidian already adds

- **Folia:** the three command ids are `folia-open-kanban-board` (`src/main.ts:140`), `folia-create-board` (`src/main.ts:378`) and `folia-convert-note-to-board` (`src/main.ts:387`).
- **Obsidian:** `Plugin.addCommand` (`obsidian.d.ts:4955`) is documented at `obsidian.d.ts:4951` as "The command id and name will be automatically prefixed with this plugin's id and name", so these resolve as `folia-kanban:folia-open-kanban-board` and so on. The submission requirements say it outright: `developer-docs: Community directory/Submission requirements for plugins.md#Don't include the plugin ID in the command ID` — "Obsidian automatically prefixes command IDs with your plugin ID. You don't need to include the plugin ID yourself" — repeated in `developer-docs: Obsidian October plugin self-critique checklist.md#Releasing and naming` as "Don't prefix commands with your plugin ID". The codified guideline is `eslint-plugin/docs/rules/commands/no-plugin-id-in-command-id.md`.
- **Differs:** the ids carry a `folia-` prefix the namespace already supplies, and the first also carries `kanban`. The command *names* are clean ("Open board"), which is the half users see; the ids surface in `hotkeys.json`, in URI links and in other plugins' command pickers. The rule does not fire: its implementation reports only when the id contains the plugin id case-insensitively, and none of the three contains the literal string `folia-kanban`.
- **Read:** **trade-off**. `open-board`, `create-board` and `convert-note-to-board` are the conventional ids and the requirement is written down, but a command id is a stable identifier: renaming these silently drops any hotkey a user has bound, with no migration path. Worth doing only alongside a release that already breaks something, or not at all — which is why this is a trade-off rather than the clear win it first looks like. (Section 07 reached the same verdict from the guideline side; see 07-08.) The command *names* ("Open board", "Create board", "Convert this note into a board") are already free of the plugin name and in sentence case.
- **Guard:** none. `obsidianmd/commands/no-plugin-id-in-command-id` is enabled at `warn` in the scanner reproduction (`scripts/obsidian-scan.mjs:276`), but it tests whether the id contains the full manifest id `folia-kanban` as a substring, which none of the three does — so the scan is clean and this is genuinely unchecked.

### 05-09. The board-setup entries land in the context menu's unsectioned tail

- **Folia:** `addBoardSetupMenuItems` (`src/main.ts:413`) builds both entries as `item.setTitle(...).setIcon(...).onClick(...)` (`src/main.ts:416`, `:426`) and never assigns them a section, so "Create Folia board here" and "Convert to Folia board" appear after the core groups rather than beside the actions they resemble.
- **Obsidian:** `MenuItem.setSection(section: string)` (`obsidian.d.ts:4367`, `@since 0.15.3`, so available at `minAppVersion` 1.7.2) places an item in a named group of the menu, which is how core actions cluster.
- **Differs:** the entries are correct but unplaced; a user with several plugins adding file-menu items gets a growing ungrouped tail.
- **Read:** **trade-off**, leaning weak. The typing itself says section ids are discovered by reading `data-section` off the rendered DOM — there is no published list — so adopting it means depending on an undocumented string, the same class of risk 05-04 records for `popstate`, for a smaller payoff.

## Settings and state

### 05-10. `Plugin.onExternalSettingsChange` is not implemented, so a synced or externally edited `data.json` is silently overwritten

- **Folia:** the plugin holds the sparse settings in memory (`this.stored`, `src/main.ts:101`), reads `data.json` exactly once at load (`loadSettings`, `src/main.ts:537`) and writes the whole in-memory object back on every settings change and on every vault rename or delete that touches a path-keyed map (`saveSettings`, `src/main.ts:578`, via `followFileOp`, `src/main.ts:280`). Nothing ever re-reads the file.
- **Obsidian:** `Plugin.onExternalSettingsChange?()` (`obsidian.d.ts:5085`, `@since 1.5.7`, so already available at `minAppVersion` 1.7.2) is called when `data.json` is modified on disk from outside Obsidian — the typings name "a Sync service or external program" — and exists so the plugin can reload.
- **Differs:** with the hook unimplemented, a change arriving through Obsidian Sync (which syncs plugin settings when the user enables that), a git-synced `.obsidian`, or a hand edit is invisible to the running plugin, and the next write — which something as ordinary as renaming a card file in the explorer can trigger — replaces it wholesale with the stale in-memory copy. `src/settings.ts:225` already reasons at length about a `data.json` shared with another install, which makes the missing hook sharper: the file format was designed for that scenario and the runtime does not watch for it.
- **Read:** **clear win** for the read side (`await this.loadSettings(); this.refreshViews();` is close to the whole implementation). It is not a complete answer to concurrent edits — a change made in two places at once still resolves last-write-wins — but it turns "silently clobbered" into "picked up".
- **Backlog:** adjacent to `docs/ai/backlog/20260827.10.separate-state-from-settings-and-design-shared-state.md`, which asks the larger question of what belongs in this file at all.

### 05-11. Per-device and per-person state lives in `data.json` alongside real settings, with no use of the per-vault local storage Obsidian offers

- **Folia:** `KanbanSettings` (`src/settings.ts:14`) is one flat object saved as `data.json`. Four of its members are not settings anybody sets in the tab: `collapsedCards` (`src/settings.ts:46`, per-card collapse override keyed by path), `commentsSeen` (`src/settings.ts:61`, read markers whose own doc comment says they are "personal to one install"), `commentsBaseline` (`src/settings.ts:73`, the install-time marker) and `mcpToken` (`src/settings.ts:94`, a secret for a server only this machine hosts — the token is written up in full as **07-02**, which owns `App.secretStorage`; it is listed here only because it is a fourth member of the same flat object). `EditableSettingKey` (`src/settingsLayout.ts:20`) correctly excludes the first three from the tab, so the split is already understood — it just has nowhere else to go. `detailWidth` (`src/settings.ts:17`) is a fifth of a different kind: it *is* a tab row, a slider at `src/settingsLayout.ts:189`, but it is also written by dragging the panel's border, so what it holds is per-device layout rather than a preference that should travel.
- **Obsidian:** `App.saveLocalStorage(key, data)` and `App.loadLocalStorage(key)` (`obsidian.d.ts:480` and `obsidian.d.ts:472`, both `@since 1.8.7` — **after** `minAppVersion` 1.7.2, so a `requireApiVersion` guard or a raised floor would be needed) store a vault-scoped value in the browser's `localStorage`: per device, never synced, never in the vault. `App.secretStorage` (`obsidian.d.ts:458`, `@since 1.11.4`) exists for secrets specifically, documented at `developer-docs: Plugins/Guides/Store secrets.md`; see 07-02 for what it costs and what the live pass established about it.
- **Differs:** everything Folia remembers travels with the vault. On a synced vault one person's collapse state and read markers reach everyone who shares it; on a non-synced vault the same person loses their read markers when they open the vault on a second machine; and the MCP bearer token — a credential for a server bound to one computer — is written into a file that syncs.
- **Read:** **trade-off**, and not one to settle inside this audit. `saveLocalStorage` is the right home for `collapsedCards`, and `mcpToken` belongs to 07-02 rather than to this finding; `commentsSeen` is person-scoped rather than device-scoped, so moving it to local storage would trade one wrong scope for another; and `detailWidth` costs more than a relocation, since its tab row and declarative definition would have to go with it.
- **Backlog:** `docs/ai/backlog/20260827.10.separate-state-from-settings-and-design-shared-state.md`. That entry is a **hard stop**: its deliverable is a conversation with the user, so nothing here proposes resolving it. Cited so the triage links this finding to it rather than opening a duplicate.

### 05-12. Three settings commit when the user leaves the field, which the settings style guide names as the thing not to do

- **Folia:** `mcpPort` and `mcpBindAddress` are marked `{ kind: "held" }` (`src/settingsLayout.ts:201`) and reach 1.13 through a `render` callback (`src/settingsDefinitions.ts:217`) that calls `renderHeldField` (`src/main.ts:854`). That builds a plain text input, holds each keystroke in `pendingMcpFields` (`src/main.ts:750`) instead of writing it, shows an inline error via `setting.setErrorMessage(...)` behind a `requireApiVersion("1.13.0")` guard (`src/main.ts:902`), and commits on `blur` and in `hide()` (`src/main.ts:811`). `userName` is held the same way in `pendingUserName` (`src/main.ts:739`, assigned at `:789` and `:994`, committed by `commitHeldFields` at `:830`), for a different reason: a name committed per keystroke would be nine distinct comment authors for "alexandra". Validation and clamping live in `heldFieldOutcome` and `settingsPatchFor` (`src/settingsDefinitions.ts:92`, `:141`).
- **Obsidian:** `SettingNumberControl` (`obsidian.d.ts:6422`) offers `type: 'number'` with `min`, `max`, `step` and `placeholder`; `SettingTextControl` (`obsidian.d.ts:6679`) offers `type: 'text'` with `placeholder`; both inherit `validate` (`obsidian.d.ts:5916`), documented as returning "a non-empty string to reject the change and surface it as an inline error message below the setting", and `defaultValue` (`obsidian.d.ts:5897`). `developer-docs: Plugins/User interface/Settings.md#Save on change, not on submit` is explicit: "A setting in your tab should persist the moment the user changes it… The user navigating away should never be a save action", and it names the sanctioned alternative — "If a setting is too complex to commit on every keystroke… Surface it through a Modal with explicit 'Save' / 'Cancel' buttons… Settings tabs and sub-pages aren't designed to act as forms."
- **Differs:** Folia does the one thing that guidance rules out, and does it for three rows. The reasoning is real and stated at `src/settingsDefinitions.ts:77`, and it is now confirmed rather than assumed: in Obsidian 1.13.7 a declarative `text` control is built with `addText(...).onChange(handler)`, and the text component binds that handler to the DOM `input` event, so it runs on every keystroke; the handler awaits `validate` and, when validation passes, calls the tab's `setControlValue`, which for a plugin tab writes `plugin.settings[key]` and calls `saveData` immediately. So `192.168.1.5` really is written on the way to `192.168.1.55` (see "Verified live"). One exception matters here: a declarative `number` control is not built that way — it commits only on `blur` and on Enter, with Escape restoring the previous value. `developer-docs: Plugins/Guides/Migrate to declarative settings.md#When to use render instead` sanctions `render` for controls with side effects on change, which is why the row is drawn imperatively at all — but that passage is about escaping `control` + `validate`, not about when a commit may be deferred, and it does not license commit-on-blur.
- **Read:** **trade-off**, honestly held for the two MCP fields, and thinner for `userName`, where nothing is destructive and the cost of a per-keystroke commit is a redundant save and re-render rather than a bound port. The Obsidian-shaped answer for all three is the one the style guide names: a modal with Save and Cancel behind an action row, which would also let the port and the address be committed together instead of restarting the server twice. One of the three has a cheaper answer than the modal, though: `mcpPort` is a number, and Obsidian's own declarative `number` control already commits on blur and on Enter and reverts on Escape, which is precisely the behaviour `renderHeldField` hand-rolls for it — so that row could become a plain `{ type: "number", min, max, validate }` definition and lose its imperative `render`. `mcpBindAddress` is text and would still be written per keystroke, so it keeps the held treatment or moves into a modal with the port; `userName` is the row where the per-keystroke commit costs only a redundant save.
- **Guard:** `test/settingsDefinitions.test.ts:365-474` covers `heldFieldOutcome` and the `render`-shaped definition; the imperative half of `renderHeldField` in `src/main.ts` sits inside the untested region 05-13 names.

### 05-13. The settings tab is maintained twice, and the half Obsidian 1.13 never draws has no test coverage

- **Folia:** `KanbanSettingTab` implements both `getSettingDefinitions()` (`src/main.ts:757`, the declarative tab for 1.13+) and `display()` (`src/main.ts:807`), which calls a hand-written `render()` (`src/main.ts:914`) that walks `SETTING_GROUPS` and dispatches on `SETTING_CONTROLS` to build the same rows with `new Setting(...)`. Both read their wording, grouping, options and disabled predicates from `src/settingsLayout.ts`, which is what keeps them from drifting, and `test/settingsDefinitions.test.ts:127` asserts that the imperative tab can only get its wording from the shared copy. `writeRow` (`src/main.ts:990`) and `TAB_REDRAW_KEYS` (`src/settingsLayout.ts:302`) hand-roll the redraw that 1.13 gets from `refreshDomState()` / `update()`.
- **Obsidian:** `developer-docs: Plugins/Guides/Migrate to declarative settings.md` describes exactly this arrangement as "Path B" and warns: "Every time you add or change a setting, update both `display()` and `getSettingDefinitions()`. Drift between the two means users on different Obsidian versions see different settings. If the maintenance overhead isn't worth it, prefer Path A and bump `minAppVersion`." The codified rules agree in both directions: `eslint-plugin/docs/rules/settings-tab/require-display.md` requires `display()` while `minAppVersion` is below 1.13.0, and `no-deprecated-display.md` wants it gone once it is not.
- **Differs:** nothing here diverges from an Obsidian API — Folia is on the sanctioned path and factored it better than the guide's example, since the two renderings share one data source rather than two code paths. What differs is the cost: `manifest.json` declares `minAppVersion: 1.7.2` and every entry in `versions.json` since `0.0.3` repeats it, so the imperative tab is what a real user below 1.13 sees, and it has no test coverage at all — `test/settingsDefinitions.test.ts:121` records that `src/main.ts` cannot be imported by the suite, because importing it pulls in the Obsidian runtime. Whether it has ever been drawn in a live Obsidian below 1.13 is not something the repository can answer.
- **Read:** **trade-off**, and the guide names the exact lever: keep both while the sub-1.13 user base matters, or raise `minAppVersion` to 1.13.0 and delete `display()` (`src/main.ts:807`), `render()` (`:914`), `renderRow()` (`:934`), `writeRow()` (`:990`), `renderTokenRows()` (`:1005`) and `TAB_REDRAW_KEYS` — about 110 lines. The held-field machinery does **not** go with it: `renderHeldField` and everything around it are shared, reached on 1.13 through the row's own `render` callback (`src/settingsDefinitions.ts:217`, and the comment at `src/main.ts:850` says so). Nobody has measured that user base, which is the missing input.
- **Backlog:** `docs/ai/backlog/20260829.03.imperative-settings-tab-has-no-coverage-of-any-kind.md` records the coverage half of this and states the same two acceptable outcomes.

## Verified live

Checked on 2026-08-29 against the running Obsidian 1.13.7 desktop build with the repository's `examples` vault open, through the Chrome DevTools bridge. Nothing was typed into a setting and no setting was changed: the question was answered by reading the app's own bundle (`app://obsidian.md/app.js`), which is minified, so what follows is behaviour read off the implementation rather than a documented contract.

- A declarative `control` of type `text` (and `textarea`, and `folder`) is rendered as `setting.addText(c => c.setValue(current).onChange(handler))`, and Obsidian's text component registers its change callback on the DOM `input` event — `inputEl.addEventListener("input", onChanged)` — so the handler fires on every keystroke. The handler awaits the definition's `validate`; a non-empty string sets the inline error and stops there, otherwise it clears the error and calls the control binding's `onChange`, which awaits `setControlValue` and then refreshes the tab's DOM state. For a `PluginSettingTab`, `setControlValue(key, value)` assigns `plugin.settings[key]` and calls `plugin.saveData(settings)`. The granularity the source pass could not pin down is therefore keystroke, not the DOM `change` event, and each accepted keystroke is a write of `data.json` — which is what `src/settingsDefinitions.ts:77` and `test/settingsDefinitions.test.ts:362` assert.
- The same renderer does not treat every control that way. `number` is built as a component whose commit runs on `blur` and on Enter, with Escape restoring the last committed value and out-of-range input producing an inline error; `slider` commits on the input's `change` unless the component is put in instant mode; `toggle`, `dropdown` and `file` commit on their own selection event. So "commit on every keystroke" is the text family's behaviour specifically, and 05-12's `mcpPort` has a supported blur-committing control available to it after all.
